## 3. Context (self-contained)

### 3.1 Broadcast scaling — `SectionBlocksUpdate` + per-viewer filtering

**Current state, verified by reading `crates/server/src/play/world.rs`.** Three functions each loop over *every* connected player unconditionally, with no per-viewer chunk-visibility check at all: `broadcast_changed_positions` (sends one `BlockUpdate` per entry in the tick's changed-positions collector, excluding the one `primary` position a direct action already covers), `broadcast_to_all` (the direct-action response `respond_place`/`respond_break` call, guaranteeing the acting player is reached even if their own `PlayerMarker` has not been spawned into the ECS world yet this same tick — a real, already-fixed join/action race, `broadcast_to_all`'s own doc comment), and `broadcast_break`'s own inline `Block Update` loop (a third real production call site, reached only from the digging-tick auto-finalize path at `world.rs` ~2280, distinct from `respond_break`). All three send one packet per position, never a batch.

**Vanilla's real behavior** (`docs/research/mc-26.2/03-world-chunks.md` §"Notes for Rusty Clanker": *"Block-update broadcasting is intentionally decoupled from block mutation — `ChunkHolder.blockChanged` only records the change; actual packet construction and sending happens once per tick in `ServerChunkCache.broadcastChangedChunks`, batching all of a section's changes into one packet."* and §3.7: *"`broadcastChanges(chunk)` ... flushes them as ... either a single `ClientboundBlockUpdatePacket` (exactly 1 changed block in a section) or a `ClientboundSectionBlocksUpdatePacket` (batch) per changed section"*). Restated as the exact rule this blueprint implements: **group same-tick changed positions by `(chunk_x, chunk_z, section_y)`; a group of size 1 sends `BlockUpdate`; a group of size ≥2 sends one `SectionBlocksUpdate` covering the whole group.**

**Wire layout — TEST-D57 claim, CONFIRMED this session against the pinned azalea checkout** (`~/.cargo/git/checkouts/azalea-55f499961895c5bc/6249c29`, rev `6249c295` — the same pinned rev this project's own `oracle-jar-bytecode-ground-truth` convention already treats as ground truth; read directly, not via a third-party-reimplementation firewall violation — azalea is a client library, already this project's established wire-shape cross-check per `packets.rs`'s own precedent throughout, e.g. `SetHealth`'s doc comment). Not present in `docs/research/mc-26.2/`'s prose form, so restated concretely here:
- `section_pos: i64` — a **plain** (not VarInt) big-endian long, packed as `((chunk_x & 0x3FFFFF) << 42) | (section_y & 0xFFFFF) | ((chunk_z & 0x3FFFFF) << 20)` (22-bit x, 20-bit y, 22-bit z — distinct bit widths from `pack_position`'s own 26/26/12 block-position split; verified from azalea's own `ChunkSectionPos::azalea_write`).
- `states: Vec<VarLong>` — VarInt count (azalea's generic `Vec<T>` `AzBuf` impl length-prefixes with a `VarInt`, matching this project's own `#[rc(prefixed_array = "VarInt")]` convention exactly), then each entry as one `VarLong` computed as `(state_id << 12) | (local_x << 8 | local_z << 4 | local_y)`, `local_*` each `0..16` (verified from azalea's own `BlockStateWithPosition::azalea_write`).
- **Packet id — TEST-D57 claim, id `0x54`**, derived the same way every other id in `packets.rs` was reconciled (its own top-of-file doc comment: "numeric ids were reconciled against a locally-generated `reports/packets.json`") — but no local `reports/packets.json` exists in this environment (git-ignored, fetched on demand). Cross-checked instead against azalea's own `Clientbound` packet declaration order (`azalea-protocol/src/packets/game/mod.rs`'s `declare_state_packets!` list), the exact convention `SetHealth`'s own doc comment already establishes and cross-validates against every already-committed id in this file (`LoginPlay` index 49 = `0x31`, `player_position` index 72 = `0x48`, ...): `block_update` is that list's own index 8 (`0x08`, matching this project's own already-committed `BlockUpdate` id exactly — a live self-check that the convention still holds), `section_blocks_update` is index 84 (`0x54`). Not independently re-verified against a real generated `reports/packets.json` or a real client capture this session — list under Claims to verify.

**Per-viewer filtering.** `crates/server/src/play/world.rs`'s `PlayerMarker::sent_chunks: HashSet<(i32, i32)>` already tracks, per connection, every chunk column ever sent to that client (`world.rs` ~2491-2498, inserted as the streaming step discovers newly-visible columns; never removed on move-away — a monotonically-growing "ever sent" set, over-inclusive relative to vanilla's own dynamic unload but never under-inclusive, an already-accepted simplification this blueprint does not change). A player must never receive a block update for a chunk column not in their own `sent_chunks` — filtering is a lookup against this existing structure, not new bookkeeping. The direct-action broadcast (`broadcast_to_all`) must still always reach the acting player unconditionally (its own pre-existing join-race guarantee, unaffected by view distance); every other connected player is filtered.

### 3.2 Hopper `ENABLED` re-evaluation on neighbor change

**Vanilla's real rule — CONFIRMED this session by `javap -c -p` disassembly of the pinned oracle jar** (`oracle/26.2/server.jar` → `META-INF/versions/26.2/server-26.2.jar` → `net/minecraft/world/level/block/HopperBlock.class`, per this project's own established `oracle-jar-bytecode-ground-truth` method — reading bytecode is not copying Mojang expression, ASSET-D18/D19). `HopperBlock.neighborChanged` and `HopperBlock.onPlace` both call the identical private `checkPoweredState(level, pos, state)`, unconditionally, with no direction filter: `newEnabled = !level.hasNeighborSignal(pos)`; if `newEnabled != state.getValue(ENABLED)`, writes `state.setValue(ENABLED, newEnabled)` via `setBlock(pos, ..., 2)`. This is exactly MECH-D8's own cited example of the generic QC relay ("`HopperBlock` (inverted: `shouldBeOn = !hasNeighborSignal`)") applied to `neighborChanged`, not only to placement.

**Current state.** `crates/server/src/play/mining.rs`'s `apply_placement_with_redstone` already reproduces the *placement* half correctly (`best_neighbor_signal(ctx_world, registry, target) > 0` → writes the `enabled=false` id, `raw_state + 5`). Nothing reproduces the *neighbor-changed* half: no `HopperBehavior` exists, and no hopper id range is registered into `BlockBehaviorRegistry` at all — a hopper's `ENABLED` bit is frozen at whatever placement computed, forever.

**Hopper's own id arithmetic** (verified directly against `crates/server/src/play/mining.rs`'s own `hopper_facing_index`/placement-time `+5` fix, both already oracle-reconciled): `HOPPER.0` (`rc_registries::generated_v776::block_states::default_state::HOPPER`) = `11313` = `enabled=true, facing=down`. `facing` is the inner, stride-1 property, order `[down=0, north=1, south=2, west=3, east=4]`; `enabled` is the outer, stride-5 property — `enabled=true` occupies `HOPPER.0 + 0..=HOPPER.0 + 4`, `enabled=false` occupies `HOPPER.0 + 5..=HOPPER.0 + 9` (same facing, `+5`). Full reachable range: `11313..=11322` (10 states).

**Stage-7 transfer gate.** `crates/mechanics/src/block_entity/hopper.rs`'s `HopperBlockEntity::tick` already gates on `world.is_locked_by_redstone(pos)` — a *different*, already-documented, currently-always-`false` gap (`crates/mechanics/src/stage7/ecs.rs`'s own doc comment: "no comparator/wire/redstone-signal-strength query exists in `rc-mechanics` outside Stage 4's own internal state, which this Stage-7-scoped adapter has no access to"). That gap is **out of scope** for this item — it concerns a different vanilla concept (a comparator/container lock), not the `ENABLED` block-state bit. This item adds a **new**, separate gate reading the raw block state's own `ENABLED` bit, confirmed by the same bytecode read as sitting in `HopperBlockEntity.tryMoveItems`'s own combined condition `!isOnCooldown() && state.getValue(ENABLED)` — i.e. checked *after* cooldown decrements (which happens unconditionally, already correctly modeled) but *before* any push/pull attempt, and *before* the pre-existing (separate) redstone-lock check.

### 3.3 Concurrent pipe drains for the remaining `xtask` piped subprocesses

**The bug, already fixed once.** `docs/findings-for-planning.md`: *"a `Stdio::piped()` child whose pipes are only drained after exit-polling can block forever on a full OS pipe buffer once its output volume grows"* — `xtask/src/m3_report.rs`'s `run_load_scenario_subprocess` hit this for real (a 20-bot run produced 700KB+ of stderr, deadlocking every run) and was fixed by starting two dedicated drain threads immediately after spawn, running concurrently with the poll loop, joined on every exit path (natural exit, poll error, timeout-kill).

| `xtask/src/m3_report.rs` | `run_load_scenario_subprocess` | Already fixed (hand-rolled) |
| `xtask/src/corpus/placement_diff.rs` | `run_placement_diff_runner_subprocess` | Already fixed (hand-rolled) |
| `xtask/src/m1_report.rs` | (idle-stability subprocess runner) | **Vulnerable** — poll-then-drain |

Rather than hand-copy the fix a third/fourth/fifth time, this item centralizes it: a new `xtask::process::spawn_drained` helper owns the drain-thread/poll-loop/kill-on-timeout shape exactly once, and **every** one of the five sites above (including the two already-fixed ones, to retire their now-duplicate hand-rolled copies) calls it. A `lint-tests` forbidden-pattern then makes the centralization structural, not merely a convention: any *added* line under `xtask/src/**` containing the literal `Stdio::piped()` outside `xtask/src/process.rs` itself fails the lint.
