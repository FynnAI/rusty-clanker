## Context (self-contained)

### 2.1 The three decisions this blueprint implements, restated in full

**TEST-D55 — Mandatory adversarial case matrix for mechanic test suites.** Every test suite for a world-interacting mechanic MUST include, as named cases: (a) both world-height boundaries (acting at, into, and across Y = −64 and Y = 319); (b) every orientation/facing a placement or component supports — all four horizontals at minimum, never only the default; (c) self-interaction (the actor's own position/body as target — build-into-self, break-under-self); (d) multi-instance composition (≥3 components chained end-to-end — a repeater line, a hopper chain — asserting the signal/item actually traverses); and (e) at least one non-default block state per shape-relevant block. `lint-tests` grows a structural check: a new `crates/*/tests/` file whose name matches a mechanic pattern must declare its matrix coverage in a machine-readable header comment, or carry an explicit waiver naming why a category is inapplicable. Rationale: every M3 field bug the suite missed lived in exactly these blind spots — bedrock at Y=−64 (boundary), three of four repeater orientations misclassified (orientation), blocks placed into the player's own body (self), repeater chains dead while single-component tests passed (composition).

**TEST-D56 — Test expectations derive from the specification, never from the implementation.** A test's expected values must cite their source in a comment — the blueprint section, the research-corpus document, or the datagen report they restate — and must be computable without running the code under test. Deriving an expectation by executing the implementation and pasting its output (self-oracle) is a forbidden pattern; golden-value updates that merely re-paste new output require the citation to be re-verified in the same changeset. Complements TEST-D45/D46: those stop implementation from editing tests, this stops tests from being born agreeing with the bug. Rationale: M3's worst confirmed defect (diode direction inverted) was green under 35 unit tests because every test placed its fixture on the same wrong side the code read — spec-independent expectations with a cited source are the structural fix.

**TEST-D57 — Reference-verification gate before implementation.** Before any blueprint's implementation changeset begins, a designated research-role pass verifies every vanilla-behavior claim that blueprint states (constants, formulas, orderings, packet layouts) against the ASSET-D18(f) reference, producing a per-claim CONFIRMED/WRONG/UNVERIFIABLE list that ships with the implementation task; WRONG claims are corrected in the blueprint (recorded per the findings-log process) before code is written from them. M4 onward this is a hard gate in the milestone execution order; already-implemented milestones are covered retroactively by the M3-era planning-reference audit. Rationale: every M3 blueprint error (diode direction, raycast reach, hopper formula, dispatch order, golden-vector slips) was caught after implementation at find-diagnose-fix-retest cost; the same verification performed before coding costs one research pass and no rework.

**Restated supporting decisions:** TEST-D45 (acceptance tests authored and committed in their own test-authoring changeset, before implementation); TEST-D46 (CI path-guard — an implementation changeset may never touch a crate's `tests/` tree, fixtures, scenario files, or the verification-verb source itself; only test-authoring or a dedicated governance changeset may); TEST-D49 (forbidden-pattern lints — this blueprint's two new checks are additional members of that same family); TEST-D50 (CI is the sole authority — a local pass is advisory only); TEST-D52 (an independent verifier-agent re-runs the full tier from a clean checkout and adversarially reviews every diff touching `tests/`).

**Changeset-Type trailer convention (M0-B08):** every commit message carries a `Changeset-Type: test-authoring|implementation|governance` trailer; `xtask path-guard`/`xtask lint-tests` parse it per commit (`path_guard::parse_changeset_type`). This blueprint's own work is two governance changesets (the three new `xtask` modules, `lib.rs`/`main.rs`/`path_guard.rs` extensions) and one test-authoring changeset (the 40-file retroactive annotation plus the one new hopper-chain test) — restated in full in Constraints.

### 2.2 The existing lint machinery this blueprint extends

`xtask/src/forbidden_patterns.rs` implements TEST-D49's five checks as pure `check_*` functions over already-extracted diff text (`file: &str`, `added_lines: &[String]` for line-based checks; `head_content`/`base_content: &str` for whole-file checks), each returning `Vec<PatternViolation>`. `run(base)` walks every commit in `<base>..HEAD` (`path_guard::rev_list`, reused via `pub(crate)`), resolves each commit's own `Changeset-Type` via `commit_lint_gate`, gathers that commit's added lines and before/after whole-file content per changed file (`git diff`/`git show` via `xshell`), unions every check's violations, and writes one `TierResult` (`tier_result::TierResult`, `{"tier": "lint-tests", "status": "pass"|"fail", "cases": [{"name", "status", "detail"}]}`) to `target/verify/lint-tests.json` — the uniform machine-readable contract every xtask verb uses (TEST-D40). This blueprint adds two more `check_*` families (case-matrix, spec-citation) that plug into the exact same per-commit, per-file loop, and a third feature (claims gate) that extends `path_guard.rs`'s own `evaluate_commit`/`check_paths` instead.

`xtask/src/path_guard.rs` holds `PROTECTED_PATHS: &[ProtectedPath]` (pattern + reason), `glob_match(pattern, path)` (a recursive segment matcher: a pattern segment that is exactly `*` consumes exactly one path segment of any content, exactly `**` consumes zero or more segments, anything else must equal the path segment literally — **a pattern segment is never partially wildcarded**, e.g. `*-CLAIMS.md` is not a valid pattern under this matcher and would only ever match a path segment that is literally the four characters `*-CL...`), `check_paths(changeset_type, changed_files)` (flags every changed file matching a `PROTECTED_PATHS` entry, only for `ChangesetType::Implementation`), and `evaluate_commit(commit_message, changed_files)` (the per-commit pure verdict `run`'s I/O shell drives). This blueprint's TEST-D57 gate cannot be expressed as a `PROTECTED_PATHS` glob (a `<ID>-CLAIMS.md` filename varies per blueprint and the matcher has no partial-segment wildcard) — Deliverables therefore add a standalone predicate function alongside, not inside, `PROTECTED_PATHS`.

`xtask/src/tier_result.rs`'s `TierResult`/`Status`/`CaseResult`/`write`/`write_to`/`exit_code_for` are reused unmodified by every new verb this blueprint adds — no new result-shape code.

### 2.3 The TEST-D55 header grammar

Every file matching a mechanic-pattern name (§2.4) must carry, as one of the `//!` doc-comment lines within its first 40 lines, exactly one line of this shape:

```
//! test-matrix: boundaries=<v> orientations=<v> self=<v> composition=<v> nondefault-state=<v>
```

`<v>` is either the literal `yes` or `waived(<reason>)` where `<reason>` is non-empty free text (may contain spaces, may not itself contain the substrings `orientations=`, `self=`, `composition=`, or `nondefault-state=`, which would break the fixed-order parse below). The five keys appear in this exact fixed order, space-separated, on one physical line. Example (a genuinely fully-waived infrastructure-flavored file, for illustration only — infrastructure files that never match a trigger pattern at all, §2.4, need no header):

```
//! test-matrix: boundaries=waived(pure NBT codec round-trip, no world position) orientations=waived(single facing per case, not a sweep) self=waived(no actor entity) composition=waived(single instance, no chain) nondefault-state=yes
```

**Parse algorithm** (`case_matrix::parse_header(line: &str) -> Result<TestMatrix, String>`): strip the `//! test-matrix:` prefix (fail if absent); then, for each of the five keys in the fixed order `["boundaries=", "orientations=", "self=", "composition=", "nondefault-state="]`, find that key's anchor via `str::find` in the remaining text (fail if a key anchor is missing or out of order relative to the previous key's found position); that key's raw value is the text from just after its `=` up to (but not including) the next key's anchor substring, or to the end of the line for `nondefault-state`; trim whitespace. A trimmed value of exactly `yes` is `Category::Yes`; a value matching `^waived\((.+)\)$` (must start with `waived(`, end with `)`, non-empty interior) is `Category::Waived(reason)`; anything else is a parse error naming the offending key.

### 2.4 The mechanic-pattern trigger (file-name patterns)

A `crates/{server,mechanics}/tests/*.rs` file is **triggered** — must carry a header or fail `lint-tests` — iff its basename (without the `.rs` extension) starts with any of these prefixes (checked via `str::starts_with`, not a segment glob — these are plain string prefixes):

```
play_movement_application   play_movement_validation   play_reach_
play_sneak_reach            play_block_                play_placement_
play_redstone_              play_creative_hotbar_held_item
mining_
redstone_    piston_    block_entity    chest_    furnace_    hopper_
container_signal_source    world_bounds
```

A file whose basename matches none of these is **exempt**: it needs no header at all, and `lint-tests` does not inspect it for this check. This is a deliberate, narrow scope, not an oversight: TEST-D55's own text gates "a new `crates/*/tests/` file whose name matches a mechanic pattern" — a file that never touches world state (protocol codec round-trips, connection/session/auth lifecycle, persistence byte-format, chunk-streaming network mechanics, or a pure ECS-agnostic substrate primitive with no block-mechanic content) is not what TEST-D55 exists to gate, and forcing a boilerplate five-way waiver onto e.g. `auth_cipher.rs` would only train authors to skim waiver text. The prefix list is intentionally precise rather than broad — `play_movement_application`/`play_movement_validation` (not a bare `play_movement_`) so `play_movement_packet_roundtrip.rs` (pure `WireWrite`/`WireRead` round-trip, no world) stays exempt without a special-case rule; `play_reach_`/`play_sneak_reach` so `play_reach_distance_measurement.rs`/`play_reach_validation.rs`/`play_sneak_reach.rs` are covered without also catching an unrelated `play_reach_config.rs` were one ever added with a different meaning — none exists today. §2.6 lists, file by file, exactly which of the 70 files in these two directories are triggered (40) and which are exempt (30), with the reasoning for every exempt call.

`case_matrix::file_requires_case_matrix(basename: &str) -> bool` is the pure function implementing this table; `MECHANIC_TEST_PREFIXES: &[&str]` is the pub const backing it, in the exact order above (order is not semantically significant, `.any(|p| basename.starts_with(p))`).

### 2.5 What `lint-tests` checks for a triggered file

For every triggered file present at a commit's `head_content` (the same `content_at(sh, sha, file)` helper `forbidden_patterns::run` already calls for the empty-test-body check):

1. **Header present.** Exactly one line matching §2.3's grammar exists within the first 40 physical lines. Zero matches → `MissingCaseMatrixHeader`. More than one candidate line (two lines both starting `//! test-matrix:`) → `MissingCaseMatrixHeader` as well (ambiguous — treated as absent, never "first one wins," so a botched copy-paste duplicate fails loudly instead of silently picking the wrong one).
2. **Header parses.** A candidate line found but failing §2.3's parse algorithm → `MalformedCaseMatrixHeader { file, error }`.
3. **Every `yes` is backed.** For each of the five categories declared `yes`, the file's own `#[test]`-annotated function names (extracted via the same brace-counting/line-based technique `forbidden_patterns::test_attr_offsets`/`extract_test_fn_names` already use — reused, not reimplemented) must include at least one name containing that category's required token:
   - `boundaries` → `_boundary_`
   - `orientations` → `_orientation_` or `_facing_`
   - `self` → `_self_`
   - `composition` → `_chain_` or `_composition_`
   - `nondefault-state` → `_nondefault_`

   A category declared `yes` with no matching test name → `CaseMatrixCategoryUnbacked { file, category }`. A category declared `waived(...)` is never checked against test names (a waiver is a claim about *absence*, no test can "back" it) — its only obligation is a non-empty reason, already enforced by the parser.

This is a **whole-file check** (like check 3, empty-test-body), not a diff-added-lines check — it runs against every triggered file's `head_content` at every commit in range, not only files the commit itself touches... **except** that would re-flag every triggered file at every unrelated commit forever once annotated. To keep the check honest without that blowup: the check runs only over files present in that commit's own `changed_files` list (mirroring every other check in this module) — a file is only re-validated on a commit that touches it. A file is validated once, at the commit that adds or last touches it; nothing re-scans the whole tree on unrelated commits. (`xtask verify-fixtures`-style whole-tree sweeps are a different, existing verb for a different purpose and are not extended here.)

### 2.8 The TEST-D56 spec-citation check

**Scope:** the same 40 files §2.4 triggers (identical trigger function, reused) — state-id literals overwhelmingly live in exactly this file set; a generated-registry file is separately covered by TEST-D47's manifest hash check and is itself a protected path, out of scope here.

**What counts as a bare block-state-id literal**, scanned only within an `assert_eq!(`/`assert!(`/`assert_ne!(` invocation's own argument span (located via the same open-paren-to-balanced-close-paren brace-counting technique `forbidden_patterns::extract_test_body_violation` already uses for `{ }`, applied to `( )` instead, starting at the macro name's `(`):

1. `BlockStateId(<digits>)` — any digit count, matched via a straightforward token scan (`"BlockStateId("`, skip whitespace, one or more ASCII digits, optional whitespace, `)`).
2. A bare five-digit decimal integer token (`\b\d{5}\b`, exactly five digits — not four, not six — a deliberately narrow net matching the task's own literal framing) appearing anywhere in the argument span, at a word boundary (not immediately preceded or followed by a letter, digit, or `_`, and not immediately preceded by `.` — excludes a float literal's fractional part).

Before scanning, each line is pre-processed exactly as `forbidden_patterns::strip_string_literals` already does (blank out `"…"` content) and `//`-line-comment tails are stripped — a literal inside a string message or a doc comment never triggers this check.

**False-positive handling, stated explicitly:**
- **Four-digit ids** (e.g. redstone-wire's own `4011` base) are *not* caught by the bare-digit form (only `BlockStateId(4011)` is caught, unconditionally regardless of digit count) — an accepted, narrow scope rather than a wider net that would flag ordinary tick counts (`12000`, a not-implausible five-digit duration) as false state-id positives. Recorded as a known, deliberately narrow scope, not silently unbounded.
- A literal introduced via an intervening `let` binding one line above the assert (`let expected = 12345; assert_eq!(actual, expected);`) is **not** caught — the check only inspects the macro's own argument text. Recorded as a known lint gap, not a promised guarantee; TEST-D52's verifier-agent adversarial review is the backstop for this class of evasion, same as it already is for TEST-D49's assertion-count check.
- A literal that is itself a rejected/sentinel value in a negative test (e.g. "this id must never appear") still requires a citation or an explicit waiver — sentinel-ness is not itself an exemption, since a wrong sentinel is exactly as capable of hiding a bug as a wrong expectation.

**The citation.** Within the three physical lines immediately preceding the assert span's *first* line (mirroring `check_undocumented_tier_cfg`'s own "previous 2 lines" lookback shape, widened to 3 per the task), a `//`-comment line must match, after stripping leading `//` and whitespace: `source: ` followed immediately by one of exactly four accepted prefixes — `blocks.json`, `blueprint M` (then at least one digit), `research/`, `oracle trace ` — followed by non-empty trailing text. A `source:` comment present but not matching any of the four prefixes is `MalformedSpecCitation` (distinct from `MissingSpecCitation` — a typo'd citation is a different, more informative failure than a silently absent one).

**Waiver syntax**, mirroring `#[ignore = "…"]`'s existing linked-reason shape: `// source-waived: <reason>`, same 3-line lookback window, non-empty reason required. Legitimate uses: a deliberately-wrong id in a negative/rejection test where "wrong" is the point and no vanilla source describes it (`// source-waived: deliberately invalid id, rejection path under test`), or a `FakeWorld`/test-double literal unrelated to any real vanilla id (`// source-waived: FakeWorld sentinel, not a real block-state id`).

`spec_citation::check_literal_citations(file: &str, head_content: &str) -> Vec<PatternViolation>` — new `PatternViolation` variants `MissingSpecCitation { file, fn_name, literal }`, `MalformedSpecCitation { file, fn_name, comment }`.

### 2.9 The TEST-D57 claims artifact and gate

**`<ID>-CLAIMS.md`**, one per blueprint, same directory as the blueprint (`blueprints/<milestone>/<ID>-CLAIMS.md`, e.g. `blueprints/M3.5/M3.5-B01-CLAIMS.md`). Fixed table format, exactly these five columns, in this order:

```markdown
# <ID> — Claims Verified (TEST-D57)

| Claim | Source location | Verdict | Verified by | Date |
|---|---|---|---|---|
| <claim text, verbatim from the blueprint's own "Claims to verify" list> | <e.g. "blocks.json, minecraft:hopper block-states"> | CONFIRMED / WRONG / WRONG — corrected / UNVERIFIABLE | <role or agent identity> | YYYY-MM-DD |
```

A `WRONG` row that has since been fixed in the blueprint (per the findings-log process CLAUDE.md's own "Planning authority" section already mandates for any blueprint factual correction) has its Verdict cell rewritten to literally contain the substring `corrected` (the convention used here: `WRONG — corrected`) — this is the only state transition a CLAIMS.md row ever undergoes after being written; a `CONFIRMED`/`UNVERIFIABLE` row is never revisited.

**Where the required claim count comes from.** Every blueprint (this one included, retroactively for M0–M3 per the M3-era planning-reference audit already named in TEST-D57's own text) carries, as the *final* subsection of its Context section, a heading `### Claims to verify (TEST-D57)` followed by either a bullet list (one `- ` line per vanilla-behavior claim the blueprint states — constants, formulas, orderings, packet layouts) or the single literal line `- None.` when the blueprint asserts no vanilla-behavior fact (this blueprint is exactly that case, §2.10). The list runs until the next `##`/`###` heading or end of file.

**`claims_gate::parse_claims_to_verify(blueprint_content: &str) -> Result<ClaimsRequirement, String>`** — `ClaimsRequirement` is `Exempt` (the `- None.` sentinel, matched as the section's *only* line) or `Required(Vec<String>)` (every other `- `-prefixed line's trimmed text). Missing heading entirely → parse error (every blueprint must carry the subsection, exempt or not — this is itself an M3.5-B04 requirement retroactively applied by whichever blueprint corrects each pre-existing blueprint file, out of scope for this blueprint's own changeset beyond stating the rule `verify-claims` enforces).

**`xtask verify-claims <milestone>`** (new positional-arg verb, e.g. `cargo xtask verify-claims M3.5`): for every `blueprints/<milestone>/M*-B[0-9][0-9]-*.md` file excluding `*-B00-index.md` and `*-COMPLETION-REPORT.md`, parse its Claims-to-verify list; `Exempt` → pass, case detail "claims-exempt". `Required(claims)` with `claims.len() == N` → look for the sibling `<ID>-CLAIMS.md`; missing → fail ("missing CLAIMS file, N claims expected"); present → parse its table rows (excluding header/separator), row count `M`; **exact match required, `M != N` fails** ("CLAIMS.md has M rows, blueprint declares N claims" — this is deliberately not "at least N", since a stale CLAIMS.md that silently dropped a row while the blueprint's own list grew is exactly the drift this exact-match rule catches); any row whose Verdict is exactly `WRONG` (not containing `corrected`) fails ("uncorrected WRONG claim: <claim text>"). Writes `target/verify/verify-claims.json` via `tier_result` exactly like every other verb. **Not** added to `tier1::SUB_VERBS` — TEST-D57's own text places this gate "before any blueprint's implementation changeset begins," a milestone-start checkpoint, not a per-PR Tier-1 gate; it is invoked once per milestone, by whichever process starts that milestone's implementation wave.

**The path-guard extension.** `path_guard::is_claims_artifact(path: &str) -> bool` — `path.starts_with("blueprints/") && path.ends_with("-CLAIMS.md")` (a direct predicate, not a `PROTECTED_PATHS` glob row — §2.2 already explains why the existing matcher cannot express a partial-segment wildcard). For `ChangesetType::Implementation` commits only, `path_guard::run` performs a second check alongside the existing `check_paths` protected-path check (`check_claims_gate`, a sibling of `evaluate_commit` whose failures are unioned into the same per-commit failure list at the call site):

1. **Ownership comes from the commit subject, never from paths.** Path-prefix ownership is ambiguous by construction in this repository — `crates/mechanics/` is declared under `Crates touched` by M3-B01, M3-B04, M3-B06, M3.5-B02 and every M4 blueprint, `crates/server/` by M1-B01/B02/B04/B05 and M11-B01 — so a prefix index resolves every production file to the earliest, heading-less blueprint and the gate never fires. The owning blueprint of an Implementation commit is therefore the ID its subject line starts with, in the established subject convention `<ID> <changeset-type>: <summary>`: `claims_gate::subject_owner(subject: &str) -> Option<SubjectOwner>` parses a leading `M<n>` or `M<n>.<m>` milestone token, optionally followed by `-B<nn>`, followed by whitespace; anything else (no leading ID at all) is `None`. `SubjectOwner::Blueprint(id)` (e.g. `M3.5-B02`, `M4-B01`) or `SubjectOwner::Milestone(m)` (e.g. `M3` from `M3 field-report implementation: …`). An Implementation commit whose subject yields `None` is itself a violation: `"implementation changesets must name their owning blueprint (or milestone, for field-report changesets) at the start of the subject"`.
2. **Per-commit gate.** `SubjectOwner::Blueprint(id)`: the file `blueprints/<milestone>/<id>-*.md` (excluding `-CLAIMS.md`) must exist — unknown ID → violation `"<id> names no blueprint file under blueprints/<milestone>/"`. Parse its Claims-to-verify requirement (§2.9's parser, reused). `Exempt` → pass. `Required(_)` → require `blueprints/<milestone>/<id>-CLAIMS.md` to exist and contain zero rows whose Verdict is exactly `WRONG` (the lighter, existence-plus-correctness check — **not** the exact-count match, which stays `verify-claims`'s own stricter, milestone-start-only audit). A blueprint file that carries no `### Claims to verify (TEST-D57)` heading at all: milestones M0–M3 are covered retroactively by the M3-era planning-reference audit (TEST-D57's own text) → pass; for M3.5 and every later milestone the missing heading is a violation `"<id> carries no Claims-to-verify subsection — every M3.5+ blueprint must"`. `SubjectOwner::Milestone(m)`: milestones up to M3 → pass (field-report changesets against retroactively audited work); M3.5 and later → violation `"implementation changesets for <m> must name their blueprint"` — TEST-D57 is a hard gate from M4 onward, and a milestone-only subject would otherwise be the one way around it.
3. Every violation above is a `Violation`-shaped failure carrying the commit hash and subject, unioned into the same per-commit failure list `evaluate_commit`'s protected-path check feeds, with the fixed message `"<subject>: owned by <id>, whose CLAIMS.md is missing/has an uncorrected WRONG row — not allowed in an implementation changeset until the claim is corrected or confirmed"` for the CLAIMS-state failure and the messages quoted in steps 1–2 for the structural ones.

New `PROTECTED_PATHS` row is **not** added (per the glob-matcher limitation above); instead, `check_paths` (or a small new sibling function `check_claims_artifact_paths`, unioned into `evaluate_commit`) flags any Implementation-changeset file for which `is_claims_artifact` is true, reason `"TEST-D57 claims-verification artifact — implementation changesets must not self-certify their own claims (test-authoring or governance only)"`.

- `claims_gate_violations_flags_a_missing_claims_file`: ownership resolves, `requirement_of` returns `Required(_)`, `claims_file_of` returns `None` → one violation naming the owning blueprint id.

### `crates/mechanics/tests/hopper_transfer_order.rs` (test-authoring addition)

`hopper_chain_of_three_relays_an_item_end_to_end`: three `HopperBlockEntity` instances at `BlockPos::new(0,1,0)` (A, facing `Direction::East`), `BlockPos::new(1,1,0)` (B, facing `Direction::East`), `BlockPos::new(2,1,0)` (C, facing `Direction::East`), inserted into a fresh `HopperChainWorld`; A seeded with one `stack("minecraft:redstone", 1)` in its first slot, B and C empty. Drives `tick` on A, then B, then C, repeatedly (mirroring `single_transfer_takes_exactly_eight_ticks_between_attempts`'s own cooldown-respecting drive loop — call each hopper's own `.tick(pos, &mut world, &DefaultMaxStackSize, &already_ticked)` across enough simulated 8-tick cooldown cycles, at least 16 ticks total, for the item to make two hops) until either C's own first slot is non-empty or an explicit iteration cap (32 ticks) is reached without it. Asserts C's own first slot holds exactly one `"minecraft:redstone"` item at that point, and that A's own first slot is empty (the item actually left the source, not merely that C independently gained one). This is the file's first and only test whose name contains `_chain_`-equivalent composition evidence — token `_chain_` itself, satisfying §2.5.3 directly without a rename.

## Constraints & forbidden actions

(a) This blueprint's own changesets never touch anything the `lint-tests`/`path-guard` machinery treats as a protected path other than what they explicitly add — no golden fixture, no scenario RON, no perf budget/SLO table.

(b) No new external dependency. Every new module uses only what `xtask`'s existing `Cargo.toml` already provides (`xshell`, `serde`/`serde_json` via `tier_result`, `std`).

(c) No Mojang or third-party reimplementation source is consulted. This blueprint asserts no vanilla-behavior fact (§2.10); its retroactive annotation work only reads and renames this repository's own existing test code, and cites sources already named in those files' own doc comments (blocks.json, the blueprint sections named in each file's `//!` header) — never re-derives a new expectation.

(d) **Changeset boundary, restated (TEST-D45/D46):** two governance changesets — (1) the four new `xtask` modules plus `lib.rs`/`main.rs` wiring plus `forbidden_patterns.rs`/`path_guard.rs` extensions, all under `xtask/` (already a protected path only implementation changesets are barred from — this is governance, not implementation, so it is allowed); (2) none other needed. One test-authoring changeset — every edit under §2.6's 40 files plus the new `xtask/tests/*.rs` fixtures (Acceptance tests) plus the one new hopper-chain test. **The retroactive annotation must never weaken any existing test**: a rename is not a weakening (TEST-D49's `check_weakened_tests` only flags a name *disappearing* between base and head — a rename makes the old name vanish and a new one appear, which `check_weakened_tests` cannot distinguish from a genuine deletion+decoy; because this is a test-authoring changeset, not an implementation changeset, `check_weakened_tests` does not even run against it, §2.2 — but as a matter of engineering discipline, not lint enforcement, no assertion, fixture, or case is ever removed or loosened by this changeset, only header/name text added). No `#[ignore]` is added anywhere in this changeset.

(e) The header-content table (§2.6) is this blueprint's own binding specification — an implementer does not re-derive verdicts, only encodes the ones given, with one exception: the exact renamed test-function names, left to implementer judgment as noted in Deliverables.

(f) `xtask verify-claims`'s exact-count matching rule (§2.9) is deliberately strict (`M != N` fails, not `M < N`) — an implementer must not loosen this to "at least" even if it seems more permissive-by-default; drift in either direction is exactly what the rule exists to catch.
