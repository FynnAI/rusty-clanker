## 2. Goal & Done definition

Every block-state id in the redstone/piston/placement/physics code paths that is today computed
by hand-derived arithmetic (a literal base id plus a hand-copied stride, restated independently
in up to four different files) must instead be computed from `rc-registries`' M3.5-B01-generated
per-block property table — so a future pinned-version bump that regenerates that table changes
every consumer automatically, instead of silently drifting the way M3's hand-synced tables did
(`docs/planning/12-workspace-structure.md` WS-D15's own rationale: "three separate hand-synced
literal-id tables... each a defect class this table removes by construction"). No production
behavior changes: every corpus/parity result stays byte-identical.

Done when:
- [ ] Every site in the Deliverables inventory (§4) computes its block-state id(s) through
      `rc-registries`' M3.5-B01 API — no hand-derived stride/base arithmetic remains in
      `crates/mechanics/src/redstone/{wire,torch,repeater,comparator,piston,registration,
      dispatch_ranges}.rs`, `crates/physics/src/shapes.rs`, or
      `crates/server/src/play/mining.rs`.
- [ ] `crates/testing/gametest/src/replay.rs`'s eight `*_RANGE` constants are retired the same
      way, in a separate **governance** changeset
      (§6, Step 9 — this file is a `xtask lint-deps`/path-guard protected path, never touchable
      by an `Implementation` changeset).
- [ ] `crates/physics/Cargo.toml` gains a normal `rc-registries` dependency (§3.4's WS-D3
      ruling); `xtask lint-deps` still reports 0 forbidden edges.
- [ ] Every equivalence test in §5 is green, including the one that starts red
      (`decode_chest_state`'s waterlogged=true ids, §3.7) and only turns green once
      `mining.rs`'s chest decode is retired against the generated table.
- [ ] `xtask parity-check redstone` still reports 52/52 and `xtask placement-diff` still reports
      85/85 — unchanged from before this blueprint.
- [ ] CI tier: `cargo nextest run --workspace --profile ci`, `xtask lint-deps`,
      `xtask lint-tests` (rejects any new literal block-state id outside `rc-registries`,
      M3.5-B01's own gate), `xtask path-guard`, `xtask parity-check redstone`,

## 3. Context (self-contained)

### 3.1 The M3.5-B01 API (prerequisite, restated as given)

M3.5-B01 adds a generated per-block-state-property table to `rc-registries`, alongside the
already-existing `rc_registries::generated_v776::block_states::default_state::<BLOCK>` per-block
default-id constants (unchanged, still used throughout this blueprint). Its public surface, as
specified by this blueprint's own governing task:

```rust
// crates/registries/generated/v776/block_states.rs (extended by M3.5-B01) — note this
// module's own `BlockStateId(pub u32)` newtype is DISTINCT from `rc_chunk_storage::BlockStateId`
// used everywhere else in this blueprint; cross into it via `.0` (raw u32), exactly the
// conversion `dispatch_ranges.rs`'s pre-existing `exclusive()`/`checked()` helpers already use.
pub struct BlockStateRange { pub first: BlockStateId, pub last: BlockStateId, pub default: BlockStateId }

pub fn properties(id: BlockStateId) -> &'static [(&'static str, &'static str)];
pub fn state_id(block: BlockId, props: &[(&str, &str)]) -> Option<BlockStateId>; // partial sets default the rest
pub fn with_property(id: BlockStateId, name: &str, value: &str) -> Option<BlockStateId>;
pub fn block_of(id: BlockStateId) -> BlockId;
```

**Naming caveat (self-containedness):** M3.5-B01 has not been written yet; its own blueprint
picks the exact module path and identifier casing for the per-block `BlockStateRange` constants
and the `BlockId` enum's variants. This blueprint illustrates them using the same
`SCREAMING_SNAKE_CASE` convention the pre-existing `default_state::<BLOCK>` constants already
use in this same generated file (e.g. `state_ranges::REDSTONE_WIRE: BlockStateRange`,
`BlockId::REDSTONE_WIRE`) — a per-block constant table, not a function, mirroring
`default_state`'s own established shape exactly (querying a range needs no runtime input; every
site below already knows which block it means at compile time). Wherever M3.5-B01's actual
emitted names differ, the implementer substitutes them 1:1; every semantic mapping below (which
field, which property string, which value) stays unchanged regardless of exact spelling.

### 3.2 The two layers this blueprint retires

**Layer A — the cross-check layer disappears.** `dispatch_ranges.rs` exists today only because
no generated per-block range table existed: it reads each component's own hand-derived
`state_range()` and `assert!`s it contains that block's `default_state` id as an "integrity
anchor" (its own module doc comment, `crates/mechanics/src/redstone/dispatch_ranges.rs:1-40`).
Once M3.5-B01 supplies the real range directly, this whole cross-check is redundant — there is
nothing left to check against, since the range itself now comes from the same generated source
the anchor used to spot-check. `derive_tier1_state_ids()`/`derive_piston_state_ids()` collapse to
direct reads of `state_ranges::<BLOCK>` (their own public signatures, and their two callers —
`crates/server/src/play/world.rs`'s `bootstrap_redstone_dispatch` — are unaffected).

**Layer B — each component's own internal encode/decode arithmetic is rewritten.** Every
component still needs to (a) recognize whether a raw id belongs to it, (b) build a fresh id from
property values, and (c) patch one property of an already-stored id while preserving the rest.
M3.5-B01's `properties`/`state_id`/`with_property`/`block_of` map onto these three needs exactly:

| Current hand-authored pattern | Replacement |
|---|---|
| `is_wire_range(raw)` / `(BASE..=MAX).contains(&raw)` | `block_of(BlockStateId(raw)) == BlockId::<BLOCK>` (or a range-containment check against `state_ranges::<BLOCK>` where a cheap bound check is preferred over a full property decode — behaviorally identical, implementer's choice per site) |
| `<block>_state_id(prop1, prop2, ...)` (construct fresh) | `state_id(BlockId::<BLOCK>, &[("prop1", "val1"), ("prop2", "val2"), ...]).expect(...)` |
| `new_<field>_state_id(current_raw, new_val)` (patch one field, preserve the rest) | `with_property(BlockStateId(current_raw), "prop", "val").expect(...)` — this is a *direct* match: `with_property`'s whole contract ("leave every other property exactly as `id` already has it") is precisely what every one of this project's own "own-state writeback" doc comments already describes by hand |
| `<block>_decode(raw)` / `decode_<block>_state(raw)` (extract property values) | `properties(BlockStateId(raw))` — a `&[(&str, &str)]` slice; look up each needed key, parse the value string back to the typed value (`u8`, `bool`, `Direction`, `ComparatorMode`, `ChestType`) with the same small `match`/`parse()` every site already has for the *reverse* direction today |
| `<x>_index(direction)` / `<x>_from_index(idx)` stride helpers (`diode_facing_index`, `piston_facing_index`, `horizontal4_index`, `hopper_facing_index`, `full6_piston_index`, `chest_type_index`, and their inverses) | **Deleted**, not replaced — once encode/decode goes through `state_id`/`with_property`/`properties`, nothing constructs a stride offset by hand any more, so nothing needs a value-to-index or index-to-value table. Only a plain `Direction <-> "north"/"east"/.../"down"` (and `bool <-> "true"/"false"`, `ComparatorMode <-> "compare"/"subtract"`, `ChestType <-> "single"/"left"/"right"`) string mapping remains — this is unavoidable glue code, not itself an "id table" (WS-D15 targets block-state *id arithmetic*, not property-value spelling), so it is **not** a retirement target; every site below keeps (or adds) a small local `fn direction_to_str`/`fn str_to_direction` pair, undocumented further here since it is ordinary, un-magic string mapping |

### 3.3 Type-crossing convention

`rc_registries::generated_v776::block_states::BlockStateId` (M3.5-B01's own type, `pub
struct BlockStateId(pub u32)`) is a different Rust type from `rc_chunk_storage::BlockStateId`
(also `pub struct BlockStateId(pub u32)`, used everywhere in `rc-mechanics`/`rc-physics`/the
server). They are never interchangeable directly — cross via `.0` (raw `u32`), exactly the
pattern `dispatch_ranges.rs`'s pre-existing `checked()`/`exclusive()` functions already use
today (`crates/mechanics/src/redstone/dispatch_ranges.rs:56-69,110-118`). Every replacement
expression below ends in `.0` where the result feeds a `rc_chunk_storage::BlockStateId` or a
plain `u32`.

### 3.4 WS-D3 decision: `rc-physics -> rc-registries` is a direct edge, not a trait seam

`crates/mechanics/Cargo.toml` **already** depends on `rc-registries` normally — added and
justified by a prior M3 field-report changeset's own comment: *"`rc-registries` as `Shared`
(reachable by both binaries), not `NETRENDER`... this dependency is therefore sanctioned, not a
new exception."* No Cargo.toml change is needed for `rc-mechanics`; every `rc-mechanics` site in
this blueprint (§3.6 rows 1-40) already has the import available.

`crates/physics/Cargo.toml` currently depends on **only** `rc-core`. `crates/physics/src/
shapes.rs`'s own module doc comment explains why its hand-authored table exists at all: *"this
crate has no dependency on `rc-registries` (WS-D3 rule 1's shared-crate isolation), so it cannot
import those constants directly."* This blueprint adds:

```toml
# crates/physics/Cargo.toml
[dependencies]
rc-core = { path = "../core" }
rc-registries = { path = "../registries" }
```

**This is allowed under `xtask lint-deps`'s literal WS-D3 checks** (`xtask/src/lint_deps.rs`),
not merely "not forbidden":
- Rule 1 (`SHARED` list: `rc-core`, `rc-nbt`, `rc-registries`, `rc-protocol-macros`,
  `rc-protocol`, `rc-mod-api`, `rc-mod-host`, `rc-physics`) only requires every listed crate be
  reachable from both binaries' transitive closures — it never forbids an *additional* edge
  between two `SHARED` crates. `rc-physics` and `rc-registries` are both already in this list.
- Rule 2 (`SIM` = `{rc-scheduler, rc-mechanics}` must never reach/be reached by `NETRENDER` =
  `{rc-render, rc-protocol, rc-transport-inproc, rc-transport-net, rc-auth, rc-cluster,
  rc-proxy}`) does not mention `rc-physics` or `rc-registries` on either side — the new edge
  cannot open a `SIM`<->`NETRENDER` path.
- Rules 3/4 are scoped exactly to `rc-messaging`'s and `rc-mod-api`'s own normal-dependency
  sets — untouched by this change.

A `BlockStatePropertyLookup` trait injected at composition time (the alternative this
blueprint's own governing task raised) would only be justified if the direct edge were
forbidden. It is not — so this blueprint takes the direct edge, matching `rc-mechanics`'
already-sanctioned precedent exactly and avoiding an indirection layer with no rule to satisfy.

### 3.5 Changeset-type split: this blueprint spans Implementation *and* Governance

`xtask/src/path_guard.rs`'s `PROTECTED_PATHS` includes `crates/testing/gametest/**` (whole
crate, `src/` included — *"rc-gametest: trace/spec/replay/capture logic (M3-B07)"*) and
`crates/*/tests/**` (every crate's `tests/` directory). `check_paths` only enforces these
against a commit whose trailer is `Changeset-Type: implementation` — `test-authoring` and
`governance` commits are exempt entirely. Consequence for this blueprint:

- `crates/mechanics/src/redstone/*.rs`, `crates/physics/src/shapes.rs`,
  `crates/physics/Cargo.toml`, `crates/server/src/play/mining.rs` are **not** protected — their
  retirement is the `implementation` changeset (§6, Steps 2-8).
- `crates/testing/gametest/src/replay.rs` and `crates/testing/gametest/Cargo.toml` **are**
  protected — their retirement is a separate `governance` changeset (§6, Step 9), same category
  M3.5-B00's own index assigns "harness/tooling work."
- New test files under any `crates/*/tests/**` are written in the `test-authoring` changeset
  (§5) regardless of which crate they live in — the path guard exempts that changeset type too.

### 3.7 Known discrepancy: `mining.rs`'s chest decode anchors on the default state, not the first

`crates/testing/gametest/src/replay.rs:461` declares `CHEST_RANGE = (3987, 4010)` — and that is
**correct**: the pinned `blocks.json` report lists `minecraft:chest` as 24 states, ids
3987..=4010, first state `{type=single, facing=north, waterlogged=true}` (3987), default
state `{…, waterlogged=false}` (3988), last `{type=right, facing=east, waterlogged=false}`
(4010); property order in the id space is `facing` (stride 6) → `type` (stride 2) →
`waterlogged` (stride 1, `true` before `false`). `crates/server/src/play/mining.rs`'s own
`chest_state_id`/`decode_chest_state` instead anchor on `default_state::CHEST.0` (3988) and
document the range as `CHEST.0 ..= CHEST.0 + 23` = `3988..=4011` — the same "the generated
default is a range boundary" fallacy `dispatch_ranges.rs`'s own doc comment already warns
against (a default state is one state *inside* its block's range, not its first). Consequences,
verified against the report: `chest_state_id` is correct for every placement this server makes
(it always produces `waterlogged=false` ids, which sit at `3988 + f*6 + t*2`); but
`decode_chest_state` is wrong for every `waterlogged=true` id — 3987 decodes to `None`,
3989 (`north, left, waterlogged=true`) decodes as `north, single`, and the wire id 4011
(`redstone_wire`, first state) decodes as a chest `east, right` — while its doc comment
asserts the opposite ("a `waterlogged=true` id still decodes correctly"). Dormant today
because this tier-1 world has no fluids, so no `waterlogged=true` chest ever exists and 4011
is never handed to the chest decoder; a live defect the moment M4 adds water. This blueprint
retires both functions against the generated table (§6 Step 6), which removes the fallacy by
construction, and §5 pins the three ids above as a test that starts **red** against today's
code — a deliberate, documented exception to "every test starts green." The `replay.rs`
constant needs no correction, only retirement (Step 9).
