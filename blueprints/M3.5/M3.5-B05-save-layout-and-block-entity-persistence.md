## 1. Goal & Done definition

Close the two persistence deviations M2/M3 shipped knowingly: worlds save under the pre-restructure legacy layout (`region/`, `DIM-1/`, `DIM1/` at the world root) instead of 26.2's real nested `dimensions/<namespace>/<path>/` scheme, and every placed chest/furnace/hopper's contents (and a comparator's analog output) are silently dropped on save — `io_pool.rs::save_one` today hands the chunk NBT encoder a permanently-empty block-entity index as a deliberate stopgap. This blueprint corrects the save layout, implements the real `BlockEntityCodec` extension point WORLD-D6 reserves, wires it through chunk save *and* load (including re-spawning ECS block-entity components when a chunk with saved block entities loads), and proves both with an `m2-report`-style real-process restart round trip.

Done when:

- [ ] `AnvilDiskBackend` writes/reads every dimension's terrain/entities/poi region files under `<world_root>/dimensions/minecraft/<overworld|the_nether|the_end>/{region,entities,poi}/`; `level.dat`(`_new`/`_old`) and `session.lock` stay at the world root; opening a world root that contains a legacy top-level `region/` folder fails fast with a clear, named error instead of silently reading/writing the wrong place.
- [ ] `BlockEntityRecord`/`BlockEntityCodec` exist in `rc-chunk-storage` exactly as WORLD-D6 specifies (adapted to this codebase's real method shapes, Context); `ChestBlockEntity`/`FurnaceBlockEntity`/`HopperBlockEntity` implement it; a `minecraft:comparator` record is produced/consumed via a small standalone helper pair, not a new ECS block entity (deliberate — Context).
- [ ] `chunk_nbt::ChunkNbtCodec::to_nbt` writes real `block_entities` entries from real data; `from_nbt` reconstructs real `BlockEntityRecord`s in on-disk order; a freshly loaded chunk re-spawns the matching typed ECS components in that same order and a comparator's `OutputSignal` is seeded back into `ComparatorBehavior`.
- [ ] `io_pool.rs::save_one`'s empty-index stopgap and its justifying doc comment are gone; a chunk holding real block entities saves and loads them for real.
- [ ] Acceptance: unit round-trips per codec; a chunk-NBT round trip with two block entities in stable load order; a save-layout directory-shape test; an `m2-report`-style live-process restart case (`AC_block_entities_survive_restart`) — CI tier `cargo xtask m35-be-report --mode smoke` green, plus `cargo nextest run -p rc-chunk-storage -p rc-mechanics --profile ci`.

## 2. Context (self-contained)

### 2.1 WORLD-D6, restated

Block entities are **not** decomposed into per-block ECS entities across the whole 98,304-cell chunk volume. Each *placed* block entity (furnace, chest, hopper, …) is one child `bevy_ecs::Entity`, tagged `BlockEntityHeader { pos: BlockPos }` plus its own typed component, referenced from its owning chunk's `BlockEntityIndex: Vec<Entity>` component in vanilla's own stable per-chunk load order (ARCH-D17). The persistence *contract* is generic: one record type, `BlockEntityRecord { pos: BlockPos, id: ResourceLocation, data: NbtCompound }`, and one trait, `BlockEntityCodec` (`to_record`/`from_record`), implemented per concrete type. The storage layer (`rc-chunk-storage`) never interprets a block entity's field semantics — it only carries the generic record in and out of the chunk's `block_entities` NBT list. Every concrete type's own (de)serialization already exists in `rc-mechanics` (M3-B06, `ChestBlockEntity::to_nbt`/`from_nbt` et al.) — this blueprint's own job is the *wrapper* that exposes those through the generic contract, and the *wiring* that gets real records to/from disk instead of the current always-empty stand-in.

### 2.2 The crate-boundary problem this blueprint actually solves

`rc-chunk-storage` (owns `ChunkSaveSnapshot`, `chunk_snapshot_system`, `ChunkNbtCodec`, `AnvilDiskBackend`) cannot depend on `rc-mechanics` (owns `ChestBlockEntity`/`FurnaceBlockEntity`/`HopperBlockEntity`/`ComparatorBehavior`) — the dependency graph runs the other way (`rc-mechanics` already depends on `rc-chunk-storage` for `BlockStateId`/`ItemStackRecord`/`BlockEntityIndex`). Concretely, `chunk_snapshot_system` (Stage 9, `DomainGroup::ChunkSerialize`) is a plain `bevy_ecs` `Query`-based system inside `rc-chunk-storage`; it can see `BlockEntityIndex` (a list of `Entity` handles) but has no way to resolve those handles to their own typed components or call anything mechanics-owned. `RC-IoPool`'s save job (`io_pool.rs::save_one`) runs even further away — off the ECS thread entirely, on a plain worker thread with no `World` access at all — so by the time a save job runs, every byte it needs must already be plain, resolved data.

The fix mirrors a pattern this codebase already uses for exactly this kind of layering (`stage7/ecs.rs`'s `EcsBlockEntityWorld` — a `rc-mechanics`-owned `bevy_ecs` system that freely combines a `Query` over mechanics-owned components with a `Query<&BlockEntityIndex>` over the chunk-storage-owned index, because two queries whose component sets are disjoint never conflict in `bevy_ecs`, regardless of which crate declared which type):

1. `rc-chunk-storage` adds one new, purely-data `Component`: `BlockEntitySaveRecords(Vec<BlockEntityRecord>)`, attached to every chunk entity right next to `BlockEntityIndex`. Chunk-storage's own Stage-9 system (`chunk_snapshot_system`) and `capture_snapshot` read this component the same way they already read `BlockStateColumn`/`BiomeColumn`/etc. — a plain clone into `ChunkSaveSnapshot`, no mechanics knowledge required.
2. `rc-mechanics` adds a **new Stage-7 system** (`DomainGroup::BlockEntity`, `Stage::BlockEntityTick = 7`, which the pipeline always runs before `Stage::ChunkSnapshot = 9` — `crates/scheduler/src/pipeline.rs`'s `Stage` enum is what actually orders execution; `DomainGroup::ALL`'s declaration order is unrelated to run order) that walks every resident chunk's `BlockEntityIndex`, resolves each entity's real typed component, calls the new `BlockEntityCodec::to_record` on it, appends any `minecraft:comparator` records for that chunk (2.5 below), and writes the result into that chunk's `BlockEntitySaveRecords`. This is the *only* place in the codebase that ever needs both type systems in scope at once, and it is allowed to, because `rc-mechanics` already depends on `rc-chunk-storage`.
3. Symmetrically on load: `rc-chunk-storage`'s `ChunkLifecycleManager` (which spawns a freshly loaded/generated chunk entity in `pre_tick`) is given one new injected trait object, `BlockEntitySpawner`, at construction time. Right after spawning the bare chunk entity, `pre_tick` hands the just-decoded `Vec<BlockEntityRecord>` to `spawner.spawn_loaded_block_entities(world, chunk_entity, records)`. The real implementation of that trait (`ProductionBlockEntitySpawner`, in `rusty-clanker-server`, the one crate that already depends on both `rc-chunk-storage` and `rc-mechanics`) dispatches on each record's `id`, spawns the matching typed component pair, and pushes the new `Entity` onto a real `BlockEntityIndex` — mirroring `world.rs`'s already-existing `spawn_block_entity_for_placement` almost exactly, just fed from disk instead of from a placement action. `rc-chunk-storage`'s own tests use a trivial `NoopBlockEntitySpawner` (a no-op) so the crate's existing test suite needs no mechanics dependency.

### 2.3 `BlockEntityRecord`/`BlockEntityCodec`, adapted signatures

WORLD-D6's own literal signatures (`fn to_record(&self) -> BlockEntityRecord`, `fn from_record(&BlockEntityRecord) -> Self`) omit `pos` because the planning document does not commit to where a block entity's own position lives at the Rust-type level. In this codebase a block entity's position lives in the sibling `BlockEntityHeader` component, not inside the typed block-entity struct itself (`ChestBlockEntity` etc. have no `pos` field) — exactly mirroring the already-committed `to_nbt(&self, pos: BlockPos)` / `from_nbt(&Compound) -> (BlockPos, Self)` shape M3-B06 already implemented. `BlockEntityCodec` is specified here with `pos` threaded through explicitly for this reason; this is an adaptation of WORLD-D6's contract to this codebase's real component layout, not a deviation from what it persists.

`BlockEntityRecord.data` is the **complete** per-entity compound (already carrying `id`/`x`/`y`/`z` plus every type-specific field — exactly what `ChestBlockEntity::to_nbt` etc. already produce) so that `chunk_nbt::to_nbt` can write it into the `block_entities` list completely unmodified, and `record.pos`/`record.id` are a cheap, NBT-free fast-access mirror of what `data` already encodes, used by the dispatch/indexing logic (2.2 step 3, 2.6) without needing to parse NBT.

`NbtCompoundExt` (`rc_nbt::schema`, already used throughout this crate — `level_dat.rs`, `player.rs`) is implemented only for `borrow::NbtCompound`, never `owned::NbtCompound`, and the existing `ChestBlockEntity::from_nbt`/etc. all take `&borrow::NbtCompound`. `BlockEntityRecord.data` is `owned::NbtCompound` (it must outlive the borrowed chunk document it may have been decoded from, and it must be constructable fresh from live ECS state at save time). `BlockEntityCodec::from_record`'s implementations therefore round-trip through bytes once (`rc_nbt::write_owned` then `rc_nbt::read_borrowed_strict`) before calling the existing `from_nbt`, exactly the same two calls `crates/mechanics/tests/block_entity_nbt_roundtrip.rs`'s own `to_bytes`/`with_borrowed_compound` helpers already perform. This is a cheap, correctness-preserving conversion (never fails on data this crate itself wrote); if the pinned `rc-nbt`/`simdnbt` version exposes a direct owned→borrow view by the time this is implemented, an implementer may use that instead — confirm against the installed crate's own docs first (this project's established "verify against installed docs" convention, e.g. M2-B03's `std::fs::File::try_lock` note).

### 2.4 26.2 container-contents item format (TEST-D57 claim, partially pre-verified)

`crates/mechanics/src/item_stack.rs` already implements the component-based 26.2 item-stack shape used by every tier-1 container: `{ id: String, count: Int, components: Compound (omitted if absent) }`, with each occupied `Items` list entry carrying a sibling `Slot: Byte`. This is **already the real production code path** (`ChestBlockEntity`/`FurnaceBlockEntity`/`HopperBlockEntity::to_nbt`/`from_nbt` all call `item_stack::slots_to_items_list`/`items_list_from_nbt`) — this blueprint does not change it, only exercises it end-to-end through a real save/load cycle for the first time. The exact tag names below are restated from the already-committed code, not newly derived; per-type key names not independently re-verified against `docs/research/mc-26.2/` at blueprint-writing time are marked as TEST-D57 claims regardless, since M3.5's own acceptance criterion 3 requires every blueprint to carry this list before M4:

- Chest (`minecraft:chest`): `Items: List<Compound>`, `CustomName: String?`, `Lock: String?`. **CONFIRMED** (code-verified against the committed, tested implementation).
- Furnace (`minecraft:furnace`): `Items`, `BurnTime: Short`, `CookTime: Short`, `CookTimeTotal: Short`, `CustomName?`, `Lock?`. **TEST-D57 claim** — the vanilla 26.2 tag names may have been renamed (the task brief that produced M3-B06 flagged `lit_time_remaining`/`cooking_time_spent`/`cooking_total_time` as a possible newer naming; `docs/research/mc-26.2/` does not resolve this at blueprint-writing time). Do not rename in this blueprint — record the open question in `docs/findings-for-planning.md` per this project's standing rule, and keep `BurnTime`/`CookTime`/`CookTimeTotal` as this crate's own internal-but-stable schema either way (WORLD-D16 already requires refusing any `DataVersion` this engine did not itself write, so this schema's own internal consistency, not vanilla naming, is what correctness depends on for round-tripping **this engine's own saves**).
- Hopper (`minecraft:hopper`): `Items`, `TransferCooldown: Int`, `RCFacing: Byte` (this project's own non-vanilla extra field, already documented in `hopper.rs` as deliberate), `CustomName?`, `Lock?`. **CONFIRMED** for `Items`/`TransferCooldown` (code-verified); `RCFacing` is intentionally non-vanilla.
- Comparator (`minecraft:comparator`): `OutputSignal: Int`, `x`/`y`/`z`/`id` (no `Items`, no other fields). **TEST-D57 claim** — restated from the M3 field-report finding (`docs/findings-for-planning.md`, "comparator has no real ECS block entity" entry) that real vanilla stores this in a `ComparatorBlockEntity`; the exact tag name `OutputSignal` is this blueprint's own best-available naming pending independent verification.

### 2.5 The comparator special case

`ComparatorBehavior` (`crates/mechanics/src/redstone/comparator.rs`) deliberately has **no** real ECS block entity — its analog `output` (`0..=15`) lives in a private `Mutex<HashMap<BlockPos, ComparatorState>>` inside `ComparatorBehavior` itself, one instance per region. This is a working, real-connection-verified M3 design decision (`play_block_entity_chunk_list.rs`'s own `comparator_appears_in_the_chunk_block_entity_list_without_a_tracked_ecs_entity` test), not a gap this blueprint closes by introducing a new ECS type. Instead:

- **Save side**: `ComparatorBehavior` gains `pub fn snapshot_outputs(&self) -> Vec<(BlockPos, u8)>` (a plain copy of every currently-tracked position's `output`). The composition root already constructs one `Arc<ComparatorBehavior>` per region (`bootstrap_redstone_dispatch`, via `Tier1RedstoneHandles`) and now also inserts it as a new `bevy_ecs::Resource`, `ComparatorOutputsResource(pub Arc<ComparatorBehavior>)` — the "lookup the composition root provides" the task brief asks for. The new Stage-7 save-record system (2.2 step 2) reads this resource, filters `snapshot_outputs()` to positions belonging to the chunk currently being processed (`pos.chunk_key(dimension) == chunk_key`), sorts the matches ascending by `(x, y, z)` (the `HashMap`'s own iteration order is not stable — this blueprint's own ordering choice, not a vanilla-parity requirement), and appends one `BlockEntityRecord` per match, via `comparator::comparator_record(pos, output)`, **after** the `BlockEntityIndex`-derived records for that chunk.
- **Load side**: `ComparatorBehavior` gains `pub fn seed_output(&self, pos: BlockPos, output: u8)` (`self.state.entry(pos).or_insert(<fresh default>).output = output`, mirroring the existing defensive `entry`/`or_insert` shape `set_mode`/`set_output`/`set_powered` already use — never panics if `pos` was never `place()`d). `ProductionBlockEntitySpawner::spawn_loaded_block_entities` (2.2 step 3), on a `"minecraft:comparator"` record, parses `OutputSignal` via `comparator::comparator_output_from_record` and calls `world.resource::<ComparatorOutputsResource>().0.seed_output(record.pos, output)` — reading the resource straight off the same `world: &mut World` reference it already has, so no extra construction-ordering dependency exists between this and `bootstrap_redstone_dispatch` beyond "the region's own bootstrap already ran before its first chunk load," which is already true by construction (chunk loading only starts once a region is ticking).
- **Explicitly out of scope, pre-existing, unrelated gap**: nothing re-seeds a comparator's `facing`/`mode` (its OTHER two properties, decoded from the raw block-state id via `on_placed`) when a chunk is loaded from disk rather than placed live in the same server session — `ComparatorBehavior::facing()`/`mode()` still panic/fall back respectively for a position that was never `place()`d this session. This is a real, separate, already-broader gap (general redstone-component re-seeding on chunk load, covering repeaters too) that this blueprint's own task brief does not ask it to close and does not touch; `seed_output` only ever writes into the `state` map via the same safe `entry`/`or_insert` pattern every other setter already uses, so it never trips this gap, but a comparator loaded from disk and then interacted with before anything else ever touches its `facing`/`mode` can still hit the pre-existing panic. Record this precisely (not just "comparator persistence is incomplete") in `docs/findings-for-planning.md` per this project's standing planning-authority rule once implementation lands.

### 2.6 WORLD-D14 save layout, restated exactly

The pinned target (Java Edition 26.2, protocol 776, NET-D1) resolves every dimension's storage folder as `<world_root>/dimensions/<namespace>/<path>/`, uniformly — **no Overworld special case** — verified directly against the pinned reference's own decompiled `DimensionType`/`ChunkMap` source. Full per-world layout (this blueprint only creates/manages the subset `ChunkStorageBackend` itself touches — `level.dat`(`_new`/`_old`), `session.lock`, and the three `{region,entities,poi}/` directories per dimension; every other entry below is a later blueprint's concern and is never created by this one):

```
<world_root>/
├── level.dat                 # + level.dat_new / level.dat_old (unchanged — world root, always)
├── session.lock               # unchanged — world root, always
├── icon.png                   # not this blueprint's concern
├── dimensions/
│   ├── minecraft/
│   │   ├── overworld/{region,entities,poi}/
│   │   ├── the_nether/{region,entities,poi}/
│   │   └── the_end/{region,entities,poi}/
│   └── <namespace>/<path>/... # custom dimensions — out of scope (StorageError::UnsupportedDimension, unchanged)
├── playerdata/ stats/ advancements/ data/ datapacks/ resourcepacks/   # not this blueprint's concern
```

Today's (M2/M3) `AnvilDiskBackend` instead writes `region/`/`entities/`/`poi/` directly at `world_root` for the Overworld and `DIM-1/`/`DIM1/` for Nether/End — the legacy pre-restructure layout, a known, scheduled M3.5 deviation (WORLD-D14's own text). `level.dat`/`session.lock` are **unaffected** — they already live at the world root in both layouts.

**Migration decision: refuse, do not migrate.** No real user-facing world exists yet at any milestone through M3 (every world this engine has ever produced is a disposable dev/test artifact — a fresh temp directory per test run, per `xtask`-driven acceptance run, or a manually deleted local dev world); a bespoke one-shot layout migrator is real, untested, load-bearing code whose only job is to move files around inside someone's world save, and a latent bug in it risks silently corrupting or losing dev-world data for zero benefit (a refused-to-open world costs nothing — delete the directory and let it regenerate). `AnvilDiskBackend::open` therefore detects the legacy layout (a top-level `region/` directory directly under `world_root`, with no `dimensions/` directory yet present) and fails immediately with a new, clearly worded `StorageError::LegacyLayoutDetected { path }` instead of silently reading stale content from the wrong place or silently writing a second, orphaned copy of the world under the new layout alongside the old one.

/// WORLD-D6's generic, registry-agnostic persistence contract for one placed block entity.
/// `data` is the complete per-entity NBT compound (id/x/y/z plus every type-specific field) —
/// already exactly what `chunk_nbt::to_nbt` writes into the chunk's `block_entities` list.

pub struct BlockEntityRecord {
    pub pos: rc_core::BlockPos,
    pub id: String,
    pub data: rc_nbt::owned::NbtCompound,
}

#[derive(Debug, thiserror::Error)]
pub enum BlockEntityCodecError {
    #[error(transparent)]
    Nbt(#[from] rc_nbt::NbtError),
    #[error(transparent)]
    Schema(#[from] rc_nbt::schema::SchemaError),

/// The extension point WORLD-D6 reserves for `05-game-mechanics.md`. Implemented per
/// concrete block-entity type in `rc-mechanics`; never implemented in this crate (Context
/// 2.1: "this document never interprets a block entity's field semantics").
pub trait BlockEntityCodec: Sized {

/// Every currently-live block entity's own resolved save record for this chunk, refreshed
/// once per tick by a `rc-mechanics`-owned Stage-7 system (Context 2.2). Empty for a chunk

    fn spawn_loaded_block_entities(
        &self,
        world: &mut bevy_ecs::world::World,
        chunk_entity: bevy_ecs::prelude::Entity,
        records: &[BlockEntityRecord],
    );
}

/// The trivial default (Context 2.2 step 3) — used by this crate's own test suite and any
/// caller with no real mechanics-backed spawner available.
pub struct NoopBlockEntitySpawner;
impl BlockEntitySpawner for NoopBlockEntitySpawner {
    fn spawn_loaded_block_entities(&self, _: &mut bevy_ecs::world::World, _: bevy_ecs::prelude::Entity, _: &[BlockEntityRecord]) {}
}

    fn to_record(&self, pos: BlockPos) -> rc_chunk_storage::BlockEntityRecord {
        rc_chunk_storage::BlockEntityRecord {
            pos,
            id: "minecraft:chest".to_string(),
            data: self.to_nbt(pos),

        let (_pos, value) = Self::from_nbt(&compound)?;
        Ok(value)
    }
}
