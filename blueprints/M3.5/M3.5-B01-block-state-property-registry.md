## 2. Goal & Done definition

Extend `xtask`'s existing codegen pipeline with a second generated table derived from the local `blocks.json` datagen report: for every one of Rusty Clanker's ~1196 block types, its full block-state id range and default state; for every one of its ~32366 block states, the resolved property list, owning block, and a `replaceable` flag. Ship this as generated Rust in `rc-registries`, hash-manifested exactly like the existing `block_states.rs`, plus a thin hand-written accessor module giving every consumer a real id↔properties API (`state_id`, `properties`, `block_of`, `with_property`) instead of the hand-maintained placeholder tables M3 accumulated. Add a `lint-tests` rule that fails a changeset introducing a new hardcoded block-state-id literal outside the generated crate. This blueprint produces the registry and the lint only — it does not touch any existing consumer (`rc-mechanics`, `rc-physics`, `crates/server/src/play/mining.rs`, `rc-gametest`); retiring their own hand-derived tables against this registry is `M3.5-B02`.

## 3. Context (self-contained)

### 3.1 What already exists

`xtask/src/datagen/codegen.rs`'s `generate(registries, blocks)` reads two already-parsed `--reports` files (`xtask/src/datagen/reports.rs`'s `RegistriesReport`/`BlocksReport`, both `BTreeMap<String, _>` keyed by the block/registry's full `minecraft:...` name — so iteration is always alphabetical by that full key) and writes three files under `crates/registries/generated/v776/`: `registries.rs`, `block_states.rs`, `registry_entries.rs`. `block_states.rs` today carries exactly two things: `BlockStateId(pub u32)` and a `pub mod default_state { pub const REDSTONE_WIRE: BlockStateId = BlockStateId(5171); ... }` — one constant per block, named via `sanitize_const_name(strip_namespace(block_name))`, in the same alphabetical block-name order the source `BlocksReport` iterates in. It carries **no** per-block id range, no per-state property data, and no reverse (id → block) lookup. `crates/registries/generated/v776/MANIFEST.json` (TEST-D47) lists one SHA-256 row per generated file; `crate::fixture_manifest::build_manifest`/`verify_manifest` are generic over whatever `GeneratedFiles::files` contains — adding a fourth file to that `Vec` is picked up by the manifest and by `xtask verify-generated` (`xtask/src/main.rs`'s `Command::VerifyGenerated`, hardcoded to `crates/registries/generated/v776`) with **no change to either**.

`crates/registries` today has no `serde`/`serde_json` dependency and doesn't need one — it only ever holds generated static Rust plus (this blueprint's own addition) hand-written pure lookup logic over it.

M3's field-report fixes left three independent, hand-derived state-id tables live in production, each documented as a stopgap pending exactly this registry: `crates/mechanics/src/redstone/{wire,torch,repeater,comparator,piston}.rs` (own-state arithmetic + `state_range()`), `crates/mechanics/src/redstone/dispatch_ranges.rs` (assembles those into dispatch ranges, cross-checked at startup against `block_states::default_state`), `crates/physics/src/shapes.rs`'s `tier1_shape_table()` (hand-listed oriented ids), `crates/server/src/play/mining.rs`'s `tier1_oriented_entries`/`chest_state_id`/`decode_chest_state`, and `crates/testing/gametest/src/replay.rs`'s own `*_RANGE` constants. All of them independently derive the **same** real ids this blueprint's registry will carry as generated data — this blueprint changes none of them (read-only reference, `M3.5-B02`'s job), but the property strings and ids used in this blueprint's own Acceptance tests below were cross-checked against every one of those modules' own doc comments and match exactly.

### 3.2 The real `blocks.json` shape (ASSET-D18(a) — official `--reports` output, read locally by this blueprint's own author, never committed)

One block entry, keyed by its full `minecraft:<name>` string:

```json
"minecraft:chest": {
  "properties": {
    "type": ["single", "left", "right"],
    "facing": ["north", "south", "west", "east"],
    "waterlogged": ["true", "false"]
  },
  "states": [
    { "id": 3987, "properties": { "type": "single", "facing": "north", "waterlogged": "true" } },
    { "id": 3988, "default": true, "properties": { "type": "single", "facing": "north", "waterlogged": "false" } },
    ...
  ]
}
```

Load-bearing, verified directly against the local report:

- The block-level `"properties"` object's key order is **not alphabetical** — it is Mojang's own declared property order (chest: `type, facing, waterlogged`; hopper: `enabled, facing`; wire: `east, north, power, south, west`, which happens to be alphabetical only for wire). This order is exactly the order every one of that block's own `states[].properties` objects repeats their keys in — verified on every block this blueprint's Acceptance tests touch.
- A block with no properties (`minecraft:air`) omits the `"properties"` key entirely, and each of its `states[]` entries omits its own `"properties"` key too (a single state, `{"id": 0, "default": true}`).
- **State ids are assigned in the order `states[]` lists them, first property varying slowest.** This is Mojang's own generation order, already report-truth — never re-derive it. The one and only source of an id's own property values is that state's own `properties` object; the one and only source of a block's own state *count* and *range* is `states[].len()`/the min and max of `states[].id`. A generator that instead re-computes ids from the block-level `properties` value-list cartesian product risks a silently wrong enumeration order (this is exactly the class of defect `dispatch_ranges.rs`'s own module doc comment already refused to attempt from generated data alone) — this blueprint's codegen reads every id and every property value straight from `states[]`, never recomputes either.
- Every state within one block carries the identical set of property names, in the identical order (verified on wire/chest/piston/hopper/furnace/torch — Mojang's own `StateDefinition` never omits a property per-state).

### 3.3 Two distinct `BlockStateId` types — use the existing one

`rc_registries::generated_v776::block_states::BlockStateId(pub u32)` (used by `default_state`, and by this blueprint's own new table) is **not** the same type as `rc_chunk_storage::BlockStateId(pub u32)` (used by every world-state/mechanics/server call site). Both are trivial `u32` newtypes, freely inter-convertible via `.0`, but never implicitly compatible. This blueprint's generated table and its accessor module use `rc_registries::generated_v776::block_states::BlockStateId` throughout — reusing the existing type via `use super::block_states::BlockStateId;`, never a third newtype. Bridging to `rc_chunk_storage::BlockStateId` at real call sites is `M3.5-B02`'s job, not this blueprint's.

### 3.4 Preserving JSON property order without a new dependency

`serde_json::from_str` into a `BTreeMap`/`HashMap`-backed type discards source key order. This blueprint needs it kept (§3.2). The standard, dependency-free technique: a hand-written `Deserialize` impl whose `Visitor::visit_map` pushes `(key, value)` pairs into a plain `Vec` as `MapAccess::next_entry` yields them — `serde_json`'s streaming deserializer always visits object entries in the source's own byte order when driven this way, regardless of whether `serde_json`'s own `preserve_order` Cargo feature is enabled (that feature only changes `serde_json::Map`'s internal storage, not the token order the deserializer feeds to a caller-supplied `Visitor`). No new `[workspace.dependencies]` entry — `serde` is already pinned and this blueprint uses only its public `Deserializer`/`Visitor`/`MapAccess` traits.

### 3.5 Two `BlockStateId` type conflicts aside — the `replaceable` flag has no report source

`blocks.json` carries no per-state `replaceable` flag at all (confirmed: no such key anywhere in the local report). WS-D15 still requires one. This blueprint derives it from a hand-authored `REPLACEABLE_BLOCKS: &[&str]` list of block *names* (local, without the `minecraft:` prefix) in `xtask/src/datagen/codegen.rs`, whose 28 non-snow members are the verified content of the vanilla `minecraft:replaceable` block tag (TEST-D57 pass, `M3.5-B01-CLAIMS.md`: read from the local datagen tags export at `<tags_root>/data/minecraft/tags/block/replaceable.json`, the same tree `xtask/src/datagen/tags.rs`'s own `discover_registries`/`load_tag_tree` already consume for `codegen-tags` — cross-check against it if available before implementation starts). Candidate list (every entry individually flagged in this blueprint's own Claims-to-verify list, §9):

One special case, stated explicitly because a plain block-name membership test is not sufficient for it: `minecraft:snow` (the thin snow-layer block, property name `layers`, legal values `"1".."8"`) is replaceable **only** in its `layers=1` state — every other layer count is a real, unreplaceable block. `snow` is deliberately **not** listed in `REPLACEABLE_BLOCKS` above; its replaceable flag is computed by a dedicated exception in the per-state predicate (§4, `is_state_replaceable`), never by list membership alone. Flagged in Claims-to-verify: whether vanilla's true rule is exactly "tag member with `layers=1`" or something the tag alone cannot express.

### 3.6 Size/perf design (~1196 blocks, ~32366 states, `BLOCK_STATE_COUNT`/`BLOCK_TYPE_COUNT` already generated in `block_states.rs`)

- `block_of(id)`/`properties(id)`/`is_replaceable(id)`: **O(1)**, direct array indexing into a dense, `BlockStateId`-indexed static slice built once at codegen time by flattening every block's own range (a "range index": codegen expands `BLOCK_RANGES` into one dense per-state row up front, so no runtime range search is ever needed).
- `state_id(block, props)`/`with_property(id, name, value)`: **O(log w)**, `w` = that one block's own state count (≤1296, `redstone_wire`'s own width, the largest single-block range in the pinned version) — a per-block array of `(resolved property list, state id)` pairs, sorted once at codegen time by the property-list's own `Ord` (lexicographic tuple comparison; since every state of one block shares an identical property-name sequence, this comparison always degenerates to comparing values position-by-position), binary-searched at call time.
- All tables are `'static` slices baked into the binary's read-only data section — zero heap allocation, zero init cost, safe to call from any thread without synchronization.

### 4.5 `crates/registries/src/block_state_properties.rs` (NEW, hand-written, not generated)

use crate::generated_v776::block_state_properties::{
    BLOCK_RANGES, BLOCK_STATE_INDEX, BlockId, BlockStateRange, STATE_BLOCK, STATE_PROPERTIES,
    STATE_REPLACEABLE,

use crate::generated_v776::block_states::BlockStateId;

/// `block`'s own full state range + default state. Panics if `block.0` is out of range
/// (a config-time bug — every real `BlockId` comes from `block_id::*` or `block_of`).
pub fn range_of(block: BlockId) -> BlockStateRange;

/// property `block` does not have among `props` -> `None`. Any property of `block` not

pub fn state_id(block: BlockId, props: &[(&str, &str)]) -> Option<BlockStateId>;

/// Rewrites exactly the one named property of `id`, all of `id`'s own other property

pub fn with_property(id: BlockStateId, name: &str, value: &str) -> Option<BlockStateId>;

- (d) `check_hardcoded_block_state_literal`'s heuristic (§4.7):
  - **Never fires** on a file whose path starts with `crates/registries/generated/`, or contains a `/tests/` path segment.
  - **Never fires** on an added line, or the immediately preceding added line, containing the substring `block-state-id-lint-waiver:`.
  - **Fires** on an added line containing `BlockStateId(` immediately followed (skipping ASCII whitespace) by one or more ASCII digits then `)`, with nothing else between — a literal integer argument. `BlockStateId(id)`, `BlockStateId(raw)`, `BlockStateId(default.0)` never match (no digit immediately follows the paren after whitespace-skipping).
  - **Fires** on an added line matching `const <IDENT>: u32 = <digits>;`, `const <IDENT>: (u32, u32) = (<digits>, <digits>);`, or containing a `<digits>..=<digits>` substring, **only if** that same line, the immediately preceding added line, or the immediately following added line (case-insensitive) contains one of: `state_id`, `state id`, `blockstate`, `block-state`, `block state`.
  - **False-positive policy**: an unrelated numeric `u32` const never trips this check unless it is also textually associated with block-state vocabulary (deliberately narrow — the bare word `state` alone does not qualify, avoiding e.g. "connection state"/"game state" comments); this check only ever inspects a commit's own added lines (never the whole file), so a pre-existing literal in a file this blueprint's own commits never touch is never flagged — exactly matching checks 1–5's own established per-commit-diff design in this same file.
- (e) `rc-mechanics`, `rc-physics`, `rusty-clanker-server`, and `crates/testing/gametest` are read-only references for this blueprint (§3.1) — zero lines of any of them change. Wiring them onto this registry is `M3.5-B02`.
- (f) `WORLDGEN_REGISTRIES` (an unrelated existing list in `codegen.rs`) is untouched.
