| A hopper does not attempt a push or pull on a tick where it is redstone-locked. | `HopperBlockEntity.tryMoveItems` (HopperBlockEntity.java:106-129) — the entire push/pull body is gated on `!entity.isOnCooldown() && state.getValue(HopperBlock.ENABLED)`; `HopperBlock.checkPoweredState` (HopperBlock.java:125-130) keeps `ENABLED` equal to `!level.hasNeighborSignal(pos)`, i.e. false exactly when redstone-locked. Both entry points route through `tryMoveItems`: `pushItemsTick` (HopperBlockEntity.java:97-104) and `entityInside` (HopperBlockEntity.java:446-452), so a locked hopper attempts neither an eject nor a suck. Its cooldown counter still decrements and is clamped to 0 each tick (HopperBlockEntity.java:98-101), which is bookkeeping, not a transfer attempt. | CONFIRMED | research role (TEST-D57 pass, claude-opus-5) | 2026-09-03 |
| A hopper attempting a transfer on a tick where transfer_cooldown == 0 pushes when it is not empty and, independently in the same tick, pulls whenever its inventory is not completely full — the pull never depends on whether the push succeeded. | `HopperBlockEntity.tryMoveItems` (HopperBlockEntity.java:113-129). CORRECTION: push and pull are independent within one tick. The body is `boolean changed = false; if (!entity.isEmpty()) changed = ejectItems(...); if (!entity.inventoryFull()) changed = changed or action.getAsBoolean(); if (changed) entity.setCooldown(8);`. The push runs only when the hopper is non-empty; the pull (`suckInItems`, HopperBlockEntity.java:218-247) runs whenever the hopper's inventory is not completely full, regardless of whether the push succeeded. Order is push-then-pull, but the pull is gated on not-full, never on push failure — both may succeed on the same tick. | WRONG — corrected | research role (TEST-D57 pass, claude-opus-5) | 2026-09-03 |
| A successful hopper push always sets the pushing hopper's own transfer_cooldown = 8; a value of 7 is assigned only to a receiving hopper that was completely empty before the insertion and had not yet been ticked this same game tick ahead of the sender. | CORRECTION, two separate hoppers are involved. (a) The acting (pushing) hopper always sets its own cooldown to 8 on any successful transfer, push or pull, with no dependence on the destination's emptiness — `HopperBlockEntity.tryMoveItems` (HopperBlockEntity.java:123-125), `entity.setCooldown(8)`. (b) The value 7 belongs to the RECEIVING hopper and is set inside `HopperBlockEntity.tryMoveInItem` (HopperBlockEntity.java:333-341): when the receiving container was empty immediately before the insertion (`wasEmpty`), is itself a `HopperBlockEntity`, and is not on a custom cooldown (`cooldownTime > 8`, HopperBlockEntity.java:432-434), it is assigned `setCooldown(8 - skipTickCount)`, where `skipTickCount` is 1 only when the source container is also a `HopperBlockEntity` and the receiver's `tickedGameTime >= ` the source's (the receiver has already been ticked this game tick) — giving 7 in that case and 8 otherwise. So "destination was empty" is a condition on the destination hopper's new cooldown, never on the pusher's, and the 7-vs-8 split additionally depends on relative tick order, not on emptiness alone. | WRONG — corrected | research role (TEST-D57 pass, claude-opus-5) | 2026-09-03 |

Any 7-or-8 value that same hopper may have received as the insertion target inside `tryMoveInItem` (HopperBlockEntity.java:340) earlier in the call is overwritten by this later `setCooldown(8)`, so the pulling hopper's post-pull cooldown is unconditionally 8. | CONFIRMED | research role (TEST-D57 pass, claude-opus-5) | 2026-09-03 |
