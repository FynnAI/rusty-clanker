| A vanilla Anvil chunk record's decompressed payload is byte-identical to the chunk's own NBT tag content, with no additional framing beyond the container's compression layer. | `RegionFileStorage.write` (RegionFileStorage.java:69-80) writes the chunk compound with `NbtIo.write(value, output)` straight into the stream from `RegionFile.getChunkDataOutputStream` (RegionFile.java:265-267), which is `version.wrap(new ChunkBuffer(pos))` — the wrapper is purely the compression layer (RegionFileVersion.java:26-45: gzip id 1, deflate id 2 = DEFAULT, none id 3, lz4 id 4). `ChunkBuffer`'s constructor (RegionFile.java:376-387) reserves the 5-byte record header (4-byte big-endian length plus 1 compression-version byte) BEFORE the wrapper starts, and `close` (:389-396) only backfills that length, so nothing is interleaved into the compressed body. The read side mirrors it: `getChunkDataInputStream` (RegionFile.java:112-153) consumes those 5 bytes, then `createChunkInputStream` (:167-185) hands the remainder to `version.wrap`, and `RegionFileStorage.read` (:51-57) parses it with `NbtIo.read`. Three nuances worth stating in §E rather than assuming: (a) the decompressed bytes are `NbtIo.writeUnnamedTag`'s output (NbtIo.java:160-166) = root tag id byte, a `writeUTF("")` empty-name pair of zero bytes, then the compound payload — i.e. the ordinary root-compound NBT document, not a bare payload; (b) an oversized chunk's whole compressed stream lives in an external `c.<x>.<z>.mcc` sidecar, flagged by bit 0x80 of the version byte (:34, :159-165, :187-195), with the same body format; (c) the reserved `VERSION_CUSTOM` id 127 (RegionFileVersion.java:40-44) would prefix a UTF-8 compression id inside the stream, but it is never selectable and reading it is a hard error (RegionFile.java:169-178) | CONFIRMED | research role (TEST-D57 pass, claude-opus-5) | 2026-09-05 |
