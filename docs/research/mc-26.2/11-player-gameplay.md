# Player & Gameplay Services — Vanilla 26.2 Research

## 1. Purpose

This domain covers everything that turns a raw network connection into a living player in the world: the login → configuration → play handshake and respawn machinery (`PlayerList`), the play-phase packet handler that validates and applies every client action including movement/anti-cheat checks (`ServerGamePacketListenerImpl`), the block-breaking state machine and game-mode rule differences (`ServerPlayerGameMode`), and the cluster of secondary player-facing services that ride alongside it: inventory synchronization, the advancements engine, statistics, scoreboard, boss bars, the fully signed chat pipeline, the new 26.2 data-driven permission system, sleep/day-skip, experience, food/exhaustion, the damage/combat-rules pipeline, death/keepInventory, and the newer dialog and waypoint (locator bar) subsystems. Nearly every other server subsystem (world, entities, items, commands) ultimately funnels player-visible state changes through this layer, so it is the widest-surface-area domain in the codebase.

## 3. How it works

### 3.1 Login flow (`PlayerList.placeNewPlayer`)

Called once the play-phase `ServerPlayer` object exists (after the configuration phase has already negotiated registries/resource packs/known packs — that handshake lives in the networking domain, not here). Sequence, in call order:

1. Look up the player's previous cached name (`UserNameToIdResolver`) to detect a rename, then register the new `ServerGamePacketListenerImpl` and switch the connection's inbound protocol to `GameProtocols.SERVERBOUND_TEMPLATE`.
2. Flushing is suspended (`playerConnection.suspendFlushing()`) so the whole burst of login packets below is coalesced into one TCP write.
3. Send, in order: `ClientboundLoginPacket` (entity id, hardcore flag, dimension keys, max players, view/simulation distance, reduced-debug-info, `doImmediateRespawn` inverted, limited-crafting, `CommonPlayerSpawnInfo`, auth/secure-profile flags) → `ClientboundChangeDifficultyPacket` → `ClientboundPlayerAbilitiesPacket` → `ClientboundSetHeldSlotPacket` → `ClientboundUpdateRecipesPacket`.
4. `sendPlayerPermissionLevel` (see §3.7) then stat/recipe-book/scoreboard sync (`markAllDirty`, `sendInitialRecipeBook`, `updateEntireScoreboard`).
5. Broadcast the "X joined the game" system message (renamed variant if the cached name differs case-insensitively).
6. `playerConnection.teleport(...)` — this is what actually arms the anti-cheat teleport-ack machinery for the player's very first position (see §3.3).
7. Send `ClientboundServerDataPacket` (MOTD/favicon) unless this is a session-transfer.
8. Broadcast `ClientboundPlayerInfoUpdatePacket` (tab-list add) both ways: existing players → new player, and new player → everyone.
9. `sendLevelInfo` (world border, clock sync, default spawn, weather, `LEVEL_CHUNKS_LOAD_START` game event) then `level.addNewPlayer` (chunk-tracking machinery, out of this domain's scope).
10. Boss-bar reattach (`CustomBossEvents.onPlayerConnect`), active potion-effect resend, `player.initInventoryMenu()`, notification hook, then flushing is resumed.

`updateEntireScoreboard` sends every `PlayerTeam` add/modify packet and then, per `DisplaySlot`, the "start tracking" packets for whichever `Objective` occupies that slot (deduplicated so an objective shown in multiple slots is only initialized once).

### 3.2 Respawn logic (`PlayerList.respawn`)

Respawn **replaces the `ServerPlayer` object** rather than mutating the live one — this is a hard architectural fact, not an implementation detail, and every place that references "the player" (connection, containers, advancements map keyed by UUID, etc.) must repoint itself.

1. `serverPlayer.findRespawnPositionAndUseSpawnBlock(!keepAllPlayerData, DO_NOTHING)` resolves a `TeleportTransition` (target level + position + yaw/pitch) by delegating to the static helper `findRespawnAndUseSpawnBlock`:
   - **Respawn anchor**: valid if it's a `RespawnAnchorBlock`, and either the respawn is `forced` (bed/anchor explosion, `/spawnpoint` etc.) or the anchor still has charge > 0, and `RespawnAnchorBlock.canSetSpawn` holds. `RespawnAnchorBlock.findStandUpPosition` locates a free spot; if not forced and `consumeSpawnBlock`, the charge is decremented by 1 in the same call.
   - **Bed**: valid if the block is a `BedBlock` and the world's `EnvironmentAttributes.BED_RULE` for that position allows setting spawn (dimension-dependent — Nether/End normally explode beds instead). `BedBlock.findStandUpPosition` finds the stand-up spot.
   - **Forced fallback** (used by `/spawnpoint`-style forced respawns with no valid block): checks both the target block and the block above are `isPossibleToRespawnInThis`; if so respawns at the block center with the stored yaw/pitch.
   - Otherwise: `missingRespawnBlock()` transition — the "no respawn block available" game event fires, and the player falls back to the world's default spawn.
2. Remove the old `ServerPlayer` from the player list and the old level; construct a brand-new `ServerPlayer` in the target level with the same `GameProfile`/`ClientInformation`.
3. `player.connection = serverPlayer.connection` (same TCP connection object is reused), then `restoreFrom(serverPlayer, keepAllPlayerData)` copies over the mutable state (see below), `setId` reuses the same entity id, `setMainArm`, respawn-position copy (unless missing), tag copy.
4. Snap to the transition position/rotation; send `ClientboundRespawnPacket`, teleport-ack, default-spawn packet, difficulty, XP packet; resend active effects and level info; `sendPlayerPermissionLevel`; `level.addRespawnedPlayer`; re-add to the player list map; `initInventoryMenu()`; `setHealth(getHealth())` (forces a health-packet resend); if a respawn anchor was depleted, play its deplete sound to the new connection.

`restoreFrom(oldPlayer, restoreAll)` — `restoreAll` is `true` only for the "keep all data" path (dimension-change end-portal / `/execute … run …` teleports never call `respawn`; it's specifically `keepAllPlayerData=true` when re-entering from the End via `PERFORM_RESPAWN` after `wonGame`):
- Always copied regardless of `restoreAll`: warden-spawn tracker, chat session, game mode + previous game mode (`ServerPlayerGameMode.setGameModeForPlayer`), base attribute values, enchantment seed, ender chest inventory, `DATA_PLAYER_MODE_CUSTOMISATION` (skin layer bits), recipe-book unlock state, `seenCredits`, nether-portal-entry position, explosion-impact bookkeeping, chunk-tracking view, debug subscriptions, shoulder entities, last-death location, waypoint icon.
- If `restoreAll`: permanent attribute modifiers, current health, active `MobEffectInstance`s, inventory+XP+scoreboard-score transfer (`transferInventoryXpAndScore`), portal-crossing process state.
- Else (death respawn): health reset to max; inventory/XP/score are transferred **only if** `GameRules.KEEP_INVENTORY` is set or the old player was already a spectator — otherwise the new player starts with an empty inventory and zero XP (the drop of the old inventory already happened in `Player.dropEquipment`/`die`, see §3.16).

### 3.3 Play-phase packet handling & anti-cheat checks (`ServerGamePacketListenerImpl`)

**Per-tick housekeeping** (`tick()` → `tickPlayer()`, called once per player per server tick from the connection's own `tick()`): snapshot `firstGood{X,Y,Z}`/`lastGood{X,Y,Z}` to the player's current position, run `player.doTick()`, snap the entity back to `firstGood*` (server-authoritative baseline before any client movement packets for this tick are applied), advance `knownMovePacketCount = receivedMovePacketCount` (rate-limit bookkeeping), and run the **floating (flying) check**: if `clientIsFloating` was armed by the last processed move packet and the player is not sleeping/passenger/dead, increment `aboveGroundTickCount`; once it exceeds `getMaximumFlyingTicks(player)` the player is kicked with `multiplayer.disconnect.flying`. The same check runs a second time for a ridden vehicle when the player is its controlling passenger. `getMaximumFlyingTicks` is gravity-scaled: `ceil(80 * max(0.08/gravity, 1))`, so zero/near-zero-gravity entities (elytra-adjacent, boats on... no, actually anything with `gravity < 1e-5`) never trigger the kick.

**Movement validation** (`handleMovePlayer`, driven by `ServerboundMovePlayerPacket`) — this is the anti-cheat core:
1. Reject NaN/non-finite coordinates outright (disconnect, `invalid_player_movement`).
2. Skip entirely while `wonGame` (waiting for the end-credits respawn) or before the client has finished loading (`hasClientLoaded()`).
3. If a teleport ack is outstanding (`updateAwaitingTeleport()`), only rotation is applied from this packet; a stale ack (waited > 20 ticks with no `ServerboundAcceptTeleportationPacket`) causes the server to **resend** the teleport.
4. Coordinates are clamped: horizontal to ±3.0e7, vertical to ±2.0e7 (`clampHorizontal`/`clampVertical`).
5. **Speed check** (only when not a passenger, not sleeping, and `shouldCheckPlayerMovement` is true — which itself is false for the singleplayer owner, for a player mid dimension-change, or when `GameRules.PLAYER_MOVEMENT_CHECK`/`ELYTRA_MOVEMENT_CHECK` disable it): the squared distance moved since the tick's first-good position is compared against `expectedDist` (the server's own predicted `getDeltaMovement().lengthSqr()`); if `movedDist − expectedDist > metersPerTick * deltaPackets` the player is snapped back and the packet is dropped. `metersPerTick` is **100.0F** normally, **300.0F** while fall-flying (elytra gets 3× budget). `deltaPackets` is the number of move packets received since the last tick (clamped to 1 if it looks like packet-count spam — a debug-log warning fires but the clamp itself is not itself a kick).
6. The move is then actually applied via `Entity.move(MoverType.PLAYER, delta)` (full collision resolution happens here, in the entity/physics domain). After moving, the server re-derives the *actual* delta and compares it against the client's requested delta: if the discrepancy exceeds `0.0625` (a re-derived squared distance) **and** the player is not mid-dimension-change/sleeping/creative/spectator/in a post-impulse grace period, it's logged as "moved wrongly" — but this alone doesn't reject the move; rejection only happens if that mismatch coincides with the move colliding with something new (`noCollision` failing or `isEntityCollidingWithAnythingNew`), in which case the player is teleported back to their tick-start position.
7. On acceptance: `clientIsFloating` is (re-)armed for next tick's check when the vertical delta is ≥ −0.03125, the player wasn't already resting on something, isn't spectator, server doesn't globally `allowFlight()`, doesn't have the fly ability, isn't levitating, isn't fall-flying, isn't auto-spin-attacking, and has no blocks in a thin box below/around it (`noBlocksAround`, an inflate(0.0625)/expandTowards(0,−0.55,0) air-check). `setOnGroundWithMovement`, `doCheckFallDamage`, movement statistics (§3.15), and impulse-context reset (on landing/liquid/climbable/spectator/elytra/spin-attack) all fire from the accepted branch.

`handleMoveVehicle` mirrors the same shape for a controlled vehicle (boat/minecart/horse/etc.): a coarser 100.0-unit budget check against the vehicle's own `getDeltaMovement()`, then move+re-derive+collision-reject, plus its own floating-vehicle tracker.

**Rate limiting**: `TickThrottler` instances gate drops (20 window / 1480 threshold, hard-coded), chat, and commands (window 20, threshold `20 * server.getChatSpamThresholdSeconds()` / `20 * server.getCommandSpamThresholdSeconds()`, both server-config-driven). Exceeding chat/command thresholds disconnects with `disconnect.spam` unless the sender is op or the singleplayer owner.

**Interaction packets** (all gated on `hasClientLoaded()`):
- `handleUseItemOn` — verifies `isWithinBlockInteractionRange` (reach = `Attributes.BLOCK_INTERACTION_RANGE`, default **4.5**, + a fixed **1.0** verification buffer), verifies the click point lies within `1.0000001` of the target block's face (anti "long reach through walls" check), then spawn-protection and `level.mayInteract` checks, then delegates to `ServerPlayerGameMode.useItemOn`. Two `ClientboundBlockUpdatePacket`s (the target block and the block on the far side of the clicked face) are **always** resent afterward regardless of outcome — this is what makes client-side block-placement prediction self-correcting even when the server silently no-ops.
- `handleUseItem` — reach-independent (right-click-in-air use, e.g. eating/bow-draw); reapplies client-reported look rotation first, then `ServerPlayerGameMode.useItem`.
- `handleAttack` — verifies `isWithinAttackRange` (entity bounding box vs. `Attributes.ENTITY_INTERACTION_RANGE`, default **3.0**, + **3.0** buffer), and **hard-disconnects** (`invalid_entity_attacked`) a client that tries to attack an item entity, XP orb, itself, or a non-attackable arrow — this is a deliberate anti-cheat trip-wire, not a soft reject.
- `handleInteract` — same reach check via `isWithinEntityInteractionRange`, dispatches to `Player.interactOn`.
- `handlePlayerAction` — `STAB` (piercing-weapon secondary attack), `SWAP_ITEM_WITH_OFFHAND`, `DROP_ITEM`/`DROP_ALL_ITEMS`, `RELEASE_USE_ITEM`, and the three block-destroy actions (delegated straight to `ServerPlayerGameMode.handleBlockBreakAction`, see §3.4).

**Signed chat handling** (`handleChat`/`handleChatCommand`/`handleSignedChatCommand`) unpacks `LastSeenMessages.Update` under a lock (`unpackAndApplyLastSeen`, disconnects with a validation-failure message on tamper), decodes/verifies the message signature chain (§3.13), runs it through the async `TextFilter` and `ChatDecorator`, then broadcasts. Illegal characters (`StringUtil.isAllowedChatCharacter` failing anywhere in the string) hard-disconnect with `illegal_characters`.

### 3.4 Block-breaking state machine (`ServerPlayerGameMode`)

Per-player fields: `isDestroyingBlock`, `destroyPos`, `destroyProgressStart` (tick count at start), `hasDelayedDestroy`/`delayedDestroyPos`/`delayedTickStart` (a *second*, queued destroy slot used when the client stops mining before the server considers the block broken — see below), `gameTicks` (monotonic per-instance tick counter), `lastSentState` (last broadcast destroy-progress stage, 0–9, or −1).

`tick()` runs once per player tick, **after** any `START_DESTROY_BLOCK`/`STOP_DESTROY_BLOCK` packets for that tick have already been processed:
- If a delayed destroy is pending: recompute progress; if the block state has since become air, cancel; if progress reaches 1.0, finalize the destroy now.
- Else if actively destroying: recompute and rebroadcast progress (`level.destroyBlockProgress`, an entity-keyed crack-overlay packet), or cancel if the block turned to air out from under the player.

`incrementDestroyProgress(state, pos, startTick)`: `progress = state.getDestroyProgress(player, level, pos) * (gameTicks - startTick + 1)`; the broadcast "stage" is `floor(progress * 10)` (0–9 visual crack stages), only rebroadcast when it changes from `lastSentState`.

`handleBlockBreakAction(pos, action, direction, maxY, sequence)`:
- Every branch first re-verifies `isWithinBlockInteractionRange(pos, 1.0)` (buffer 1.0) and `pos.getY() <= maxY`; failures resend the true block state to correct client-side prediction and are logged via `debugLogging` when `SharedConstants.DEBUG_BLOCK_BREAK` is enabled (a build flag, off in release).
- **START_DESTROY_BLOCK**: spawn-protection check → `level.mayInteract` check → **creative fast path**: if `abilities.instabuild`, destroy immediately (`destroyAndAck`) and return, skipping every other check (no tool-effectiveness gate in creative). Otherwise `blockActionRestricted` (adventure-mode block-tag gating) is checked; then `EnchantmentHelper.onHitBlock` fires (mining-fatigue-adjacent enchant hooks e.g. Efficiency triggers here indirectly through attribute modifiers) and `blockState.attack(...)` runs (per-block on-hit hook, e.g. note blocks). Progress is computed once; if it's already ≥ 1.0 (bare-handed insta-mine blocks, or creative-equivalent effective tools on 0-hardness blocks) the block is destroyed immediately ("insta mine" path). Otherwise the block enters the active-destroying state (any previously in-progress different block is silently aborted client-visually by resending its true state).
- **STOP_DESTROY_BLOCK**: only meaningful if `pos == destroyPos`. Recomputes `destroyProgress` scaled by ticks spent; **≥ 0.7** finalizes destruction immediately (a deliberate small grace margin below 1.0, not a bug); otherwise, if no delayed-destroy is already queued, the *in-progress* state is converted into a **delayed destroy** (`hasDelayedDestroy=true`) that keeps accumulating progress every tick from the original `destroyProgressStart` even though the client has stopped sending destroy packets — this lets a block finish breaking from residual accumulated progress if the player briefly releases and re-presses within the same block/tick window, matching vanilla's forgiving mining feel.
- **ABORT_DESTROY_BLOCK**: unconditionally clears `isDestroyingBlock`; if the aborted `pos` doesn't match the tracked `destroyPos` a mismatch warning is logged and *both* positions get their crack overlay cleared (defensive double-clear).

`destroyBlock(pos)` (the actual break, called from `destroyAndAck` or the tick-driven finalizers): re-verifies `mainHandItem.canDestroyBlock` (mostly Adventure-mode `CAN_DESTROY` tag check for the low-instabuild creative case), rejects `GameMasterBlock`s (command blocks, structure blocks, etc.) unless `player.canUseGameMasterBlocks()`, re-checks `blockActionRestricted`, then `block.playerWillDestroy` (drop-adjacent pre-hook) → `level.removeBlock` → `block.destroy` (post-hook, e.g. neighbor updates) → unless `player.preventsBlockDrops()` (creative or specific game-rule states), computes `hasCorrectToolForDrops` **before** calling `itemStack.mineBlock` (which applies tool durability/Efficiency-adjacent side effects) so the drop-eligibility snapshot is taken against the un-damaged tool, then `block.playerDestroy` actually spawns the loot-table drops using the pre-copied `destroyedWith` item stack.

### 3.5 Game-mode differences (`GameType`)

`GameType.updatePlayerAbilities` is the single source of truth for what changes between modes — see the Constants table (§5) for the exact `Abilities` field matrix. Key behavioral branch points elsewhere:
- `ServerPlayerGameMode.changeGameModeForPlayer` additionally **cancels flight** if the player was flying, is leaving Spectator, and `isInRangeOfGround()` (no colliders around the bounding box and < 1 block of open space below) — prevents fall-through-floor when switching out of Spectator mid-air over solid ground.
- Creative `useItem`/`destroyBlock` paths bypass cooldown-adjacent and drop bookkeeping as noted in §3.4.
- `isSurvival()` returns true for **both** Survival and Adventure (Adventure is "restricted survival": `isBlockPlacingRestricted()` is true for Adventure and Spectator, gating `mayBuild`).
- Spectator: `useItemOn` opens a block's menu (if any) without any item interaction at all, otherwise passes through untouched; movement checks are relaxed (no speed-hack kick applies while spectator per the collision-reject exemption in §3.3); `isReceivingWaypoints`/interaction range checks still apply but attack packets are outright ignored (`handleAttack` early-returns on `isSpectator()`).

### 3.6 Inventory synchronization

The server never diffs inventories client-side; every container (`AbstractContainerMenu`, including the player's own 46-slot `InventoryMenu`) owns an incrementing `stateId`, and each mutating packet the server sends bumps it. `ServerPlayer.containerSynchronizer` (an anonymous `ContainerSynchronizer`) is the sole channel: `sendInitialData` → `ClientboundContainerSetContentPacket` (full slot dump + carried item, `incrementStateId()`), `sendSlotChange` → `ClientboundContainerSetSlotPacket`, `sendCarriedChange` → `ClientboundSetCursorItemPacket`, `sendDataChange`/property arrays → `ClientboundContainerSetDataPacket`.

To avoid resending full `ItemStack` NBT on every tick for unchanged slots, `RemoteSlot.Synchronized` (created via `createSlot()`) hashes each slot's data components through a `LoadingCache<TypedDataComponent<?>, Integer>` keyed by CRC32C over the component's registry-aware encoding — i.e. the server keeps a **content hash**, not the stack itself, per remote slot, and only emits a packet when the hash changes. This is the `net.minecraft.world.inventory.HashedStack` concept referenced by the client's own hashed-slot acking.

Client → server flow (`handleContainerClick`): validates `containerId` still matches the open menu, rejects invalid slot indices, then `stateId` mismatch triggers a **full resync** (`broadcastFullState()`) instead of the normal incremental `broadcastChanges()` — this is the self-healing path for any client/server desync. Updates are wrapped in `suppressRemoteUpdates()`/`resumeRemoteUpdates()` so the click's own server-side echo doesn't get sent back to the clicking player redundantly; `changedSlots`/`carriedItem` from the packet are applied via `setRemoteSlotUnsafe`/`setRemoteCarried` to keep the server's *belief about what the client currently displays* accurate for future diffing.

A separate `containerListener` fires `CriteriaTriggers.INVENTORY_CHANGED` whenever a slot backed by the player's own `Inventory` (not a `ResultSlot`, i.e. not a crafting-output preview slot) changes.

### 3.7 Permissions & op levels (`net.minecraft.server.permissions`, new in 26.2)

26.2 replaces the historic raw `int` op-level (0–4) with a small data-driven permission engine. It is **not** exposed to datapacks as content (no `data/minecraft/permission/*.json` in the data-generator output), but it *is* built as codec-dispatch registries (`BuiltInRegistries.PERMISSION_TYPE`, `PERMISSION_CHECK_TYPE`) so third-party code (Rusty Clanker's mod API, in our case) can register new `Permission`/`PermissionCheck` kinds beyond vanilla's two each.

- **`PermissionLevel`** enum: `ALL(0)`, `MODERATORS(1)`, `GAMEMASTERS(2)`, `ADMINS(3)`, `OWNERS(4)` — numerically and semantically identical to the historic op levels, `isEqualOrHigherThan` does the ordinal comparison.
- **`Permission`** is a sealed-style interface with two shipped variants: `Permission.Atom(Identifier id)` (an arbitrary named capability, e.g. `minecraft:commands/entity_selectors`, `minecraft:chat/send_messages`) and `Permission.HasCommandLevel(PermissionLevel level)` (the level-gate wrapper commands use).
- **`Permissions`** is the constant table: `COMMANDS_MODERATOR/GAMEMASTER/ADMIN/OWNER` (each a `HasCommandLevel`), `COMMANDS_ENTITY_SELECTORS` (atom — `@e`/`@a` etc. in commands), and four `CHAT_*` atoms (`send_messages`, `send_commands`, `receive_player_messages`, `receive_system_messages`) grouped as `CHAT_PERMISSIONS`.
- **`PermissionSet`** is the *evaluator* a subject carries: `hasPermission(Permission)`. `NO_PERMISSIONS`/`ALL_PERMISSIONS` are trivial constants; `union(other)` composes two sets (OR semantics) via `PermissionSetUnion`, which flattens nested unions and de-duplicates.
- **`LevelBasedPermissionSet`** is the concrete set every real player/op-entry actually uses: it answers `HasCommandLevel` checks by level comparison, and answers `COMMANDS_ENTITY_SELECTORS` specifically as "true iff level ≥ GAMEMASTERS" (all *other* atoms are unconditionally false for a pure level-based set — atoms beyond entity-selectors have no vanilla level-based grant path, they're plumbing for a future finer-grained permission provider). `ALL`/`MODERATOR`/`GAMEMASTER`/`ADMIN`/`OWNER` singletons exist per level; `union` between two level-based sets just keeps the higher one (cheap fast path instead of building an actual `PermissionSetUnion`).
- **`PermissionCheck`** is what a command's `.requires(...)` predicate is built from: `AlwaysPass` (singleton) and `Require(Permission)` (delegates to `set.hasPermission(permission)`). `Commands.hasPermission(PermissionCheck)` wraps it in a `PermissionProviderCheck<T extends PermissionSetSupplier>` — any `T` (command source, whatever) that exposes `permissions()` can be checked.
- `Commands.LEVEL_ALL/MODERATORS/GAMEMASTERS/ADMINS/OWNERS` are the ready-made `PermissionCheck` constants (`LEVEL_ALL = AlwaysPass.INSTANCE`, the rest are `Require(Permissions.COMMANDS_*)`) — these are what every vanilla command's `.requires(Commands.hasPermission(Commands.LEVEL_GAMEMASTERS))` (etc.) actually references. This is a drop-in rename of the old `Commands.hasPermission(2)`-style call, not a behavioral change for vanilla commands.

**Resolution chain**: `ServerPlayer.permissions()` → `MinecraftServer.getProfilePermissions(nameAndId)` → if the player is an op, look up their `ServerOpListEntry` and return its stored `LevelBasedPermissionSet` (falls back to `LevelBasedPermissionSet.OWNER` for the singleplayer world owner even without an explicit ops-list entry, or `operatorUserPermissions()`/`ALL` for the dedicated-server default) → else `LevelBasedPermissionSet.ALL`. `CommandSourceStack.permissions()` instead carries its **own** `PermissionSet` field (set at construction from the invoking entity, or overridden via `withPermission`/`withMaximumPermission` for `/execute as` and function-call contexts) so command execution can run with an elevated or reduced permission set independent of the invoking player's live permission.

`ServerOpListEntry` still persists as `level: <0-4 int>` + `bypassesPlayerLimit: <bool>` in `ops.json` — the on-disk format is unchanged from prior versions; only the in-memory representation moved from a bare int to `LevelBasedPermissionSet.forLevel(...)`. `PlayerList.sendPlayerPermissionLevel` maps the five levels onto entity-status event ids **24–28** (`ClientboundEntityEventPacket`) — this is the packet-level signal the client uses to unlock creative-mode command-block editing, F3+... debug affordances, etc., unchanged from the pre-26.2 numeric scheme — and unconditionally calls `Commands.sendCommands(player)` to regenerate the client's command tree for the new permission set.

### 3.8 Advancements engine

**Static structure** (`AdvancementTree`, world-shared, rebuilt on datapack reload): `addAll` inserts `AdvancementHolder`s in dependency order (an advancement is only insertable once its declared `parent()` is already present; the loop retries until nothing more can be inserted, logging remaining orphans as a failure). Each `AdvancementNode` caches its resolved parent/children and its root. `roots`/`tasks` are separate ordered sets (root = no parent, i.e. a tab; task = everything else) — this split is what backs the client's tab-vs-tree rendering split.

**Per-player state** (`PlayerAdvancements`, one per online player, loaded from `world/advancements/<uuid>.json` via a `DataFixer`-wrapped codec, current version constant **1343**): `progress: Map<AdvancementHolder, AdvancementProgress>`, `visible: Set<AdvancementHolder>` (what's been sent to the client so far — advancement *visibility* is itself incrementally streamed, not just progress), `activeTriggers: Map<CriterionTrigger<?>, Map<TriggerInstanceKey, Instance>>` — an index from trigger type → the specific criterion instances currently "armed" (i.e. belonging to an advancement not yet completed, for a criterion not yet done), keyed by `(AdvancementHolder, criterionName)`.

**Award flow** (`SimpleCriterionTrigger.trigger(player, matcher)` → `PlayerAdvancements.award`): a game event (e.g. `KilledTrigger` on a kill) looks up **only** the currently-armed instances for its own trigger type from `activeTriggers` (never scans all advancements — this is the perf-critical index), runs the type-specific `matcher` predicate against each instance, then re-checks the instance's optional `player()` `ContextAwarePredicate` against an `EntityPredicate` context built from the player. Every match calls `advancements.award(holder, criterionName)`, which: grants progress on that one named criterion (`AdvancementProgress.grantProgress`), and if the advancement's overall `AdvancementRequirements` now evaluate true where they weren't before, **unregisters** its listeners (no more trigger checks needed), grants `AdvancementRewards` (XP/items/loot table/recipes/function), and — gated by `GameRules.SHOW_ADVANCEMENT_MESSAGES` and the advancement's own `display.shouldAnnounceChat()` — broadcasts the "X has made the advancement Y" system message.
`AdvancementRequirements` is a `List<List<String>>` of criterion names: outer list = AND, inner list = OR, i.e. `[[a,b],[c]]` means `(a OR b) AND c`. `AdvancementProgress.isDone()` just calls `requirements.test(criterionDone::apply)`.

**Automatic advancements**: on load, any advancement with **zero** declared criteria is force-awarded immediately (`checkForAutomaticTriggers`) — this is the mechanism vanilla uses for advancements that are purely organizational parents with no completion condition of their own.

**Visibility propagation**: whenever a criterion changes, `markForVisibilityUpdate` schedules the **root** of that advancement's tree for a visibility recompute (`AdvancementVisibilityEvaluator`, elsewhere) on the next `flushDirty` call — visibility can depend on sibling/parent completion state (hidden advancements only reveal once a prerequisite is done), hence whole-root recompute rather than a single-node check.

**Network sync** (`flushDirty`, called once per player per tick from the server tick loop — not shown in this file but invoked externally): batches all `rootsToUpdate` visibility recomputes and all `progressChanged` advancements (filtered to only those currently `visible`) into a single `ClientboundUpdateAdvancementsPacket` (added/removed identifiers + progress map), only sent if there's actually something to say. The very first flush for a session always sends (`isFirstPacket`), even if empty of changes, to establish baseline state client-side.

### 3.9 Statistics

`Stats` defines four **registry-backed** `StatType`s (`BLOCK_MINED`, `ITEM_CRAFTED`, `ITEM_USED`, `ITEM_BROKEN`, `ITEM_PICKED_UP`, `ITEM_DROPPED`, `ENTITY_KILLED`, `ENTITY_KILLED_BY` are all keyed by the corresponding vanilla registry) plus one **custom** type (`CUSTOM`, keyed by the freestanding `CUSTOM_STAT` registry of ~65 `Identifier`s — see Constants for the full lifetime-counter list: play time, distance-by-mode, damage dealt/taken/blocked/absorbed, deaths, kills, interactions with ~20 different block/UI kinds, etc.).

`ServerStatsCounter` persists to `world/stats/<uuid>.json` as a single dispatched-map codec (`{"stats": {"minecraft:mined": {"minecraft:stone": 12, ...}, "minecraft:custom": {...}}, "DataVersion": ...}`). A `dirty: Set<Stat<?>>` tracks unsent increments; `sendStats` (triggered by the client's `REQUEST_STATS` client-command, i.e. opening the in-game stats screen) drains `dirty` into a single `ClientboundAwardStatsPacket`. `markAllDirty()` (called once at login) is what makes the very first stats-screen open show everything even though nothing changed "this session".

Every `awardStat` call also feeds the scoreboard: `ServerPlayer.awardStat` calls `scoreboard.forAllObjectives(stat, this, count -> score.add(count))`, so any objective whose criteria is a stat-backed `ObjectiveCriteria` (see §3.10) tracks automatically with zero extra plumbing — stats and scoreboard share one increment path.

### 3.10 Scoreboard

`ObjectiveCriteria` has a small set of hard-coded **non-stat** criteria (`dummy`, `trigger`, `deathCount`, `playerKillCount`, `totalKillCount`, plus `health`/`food`/`air`/`armor`/`xp`/`level` which are `readOnly=true` and carry a fixed `RenderType`: `HEARTS` for health, `INTEGER` for the rest) and a per-`TeamColor` family (`teamkill.<color>`, `killedByTeam.<color>`) used by `ServerPlayer.handleTeamKill`. Any other name is resolved dynamically as `<stat-type-namespace>.<key>:<stat-namespace>.<stat-key>` against the stat-type registry (`ObjectiveCriteria.byName`), which is how `/scoreboard objectives add ... minecraft.mined:minecraft.stone` works without a bespoke criteria class per stat.

`Objective` carries `displayName`, `renderType` (`INTEGER`/`HEARTS`), `displayAutoUpdate`, and an optional `NumberFormat` override (`BlankFormat`/`FixedFormat`/`StyledFormat` — controls how the number renders in sidebar/list/below-name, independent of the raw value). `DisplaySlot` is a 19-value enum: `LIST`, `SIDEBAR`, `BELOW_NAME`, plus one `TEAM_<COLOR>` slot per of the 16 team colors (sidebar-filtered-by-viewing-player's-team-color) — ids 0–18, `ByIdMap.OutOfBoundsStrategy.ZERO`.

`Team`/`PlayerTeam` carry: `CollisionRule` (`ALWAYS`/`NEVER`/`PUSH_OTHER_TEAMS`/`PUSH_OWN_TEAM`, ids 0–3), name-tag `Visibility` and death-message `Visibility` (both the same 4-value enum: `ALWAYS`/`NEVER`/`HIDE_FOR_OTHER_TEAMS`/`HIDE_FOR_OWN_TEAM`, ids 0–3), `canSeeFriendlyInvisibles`, `allowFriendlyFire`, an optional `TeamColor`. `ServerPlayer.die` reads `team.getDeathMessageVisibility()` directly to decide whether the death message broadcasts to everyone, only the dying player's own team, or everyone except that team.

### 3.11 Boss bar

`BossEvent` is the abstract shared model (`name`, `progress` 0.0–1.0, `BossBarColor` — 7 values, `BossBarOverlay` — `PROGRESS`/`NOTCHED_6`/`NOTCHED_10`/`NOTCHED_12`/`NOTCHED_20`, `darkenScreen`/`playBossMusic`/`createWorldFog` flags). `ServerBossEvent` adds a `players: Set<ServerPlayer>` and a `visible` flag; every mutator (`setProgress`/`setColor`/`setOverlay`/`setDarkenScreen`/`setPlayBossMusic`/`setCreateWorldFog`/`setName`) is a **no-op unless the value actually changed**, and on change calls the matching `ClientboundBossEventPacket` factory (`createUpdateProgressPacket`/`createUpdateStylePacket`/`createUpdatePropertiesPacket`/`createUpdateNamePacket`) broadcast to exactly the tracked player set — this is a plain per-instance dirty-check pattern, no batching. `addPlayer`/`removePlayer` send the full add/remove packet immediately (not deferred to next tick).

`CustomBossEvent` (backing `/bossbar`) layers a `value`/`max` (default max **100**) integer pair on top (used for `/bossbar set <id> value`), a persistent `Identifier customId`, and its own `players: Set<UUID>` (separate from the transient `ServerBossEvent.players`, since custom bars must survive server restarts and reference players who may currently be offline) plus a `dirtyCallback` that flags the whole `CustomBossEvents` registry for a resave.

### 3.12 Sleep & day skip

`SleepStatus` (one instance per `ServerLevel`) tracks `activePlayers` (non-spectator players in the level) and `sleepingPlayers`, recomputed every time `updateSleepingPlayerList()` fires (on any player sleep-state change or player-list change in that level). `sleepersNeeded(percentage) = max(1, ceil(activePlayers * percentage / 100))` — `percentage` is the `GameRules.PLAYERS_SLEEPING_PERCENTAGE` gamerule (default **100**, i.e. vanilla's classic "everyone must sleep"). Each level's tick checks `sleepStatus.areEnoughSleeping(percentage) && sleepStatus.areEnoughDeepSleeping(percentage, players)` — the **deep-sleep** condition additionally requires that many players have `Player.isSleepingLongEnough()`, i.e. `sleepCounter >= 100` (100 ticks = 5 seconds actually asleep, not just "in bed this instant" — this debounce prevents a single-tick flicker of "everyone sleeping" from prematurely skipping night). On success: `wakeUpAllPlayers()`, optionally jump the world clock to the dimension's `WAKE_UP_FROM_SLEEP` marker (gated by `GameRules.ADVANCE_TIME` and the dimension having a `defaultClock`), and optionally clear weather (gated by `GameRules.ADVANCE_WEATHER`).

`Player.sleepCounter`: increments each tick while sleeping, caps at 100 while still sleeping; after waking (`forcefulWakeUp=false` sets it to exactly 100, i.e. instantly "done"; a forced/kicked wake sets it to 0) it continues counting *up* to 110 as a short cross-fade/grace window before resetting to 0. `canSleepThroughNights()` is just `PLAYERS_SLEEPING_PERCENTAGE <= 100` (a percentage set above 100 disables the whole night-skip feature, which is also how "sleep is required but insufficient population" scenarios read on multiplayer — see `announceSleepStatus`, which sends the "X/Y players sleeping" or "skipping night" overlay to everyone whenever the tally changes, except on an unpublished singleplayer world).

### 3.13 Signed chat, in full

**Chain identity**: `SignedMessageLink` (elsewhere) is `(sender UUID, session UUID, index)`; `SignedMessageChain` tracks the next expected link per sender and rejects out-of-order timestamps (`OUT_OF_ORDER_CHAT`) or a broken chain (missing/invalid signature → `nextLink = null`, permanently wedging that sender's chain until a fresh chat-session handshake). `Encoder`/`Decoder` are the two halves — the server only ever **decodes** (verifies) player-originated chat; it never signs outgoing chat itself (system messages are simply unsigned `PlayerChatMessage`s with `sender = NIL_UUID`).

**Message body & signature**: `SignedMessageBody(content, timeStamp, salt, lastSeen: LastSeenMessages)` is exactly what gets cryptographically signed (`updateSignature` feeds salt → epoch-seconds → UTF-8 content-length-prefixed bytes → the `lastSeen` acknowledgement set into the running signature). `MessageSignature` wraps the raw signature bytes; `MessageSignatureCache`/`SignedMessageBody.Packed` exist purely to let the network layer send **short integer references** to recently-seen signatures instead of the full 256-byte signature on every packet (a bandwidth optimization, transparent to the signing semantics). `PlayerChatMessage` is the full envelope: `link + signature + signedBody + unsignedContent (nullable, decorated/filtered display override) + filterMask`. `MESSAGE_EXPIRES_AFTER_SERVER = 5 minutes`, `MESSAGE_EXPIRES_AFTER_CLIENT = 7 minutes` (server enforces the tighter window; the 2-minute slack lets a message already in flight to the client still render as "recently sent" even if the server has started treating it as stale for trust purposes).

**Verification**: `SignedMessageChain.Decoder.unpack` requires a non-null signature and a non-expired `ProfilePublicKey`, requires the chain isn't broken, requires the timestamp isn't older than the last accepted one, constructs the `PlayerChatMessage`, and calls `verify(signatureValidator)` against the profile's public key — any failure sets the chain broken and throws a typed `DecodeException` with a specific user-facing reason (`MISSING_PROFILE_KEY`/`CHAIN_BROKEN`/`EXPIRED_PROFILE_KEY`/`INVALID_SIGNATURE`/`OUT_OF_ORDER_CHAT`), which `ServerGamePacketListenerImpl.handleMessageDecodeFailure` echoes back to the sender as a red system message (not a disconnect — a signature failure is recoverable, unlike a `LastSeenMessages` tamper which **is** a hard disconnect via `unpackAndApplyLastSeen`'s validator).

**Insecure/offline fallback**: `SignedMessageChain.Decoder.unsigned(profileId, enforcesSecureChat)` is used when the connection has no profile key at all; it throws `MISSING_PROFILE_KEY` if the server has `enforce-secure-profile` enabled, otherwise silently wraps the content as an unsigned `PlayerChatMessage` — this is the entire "no chat reporting / offline-mode chat" code path, and confirms there is **no separate "chat preview" concept anywhere in 26.2** (chat previews were removed from vanilla well before this pin; the signed-chat pipeline described here is the complete and only chat-composition path — there is no server-side preview/decoration round-trip before send).

**Chat types & decoration** (`ChatType` registry, `data/minecraft/chat_type`): 7 built-in bindings — `CHAT` (default player chat), `SAY_COMMAND` (`/say`), `MSG_COMMAND_INCOMING`/`_OUTGOING` (`/msg`, asymmetric decoration for sender vs. recipient), `TEAM_MSG_COMMAND_INCOMING`/`_OUTGOING` (`/teammsg`), `EMOTE_COMMAND` (`/me`). Each `ChatType` is a pair of `ChatTypeDecoration` (one for the rendered chat line, one for narration/accessibility) — decoration is a translation-key template plus which parameter slots (sender, target, content) get substituted in, entirely data-driven and datapack-overridable. `ChatType.Bound` is the per-message instantiation (resolved sender display name + optional target name) actually attached to a `ClientboundPlayerChatPacket`.

**Commands vs. chat**: a leading `/` routes to `handleChatCommand`/`handleSignedChatCommand` instead of `handleChat`. The **signed** command variant additionally carries per-argument signatures (`ArgumentSignatures`) for any command argument type that's independently signable (`SignableCommand.hasSignableArguments` — chat-content-bearing arguments like `/say <message>` or `/execute ... run say ...`); `collectSignedArguments` validates that the client's declared signed-argument set exactly matches what the parsed command actually expects, and mismatches are a hard chain-break + `DecodeException`, not a silent partial-trust. An **unsigned** command containing a signable argument is rejected outright (not executed) when `server.enforceSecureProfile()` is on — this is the concrete mechanism preventing an unsigned client from impersonating chat content through a command argument on a secure-chat-enforcing server.

**Muting/reporting plumbing**: the server has **no player-facing "mute" or "report" command/packet surface of its own** — `ChatVisiblity` (`FULL`/`SYSTEM`/`HIDDEN`, a client-side chat-visibility *preference* the client reports via `ServerboundClientInformationPacket`) is the closest thing, and it only gates whether the *receiving* client wants chat/system messages at all (`tryHandleChat` bounces a plain player message with an in-chat notice if the sender's own visibility is `HIDDEN`). Actual chat reporting (the Mojang "Report Player" flow) is entirely a client-to-Mojang-API concern outside this server's source tree; the server's only contribution is guaranteeing every chat message carries a verifiable signature chain (§ above) so a report submitted later can be cryptographically substantiated. Server-side profanity/abuse filtering is the pluggable `TextFilter` interface (`server.network.TextFilter`), invoked via `filterTextPacket` before broadcast and producing a `FilterMask` that can redact (`FilterMask.isFullyFiltered()`) the message for players who've opted into filtered chat — vanilla's own dedicated server ships a no-op filter; hosted platforms (Realms, etc.) supply a real implementation out of tree.

### 3.14 Dialogs (26.x server-driven UI)

A `Dialog` (registry `Registries.DIALOG`, `data/minecraft/dialog`) is a datapack-defined GUI screen the server can push to a client via `ServerPlayer.openDialog(Holder<Dialog>)` (also reachable in-game via `/dialog show`/`DialogCommand`, `LEVEL_GAMEMASTERS`-gated). Every dialog shares `CommonDialogData`: `title` + optional `externalTitle` (fallback shown outside the dialog frame, e.g. pause-menu button label), `canCloseWithEscape` (default true), `pause` (default true — pauses singleplayer time while open; **validated at load time** that a pausing dialog's `afterAction` actually unpauses on exit, or the datapack fails to load), `afterAction: DialogAction` (`CLOSE`/`NONE`/`WAIT_FOR_RESPONSE`, default `CLOSE`), a `body: List<DialogBody>` (compact-list-codec — plain text or item-display widgets), and `inputs: List<Input>` (named `InputControl`s: `BooleanInput`, `TextInput`, `NumberRangeInput`, `SingleOptionInput` — their values become named template substitutions available to the dialog's `Action`s).

Five concrete dialog kinds registered in `DialogTypes`: `notice` (single acknowledge button), `server_links` (auto-populated from the server's advertised link list), `dialog_list` (a paged grid of *other* dialogs, e.g. the vanilla `custom_options`/`quick_actions` pause-menu screens, which reference dialogs via a tag like `#minecraft:pause_screen_additions`), `multi_action` (`N` buttons in a configurable-column grid + optional exit button), `confirmation` (exactly a yes/no button pair; `onCancel()` is wired to the `no` button's action). `ActionButton` pairs a `CommonButtonData` (label/width/tooltip) with an optional `Action` (dispatched through `BuiltInRegistries.DIALOG_ACTION_TYPE`; concrete actions ultimately resolve to a `ClickEvent` — running a command template with input substitutions, opening a URL, opening another dialog, etc. — `ActionTypes`/`CommandTemplate`/`ParsedTemplate` handle `{variable}`-style substitution from the dialog's live `Input` values into command strings before dispatch, `Action.ValueGetter` is the substitution-value abstraction).

The three shipped vanilla dialog JSONs (`custom_options`, `quick_actions`, `server_links`) are all thin `dialog_list`/`server_links` wrappers around tag-driven content — vanilla itself defines almost no *leaf* dialogs; the system exists primarily as a datapack/mod extension point for pause-menu and command-driven custom UI.

### 3.15 Waypoints / locator bar

Fully server-authoritative, opt-in per receiving player via `GameRules.LOCATOR_BAR`. Any `LivingEntity` (players included) can be a **waypoint source** by having the `Attributes.WAYPOINT_TRANSMIT_RANGE` attribute > 0; any player is a **waypoint receiver** by having `Attributes.WAYPOINT_RECEIVE_RANGE` > 0 (`ServerPlayer.isReceivingWaypoints()` / `onAttributeUpdated` wires attribute changes straight into `ServerWaypointManager.addPlayer`/`removePlayer`). Broadcast range is `min(source.transmitRange, receiver.receiveRange)`; a compass-item-style `WAYPOINT_TRANSMIT_RANGE_HIDE_MODIFIER` (`ADD_MULTIPLIED_TOTAL`, value −1.0) lets an equipped item zero out a source's effective transmit range entirely (i.e. "hide me from other players' locator bars").

`ServerWaypointManager` is a full bipartite connection graph: a `Table<ServerPlayer, WaypointTransmitter, Connection>`. Every waypoint-add/waypoint-update/player-add/player-update event walks the relevant row/column and creates, updates, or tears down the per-pair `Connection` as needed (`doesSourceIgnoreReceiver` — spectator/passenger/out-of-range checks — and `isBroken()` per connection kind gate this). Three connection/precision tiers, chosen automatically by distance:
- **`EntityBlockConnection`** (close range): sends exact block position, updates only when the source moves to a new block (Manhattan distance > 0). `isBroken()` once Manhattan distance from last-sent position exceeds **1** — forces a fresh full update rather than a delta once precision drifts.
- **`EntityChunkConnection`** (mid range, and specifically while the source's chunk isn't currently within the receiver's loaded view — `isChunkVisible`): coarser chunk-granularity position, breaks once Chebyshev ("chessboard") chunk-distance from last update exceeds **1**, or once the source re-enters view distance (hands off to a closer connection tier) or starts being ignored.
- **`EntityAzimuthConnection`** (very far, beyond `WaypointTransmitter.REALLY_FAR_DISTANCE = 332` blocks): only a compass-style bearing angle is sent (no position at all), updated only once the angle drifts more than **0.008726646 radians** (~0.5°) since the last update.

Each tier's `connect()`/`disconnect()`/`update()` map directly to `ClientboundTrackedWaypointPacket` add/update/remove variants keyed by the source entity's UUID; `Waypoint.Icon` (a style-asset reference + optional RGB override) rides along and can inherit the source's team color (with a hardcoded exception: `TeamColor.BLACK` renders as `-13619152`, i.e. not literal black, presumably for on-screen contrast) via `cloneAndAssignStyle`.

### 3.16 Death, `keepInventory`, and damage/combat math

**Damage pipeline** (`LivingEntity.actuallyHurt`, the shared entity path `ServerPlayer.hurtServer` ultimately reaches after its player-specific PvP gate): item-blocking absorption is applied first (`applyItemBlocking`), then a **freezing-damage 5× multiplier** for entities tagged `FREEZE_HURTS_EXTRA_TYPES` taking a `DamageTypeTags.IS_FREEZING` hit, then a **helmet-damaging 0.75× reduction** for `DAMAGES_HELMET`-tagged sources (falling blocks/anvils) when a non-empty helmet is worn (the helmet itself also takes durability damage here). NaN/Infinite damage is clamped to `Float.MAX_VALUE` rather than propagating.

**Invulnerability frames**: `invulnerableTime` is set to **20** ticks on any damage instance that isn't itself a "bypasses cooldown" (`DamageTypeTags.BYPASSES_COOLDOWN`) hit; while `invulnerableTime > 10` a **second** hit within the same window only applies if its raw damage exceeds `lastHurt` (the previous hit's damage), and only the **delta** above `lastHurt` is actually dealt — i.e. vanilla's classic "can't be hit twice by the same/weaker attack within half a second, but a strictly bigger hit still does the difference" rule. Generic `LivingEntity.tick()` decrements `invulnerableTime` unconditionally **except** for `ServerPlayer` instances (guarded out by an explicit `!(this instanceof ServerPlayer)` check) — `ServerPlayer` instead decrements its own `invulnerableTime` inside its own `tick()`, unconditionally every tick regardless of game mode; this split exists so a subclass can special-case the decrement without touching the shared mob path.

**Armor/enchantment reduction** (`CombatRules.getDamageAfterAbsorb`): `toughness = 2.0 + armorToughness/4.0`; `realArmor = clamp(totalArmor − damage/toughness, totalArmor*0.2, 20.0)` (the `totalArmor*0.2` floor is `MIN_ARMOR_RATIO` — a very high-damage hit can still be reduced to at most 80% of nominal armor's worth of mitigation, it can never be reduced to *zero* mitigation purely by damage magnitude); `armorFraction = realArmor / 25.0` (`ARMOR_PROTECTION_DIVIDER`); if the attack carries a weapon item, `EnchantmentHelper.modifyArmorEffectiveness` (Breach-enchantment-style effects live here) adjusts the fraction, clamped to `[0,1]`; final damage `= damage * (1 − armorFraction)`. A **separate** formula, `getDamageAfterMagicAbsorb`, applies "magic armor" (Protection-family enchantment EPF, resolved elsewhere) the same way but without the toughness/weapon-effectiveness terms: `damage * (1 − clamp(totalMagicArmor,0,20)/25)`. `MAX_ARMOR = 20`, `ARMOR_PROTECTION_DIVIDER = 25`, `BASE_ARMOR_TOUGHNESS = 2.0`.

**Death** (`ServerPlayer.die`): fires `GameEvent.ENTITY_DIE`, builds the death message from `CombatTracker.getDeathMessage()` (gated by `GameRules.SHOW_DEATH_MESSAGES`; if the composed message is too long to fit a packet a `death.attack.message_too_long` fallback with the truncated text as a hover-tooltip is substituted — an exception-listener path, not a pre-check), routes the broadcast by team death-message-visibility (§3.10), fires `world.broadcastEntityEvent(this, (byte)3)` (death animation/particles), the neutral-mob "someone I'm angry at died" notification (gated by `GameRules.FORGIVE_DEAD_PLAYERS`), non-spectator loot drop (`dropAllDeathLoot`, which is `Player.die`'s override → `dropEquipment` → conditionally `inventory.dropAll()`), kill-credit stat/score bookkeeping, and resets the death/rest custom-stat timers plus fire/freeze state.

`Player.dropEquipment` drops the whole inventory **unless** `GameRules.KEEP_INVENTORY` is set, and even when dropping, first strips out any item carrying `EnchantmentEffectComponents.PREVENT_EQUIPMENT_DROP` (Curse of Vanishing) via `destroyVanishingCursedItems` rather than dropping it. `Player.getExperienceReward` (the XP orb payout on death) is `min(experienceLevel * 7, 100)` — but only when `KEEP_INVENTORY` is **off** and the dying entity isn't a spectator; with `KEEP_INVENTORY` on, death drops zero XP as well as zero items, treated as one combined "soft death" toggle rather than two independent gamerules. The actual respawn-time application of `KEEP_INVENTORY` (whether the *new* `ServerPlayer` receives the old inventory/XP) is `PlayerList.respawn` → `ServerPlayer.restoreFrom`, described in §3.2.

## 6. Cross-subsystem interfaces

**Consumes from:**
- **World/chunks** — chunk loading/tracking state gates teleport/respawn completion (`ServerLevel.addNewPlayer`/`addRespawnedPlayer`), spawn-position search reads block state and `EnvironmentAttributes.BED_RULE`.
- **Entities/ECS** — `Player extends LivingEntity extends Entity`; movement, collision, attribute system (`Attributes.BLOCK_INTERACTION_RANGE` etc., `WAYPOINT_TRANSMIT/RECEIVE_RANGE`), effects, and combat/knockback all live in the entity domain and are only orchestrated from here.
- **Items/enchantments** — tool effectiveness, `EnchantmentHelper.onHitBlock`/`modifyArmorEffectiveness`, data components (`BLOCKS_ATTACKS`, `PIERCING_WEAPON`, `PREVENT_EQUIPMENT_DROP`) drive block-break and combat outcomes.
- **World generation / registries** — advancement/dialog/chat-type/damage-type/permission-check-type are all registry-backed and depend on datapack/registry bootstrap having already run.
- **Networking/protocol** — every packet type referenced here (`Clientbound*`/`Serverbound*`) is owned by the protocol domain; this domain only consumes the generated packet classes.

**Provides to:**
- **Commands** — `CommandSourceStack.permissions()` is this domain's `PermissionSet`; nearly every command's `.requires(...)` gate is built from `Commands.LEVEL_*`.
- **World/game rules** — many gamerules (`KEEP_INVENTORY`, `PLAYERS_SLEEPING_PERCENTAGE`, `SHOW_DEATH_MESSAGES`, `SHOW_ADVANCEMENT_MESSAGES`, `LOCATOR_BAR`, `PLAYER_MOVEMENT_CHECK`, `ELYTRA_MOVEMENT_CHECK`, `NATURAL_HEALTH_REGENERATION`, `FORGIVE_DEAD_PLAYERS`) are read exclusively by logic in this domain.
- **Mods/plugins (future)** — the `PERMISSION_TYPE`/`PERMISSION_CHECK_TYPE` registries and the `CriterionTrigger`/`ObjectiveCriteria` registration points are the extension seams a modding API would hook.

## 8. Notes for Rusty Clanker

- **Movement validation must run server-authoritatively every tick, not just "on packet"**: the flying-kick check (`clientIsFloating`/`aboveGroundTickCount`) is armed by one packet's outcome and evaluated on the *next* tick's `tickPlayer()`, independent of whether any move packet arrives that tick. An ECS translation needs a per-player "floating ticks" component ticked unconditionally, not just inside a move-packet-handling system.
- **The speed check compares against the server's own predicted velocity, not a flat cap**: `expectedDist = deltaMovement.lengthSqr()` means the budget is relative to what physics already expects this tick (elytra diving fast is fine; a stationary player suddenly teleporting isn't). A reimplementation must run physics/velocity prediction *before* comparing, not use a naive fixed max-speed constant — a fixed cap will false-positive on legitimate high-velocity vanilla mechanics (boosted elytra, launch pads, etc.).
- **Respawn replaces the entity, it does not mutate it.** Any ECS design must treat "player entity" as re-creatable at a stable identity (network connection + UUID) while the underlying entity id/component set is thrown away and rebuilt via an explicit copy list (`restoreFrom`). Anything that holds a raw reference to the old `ServerPlayer`/entity (open containers, advancement listener maps, chunk-tracking views) must be re-pointed, not assumed stable across death.
- **`keepInventory` is really two independent decision points, not one**: drop suppression happens at death (`Player.dropEquipment`), while the *transfer* of the surviving old inventory to the new respawned entity happens separately at respawn (`ServerPlayer.restoreFrom`, gated a second time on the same gamerule). Getting only one of these right will silently duplicate or lose items under gamerule-toggle edge cases (e.g. gamerule flipped between death and respawn packet).
- **The 26.2 permission system is a deliberate seam for a future finer-grained permission/plugin model** — it is currently behaviorally identical to the old int op-level for vanilla content (only `HasCommandLevel` and one `entity_selectors` atom are ever actually granted by `LevelBasedPermissionSet`), but the registry-backed `Permission`/`PermissionCheck` *type* system exists specifically so third parties can add new kinds without touching core dispatch. Rusty Clanker's modding API should treat this as the intended extension point for a Bukkit-style granular permission system, rather than re-inventing one alongside it — implement `PermissionSet`/`Permission`/`PermissionCheck` as the stable interface and let a mod register new `Permission.Atom`s and new `PermissionSet` implementations (e.g. a wildcard/group-based one) without needing engine changes.
- **Advancement award is index-driven, never a full scan** — `activeTriggers` is keyed by trigger *type* and only contains instances belonging to not-yet-completed advancements. A naive reimplementation that re-evaluates every advancement's every criterion on every relevant game event will not scale; the registration/unregistration dance (`registerListeners`/`unregisterListeners` on progress change) is load-bearing for performance, not just correctness.
- **Container sync relies on content-hash diffing (`RemoteSlot.Synchronized`), not raw NBT diffing** — replicating this (rather than just re-serializing and byte-comparing full stacks) matters for perf with the wide `DataComponent` model; the `stateId` mismatch → full-resync fallback is the correctness safety net and should be preserved verbatim (never silently drop it as "redundant" — it is exactly what makes any missed-increment bug self-healing instead of a permanent desync).
- **Determinism hazard — advancement/criterion evaluation order matters for tie-broken outcomes** (e.g. multiple simultaneous criteria completing an advancement whose rewards include score/scoreboard mutations that other systems observe same-tick). Preserve per-player, single-threaded advancement processing per tick; do not parallelize `PlayerAdvancements.award` calls for the same player across worker threads.
- **Redstone/tick-sequential invariant intersects here**: block-break finalization (`ServerPlayerGameMode.tick()`/`destroyBlock`) mutates world block state and must be sequenced with the single-worker-per-region block/redstone tick per `ARCH`/region rules — block-break should not run concurrently with that region's scheduled block ticking, since `destroyBlock` triggers neighbor updates synchronously.
- **Signed chat has zero server-side "preview" concept in 26.2** — do not build a chat-preview round-trip; the entire flow is submit-once (signed) → filter/decorate → broadcast. Building a preview mechanism would be inventing a feature vanilla explicitly does not have at this pin.
- **Waypoint connection tiers are a deliberate bandwidth/precision tradeoff (block → chunk → azimuth) keyed purely on distance and view-distance visibility** — this is a good template for Rusty Clanker's own cluster-mode cross-partition state sync (bounded-latency, precision degrading with "distance" from the observer) even outside the waypoint feature itself, but it is *not* itself cross-partition-aware in vanilla (single monolithic-world assumption) — cluster mode will need `ServerWaypointManager`'s per-pair connection table to become a cross-node-aware structure, likely piggybacking on the message substrate rather than direct player-connection sends.
