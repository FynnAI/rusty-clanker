# Redstone & Tick Scheduling — Vanilla 26.2 Cartography

## 1. Purpose

This subsystem is the deterministic simulation engine underneath every "machine" a player can build: the redstone wire power-flow model, the six-directional block/shape update propagation graph, the two per-level tick schedulers (scheduled/"pending" ticks and per-section random ticks), and the diode-family components (repeater, comparator, torch, observer) that consume and re-emit signals with delay. It also owns the sculk sensor / vibration / game-event notification pipeline, which is architecturally a second, independent "signal propagation" system that mirrors redstone's neighbor-update graph but travels through open space instead of block faces. Every mechanism in this document is order-sensitive: vanilla's exact iteration order over directions, containers and listeners is part of observable, buildable behavior (contraption timing), not an implementation detail.

## 3. How it works

### 3.1 Redstone wire signal model

`RedStoneWireBlock` stores five `BlockState` properties: `POWER` (0–15, `IntegerProperty`) and four `RedstoneSide` enum properties (`NORTH`/`EAST`/`SOUTH`/`WEST`, values `NONE`/`SIDE`/`UP`). Visual connectivity (which of the four horizontal slots render as flat, rising, or absent) is computed independently of power by `getConnectionState`/`getMissingConnections`/`getConnectingSide`: a wire connects to another wire, to a repeater/observer facing it, or to any other `isSignalSource()` block when approached from a `Direction` — with a same-height check first, then a check one block up (through a non-conductor ceiling) and one block down (over open air), preferring `UP` over `SIDE` when the neighbor's top face is sturdy.

Two independent evaluators compute the numeric `POWER` value, selected per-call by `useExperimentalEvaluator` (`FeatureFlags.REDSTONE_EXPERIMENTS`, an experimental/unlocked-by-datapack feature flag — not the shipped default):

- **`DefaultRedstoneWireEvaluator`** (classic behavior). `calculateTargetStrength` = `max(getBlockSignal(pos), getIncomingWireSignal(pos))`, short-circuited to 15 if the direct block signal (`level.getBestNeighborSignal`, wire's own `isSignalSource` temporarily disabled via the `shouldSignal` flag to avoid self-counting) is already 15. `getIncomingWireSignal` looks at the four horizontal neighbors, plus — for each neighbor that is a redstone conductor — the wire one block above it (through a non-conductor ceiling above the wire's own position), and — for each non-conductor neighbor — the wire one block below it; the result is `max(neighborWireSignal) - 1`, floored at 0. If the recomputed value differs from the stored one, the block is written back (update flag `2` = clients-only, no cascading shape update) and **every position in a 7-cell plus-shape** (`pos` + its 6 `Direction.values()` neighbors) receives `level.updateNeighborsAt`, unconditionally, even positions that did not change — this is a full local re-notify, not a minimal diff.
- **`ExperimentalRedstoneWireEvaluator`** (new algorithm, "Alternate Current"-style two-wave propagation). Given an `initialOrientation` (either the `Orientation` passed in from the triggering neighbor update, or `Orientation.random(level.getRandom())` if none — always normalized to `up=UP`, `sideBias=LEFT`), it performs:
  1. Seed: if the position that changed is itself a wire, record its current power/orientation and push it onto a **turn-off** queue; otherwise treat it as an external signal change and immediately fan out via `propagateChangeToNeighbors` with power 0.
  2. **Turn-off wave** (`wiresToTurnOff`, a `Deque` drained FIFO): recompute `max(blockSignal, incomingWireSignal)` for each dequeued wire; if lower than the previously recorded value, stage it to 0 (and, if it still has a nonzero direct block signal, also enqueue it on the turn-on queue so it gets its own-block-signal reinstated in the second wave) and propagate the *decrease* to neighbors (`allowTurningOff=true`, which lets neighbors with a still-higher stored value also be queued for turn-off); otherwise stage the recomputed (possibly unchanged or higher) value directly.
  3. **Turn-on wave** (`wiresToTurnOn`, also FIFO): recompute the same max; any wire whose new value exceeds its staged value is raised (a value going the other way — new < old during this phase — is treated as an invariant violation and throws `IllegalStateException`).
  4. All staged power values are stored (packed as `orientation.getIndex() << 4 | power`, a single `int`) in an `Object2IntLinkedOpenHashMap<BlockPos>` that preserves **insertion order** — this map, not the queues, is what finally gets written back to `BlockState`s and is what neighbor-changed notifications iterate over afterward, so the notification order is the order wires were first touched, not proximity order.
  5. `causeNeighborUpdates` then walks the touched-wires map in that insertion order and, for each, fires `level.neighborChanged` on every connected neighbor in `orientation.getDirections()` order (see §3.6 for what that order is), additionally cascading through the neighbor if it is itself a redstone conductor (quasi-connectivity fan-out, §3.5).

  `getWireSignal` is overridden in the experimental evaluator to consult the in-flight `updatedWires` map first (`-1` sentinel = "not yet touched this pass, fall back to the live block state"), so a wire that already changed earlier in the same propagation is seen with its *new* value by wires processed later in the same pass — this is what makes the algorithm converge in two passes instead of the old evaluator's implicit fixed-point iteration via repeated neighbor updates.

  Both evaluators share `RedstoneWireEvaluator.getIncomingWireSignal`'s exact geometry (4 horizontal + conditional up/down through non-conductor ceilings/floors, `-1` decay, floored at 0) — the experimental evaluator does not change the *shape* of what "incoming wire signal" means, only how the fixed point is reached and in what order side effects fire.

  `RedStoneWireBlock.getSignal`/`getDirectSignal` gate on the private `shouldSignal` flag (used to suppress wire self-signaling while it queries its own best-neighbor-signal) and, for `getSignal`, additionally check that the queried direction's corresponding `RedstoneSide` is `isConnected()` before returning nonzero (a wire dead-ends visually where it doesn't connect, and dead ends don't power that face).

### 3.2 Orientation — the experimental-redstone determinism device

`Orientation` (package `redstone`) is a value object with `up`/`front`/`side` `Direction`s plus a `SideBias` (`LEFT`/`RIGHT`), pre-baked into a **48-entry static table** (`ORIENTATIONS[48]`, generated once by exhaustive `generateContext` recursion: 6 possible `up` axes with only 4 valid `front` axes each — perpendicular to `up` — times 2 side biases = 48). `getIndex()`/`fromIndex()` round-trip through this table, so an `Orientation` can be packed into 6 bits and shipped in a debug packet or, as above, packed alongside a 4-bit power value into a single `int`.

`getDirections()` returns exactly six directions in the fixed order **`[front.opposite, front, side, side.opposite, up.opposite, up]`** — this is *the* iteration order the experimental wire evaluator and several diode/torch/observer `neighborChanged` notifications walk when an `Orientation` is available. `withFront`/`withUp`/`withSideBias` are precomputed transition tables (built during the same static-init recursion) so re-orienting is an O(1) map lookup, not a recomputation.

`ExperimentalRedstoneUtils.initialOrientation(level, front, up)` is the single entry point components use to *seed* an orientation: it draws `Orientation.random(level.getRandom())` (biased `LEFT`) and returns `null` outright if `FeatureFlags.REDSTONE_EXPERIMENTS` is not enabled for the level — every call site that threads an `Orientation` through a neighbor update degrades to plain `null` (i.e., order-agnostic, classic behavior) automatically when the flag is off. Because the seed comes from `level.getRandom()`, the exact neighbor-visitation order for a given contraption trigger is **not fixed across worlds/runs** under the experimental evaluator — only self-consistent *within* one propagation, since the same `Orientation` value is threaded through every recursive call of that propagation via `withFront`/`withFrontPreserveUp`.

### 3.3 Neighbor update system

Two orthogonal notification kinds exist and must not be conflated:

- **Shape updates** (`BlockState.updateShape` / `updateShape(...)`) — "does my `BlockState` need to change because a neighbor's block changed" (rail curving, fence connecting, wire connectivity, stair shape, torch popping when its support is gone). Dispatched via `LevelAccessor.neighborShapeChanged` → `NeighborUpdater.executeShapeUpdate`, iterated in **`BlockBehaviour.UPDATE_SHAPE_ORDER = [WEST, EAST, NORTH, SOUTH, DOWN, UP]`** by `Block.updateFromNeighbourShapes`/`BlockStateBase.updateNeighbourShapes`.
- **Block ("neighbor changed") updates** (`Block.neighborChanged`) — "react to a neighbor's *signal/state* changing" (redstone components recomputing power, pistons checking whether to extend, doors/fences re-evaluating). Dispatched via `NeighborUpdater.neighborChanged` → `BlockStateBase.handleNeighborChanged` → `Block.neighborChanged`, iterated in **`NeighborUpdater.UPDATE_ORDER = [WEST, EAST, DOWN, UP, NORTH, SOUTH]`** by `updateNeighborsAtExceptFromFacing` (and, transitively, by `Level.updateNeighborsAt`, which is `updateNeighborsAtExceptFromFacing` with no direction skipped).

**These two orders are different from each other** (`DOWN`/`UP` sit in position 3–4 for shape updates but 5–6 for block updates relative to `NORTH`/`SOUTH`) — this is a real, load-bearing asymmetry in vanilla, not an oversight to "fix" in a reimplementation.

`NeighborUpdater` is implemented twice:
- **`CollectingNeighborUpdater`** — the one actually wired into `Level`/`ServerLevel` (`Level.neighborUpdater` field, constructed with `maxChainedNeighborUpdates` from `DedicatedServerProperties.maxChainedNeighborUpdates`, default **1,000,000**, server.properties key `max-chained-neighbor-updates`). It turns the naturally-recursive "notify neighbor → which recomputes → which notifies its neighbors" call graph into an explicit **LIFO stack of `NeighborUpdates` work items** (`ShapeUpdate`, `SimpleNeighborUpdate`, `FullNeighborUpdate`, `MultiNeighborUpdate`) to avoid unbounded Java call-stack recursion. Re-entrant calls made *while* a batch is already draining are buffered into `addedThisLayer` and pushed onto the stack **in reverse** right before the next pop, which preserves depth-first, most-recently-queued-first semantics (i.e. it behaves like ordinary recursion would, just on a heap-allocated stack) rather than breadth-first. A running counter (`count`) is compared against `maxChainedNeighborUpdates`; once exceeded, further work items are silently dropped (one `LOGGER.error` line naming the first skipped position) rather than queued — this is vanilla's neighbor-update runaway breaker, distinct from the shape-update `updateLimit`.
- **`InstantNeighborUpdater`** — a non-batching, immediately-recursive implementation of the same interface. It exists in the codebase but **no construction site was found in this build**; `Level`'s only `NeighborUpdater` field is the `CollectingNeighborUpdater`. Treat it as present-but-currently-unused plumbing (possibly retained for a worldgen/test harness elsewhere, or vestigial) rather than an active code path.

Shape-update recursion depth is bounded separately by an explicit **`updateLimit` int**, threaded through `Block.updateOrDestroy`/`LevelAccessor.neighborShapeChanged`/`BlockStateBase.updateNeighbourShapes`, decrementing by one on every hop (`InstantNeighborUpdater.shapeUpdate` does `updateLimit - 1`) and default-seeded to **`Block.UPDATE_LIMIT = 512`** wherever an overload omits it. This is the historical "512-deep shape-update chain" limit; it is orthogonal to the 1,000,000-item `CollectingNeighborUpdater` counter, which bounds *block* updates, not shape updates.

`Block.UpdateFlags` (an `int`, `@Block.UpdateFlags`-annotated for documentation, not a real Java enum) is a bitset:

### 3.4 Scheduled ("pending") ticks

A `ScheduledTick<T>` is `(type, pos, triggerTick, priority, subTickOrder)` — `T` is `Block` for block ticks and `Fluid` for fluid ticks, two entirely separate `LevelTicks<T>` instances live on `ServerLevel` (`blockTicks`, `fluidTicks`). `subTickOrder` is a per-level monotonically increasing counter (`Level.nextSubTickCount()`, backed by `Level.subTickCount++`) assigned at scheduling time — it is the final tiebreaker (FIFO-within-tick-within-priority) whenever `triggerTick` and `priority` are equal.

`LevelTicks<T>` is a **two-level scheduler**: each chunk owns a `LevelChunkTicks<T>` (a `PriorityQueue<ScheduledTick<T>>` ordered by `ScheduledTick.DRAIN_ORDER` = `triggerTick` then `priority.ordinal()` then `subTickOrder`), and the level keeps a `Long2LongMap` cache of "next trigger tick per chunk" plus a `PriorityQueue<LevelChunkTicks<T>>` (`containersToTick`) ordered by `INTRA_TICK_DRAIN_ORDER` = `priority` then `subTickOrder` (trigger tick omitted — everything in this queue is already known to be due). Each level tick:
1. **`collectTicks`** → `sortContainersToTick` scans the cache, and for every chunk whose next tick is due (`nextTick <= currentTick`) *and* passes `tickCheck` (a `LongPredicate` bound to `ServerLevel::isPositionTickingWithEntitiesLoaded` — i.e. the chunk must actually be in the fully-ticking state), moves that chunk's container into `containersToTick`.
2. **`drainContainers`** repeatedly pops the container whose head tick is globally "best" (lowest priority ordinal, then lowest subTickOrder — since all containers here are already due for the current game tick, only priority/subTickOrder differentiate), pulls its head tick into `toRunThisTick`, then `drainFromCurrentContainer` keeps pulling additional due ticks from that *same* container as long as they still compare "before" the next-best other container's head — this lets one busy chunk contribute many ticks per level-tick without starving others, while still draining in globally-consistent priority order.
3. Both `blockTicks` and `fluidTicks` are drained with a hard cap of **`maxTicksToProcess = 65536`** ticks per game tick (`ServerLevel.MAX_SCHEDULED_TICKS_PER_TICK`) — `canScheduleMoreTicks` stops collection once `toRunThisTick.size()` reaches that cap; anything left over is simply re-queued (`rescheduleLeftoverContainers`) and picked up on a later tick.
4. **`runCollectedTicks`** finally pops `toRunThisTick` (an `ArrayDeque`, so simple FIFO of whatever collection order produced) and calls the consumer — `ServerLevel::tickBlock`/`tickFluid`, which each re-fetch the live `BlockState`/`FluidState` at `pos` and only actually invoke `.tick(...)` if the state's type still matches the scheduled `type` (a block that changed between scheduling and firing silently no-ops its stale tick).

`TickPriority` is a 7-value ordered enum, `EXTREMELY_HIGH(-3)` … `NORMAL(0)` … `EXTREMELY_LOW(3)`; lower numeric value = drained first within the same `triggerTick`. `willTickThisTick(pos, type)` (backed by a lazily-built `ObjectOpenCustomHashSet` snapshot of `toRunThisTick`) is the standard guard diode/torch/tripwire/etc. code uses before scheduling a duplicate tick for the same position this tick.

**Persistence**: `LevelChunkTicks.pack(currentTick)` converts live `ScheduledTick`s to `SavedTick`s with `delay = triggerTick - currentTick` (i.e. stored **relative**, not absolute) plus `priority`; on load, `unpack(currentTick)` restores absolute `triggerTick = currentTick + delay` and assigns `subTickOrder` values counting *up from a negative base* (`-pendingTicks.size()` incrementing to `-1`) so that loaded ticks always sort before any tick freshly scheduled after load (whose `subTickOrder` starts at whatever the level's live counter has reached, ≥ 0) — this preserves the on-disk relative ordering of simultaneously-due ticks across a save/load cycle.

### 3.5 Random ticks

Driven from `ServerChunkCache.tickChunks` → `this.chunkMap.forEachBlockTickingChunk(chunk -> this.level.tickChunk(chunk, tickSpeed))`, where `tickSpeed = GameRules.RANDOM_TICK_SPEED` (default **3**). `ServerLevel.tickChunk(chunk, tickSpeed)`:
- Precipitation: `tickSpeed` draws of `random.nextInt(48) == 0` at a random column in the chunk (independent of sections — snow/ice accumulation, not a block random tick).
- Per **`LevelChunkSection`**: skipped entirely unless `section.isRandomlyTicking()` — this is not recomputed per tick; each section maintains **incremental counters** `tickingBlockCount`/`tickingFluidCount`, bumped in the section's `set`/palette-swap path whenever a placed `BlockState`/`FluidState`'s `isRandomlyTicking()` flips true/false, so the "does this 16³ section contain anything that random-ticks" check is O(1) instead of a per-tick scan.
- For each non-skipped section, exactly `tickSpeed` iterations draw one random position via `Level.getBlockRandomPos(minX, minYInSection, minZ, 15)` — a **hand-rolled 32-bit LCG**, not `RandomSource`: `randValue = randValue * 3 + 1013904223; val = randValue >> 2; pos = (xo + (val & 15), yo + (val >> 16 & 15), zo + (val >> 8 & 15))` (the multiplier `3`/increment `1013904223` pair and the `randValue` seed — `RandomSource.createThreadLocalInstance().nextInt()` at `Level` construction — are exact reproducibility requirements, not incidental). The block/fluid state at that position is fetched directly from the section (bypassing chunk lookup) and ticked only if `isRandomlyTicking()` is still true for that specific state (the section-level flag is necessary-but-not-sufficient — a section can mix ticking and non-ticking states).

Thunder (lightning strike selection, `random.nextInt(100000) == 0` when raining+thundering) uses the same per-chunk random draw machinery but is not itself a block random tick.

### 3.6 Diodes: repeaters and comparators (`DiodeBlock` shared base)

Both extend `HorizontalDirectionalBlock` via the shared abstract `DiodeBlock`, which owns:
- **`tick`**: if not `isLocked`, compare current `POWERED` against `shouldTurnOn`. Turning **off** happens immediately (no extra delay beyond whatever scheduled this tick). Turning **on** also happens immediately, but if the *recomputed* `shouldTurnOn` is already false again by the time this tick fires (i.e., the input pulse was shorter than the component's own delay), a **second** tick is self-scheduled at `getDelay(state)` with `TickPriority.VERY_HIGH` to turn back off — this is how a diode reproduces a short input pulse at its own fixed width rather than swallowing it.
- **`checkTickOnNeighbor`** (called from `neighborChanged`): if not locked and `on != shouldTurnOn` and no tick is already pending this tick for this position (`willTickThisTick`), schedule one at `getDelay(state)` with a priority chosen by:
  - `TickPriority.EXTREMELY_HIGH` if `shouldPrioritize` — the diode directly behind it (`pos.relative(state.getValue(FACING).getOpposite())`) is itself a diode whose own `FACING` does *not* point back (i.e. it isn't feeding straight through) — used to keep perpendicular diode chains updating in the "expected" order;
  - else `TickPriority.VERY_HIGH` if currently **on** (turning off is prioritized over turning on);
  - else `TickPriority.HIGH` (the default, turning on).
- **`getInputSignal`**: front-face signal via `level.getSignal(facingPos, FACING)`, raised to the neighbor's `RedStoneWireBlock.POWER` if that neighbor is a wire and the plain signal read was lower (wires under 15 signal strength don't otherwise self-report through `getSignal`'s conductor path the same way).
- **`getAlternateSignal`** ("side input"): `max` of `getControlInputSignal` on the clockwise and counter-clockwise neighbors; `sideInputDiodesOnly` (repeaters: `true`, comparators: `false`) restricts repeater locking to only react to *other diodes* as side inputs (a wire running past a repeater's side does not lock it; a repeater or comparator pointed into its side does).
- **`updateNeighborsInFront`**: on place/remove, notifies only the block directly in front (`neighborChanged` with a freshly-seeded `Orientation`) plus everything else via `updateNeighborsAtExceptFromFacing` skipping the `FACING` direction back toward the diode itself.

**Repeater specifics** (`RepeaterBlock`): `DELAY` property (`1..4`, right-click cycles it), `getDelay(state) = DELAY * 2` game ticks (**2/4/6/8 ticks**). `isLocked` = `getAlternateSignal(...) > 0` (any side-diode input at all locks a repeater, regardless of magnitude — repeater locking is boolean, not comparator-style magnitude comparison). `sideInputDiodesOnly()` = `true`.

**Comparator specifics** (`ComparatorBlock`, `implements EntityBlock` — backs a `ComparatorBlockEntity` holding a single `int output` field, separate from the `POWERED` boolean): fixed `getDelay = 2` ticks always. `getInputSignal` extends the base by additionally reading `hasAnalogOutputSignal`/`getAnalogOutputSignal` off the block directly in front (containers, etc.), and — if that block is itself a redstone conductor and the plain signal is still under 15 — probing **one block further** for either an `ItemFrame` entity attached to that block's face (`getAnalogOutput()`) or another analog-signal block, taking the max of the two. `calculateOutputSignal`: 0 if input is 0; else 0 if `alternateSignal > inputSignal`; else `inputSignal` in `COMPARE` mode or `inputSignal - alternateSignal` in `SUBTRACT` mode. `shouldTurnOn`: `input > sideInput`, or `input == sideInput && mode == COMPARE` (subtract mode never turns on from an exact tie). `refreshOutputState` (called from both `tick` and the use-item mode-cycle handler) recomputes the analog output, stores it into the block entity, and only flips the `POWERED` boolean / notifies neighbors if the analog value changed or the mode is `COMPARE` (subtract-mode analog-only changes with no boolean flip still propagate because redstone dust and other comparators read the analog value, not just `POWERED`). `checkTickOnNeighbor` is overridden to compare against the *stored analog value* in addition to the boolean, so silent magnitude-only changes still get scheduled.

### 3.7 Torches (plain and redstone) — quasi-connectivity's mechanical origin

`BaseTorchBlock` (shared by decorative and redstone torches, floor-mounted): survives only if `canSupportCenter(level, pos.below(), UP)`; a `DOWN`-direction shape update destroys the torch if that support is gone.

`RedstoneTorchBlock`: `LIT` boolean; `hasNeighborSignal = level.hasSignal(pos.below(), DOWN)` — the torch's *only* input is whatever signal reaches the single block it's mounted on, queried from the `DOWN` direction. Because `SignalGetter.getSignal(pos, direction)` special-cases redstone conductors — `state.isRedstoneConductor(this, pos) ? max(directSignal, getDirectSignalTo(pos)) : directSignal` — and `getDirectSignalTo` checks **all six faces** of that conductor block (not just the queried direction), a torch mounted on a solid block is powered by *any* redstone source touching *any* face of that block, including a wire running past its side rather than underneath it. This all-faces-of-the-supporting-block behavior is quasi-connectivity's mechanical root; it is not special-cased anywhere in the torch code, it falls straight out of `SignalGetter`'s general conductor rule, and the same rule is what makes pistons, redstone lamps and every other "block reads its neighbor" style consumer exhibit quasi-connectivity too (see `PistonBaseBlock.getNeighborSignal`, §3.9). `neighborChanged` schedules a **2-tick** delayed re-evaluation (only if `LIT != hasNeighborSignal` and nothing is already scheduled this tick) rather than reacting instantly, and `tick` performs the actual flip.

**Burnout**: a per-`BlockGetter` (i.e., per-level) `WeakHashMap<BlockGetter, List<Toggle>>` (`RECENT_TOGGLES`) records the game time of every LIT→OFF toggle. `isToggledTooFrequently` first prunes entries older than **`RECENT_TOGGLE_TIMER = 60`** ticks, then counts remaining entries at the *same position*; at **`MAX_RECENT_TOGGLES = 8`** occurrences within that 60-tick window the torch stops responding and self-schedules a **`RESTART_DELAY = 160`**-tick tick before it will consider turning back on — this is the classic "redstone torch burns out under a fast clock" behavior, and the state (`RECENT_TOGGLES`) lives entirely in a static, non-persisted, in-memory map keyed by level identity, so it does **not** survive a server restart/chunk unload — a reimplementation that persists it would diverge from vanilla.

`RedstoneWallTorchBlock` is a `RedstoneTorchBlock` subclass that reads its single input from the block it's attached to horizontally (`FACING.getOpposite()`) instead of `below()`.

### 3.8 Observers

Single `POWERED` boolean, no delay property. `updateShape`, when the changed neighbor is on the observer's `FACING` side (the side it's "looking" at) and it isn't already powered, calls `startSignal` which schedules a tick **2 game ticks** out (only if none already pending) — i.e. observers detect *shape* changes (block identity/state changes in front of them), not signal changes, and always pulse exactly 2 ticks after any qualifying shape update regardless of magnitude. `tick` toggles: `POWERED=true` on the first firing, then on the *next* scheduled tick (self-scheduled again at 2 ticks when going from false→true — mirroring the repeater double-schedule pattern) flips back to `false`; either transition calls `updateNeighborsInFront` (notifies the block behind it, i.e. opposite `FACING`, the direction observers actually output power toward). `onPlace`/`affectNeighborsAfterRemoval` special-case the case where an observer is placed/removed already carrying a pending pulse, to avoid leaking a stray notification.

### 3.9 Pistons

`PistonBaseBlock` (sticky/regular share one class, `isSticky: boolean` field baked into the codec) never moves blocks synchronously from `neighborChanged`/`setPlacedBy` — it only decides *whether to start* via `checkIfExtend`, then fires a **block event** (`level.blockEvent(pos, this, actionId, direction.get3DDataValue())`, actionId `0=TRIGGER_EXTEND`, `1=TRIGGER_CONTRACT`, `2=TRIGGER_DROP`) which is delivered (and can be dropped/coalesced) through the generic block-event queue, then actually executed in `triggerEvent`. This decouples "signal says extend" from "extension actually happens" by at least the block-event delivery latency, and is why piston timing has historically been a rich source of edge cases.

**Quasi-connectivity input** (`getNeighborSignal`): checks `hasSignal` on all 4 side faces except the push direction, `hasSignal(pos, DOWN)` (signal into the piston's own block from below), **and** all 4 side faces of the block *above* the piston except `DOWN` — i.e. a piston can be triggered by a signal touching the top-adjacent block from the side, exactly the same "read all faces of the block you're touching" quasi-connectivity rule as torches.

**Structure resolution** (`PistonStructureResolver`, `MAX_PUSH_DEPTH = 12`): walks outward from the pushed position (`addBlockLine`), refusing (returning `false`, i.e. "piston does not move") if the push line would exceed 12 blocks, if it hits an unpushable block (`isPushable` — false for obsidian/crying obsidian/respawn anchor/reinforced deepslate always, false for anything with `getDestroySpeed == -1` (unbreakable), gated by `PushReaction` otherwise: `BLOCK` refuses, `DESTROY` is allowed only when `allowDestroyable` is set for the block *at the very front* of the line, `PUSH_ONLY` only accepts pushes exactly along the connection direction), or a world-border/Y-bound violation. Sticky blocks (slime/honey, mutually non-sticking to each other per `canStickToEachOther`) additionally pull blocks stuck to their other 4 faces (`addBranchingBlocks`) recursively, with a `reorderListAtCollision` step handling the case where a branch loops back into the main push line.

**Movement mechanics** (`moveBlocks`): all destroyed/pushed blocks are converted to a placeholder `MOVING_PISTON` block state carrying a `PistonMovingBlockEntity` (which stores the *real* `movedState`, `direction`, `extending`, `isSourcePiston`), then all real neighbor notifications fire only after every block in the batch has already been converted (`updateIndirectNeighbourShapes` + `updateNeighborsAt` loops at the end of `moveBlocks`, not interleaved per-block) — this batches the visual/logical settling of a multi-block push into one consistent post-state rather than notifying mid-move.

`PistonMovingBlockEntity.progress` animates from `0.0` to `1.0` in steps of **`0.5F` per tick** (`TICKS_TO_EXTEND = 2` — matches: two ticks × 0.5 = full extension), `finalTick()` snaps `progress = progressO = 1.0F` and is what converts the placeholder back into the real settled block (piston head / pushed block) once movement completes; `getExtendedProgress` flips the sign for retraction (`progress - 1` extending vs `1 - progress` retracting) so both directions share one progress scalar.

### 3.10 Daylight sensor

Not scheduled-tick driven at all — `DaylightDetectorBlockEntity` is polled by its `BlockEntityTicker` every game tick, but the actual signal recompute (`updateSignalStrength`) only runs when `level.getGameTime() % 20 == 0` (i.e. effectively once per second, but phase-locked to absolute game time, not to placement time). `target = level.getEffectiveSkyBrightness(pos)`, inverted (`15 - target`) if the `INVERTED` property is set (right-click toggles it, which — unlike the periodic ticker — recomputes immediately), otherwise scaled by `round(target * cos(sunAngle))` where `sunAngle` is smoothed 20% per recompute toward the "far" side of noon (`offset - sunAngle) * 0.2`) to avoid an instantaneous jump at sunrise/sunset, then clamped to `0..15`.

### 3.11 Tripwire and tripwire hooks

`TripWireHookBlock.calculateState` is the single authority for the whole wire-chain state (invoked from placement, from the hook's own tick, and from any wire segment's `onPlace`/`affectNeighborsAfterRemoval` via `TripWireBlock.updateSource`): it scans up to **`WIRE_DIST_MAX = 42`** blocks along `FACING`, requiring every intervening block to be `TRIPWIRE` (or the specific position that triggered the recalculation, passed as `wireSource`/`wireSourceState` so a not-yet-committed state can be considered) until it finds a second hook facing back (`receiverPos`); `ATTACHED` requires `receiverPos > 1` (i.e. at least one wire block between the hooks — two adjacent hooks never attach) and every segment being armed (`!DISARMED`); `POWERED` requires `ATTACHED` and at least one segment's own `POWERED` (set by entity detection) being true. Both endpoints are written in the same call, and both `RECHECK_PERIOD`s (`TripWireBlock`/`TripWireHookBlock`, both **10 ticks**) drive periodic re-validation while an entity is standing on a pressed wire, mirroring pressure-plate-style debounce.

### 3.12 Rails as redstone components

`PoweredRailBlock`: powered by ordinary quasi-connectivity (`hasNeighborSignal`) **or** by `findPoweredRailSignal`, which recursively walks up to **`searchDepth < 8`** consecutive powered-rail segments along the rail's own orientation (following slopes up/down one Y level as needed) looking for another powered segment with its own neighbor signal — this is how a single lever/redstone-block can power a chain of powered rails without a repeater relay, but only for 8 segments before the signal simply stops (no decay value, it's a hard cutoff). `DetectorRailBlock`: `POWERED` set by minecart presence in a tight bounding box (`getSearchBB`, ±0.2 block inset), rechecked every **20 ticks** while pressed; analog output signal reads a `MinecartCommandBlock`'s last command success count if present, else the redstone signal a Container-minecart's inventory fill level would produce (`AbstractContainerMenu.getRedstoneSignalFromContainer`).

### 3.13 Game events, vibrations, and the sculk sensor family

**Dispatch** (`GameEventDispatcher.post`): every `GameEvent` carries a fixed `notificationRadius` (default **16** blocks, `DEFAULT_NOTIFICATION_RADIUS`, per-event override at registration). Posting a event scans every world **section** (16³) whose bounding box intersects a cube of that radius around the event position, and for each intersected section asks that section's own `GameEventListenerRegistry` (one `EuclideanGameEventListenerRegistry` per `(level, sectionY)` per chunk — listeners are bucketed by which vertical section they occupy, not stored globally) to `visitInRangeListeners`. Listeners with `DeliveryMode.BY_DISTANCE` are collected and only dispatched *after* the full section scan, sorted (`Comparable` on `GameEvent.ListenerInfo`, closest first) — so multiple sculk sensors in range of one event resolve deterministically by distance, not registration order.

**Listener registry** (`EuclideanGameEventListenerRegistry`): a plain `ArrayList` guarded by a re-entrancy flag (`processing`) — registrations/unregistrations that happen *while* a visit is in progress are buffered (`listenersToAdd`/`listenersToRemove`) and only applied after the visit completes, so a listener can safely register or unregister itself in response to the very event being dispatched. Distance filtering (`getPostableListenerPosition`) is a simple squared-distance-vs-`listenerRadius²` check against the listener's own `PositionSource`.

**Vibration travel** (`VibrationSystem`, mixed into sensor/shrieker block entities): each candidate event a listener could react to this tick is offered to a `VibrationSelector`, which keeps only the best candidate **per game tick** — "best" meaning shortest distance, ties broken by higher `VIBRATION_FREQUENCY_FOR_EVENT` (see table below); a chosen candidate is committed once `VibrationSelector.chosenCandidate` sees a strictly later tick than the one it was recorded on (so same-tick competition always has one full tick to resolve before commitment). Once committed (`VibrationSystem.Ticker.tick`, called from the block entity's `BlockEntityTicker` every tick): travel time = `floor(distance)` ticks (`calculateTravelTimeInTicks`, one tick per block of straight-line distance, no partial-tick interpolation of the countdown itself — only the *particle* position is interpolated for rendering via `lerp`), decremented once per tick; on reaching 0, `onReceiveVibration` fires with the *receiving* distance (used for signal-strength falloff) recomputed from listener-to-source at delivery time, not the originally scheduled distance — a listener that moved during travel gets a strength based on where it ended up. Occlusion (`isOccluded`) is a coarse check: nudge the source position 1e-5 blocks toward each of the 6 axis directions and raycast to the destination against the `DAMPENS_VIBRATION_SIGNALS`-tagged blocks; if **all six** nudged rays are blocked, the event is entirely discarded (a genuine line-of-sight-ish check, not a partial attenuation).

**Vibration frequency table** (`VibrationSystem.VIBRATION_FREQUENCY_FOR_EVENT`, used for tiebreaking, comparator output selection on sculk sensors, and resonance-event lookup):

| Frequency | Game events |
|---|---|
| 1 | `step`, `swim`, `flap` |
| 2 | `projectile_land`, `hit_ground`, `splash`, `bounce` |
| 3 | `item_interact_finish`, `projectile_shoot`, `instrument_play` |
| 4 | `entity_action`, `elytra_glide`, `unequip` |
| 5 | `entity_dismount`, `equip` |
| 6 | `entity_interact`, `shear`, `entity_mount` |
| 7 | `entity_damage` |
| 8 | `drink`, `eat` |
| 9 | `container_close`, `block_close`, `block_deactivate`, `block_detach` |
| 10 | `container_open`, `block_open`, `block_activate`, `block_attach`, `prime_fuse`, `note_block_play` |
| 11 | `block_change` |
| 12 | `block_destroy`, `fluid_pickup` |
| 13 | `block_place`, `fluid_place` |
| 14 | `entity_place`, `lightning_strike`, `teleport` |
| 15 | `entity_die`, `explode` |
| 1–15 | `minecraft:resonate_<n>` (synthetic "an amethyst block just resonated at frequency n" events, self-mapped so resonance can itself trigger further resonance) |

Redstone strength from a received vibration: `getRedstoneStrengthForDistance(distance, listenerRadius) = max(1, 15 - floor((15/listenerRadius) * distance))` — a linear falloff from 15 at distance 0 to 1 at the listener's own radius, never reaching 0 (a sensor that fires always outputs at least strength 1).

**Sculk sensor** (`SculkSensorBlock`): `ACTIVE_TICKS = 30`, `COOLDOWN_TICKS = 10`, listener radius **8**. On receiving a qualifying vibration it sets `PHASE=ACTIVE`, `POWER = calculatedPower` and self-schedules the phase-out tick 30 ticks later; that tick moves to `COOLDOWN` (10 more ticks) before finally returning to `INACTIVE` — the sensor cannot re-trigger while `ACTIVE` or `COOLDOWN` (`canActivate` only true when `INACTIVE`). It also has a manual trigger path: `stepOn` (a player/mob stepping on it) directly force-schedules a `STEP` vibration rather than waiting for the normal dispatch pipeline, excluding the Warden (which doesn't trigger sensors it's meant to be hunted by). `tryResonateVibration` re-emits a synthetic `resonate_<frequency>` event toward any adjacent block tagged `VIBRATION_RESONATORS` (amethyst blocks/clusters), with a pitch bend table (`RESONANCE_PITCH_BEND`, 16 entries mapped through a note-block tone table) for the resulting sound.

**Calibrated sculk sensor** (`CalibratedSculkSensorBlock`): listener radius **16** (double the base sensor), `ACTIVE_TICKS` overridden to **10**, and directional — its `getSignal` only outputs on the face opposite `FACING`. Its `canReceiveVibration` reads a **comparator-style back signal** from the block behind its `FACING.getOpposite()` face; if that back signal is nonzero, only vibrations whose frequency exactly matches the back-signal strength (1–15) are accepted — this is the "frequency filter" mechanic letting redstone circuitry select which specific event type a calibrated sensor listens for.

**Sculk shrieker**: separate `VibrationUser` restricted to `GameEventTags.SHRIEKER_CAN_LISTEN`, listener radius **8**, only reacts to vibrations whose ultimate source resolves to a player (`tryGetPlayer`); tracks a `warningLevel` and, once it reaches **4**, attempts a Warden spawn (`SpawnUtil.trySpawnMob`, radius 20/height 5/6) instead of shrieking again.

## 6. Cross-subsystem interfaces

**Consumes from:**
- **World/chunk system** (`03-world-chunks-persistence.md` domain): `BlockState`/`FluidState` storage and mutation (`Level.setBlock`, `LevelChunkSection` incremental random-tick counters), section-addressed structures (`LevelChunkTicks` per chunk, `GameEventListenerRegistry` per section), NBT persistence hooks (`SavedTick` codec, `ComparatorBlockEntity`/sculk block entities' `loadAdditional`/`saveAdditional`).
- **Gamerules**: `RANDOM_TICK_SPEED` feeds random ticking directly; other gamerules are consulted by individual components (not itself part of this domain).
- **Entity system**: piston push/entity collision (`Block.pushEntitiesUp`), tripwire/detector-rail entity-in-box queries, sculk sensor/shrieker entity source attribution for vibrations, item frame analog output for comparators.
- **RNG**: `Level.getRandom()` seeds `Orientation.random` (experimental redstone) and piston/torch particle effects; the dedicated random-position LCG (`Level.getBlockRandomPos`) is local to this subsystem, not shared with worldgen RNG.

**Provides to:**
- **Game mechanics** (`05-game-mechanics.md`): the tick-scheduling substrate (`LevelTicks`/`TickPriority`) is the generic mechanism many non-redstone blocks use for delayed behavior (fluids, farmland, fire spread, crop growth via random ticks) — this document owns the scheduler, not every consumer.
- **Modding API** (`06-modding-api.md`): game events are a natural hook surface (mods can post/observe `GameEvent`s); neighbor-update flags (`UpdateFlags`) are consulted by any block-behavior override a mod supplies.
- **Networking** (`02-protocol-networking.md`): block-event packets (piston/observer-adjacent triggers go through the generic block-event queue), block-change packets carry `UpdateFlags`-derived visibility (`UPDATE_CLIENTS`/`UPDATE_INVISIBLE`), debug packets expose `Orientation`/vibration/game-event state when a debug subscriber is attached (`DebugSubscriptions.REDSTONE_WIRE_ORIENTATIONS`, `.GAME_EVENTS`, `.GAME_EVENT_LISTENERS`).

## 8. Notes for Rusty Clanker

- **Two distinct update orders must both be preserved exactly**: `BlockBehaviour.UPDATE_SHAPE_ORDER = [W,E,N,S,D,U]` for shape updates vs `NeighborUpdater.UPDATE_ORDER = [W,E,D,U,N,S]` for block/signal updates. Collapsing these into one order (an easy "simplification" temptation) will desync contraption timing in any circuit whose behavior depends on which of two simultaneously-changed neighbors gets processed first — which is a lot of redstone circuits.
- **The classic (non-experimental) wire evaluator's "notify a full 7-cell plus-shape unconditionally" behavior is a real vanilla quirk**, not incidental — `DefaultRedstoneWireEvaluator.updatePowerStrength` calls `updateNeighborsAt` on all 6 neighbors plus the wire itself *every time the power value changes*, even neighbors whose own state didn't need to change. A "smarter" diff-only notifier would be observably faster but behaviorally wrong (some vanilla contraptions rely on the extra notifications as a forced re-evaluation trigger).
- **`CollectingNeighborUpdater`'s reentrant-buffer-then-reverse-push pattern is the actual recursion order**, not an implementation detail to optimize away: a naive "just use a `Vec` as a stack and push new work as it arrives" port will process re-entrant updates in the wrong order relative to genuine recursion (LIFO-of-batches, where each batch is itself reversed before pushing, reproduces call-stack depth-first order — get the reversal backwards and updates within one "layer" run in the opposite of vanilla's order).
- **The experimental wire evaluator's determinism is *relative*, not absolute**: it seeds `Orientation` from `level.getRandom()` when no orientation was threaded in from the triggering update. A reimplementation aiming for wire-for-wire vanilla parity needs the *same* RNG algorithm (Java's `java.util.Random`/xoroshiro variant — not covered in this document, see the general RNG notes elsewhere) advanced in the *same call sequence*, or contraptions that depend on experimental-redstone tie-breaking will differ. Since `REDSTONE_EXPERIMENTS` is an opt-in feature flag (not the shipped default), this only matters if Rusty Clanker intends to support the experimental datapack feature at all — the default evaluator has no such RNG dependency and is otherwise fully deterministic given block-state input.
- **Quasi-connectivity is not a special case anywhere** — it's the direct, intentional consequence of `SignalGetter.getSignal`'s "if the queried block is a redstone conductor, also check `getDirectSignalTo` (all 6 faces)" rule. Any block that is a conductor and reads `level.getSignal`/`hasSignal`/`hasNeighborSignal` on itself or a neighbor inherits this automatically (torches, pistons, redstone lamps, dispensers via their own analog paths, etc.). A reimplementation must replicate this rule structurally (in the shared signal-query layer) rather than re-adding "and also check the block below/above" logic ad hoc per component, or it will miss quasi-connectivity cases in blocks not covered by this document.
- **Redstone torch burnout state is process-local, non-persisted, and keyed by object identity of the `Level`/`BlockGetter`** (`WeakHashMap<BlockGetter, List<Toggle>>`). It does not survive a server restart, and — subtly — does not survive a chunk unload/reload cycle either if a new `Level`-equivalent object were substituted; in a cluster/sharded architecture (`13-cluster-architecture.md`), any region migration or handoff that swaps the owning object identity would silently reset burnout tracking unless this state is explicitly carried across the handoff (or explicitly decided to *not* be, as a documented deviation — this must be a deliberate ARCH/CLUSTER decision, not an accident of the port).
- **Scheduled-tick save/load ordering (`SavedTick`'s negative-`subTickOrder` trick) matters for reproducing exact drain order after a save/load cycle** — ticks loaded from disk must sort strictly before any tick scheduled after load when they tie on `triggerTick`/`priority`; get the base/sign wrong and post-reload tick draining order silently diverges from a server that never restarted.
- **`willTickThisTick` is a load-bearing dedup guard used pervasively** (diodes, torches, tripwire, observers, sculk sensors) to avoid double-scheduling within the same tick; it is backed by a lazily-populated hash set snapshot of the current tick's already-collected work. A reimplementation must expose an equivalent "is a tick for `(pos, type)` already queued to run *this* tick" query with the same timing (populated only after `collectTicks` runs, not available before), or components will double-schedule and desync from vanilla's pulse-width behavior.
- **The repeater/observer "self-reschedule a second tick to catch a too-short pulse" pattern** (`DiodeBlock.tick`, `ObserverBlock.tick`) is how vanilla reproduces fixed-width output pulses regardless of input pulse width — this must be preserved as an explicit two-phase state machine (not collapsed into "compute steady-state output," which would drop single-tick pulses that a diode is specifically supposed to stretch/reproduce).
- **Redstone and scheduled block ticking are pinned single-worker-per-region in Rusty Clanker's architecture (ARCH binding principle)** — this document's exact vanilla iteration/priority orders are therefore the full specification for that single-worker execution, with no additional data-race or partial-ordering concerns; the challenge is purely faithful sequential reproduction, not concurrency-safety of this subsystem itself. The one place this subsystem's design brushes against the message-substrate/cross-partition rule is vibration travel across a chunk-load boundary (`requiresAdjacentChunksToBeTicking`) and any redstone circuit crossing a cluster partition boundary — both are out of this document's scope and belong to `13-cluster-architecture.md`, but this document is the source of truth for what exact sequential behavior must be reproduced *within* one partition.
