# Structure Generation — vanilla 26.2 (protocol 776)

## 1. Purpose

Structure generation places all pre-authored, multi-block "features with identity" into the world: villages, strongholds, nether fortresses, ocean monuments, mineshafts, ruined portals, and every other named structure. It owns three cooperating layers: **where** a structure may start (`StructureSet` + `StructurePlacement`, driven by per-chunk hashing), **what shape** it takes once it starts (`Structure` subclasses producing a tree of `StructurePiece`s, either hand-coded or assembled at runtime by the jigsaw system from NBT templates), and **how templates are stamped into the world** (`StructureTemplate`/`StructureTemplateManager` plus a pipeline of `StructureProcessor`s that mutate blocks during placement). Everything here is deterministic from the world seed and chunk coordinates alone; no structure placement depends on load order or player behavior.

## 3. How it works

### 3.1 Structure types and the structure registry

`StructureType<S extends Structure>` (interface, `structure/StructureType.java`) is the **codec dispatch registry** — 15 entries, each a `MapCodec` keyed by a string id and bound to one `Structure` subclass:

`buried_treasure`, `desert_pyramid`, `end_city`, `fortress`, `igloo`, `jigsaw`, `jungle_temple`, `mineshaft`, `nether_fossil`, `ocean_monument`, `ocean_ruin`, `ruined_portal`, `shipwreck`, `stronghold`, `swamp_hut`, `woodland_mansion`.

Every *individual* structure instance (a specific village biome variant, a specific ruined-portal biome variant, etc.) is a separate datapack entry under `data/minecraft/worldgen/structure/*.json`, referencing one of these 15 types via its `"type"` field. `BuiltinStructures` (interface, 37 constants) enumerates every vanilla structure resource key: `pillager_outpost`, `mineshaft`, `mineshaft_mesa`, `mansion`, `jungle_pyramid`, `desert_pyramid`, `igloo`, `shipwreck`, `shipwreck_beached`, `swamp_hut`, `stronghold`, `monument`, `ocean_ruin_cold`, `ocean_ruin_warm`, `fortress`, `nether_fossil`, `end_city`, `buried_treasure`, `bastion_remnant`, `village_plains/desert/savanna/snowy/taiga` (5), `ruined_portal` + 6 biome variants (7 total), `ancient_city`, `trail_ruins`, `trial_chambers`. Most of the "modern" structures — villages, pillager outposts, bastion remnants, ancient city, trail ruins, trial chambers — all share the single `jigsaw` `StructureType` and differ purely by datapack configuration (start pool, size, height, pool aliases). Only the 15 legacy/hand-coded families listed above have dedicated Java piece-generation code.

`Structure` (abstract base, `Structure.java`) holds four settings common to every structure (`StructureSettings` record): `biomes` (a `HolderSet<Biome>`, i.e. which biomes the structure may start in), `spawnOverrides` (`Map<MobCategory, StructureSpawnOverride>`, §3.8), `step` (a `GenerationStep.Decoration` value controlling *when during chunk decoration* the structure's pieces are stamped — see §3.4), and `terrainAdaptation` (`TerrainAdjustment`: `NONE`, `BURY`, `BEARD_THIN`, `BEARD_BOX`, `ENCAPSULATE` — post-placement terrain carving/filling around the structure, inflates the effective bounding box by 12 blocks when non-`NONE`). Subclasses implement `findGenerationPoint(GenerationContext)`, returning `Optional<GenerationStub>` — a `(BlockPos position, Either<Consumer<StructurePiecesBuilder>, StructurePiecesBuilder> generator)` pair. The `Either` distinguishes lazy piece generation (most structures: a `Consumer` that appends to a builder only when actually invoked) from eager generation (mineshafts pre-build the full piece tree just to compute a vertical offset, then hand the finished builder over). `findValidGenerationPoint` wraps `findGenerationPoint` with a biome check at the returned position (`context.validBiome` tested against the noise biome at the stub's position, quart-resolution).

### 3.2 StructureSet and placement: spacing, separation, salt

A `StructureSet` (record: `List<StructureSelectionEntry> structures`, `StructurePlacement placement`) groups one or more weighted structure choices under one placement rule (e.g. the `villages` set lists all 5 village biome variants under one `random_spread` rule). `StructureSelectionEntry(Holder<Structure> structure, int weight)`.

`StructurePlacement` (abstract) is shared config for every placement kind: `locateOffset` (world-space offset applied to the reported location, e.g. buried treasure reports the chunk center at `+9,0,+9`), `frequencyReductionMethod` (an extra per-chunk coin-flip applied *on top of* spacing — see below), `frequency` (probability `0..1`, only relevant when `frequencyReductionMethod` is used), `salt` (the RNG-seeding constant that decorrelates different structure sets that would otherwise land on identical chunks — see §Constants for the actual numbers), and an optional deprecated `exclusionZone` (forbids placement within N chunks of any chunk from *another* named `StructureSet`; pillager outposts use this to avoid villages).

**`isStructureChunk(state, x, z)`** — the entry point every placement kind funnels through — is a three-stage AND:
1. `isPlacementChunk` (kind-specific — see below).
2. `applyAdditionalChunkRestrictions`: if `frequency < 1.0`, re-seed a `WorldgenRandom` and roll against `frequency` using one of four interchangeable hash functions (`FrequencyReductionMethod` enum, `DEFAULT`/`LEGACY_TYPE_1`/`LEGACY_TYPE_2`/`LEGACY_TYPE_3` — kept only so old worldgen presets remain bit-identical; `LEGACY_TYPE_1` is the pillager-outpost-specific hash using `cx ^ (cz << 4) ^ seed`, `LEGACY_TYPE_2`/`LEGACY_TYPE_3` are `nextFloat`/`nextDouble` variants of the salted RNG, all seeded via `WorldgenRandom.setLargeFeature*`).
3. `applyInteractionsWithOtherStructures`: exclusion-zone check via `ChunkGeneratorStructureState.hasStructureChunkInRange`, which brute-force scans a `(2·range+1)²` chunk square around the candidate calling `isStructureChunk` recursively on the *other* set's placement.

#### RandomSpreadStructurePlacement — grid + jitter

Parameters: `spacing` (0–4096, chunk units — size of one grid cell), `separation` (0–4096, must be `< spacing`; the guaranteed empty margin inside each cell, i.e. the structure can only spawn within an inner `spacing − separation` sized offset), `spreadType` (`LINEAR` or `TRIANGULAR`).

Algorithm (`getPotentialStructureChunk`): given any chunk `(sourceX, sourceZ)`, compute its grid cell `(spacedGridX, spacedGridZ) = floorDiv(sourceX, spacing), floorDiv(sourceZ, spacing)`. Seed a `WorldgenRandom` via `setLargeFeatureWithSalt(seed, spacedGridX, spacedGridZ, salt)` (note: the *cell coordinates*, not the source chunk, are hashed — every chunk in the same cell computes the identical candidate). Draw `spreadX, spreadZ = spreadType.evaluate(random, spacing − separation)` twice in sequence. `LINEAR` is a flat `nextInt(limit)`; `TRIANGULAR` is `(nextInt(limit) + nextInt(limit)) / 2` (bell-shaped, biased toward the cell center — used by ocean monuments, woodland mansions, end cities to reduce edge-adjacency clumping). The **one** candidate chunk for that cell is `(gridX·spacing + spreadX, gridZ·spacing + spreadZ)`. `isPlacementChunk` simply checks whether the queried chunk *is* that candidate — so at most one chunk per `spacing×spacing` cell can ever start this structure, and every chunk in the cell agrees on which one (this is what makes `/locate` and mob-spawn-override checks cheap: they only ever need to test the one candidate per cell, not every chunk).

#### ConcentricRingsStructurePlacement — the stronghold ring algorithm

Parameters: `distance` (0–1023), `spread` (0–1023), `count` (1–4095), `preferredBiomes` (a `HolderSet<Biome>` biome-search target). Unlike random-spread, positions are **precomputed once per world** (not derived per-chunk) by `ChunkGeneratorStructureState.generateRingPositions`, seeded from `concentricRingsSeed` (== the *legacy* level seed, separate from the modern per-structure seed, kept for compatibility with old strongholds). Algorithm, in the caller's own words:

1. Seed one `RandomSource` from the concentric-rings seed; draw a uniformly random starting `angle ∈ [0, 2π)`.
2. Maintain `circle = 0` (ring index) and `spread` doubling as "positions placed so far in the current ring" (confusingly reusing the field name — starts at the placement's configured `spread`, i.e. the *first* ring holds `spread` positions).
3. For each of `count` positions: `dist = 4·distance + distance·circle·6 + (random.nextDouble() − 0.5)·distance·2.5` (rings step outward by `6·distance` blocks-of-32-chunks per ring, with the base ring starting at `4·distance`, plus up to `±1.25·distance` jitter). Compute a raw `(x, z)` from `cos(angle)·dist, sin(angle)·dist` in **chunk-section** units (`SectionPos.sectionToBlockCoord(_, 8)` — i.e. these coordinates are in units of 8-chunk sectors before biome search), then **biome-search** outward from that point (`BiomeSource.findBiomeHorizontal`, radius 112 sections, step matching `preferredBiomes`) on a background executor (`Util.backgroundExecutor().forName("structureRings")` — this part of world creation is parallelized across all `count` candidate positions); if a matching biome is found, use its position, otherwise fall back to the raw unmodified point.
4. Advance `angle += 2π / spread`. When `spread` positions have been placed on the current ring, increment `circle`, reset the in-ring counter, grow `spread += 2·spread/(circle+1)` (capped at `count − i` remaining), and add one more random angular jitter before continuing.
5. Results are collected as a `List<ChunkPos>` (`CompletableFuture.thenApply`), cached per `ConcentricRingsStructurePlacement` instance in `ChunkGeneratorStructureState.ringPositions`. `isPlacementChunk` is then just `ringPositions.contains(chunkPos)`.

Strongholds use `distance=32, spread=3, count=128, salt=0`, biased toward `#minecraft:stronghold_biased_to` (see §7). This is the *only* built-in use of concentric rings.

### 3.3 Structure start / reference ladder across chunk statuses

`ChunkStatus` (in `world.level.chunk.status`) defines the ordered protochunk pipeline; the first three stages are structure-relevant, in order: `EMPTY → STRUCTURE_STARTS → STRUCTURE_REFERENCES → BIOMES → NOISE → SURFACE → CARVERS → FEATURES → …`. `MAX_STRUCTURE_DISTANCE = 8` (chunks) bounds how far a structure's pieces may reach from its start chunk — this is why generating/loading any chunk requires its full 17×17 (`8` radius) neighborhood to already be at `STRUCTURE_STARTS` before it can reach `STRUCTURE_REFERENCES`.

**`STRUCTURE_STARTS`** (`ChunkGenerator.createStructures`): for every `StructureSet` in `state.possibleStructureSets()` (pre-filtered to sets containing at least one structure whose biome list intersects the biome source's possible biomes):
- Skip the set entirely if *any* of its member structures already has a valid start recorded for this chunk (idempotent re-entry).
- If `placement.isStructureChunk(state, x, z)` is true and the set has one structure, generate it directly.
- If the set has multiple weighted structures (only `villages`, `nether_complexes`, `ocean_ruins`, `ruined_portals`, `shipwrecks`, `mineshafts` do), seed a `WorldgenRandom` from `setLargeFeatureSeed(seed, x, z)` and repeatedly pick a weighted-random entry from the shrinking candidate list, calling `tryGenerateStructure` on each until one succeeds (returns a valid `StructureStart`) or the list is exhausted — so a failed biome/height check for one candidate (e.g. `village_snowy` picked but the chunk isn't actually snowy by the time the fine biome check runs) falls through to try a different weighted pick, not to giving up outright.
- `tryGenerateStructure` calls `structure.generate(...)` → `findValidGenerationPoint` → builds the `PiecesContainer` → wraps as `StructureStart`; on success, `structureManager.setStartForStructure` writes it into the **current** chunk's own `StructureAccess` (`Structure → StructureStart` map). A start's `references` counter is seeded from any *previous* start already stored (re-roll safety net for regenerated chunks).

**`STRUCTURE_REFERENCES`** (`ChunkGenerator.createReferences`): scans the full `17×17` chunk neighborhood (`±8` in both axes) around the target chunk; for every `StructureStart` found in `getAllStarts()` of each neighbor, if it `isValid()` and its bounding box intersects the target chunk's 16×16 footprint, record a **reference**: `structureManager.addReferenceForStructure(pos, start.getStructure(), sourceChunkKey, centerChunk)`, i.e. the target chunk's `StructureAccess` gets an entry `Structure → LongSet` accumulating the packed chunk-pos of every start chunk whose structure reaches into it. This reference map is what later decoration/mob-spawn code use to cheaply answer "which structure starts (possibly rooted in a distant chunk) touch this chunk" without rescanning the whole world.

**Decoration (during `FEATURES`)**: `ChunkGenerator.applyBiomeDecoration` groups all registered `Structure`s by `step().ordinal()` (the `GenerationStep.Decoration` enum: `RAW_GENERATION, LAKES, LOCAL_MODIFICATIONS, UNDERGROUND_STRUCTURES, SURFACE_STRUCTURES, STRONGHOLDS, UNDERGROUND_ORES, UNDERGROUND_DECORATION, FLUID_SPRINGS, VEGETAL_DECORATION, TOP_LAYER_MODIFICATION` — 11 steps, interleaved with ordinary feature placement steps of the same enum so a structure's `step` decides which normal-feature pass it is sandwiched between). For each step index, for each structure registered at that step: `structureManager.startsForStructure(sectionPos, structure)` resolves the reference `LongSet` back into actual `StructureStart` objects (loading each referenced start-chunk at `STRUCTURE_STARTS` status if needed) and calls `start.placeInChunk(...)` for each — which iterates every `StructurePiece` in the start whose bounding box intersects the *current* chunk's writable area and calls `piece.postProcess(...)` on it, then `structure.afterPlace(...)` once per placed start (used e.g. by desert pyramids to scatter suspicious-sand loot pots, woodland mansions to backfill hanging floors with cobblestone).

`StructureCheck` (`checkStart`) is a fast-path cache sitting in front of full chunk generation: given a `(chunkPos, structure, placement)` triple it first checks an in-memory `Long2ObjectMap`, then attempts to read just the `structures.starts` NBT tag directly off disk via a `CollectFields` selector (without deserializing the whole chunk), then — only if neither cache hits — falls back to `applyAdditionalChunkRestrictions` + a cheap re-run of `findValidGenerationPoint` to decide `START_PRESENT` / `START_NOT_PRESENT` / `CHUNK_LOAD_NEEDED`. This is the mechanism `/locate` and the mob-spawn override path use to probe candidate chunks without forcing full `STRUCTURE_STARTS` generation everywhere.

### 3.4 StructurePiece hierarchy

`StructurePiece` (abstract) is the shared base for every placeable unit: a mutable `BoundingBox`, `orientation`/`rotation`/`mirror` (rotation/mirror are *derived* from `orientation` via `setOrientation` — `SOUTH`→mirror LEFT_RIGHT, `WEST`→mirror LEFT_RIGHT + rotate CW90, `EAST`→rotate CW90 only, `null`→identity), a `genDepth` (tree depth, used by several piece families to bound recursion), and a `StructurePieceType` (the NBT-load registry key, see below). It provides the shared box-fill primitives every hand-coded piece uses: `generateBox` (edge/fill block variants, with or without a per-block `BlockSelector` callback), `generateAirBox`, `generateMaybeBox`/`maybeGenerateBlock` (probabilistic), `generateUpperHalfSphere`, `fillColumnDown`, `createChest`/`createDispenser` (loot-table-backed container placement with automatic `reorient` facing-toward-open-space heuristics), and `placeBlock` (the single choke point: applies mirror then rotation, checks `chunkBB.isInside`, sets the block with flag `2`, propagates scheduled fluid ticks, and marks certain shape-sensitive blocks — fences, torches, ladders, iron bars — for post-processing shape recalculation).

Three intermediate abstractions cover the recurring construction patterns:
- **`PoolElementStructurePiece`** — the jigsaw system's only piece type (registered under id `"jigsaw"`), wrapping a `StructurePoolElement` + position + rotation + accumulated `JigsawJunction` list (terrain-following hints, §3.5) + `LiquidSettings`. `postProcess` simply delegates to `element.place(...)`.
- **`TemplateStructurePiece`** — base for every piece that is *one* NBT template stamped at a fixed rotation (desert pyramid, jungle temple, swamp hut, igloo pieces, ocean ruin, shipwreck, end city, woodland mansion, nether fossil, ruined portal). Holds the resolved `StructureTemplate`, a `StructurePlaceSettings`, and a `templatePosition`; `postProcess` calls `template.placeInWorld` then post-scans placed blocks for `STRUCTURE_BLOCK` "data markers" (dispatched to the subclass's `handleDataMarker`, used e.g. to spawn loot chests or mobs at named marker positions) and any leftover `JIGSAW` blocks (which get resolved to their `final_state` — normally air — since jigsaw blocks are gameplay-invisible scaffolding).
- **`ScatteredFeaturePiece`** — base for the fully procedural, non-template pieces (desert pyramid, jungle temple, swamp hut, buried treasure, mineshaft rooms, nether-fortress/stronghold pieces indirectly via their own hierarchies) that need a computed ground height; provides `updateAverageGroundHeight` (averages `MOTION_BLOCKING_NO_LEAVES` heightmap samples across the box footprint) and `updateHeightPositionToLowestGroundHeight`.

`StructurePieceType` (registry interface) lists every concrete piece id — ~60 entries spanning mineshaft (4), nether fortress (14), stronghold (11), ocean monument (11), end city, woodland mansion, buried treasure, shipwreck, nether fossil, igloo, ocean ruin, ruined portal, desert pyramid, jungle temple, swamp hut, and the single `jigsaw` piece. Three loader shapes: `ContextlessType` (plain `CompoundTag → StructurePiece`, most hand-coded pieces), `StructureTemplateType` (needs the `StructureTemplateManager` to resolve its template), and the full-context default (needs the whole `StructurePieceSerializationContext`, used by `jigsaw`/`ruined_portal`).

### 3.5 The jigsaw system in full

#### Template pools

A `StructureTemplatePool` (registry `Registries.TEMPLATE_POOL`, datapack dir `worldgen/template_pool`) is a **weighted flattened list** of `StructurePoolElement`s plus a `fallback` pool (another pool, used when the chosen pool is exhausted at max recursion depth — almost always `minecraft:empty`). Construction expands `List<Pair<element, weight>>` into a flat `ObjectArrayList` by literal repetition (`weight` copies of the element pointer), so `getRandomTemplate` is a plain uniform `nextInt(size)` and `getShuffledTemplates` is a Fisher-Yates shuffle of that flattened list — meaning **higher weight does not just increase probability, it increases how many list slots the element occupies**, which matters for anyone reimplementing selection without literal duplication (an equivalent weighted-pick must reproduce the same RNG draw count/pattern). `getMaxSize` caches the tallest (Y-span) non-empty element's bounding box height, used by the jigsaw expansion-hack (below).

Five `StructurePoolElementType`s:

| Type id | Class | Behavior |
|---|---|---|
| `single_pool_element` | `SinglePoolElement` | One NBT template, resolved lazily via `Either<Identifier, StructureTemplate>`; carries a `StructureProcessorList` holder and an optional liquid-settings override. Adds `BlockIgnoreProcessor.STRUCTURE_BLOCK` and (unless `keepJigsaws`) `JigsawReplacementProcessor` automatically at placement time, on top of any datapack-declared processors and the pool's `Projection` processors. |
| `legacy_single_pool_element` | `LegacySinglePoolElement` | Same as `single_pool_element` but swaps `BlockIgnoreProcessor.STRUCTURE_BLOCK` for `BlockIgnoreProcessor.STRUCTURE_AND_AIR` (air blocks in the template are treated as "ignore", not "place air") — kept for templates authored before block-ignore semantics changed; villages/pillager outposts/most legacy structures still use this variant exclusively. |
| `feature_pool_element` | `FeaturePoolElement` | Wraps a `PlacedFeature` (ordinary worldgen feature, e.g. a tree or a lake) as if it were a pool element with a single synthetic downward jigsaw block (name `bottom`), letting village decoration pools splice ordinary features into the jigsaw graph. |
| `list_pool_element` | `ListPoolElement` | Places a fixed ordered list of sub-elements at the *same* anchor; jigsaw connectors are taken only from `elements.get(0)`. |
| `empty_pool_element` | `EmptyPoolElement` | The sentinel "nothing here" element (singleton `INSTANCE`); terminates jigsaw branches. Picking it from `getRandomTemplate` aborts structure generation entirely if it is the very first (start) pool draw. |

Every `StructurePoolElement` carries a `Projection` (`RIGID` or `TERRAIN_MATCHING`): `RIGID` has no implicit processors (used for anything that must keep exact shape — most rooms); `TERRAIN_MATCHING` implicitly appends a `GravityProcessor(WORLD_SURFACE_WG, offset=-1)` that re-projects every block onto the current surface height (used by village streets/decor pieces that should hug terrain instead of floating/burying).

#### JigsawPlacement.addPieces — the algorithm

Entry point (`JigsawStructure.findGenerationPoint` → `JigsawPlacement.addPieces`):

1. Resolve the **center pool** (applying any `PoolAliasLookup` substitution first — §3.6) and draw one random element via `getRandomTemplate`. If it resolves to `EmptyPoolElement`, generation fails immediately.
2. If the structure specifies a `start_jigsaw_name`, search the center element's jigsaw blocks for one matching that name and re-anchor the whole placement so *that* jigsaw block lands at the structure's chosen start position (used by ancient city, whose start pool's `city_anchor` jigsaw must land exactly at the configured Y, not the pool template's own origin).
3. Build the center `PoolElementStructurePiece`, project it onto the heightmap if `project_start_to_heightmap` is set (villages: `WORLD_SURFACE_WG`), then reject the whole attempt if `dimension_padding` would be violated (keeps e.g. deep structures away from the world's hard Y limits).
4. If `size` (max depth) `> 0`, run the **BFS placer**: a `Placer` instance holds a `SequencedPriorityIterator<PieceState>` — a priority queue of `(piece, remainingFreeSpace, depth)` states bucketed by integer priority with FIFO order *within* a priority (`add`/`computeNext` in `util/SequencedPriorityIterator.java`), so pieces whose *source jigsaw block* declared a higher `placement_priority` NBT value are always fully expanded before any lower-priority piece is touched, and pieces at equal priority expand in insertion (breadth-first) order.

For each `PoolElementStructurePiece` popped off the queue (`tryPlacingChildren`), iterate its **shuffled** jigsaw blocks (shuffle first, then a stable sort by `selection_priority` descending — so within one piece, higher `selection_priority` jigsaws are tried first, ties broken by the shuffle). For each source jigsaw:
- Resolve its declared target pool (through the alias lookup again), reading the **fallback** pool too. If `depth == maxDepth`, only the fallback pool's templates are considered (this is the actual depth cutoff — target pools stop contributing *new branches* at the configured `size`, but the fallback pool, almost always `minecraft:empty`, still gets a chance so the branch terminates cleanly rather than leaving a dangling connector).
- For each candidate target element (shuffled) × each of the 4 `Rotation`s (shuffled): find a target jigsaw block that `JigsawBlock.canAttach(source, target)` — the compatibility rule is **`sourceFront == targetFront.opposite()` AND (source is `ROLLABLE` joint OR `sourceTop == targetTop`) AND `source.target() == target.name()`** (note: only the source's declared `target` name has to match the candidate's `name`; there is no reciprocal check on the target's own `target` field — an asymmetric, one-directional handshake that must be reproduced exactly for parity).
- Compute the target piece's vertical placement: **rigid-to-rigid** connections stack by their fixed jigsaw-block Y offsets (`sourceBoxY + deltaY`); anything involving a non-rigid (terrain-matching) piece instead re-samples `chunkGenerator.getFirstFreeHeight` at the source jigsaw's column and anchors relative to that surface height — this is why terrain-matching branches (village streets, decor) "reset" to the surface at every non-rigid jigsaw, while an all-rigid branch (a chain of building interiors) stays rigidly stacked regardless of terrain.
- Collision test: build the candidate's `AABB` (deflated by `0.25` to allow touching-but-not-overlapping), test against the running `VoxelShape` "free space" accumulator (`Shapes.joinIsNotEmpty(..., ONLY_SECOND)` — reject on any overlap). Free space is tracked **per branch**, not globally: if the target jigsaw's connector lands *inside* the source piece's own box, the source's private free-space shape is reused (branches within the same room don't collide with themselves); otherwise the caller-supplied ambient free-space shape (shared with sibling branches from the same depth) is used and updated.
- On success: register a bidirectional `JigsawJunction` pair on both pieces (records the connector world column, a "ground Y" used later by terrain-following processors, `deltaY`, and the *other* side's projection type — this is what `GravityProcessor`-driven pieces use to know how far they can legally sink/rise without breaking the joint), add the new piece to the output list, and — unless already at `maxDepth` — enqueue it for further expansion at `depth+1` under the source jigsaw's `placement_priority`. First successful `(element, rotation, jigsaw)` combination wins; the search aborts the remaining rotations/elements for that source jigsaw block (`continue label129`).

**Expansion hack** (`use_expansion_hack`, villages only): when enabled, any candidate target whose own box is short (`≤16` blocks tall) has its box artificially inflated to accommodate the *tallest* thing that could still attach to *its* connectors (computed recursively one level via `getMaxSize`) before the collision test — a historical hack that reserves vertical headroom so tall follow-on pieces (e.g. a well or watchtower) aren't rejected purely because the immediate neighbor's own box under-reported the space it would end up needing.

Depth/range limits (constants on `JigsawStructure`): `MIN_DEPTH=0`, `MAX_DEPTH=20` (datapack `size` field, `0..20` codec range), `MAX_TOTAL_STRUCTURE_RANGE=128` — `max_distance_from_center` is clamped `1..128` horizontally and `1..world-height` vertically, and a codec `.validate` step additionally rejects any structure where `max_distance_from_center.horizontal() + terrainAdaptationEdgePadding > 128` (`terrainAdaptationEdgePadding` is `12` for any non-`NONE` terrain adaptation, `0` otherwise) — this is a hard ceiling on how large any single jigsaw structure's bounding volume may ever be, independent of how many pieces the depth limit would otherwise allow.

### 3.6 Pool aliases

`PoolAliasBinding` (registry-dispatched, 3 kinds) lets a `JigsawStructure` declare, in its own JSON (`pool_aliases` list), that some jigsaw-block `pool` name should be **runtime-substituted** for a different pool before it is ever looked up — without editing the referring template. Resolution happens once per structure-start attempt via `PoolAliasLookup.create(bindings, structureStartPos, seed)`: a positionally-forked `RandomSource` (`RandomSource.create(seed).forkPositional().at(pos)` — deterministic per structure instance, independent of generation order) is handed to each binding's `forEachResolved`, which pushes `(alias, resolvedTarget)` pairs into an immutable map; every subsequent pool lookup throughout jigsaw placement (`JigsawPlacement.addPieces`, both for the center pool and every target pool inside `Placer.tryPlacingChildren`) is passed through `poolAliasLookup.lookup(name)` first.

Three binding kinds:
- `DirectPoolAlias(alias, target)` — unconditional 1:1 rename.
- `RandomPoolAlias(alias, WeightedList<target>)` — one weighted random target per alias, drawn once from the shared random.
- `RandomGroupPoolAlias(WeightedList<List<PoolAliasBinding>>)` — draws one whole *group* of bindings together (weighted), then resolves every binding inside the chosen group with the same random stream — this is how trial chambers keeps a spawner's "ranged" and "slow_ranged" mob variants correlated (both aliases resolve to the *same* mob species per chamber, e.g. both point at `stray` or both at `skeleton`, never a mismatched pair), since both `direct` bindings live inside one weighted group entry.

### 3.7 StructureTemplate NBT format and StructureTemplateManager

An `.nbt` structure template (root compound, current keys) has: `size` (3 ints), `palette`/`palettes` (list of block-state palette entries — plural form used when a template's blocks are placed with *randomly chosen* alternate block palettes at load time, resolved once per `StructurePlaceSettings` via `getRandomPalette`), `blocks` (list of `{pos:[x,y,z], state: paletteIndex, nbt?: block-entity compound}`), `entities` (list of `{pos:[3 doubles], blockPos:[3 ints], nbt: entity compound}`), and a `DataVersion` int for datafixing. Block info is bucketed at save time into full-cube blocks / partial-shape blocks / block-entity-carrying blocks and re-concatenated in that order (`buildInfoList`) purely as a save-format optimization; load reconstructs the same ordering.

`StructureTemplate.placeInWorld` is the single choke point every pool element / template piece routes through: resolves the palette, runs every block through `processBlockInfos` (the processor pipeline, §3.9 next), places blocks (setting a temporary `BARRIER` first for anything carrying block-entity NBT, to avoid transient invalid states), performs a flood-fill liquid reconciliation pass for any fluid displaced by the template (a fixed-point loop over `toFill` positions pulling from adjacent source-fluid neighbors until stable), recalculates shapes at the placed region's edge (`updateShapeAtEdge`, skipped when `settings.getKnownShape()` — jigsaw/pool placement always sets this true since bounding boxes are already known-safe), and finally places entities (`placeEntities`, transform position + rotate/mirror yaw, strip the saved `UUID` so a fresh one is assigned, optionally `finalizeSpawn` for `Mob`s when `settings.shouldFinalizeEntities()`).

`StructureTemplateManager` resolves template `Identifier`s through an ordered list of `TemplateSource`s, first match wins: (1) a per-world `generated/` directory (player-saved structures via the Structure Block, `.nbt` binary), (2) an optional test-structure source directory (`.snbt` text, gametest framework only), (3) `ResourceManagerTemplateSource` — the datapack/resource-pack search path, i.e. every vanilla structure template ships as a `.nbt` resource under `data/minecraft/structure/**.nbt`. Loaded templates are cached indefinitely in a `ConcurrentHashMap<Identifier, Optional<StructureTemplate>>`, invalidated wholesale on resource-pack reload.

### 3.8 Structure processors — full enumeration

`StructureProcessor` is applied per-block during `StructureTemplate.processBlockInfos`: each processor's `processBlock` may replace, keep, or **cancel** (`null` return removes the block from the placement list entirely) a block as it is stamped; a small subset additionally implement `finalizeProcessing` (whole-list post-pass) and set `evaluatesEntirePieceState()=true`, which switches `processBlockInfos` from a "clip to current chunk bounding box during iteration" fast path to a "process every block across the whole piece regardless of chunk bounds" slow path (only `CappedProcessor` needs this, since it must see the *entire* candidate set before picking N to replace). All 11 are registered in `StructureProcessorTypes.bootstrap`:

| Registry id | Class | Effect |
|---|---|---|
| `blackstone_replace` | `BlackstoneReplaceProcessor` | Unconditional 1:1 block substitution table (cobblestone→blackstone, stone→polished blackstone, stone bricks→polished blackstone bricks, their stairs/slabs/walls, chiseled/cracked variants, iron bars→iron chain — ~20 mappings), preserving stair/slab shape properties. Used to reskin nether-fortress-style templates as bastion remnants. |
| `block_age` | `BlockAgeProcessor(mossiness)` | Per-block-type random "weathering": 50% chance to swap full stone-brick blocks for cracked/stairs variants (further split moss vs. non-moss by `mossiness`), 50% chance to age stairs, `mossiness`-chance to moss slabs/walls, 15% chance to turn obsidian into crying obsidian. |
| `block_ignore` | `BlockIgnoreProcessor(List<Block>)` | Drops any block matching the list from placement (returns `null`). Three static presets: `STRUCTURE_BLOCK`, `AIR`, `STRUCTURE_AND_AIR`. |
| `block_rot` | `BlockRotProcessor(rottableBlocks?, integrity)` | Per-block coin-flip (seeded from world seed + block pos) to drop the block entirely (simulating decay), gated to an optional block tag; `integrity` is the *keep* probability. |
| `capped` | `CappedProcessor(delegate, limit: IntProvider)` | Runs `delegate` against only a random `limit`-sized subset of the whole piece's blocks (positional-random subset selection), used to bound how many blocks a sub-processor (e.g. rot/age) may touch regardless of structure size. `evaluatesEntirePieceState()=true`. |
| `gravity` | `GravityProcessor(heightmap, offset)` | Re-projects a block onto the *live world* heightmap at its column (translating `_WG` heightmap types to their final equivalents when placing into a real `ServerLevel`) plus a fixed `offset`, preserving the block's *relative* height within the template. This is the sole mechanism behind `Projection.TERRAIN_MATCHING`. |
| `jigsaw_replacement` | `JigsawReplacementProcessor` | Replaces every placed `JIGSAW` block with the block state parsed from its `final_state` NBT tag (or air/void), unless `SharedConstants.DEBUG_KEEP_JIGSAW_BLOCKS_DURING_STRUCTURE_GEN`; a `final_state` of `structure_void` drops the block entirely. Auto-appended by `SinglePoolElement.getSettings` unless `keepJigsaws` (used by the `/place jigsaw` debug command). |
| `lava_submerged_block` | `LavaSubmergedBlockProcessor` | If the target world position was already lava and the incoming template block isn't a full cube, forces the placed block to stay lava (prevents partial blocks like torches/rails from awkwardly floating in lava lakes inside nether structures). |
| `nop` | `NopProcessor` | Identity — placeholder / explicit "no processing" declaration. |
| `protected_blocks` | `ProtectedBlockProcessor(HolderSet<Block>)` | Cancels placement (`null`) if the *existing world block* at the target position matches the protected set — used to avoid overwriting certain block types already present. |
| `rule` | `RuleProcessor(List<ProcessorRule>)` | The general-purpose conditional-replace processor (below). |

`ProcessorRule` = `(inputPredicate: RuleTest, locPredicate: RuleTest, posPredicate: PosRuleTest, outputState, blockEntityModifier)`. A rule fires when the *template's own block* passes `inputPredicate`, the *current world block* at the target position passes `locPredicate` (both `RuleTest`s, tested against different block states despite sharing a type), and `posPredicate` passes given `(templateRelativePos, worldPos, referencePos)`; on success the block becomes `outputState` (with an optional block-entity NBT transform via `RuleBlockEntityModifier`, default `Passthrough`). `RuleProcessor` seeds its per-block `RandomSource` from `Mth.getSeed(pos)` — deterministic per world position, independent of processing order.

`RuleTest` kinds (registry `RULE_TEST`, 6): `always_true` (`AlwaysTrueTest`), `block_match` (`BlockMatchTest`, exact `Block` match), `blockstate_match` (`BlockStateMatchTest`, exact `BlockState` match), `tag_match` (`TagMatchTest`, block tag), `random_block_match`/`random_blockstate_match` (same as above ANDed with a `nextFloat() < probability` roll).

`PosRuleTest` kinds (registry `POS_RULE_TEST`, 3): `always_true` (`PosAlwaysTrueTest`), `linear_pos` (`LinearPosTest`: probability linearly interpolated between `minChance`/`maxChance` over Manhattan distance `minDist..maxDist` from the piece's reference position — used for "decay increases with distance from structure edge" effects), `axis_aligned_linear_pos` (`AxisAlignedLinearPosTest`: same interpolation but measured only along one `Direction.Axis`, e.g. purely vertical decay gradients).

### 3.9 Per-structure generation specifics

#### Villages, pillager outposts, bastions, ancient city, trial chambers, ruined-portal variants → all `JigsawStructure`

No dedicated Java generation code beyond §3.5; each is fully defined by its `worldgen/structure/*.json` (start pool, `start_jigsaw_name`, `size`, `start_height`, `max_distance_from_center`, `pool_aliases`, `terrain_adaptation`) and its tree of `worldgen/template_pool/**.json` files. Concrete examples pulled from the datapack: `village_plains` starts at `village/plains/town_centers`, depth `size=6`, `max_distance_from_center=80`, projects onto `WORLD_SURFACE_WG`, `use_expansion_hack=true`, `terrain_adaptation=beard_thin`. `ancient_city` starts at `ancient_city/city_center` anchored to its `city_anchor` named jigsaw, `start_height.absolute=-27`, `size=7`, `max_distance_from_center=116`, `step=underground_decoration`, `terrain_adaptation=beard_box`, and zeroes out **every** `MobCategory`'s natural spawn list via `spawn_overrides` (see §3.10 — the Warden/sculk gameplay depends on nothing else spawning inside). `trial_chambers` uses a `random_group` pool alias set to correlate paired spawner-content aliases (e.g. `.../spawner/contents/ranged` and `.../spawner/contents/slow_ranged` always resolve to the same mob species — skeleton, stray, or poison skeleton — per chamber) plus `dimension_padding=10` and `liquid_settings=ignore_waterlogging`.

#### Stronghold — concentric rings + retry-until-portal-room

Placement: `concentric_rings, distance=32, spread=3, count=128, salt=0`, biased toward `#minecraft:stronghold_biased_to`. Generation (`StrongholdStructure.generatePieces`) is a **retry loop keyed by an incrementing salt**: it re-seeds `context.random()` with `context.seed() + tries` on every attempt, resets the shared static piece-weight bookkeeping (`StrongholdPieces.resetPieces`), builds a `StartPiece`, and recursively grows children (weighted-random piece selection from `STRONGHOLD_PIECE_WEIGHTS`, breadth-first via a `pendingChildren` list drained in *random* removal order rather than FIFO) — and **rejects and retries the entire attempt** if the piece tree ends up empty or if no `PortalRoom` piece happened to be placed (a stronghold without an end portal is not a valid stronghold). `MAX_DEPTH=50`, pieces are only attempted within `112` blocks (Chebyshev, both X and Z) of the start room, `LOWEST_Y_POSITION=10`, `MAGIC_START_Y=64` (piece-tree Y origin before the final `moveBelowSeaLevel(seaLevel, minY, random, 10)` shift). Piece weight table (`class, weight, maxPlaceCount`): `Straight 40/∞`, `PrisonHall 5/5`, `LeftTurn 20/∞`, `RightTurn 20/∞`, `RoomCrossing 10/6`, `StraightStairsDown 5/5`, `StairsDown 5/5`, `FiveCrossing 5/4`, `ChestCorridor 5/4`, `Library 10/2` (only placeable at `depth>4`), `PortalRoom 20/1` (only at `depth>5`). Selection tries up to 5 weighted draws before falling back to a generic `FillerCorridor` dead-end piece if nothing fits the available space.

#### Nether fortress — dual weighted-piece grammar (bridge vs. castle)

Single-chunk piece-tree start (`BlockPos(chunkMinX, 64, chunkMinZ)`), no retry loop (unlike stronghold, an incomplete fortress is still accepted). Two separate weighted piece tables (`BRIDGE_PIECE_WEIGHTS` for corridor/bridge segments, `CASTLE_PIECE_WEIGHTS` for room-like segments), `MAX_DEPTH=30`, final piece tree is shifted with `moveInsideHeights(random, 48, 70)` rather than sea-level-relative placement (fortresses always land in a fixed nether Y-band regardless of terrain). Spawns its own `FORTRESS_ENEMIES` weighted mob list (blaze/zombified piglin/wither skeleton/skeleton/magma cube) used by spawner block entities placed directly by piece code, independent of natural biome spawn tables.

#### Woodland mansion — fixed 11×11 room grid with recursive corridor carving

Start point requires `Y ≥ 60` (checked via a legacy 5×5-box lowest-height sample offset 7 blocks from chunk origin) or generation is skipped outright. `WoodlandMansionPieces.MansionGrid` lays out a hand-authored base grid (entrance at a fixed `(7,4)` cell, a `3×3` foyer footprint carved by four `baseGrid.set` calls) then grows four **recursive corridors** outward from the foyer (`recursiveCorridor`, west-biased, lengths 6/6/3/3) that stochastically branch and terminate, filling a `1x1/1x2/2x2` room-size classification into three separate `11×11×5`-cell `SimpleGrid`s (one per floor: ground, first, second — `identifyRooms` run once per floor against the shared corridor skeleton). Concrete room templates are then chosen per classified cell via a `FloorRoomCollection` abstraction (`FirstFloorRoomCollection` etc., each `get1x1`/`get1x2SideEntrance`/`get1x2FrontEntrance`/`get2x2` method picking a numbered NBT template variant, with separate `*Secret` variants for the mansion's hidden rooms) — every room is one `TemplateStructurePiece`, not jigsaw. `afterPlace` performs a downward cobblestone backfill under any exposed floor to avoid floating mansion pieces over cliffs/ravines.

#### Ocean monument — single top-level procedural piece, biome-gated

Requires **every** biome sampled in a `29×29` block area around the chunk center to be tagged `#minecraft:required_ocean_monument_surrounding` (checked before any piece generation is attempted, via `biomeSource.getBiomesWithin`) — this is the enforcement mechanism for "monuments only spawn in the middle of large deep-ocean regions, never near a coastline." A single `MonumentBuilding` piece (procedural room-grid layout internal to `OceanMonumentPieces`, not template-based) is placed with a random horizontal orientation. On chunk **load** (not fresh generation), `regeneratePiecesAfterLoad` deliberately re-derives the top piece's orientation default from a freshly-seeded random rather than trusting a null-orientation save — a defensive fixup for old save format quirks.

#### Mineshaft — two skins (normal/mesa) sharing one piece grammar, height handling differs by type

`MineshaftStructure.Type` enum (`NORMAL` using oak, `MESA` using dark oak) carries its own wood/plank/fence block states, consumed throughout `MineshaftPieces` room/corridor code. Placement set is degenerate by design: `spacing=1, separation=0`, `frequency=0.004` via `legacy_type_3` — i.e. *every* chunk is a placement candidate, and the ~0.4% roll (using the legacy `nextDouble` reducer for save compatibility) is the entire spatial-density control, not a spacing grid; mineshafts of both types share one `StructureSet` and are weighted-picked per successful roll. Piece tree is generated **eagerly** inside `findGenerationPoint` (unusual — most structures defer to the lazy `Consumer` path) purely so the final vertical offset can be computed and folded into the returned `GenerationStub` position: `NORMAL` mineshafts sink `moveBelowSeaLevel`-style; `MESA` mineshafts instead center on a `Mth.randomBetweenInclusive(seaLevel, surfaceHeight)` band (mesa mineshafts intentionally run higher/shallower, matching their badlands canyon-carved appearance).

#### End city — recursive tower with chance-based side extensions

`EndCityPieces.startHouseTower` grows a tower of stacked template segments upward from a fixed base, at each level rolling whether to continue straight up, add a side "wing," or branch into the (rare) ship/gateway pieces near the top — entirely template-driven (`TemplateStructurePiece` subclasses), no jigsaw. Requires start `Y ≥ 60` (same 5×5-box lowest-height helper as woodland mansion).

#### Small single/template structures

- **Desert pyramid / jungle temple / swamp hut** (`SinglePieceStructure`, width/depth `21×21` for the pyramid) — one procedurally-coded `ScatteredFeaturePiece`-derived piece each, placed only if `getLowestY(width, depth) ≥ seaLevel`. Desert pyramid additionally scatters `SUSPICIOUS_SAND` archaeology blocks post-placement (`afterPlace`): collects every candidate sand position across all its pieces, shuffles with a positionally-forked random, keeps `5..8` as loot-bearing suspicious sand and the rest reverts to plain sand.
- **Igloo** (`IglooPieces`, template-based) — occasionally spawns as an "igloo + basement" two-piece variant instead of the plain surface hut.
- **Ocean ruin** — `Type.WARM`/`COLD` biome-temperature variants, plus `largeProbability`/`clusterProbability` floats controlling small-vs-large template selection and whether multiple ruins cluster together around one origin.
- **Shipwreck** — `shipwreck`/`shipwreck_beached` (separate structures sharing one `StructureSet`), template-based, oriented/sunk per surrounding terrain.
- **Buried treasure** — single fixed-size procedural piece (no template), placed at the chunk center on the ocean floor.
- **Ruined portal** — up to 7 biome-flavored `Setup` variants per structure JSON (weighted pick among `setups` when >1), each independently configuring `VerticalPlacement` (`ON_LAND_SURFACE`, `PARTLY_BURIED`, `ON_OCEAN_FLOOR`, `IN_MOUNTAIN`, `UNDERGROUND`, `IN_NETHER`), `airPocketProbability`, `mossiness`, `overgrown`, `vines`, `canBeCold` (biome-driven ice/blackstone-vs-obsidian frame reskinning at runtime, independent of the `blackstone_replace` processor which handles the nether variant's material swap), and a `5%` chance of substituting one of 3 dedicated "giant portal" templates for the normal 10 standard-size ones. `findSuitableY` walks downward from a placement-mode-dependent starting estimate until 3 of the 4 bounding-box corners rest on opaque ground.
- **Nether fossil** — vertical stack of bone-template segments (`NetherFossilPieces`), spacing/separation `2/1` (near-continuous candidate grid, sparse via low density elsewhere).

### 3.10 Structure spawning overrides

`StructureSpawnOverride(BoundingBoxType, WeightedList<MobSpawnSettings.SpawnerData> spawns)` lets a structure JSON *replace* the natural per-biome mob spawn table for one `MobCategory` while an entity-spawn attempt's position falls inside the structure. `BoundingBoxType` is either `piece` (must fall inside an actual placed `StructurePiece`'s box — tighter, used where interior/exterior distinction matters) or `full` (the structure start's overall encompassing bounding box — used by ancient city, which sets every category's override to an **empty** spawn list across the `full` box, i.e. natural mob spawning is entirely disabled anywhere inside the structure's outer bounds, relying solely on sculk-sensor-triggered warden emergence for hostiles).

Consumption path: `ChunkGenerator.getMobsAt(biome, structureManager, mobCategory, pos)` first checks `structureManager.getAllStructuresAt(pos)` (the `STRUCTURE_REFERENCES` map — cheap, already computed) for any structure with a non-null override for the requested category; if found, resolves the actual `StructureStart`s via the reference set and tests the appropriate bounding predicate, returning the override's `spawns` list in place of `biome.getMobSettings().getMobs(mobCategory)` the moment one matches. This entirely bypasses normal biome spawn tables — it is not an addition, it is a full replacement for anything spawning inside the box.

### 3.11 `/locate` command flow

`LocateCommand` (three subcommands — `structure`, `biome`, `poi`) resolves a target (single resource or tag) and calls into `ChunkGenerator.findNearestMapStructure(level, targetStructures, sourcePos, maxSearchRadius=100, createReference=false)`. Internally this groups the requested structures by which `StructurePlacement` instances can produce them (`ChunkGeneratorStructureState.getPlacementsForStructure`), then dispatches per placement kind:

- **Concentric rings** (`getNearestGeneratedStructure` overload taking a `ConcentricRingsStructurePlacement`): iterates the placement's already-precomputed `ringPositions` list, tracking the closest by squared distance, and for each candidate calls `structureManager.checkStructurePresence` (the `StructureCheck` fast path from §3.3) before falling back to actually loading that chunk to `STRUCTURE_STARTS` only if the fast check can't resolve from cache/disk metadata alone.
- **Random spread**: an expanding **square-ring scan** in grid-cell units (`-radius..radius` in both axes, only testing cells on the current ring's edge, `radius` growing implicitly by iterating all edge cells at increasing `radius` up to `maxSearchRadius=100` cells — i.e. up to `100·spacing` blocks out), converting each candidate grid cell to its one deterministic structure chunk via `getPotentialStructureChunk` and probing it the same way.

`MAX_STRUCTURE_SEARCH_RADIUS = 100` (grid cells, **not** blocks — the effective block radius scales with the structure's own `spacing`), `MAX_BIOME_SEARCH_RADIUS = 6400`, `BIOME_SAMPLE_RESOLUTION_HORIZONTAL/VERTICAL = 32/64`, `POI_SEARCH_RADIUS = 256`. `/locate structure` never forces piece generation beyond `STRUCTURE_STARTS` (`createReference=false` in the top-level command) — it reports the start position without materializing the full structure or registering a reference (that only happens for the internal navigator/nearby-structure code paths that pass `createReference=true`, e.g. Eye of Ender stronghold guidance).

## 6. Cross-subsystem interfaces

**Consumes from:**
- **World generation core / `ChunkGenerator`** — biome source (`BiomeSource.getNoiseBiome`, `possibleBiomes`, `findBiomeHorizontal`), terrain height queries (`getFirstOccupiedHeight`, `getFirstFreeHeight`, `getBaseHeight`, `getBaseColumn`), sea level, min/max Y, `RandomState` (noise sampler access for biome queries during structure placement checks).
- **Registry/datapack system** — `Registries.STRUCTURE`, `STRUCTURE_SET`, `TEMPLATE_POOL`, `STRUCTURE_PROCESSOR_LIST`, `STRUCTURE_PIECE`, `STRUCTURE_TYPE`, `POOL_ALIAS_BINDING_TYPE`, `RULE_TEST`, `POS_RULE_TEST` — all structure/pool/processor definitions are datapack-driven registry entries, not hardcoded (except the 15 `StructureType` Java classes and their piece-generation code).
- **Tag system** — biome tags gate both individual structures (`biomes` field, typically `#minecraft:has_structure/<name>`) and concentric-ring biasing (`#minecraft:stronghold_biased_to`); block tags feed `RuleTest`/`BlockRotProcessor`/`ProtectedBlockProcessor`.
- **Loot table system** — chests/dispensers placed by hand-coded pieces reference `ResourceKey<LootTable>`; suspicious sand/gravel brushable blocks reference `BuiltInLootTables`.
- **Entity system** — template-placed entities (`StructureEntityInfo`), hand-placed mob spawners (nether fortress `FORTRESS_ENEMIES`), `EntityType.create` via `TagValueInput`.
- **Persistence (NBT/Anvil)** — `StructureStart`/`StructurePiece` (de)serialization into per-chunk `structures.starts`/`structures.References` NBT; `.nbt` structure-template files on disk and in datapacks; datafixing (`DataFixTypes.CHUNK`, `DataFixTypes.STRUCTURE`) on load.
- **Chunk/region system (`ChunkAccess`/`StructureAccess`/`ProtoChunk`)** — per-chunk storage of `Map<Structure, StructureStart>` (own starts) and `Map<Structure, LongSet>` (references from elsewhere), keyed at `SectionPos`/`ChunkPos` granularity.

**Provides to:**
- **Mob spawning (`NaturalSpawner`/`ChunkGenerator.getMobsAt`)** — per-category spawn table overrides inside structure bounds (§3.10).
- **Commands** — `/locate structure`, `/place structure`/`/place jigsaw` (test-facing jigsaw debug entry `JigsawPlacement.generateJigsaw`), Eye of Ender stronghold-guidance lookups (`findNearestMapStructure` with `createReference=true`).
- **World map / advancement / statistics systems** — structure presence at a position (`StructureManager.getStructureAt`/`getStructureWithPieceAt`) backs "entered structure" advancement triggers and map-decoration icons for explored structures.
- **Client** — none directly; structures are fully server-authoritative and are streamed to clients only as ordinary placed blocks/entities/block-entities inside chunk packets, never as a distinct structure concept over the wire.

## 8. Notes for Rusty Clanker

- **Salt-seeded per-cell hashing must be bit-exact.** `RandomSpreadStructurePlacement` hashes the *grid cell* coordinates (not the queried chunk) through `WorldgenRandom.setLargeFeatureWithSalt`, drawing exactly two `spreadType.evaluate` calls in X-then-Z order. Any reimplementation of the RNG stream (`LegacyRandomSource`) or of `Rotation`/`RandomSpreadType` draw ordering that doesn't match call-for-call will silently desync every structure position from vanilla — this is the single highest-leverage determinism hazard in the whole subsystem, since it fans out into every downstream piece placement.
- **`FrequencyReductionMethod` legacy variants are not vestigial** — `LEGACY_TYPE_1` (pillager outposts), `LEGACY_TYPE_2` (buried treasure), `LEGACY_TYPE_3` (mineshafts) are still live, actively used by built-in structure sets in 26.2, not just historical compatibility shims. All four hash functions must be implemented, not just `DEFAULT`.
- **Weighted pool selection is draw-count-sensitive.** `StructureTemplatePool` flattens weights into literal list repetition before drawing (`nextInt(flattenedSize)`), not a cumulative-weight scan. An equivalent-probability-but-different-algorithm reimplementation (e.g. alias-method or cumulative-sum sampling) will select the *same distribution* but consume the RNG differently and desync the very next draw. Reimplement the flatten-then-`nextInt` approach exactly, or accept that seed-identical parity is impossible for jigsaw structures.
- **The jigsaw attach rule is asymmetric.** `JigsawBlock.canAttach` only checks `source.target() == target.name()` — never the reverse. A naive "both sides must agree" reimplementation will reject valid vanilla connections (or accept invalid ones) that vanilla's one-directional check allows.
- **Depth cutoff behavior is subtle**: at `depth == maxDepth`, target pools stop contributing new candidate pieces but their **fallback** pool is still consulted — branches terminate via the fallback (usually `minecraft:empty`), they don't just stop being drawn. A reimplementation that hard-stops at `maxDepth` without still trying fallback will produce structures with dangling unfilled connectors (visible holes/gaps) that vanilla never has.
- **Priority-bucketed BFS, not plain BFS or plain priority-queue.** `SequencedPriorityIterator` fully drains one priority bucket (FIFO within it) before touching the next-lower bucket — this is neither pure breadth-first (a plain FIFO queue) nor pure priority-first (a heap that could interleave depths within one priority). Getting this wrong changes which branches "win" limited free-space contention when a `placement_priority` NBT value is set (used sparingly in vanilla but load-bearing where it appears, e.g. ancient city city-center connectors).
- **Two independent RNG streams feed one structure's world seed derivation**: `ChunkGeneratorStructureState` keeps `levelSeed` (per-chunk placement hashing) separate from `concentricRingsSeed` (ring generation — deliberately equal to the *legacy* level seed for save-format compatibility, not derived the same way as everything else). Any "just derive everything from one canonical seed" simplification will break stronghold positions relative to vanilla on the same seed.
- **Structure start/reference is a two-phase commit spanning a 17×17 chunk neighborhood**, not a local, single-chunk operation — `STRUCTURE_REFERENCES` for chunk C requires `STRUCTURE_STARTS` already resolved for all of C's `±8` neighbors. In a multithreaded/region-partitioned engine (per `ARCH-D1`ff and the message-substrate rule), this is exactly the kind of cross-chunk dependency that must be expressed as an explicit ordering constraint in the chunk-generation task graph — a region worker generating chunk C cannot reach `STRUCTURE_REFERENCES` while any of the 8-radius neighbor chunks (potentially owned by an adjacent partition in cluster mode) haven't yet produced their `STRUCTURE_STARTS` result. This is a legitimate, bounded cross-partition read dependency, not a violation of the "no cross-partition blocking" rule, provided it's satisfied via prefetch/ordering rather than a blocking wait inside a tick.
- **`StructureCheck`'s three-tier fast path exists specifically to avoid full chunk generation** during `/locate` and mob-spawn-override queries — a partial-NBT scan (`CollectFields`) that reads only the `structures.starts` compound without deserializing blocks. Skipping this optimization (i.e. always materializing full protochunks to answer a presence query) would be correct but catastrophically slower for `/locate` on large `random_spread` search radii (up to 100×spacing chunks scanned) — worth preserving as a first-class engine capability (a "peek chunk metadata without full generation" storage API) rather than retrofitting later.
- **Mineshafts generate their piece tree eagerly** inside `findGenerationPoint` (the only vanilla structure that does), purely to fold a computed Y-offset into the stub position before pieces are ever built via the lazy path everything else uses. A reimplementation that assumes "all `GenerationStub`s defer piece building" will need an explicit escape hatch for this one case (the `Either<Consumer, StructurePiecesBuilder>` in `GenerationStub.generator` exists precisely for it).
- **Ocean monument's post-load `regeneratePiecesAfterLoad`** re-randomizes orientation from a fresh RNG on chunk *load* rather than trusting the saved piece — a deliberate historical-format fixup, not a bug. Any from-scratch NBT format doesn't need to reproduce this, but a *save-compatible* reimplementation reading old-format saves would.
- **`StructureSpawnOverride` fully replaces, never merges with, biome spawn tables** for the matching category+bounding-box — ancient city zeroes every category to disable natural spawning entirely inside its `full` bounding box. An ECS-based mob-spawner system must check structure overrides *before* falling back to biome tables, not blend the two.
- **Terrain adaptation (`TerrainAdjustment`) inflates the effective bounding box by a fixed 12 blocks** for any non-`NONE` mode, and this same 12-block figure is separately re-used as a hard-cap addend in `JigsawStructure`'s range validation (`max_distance_from_center + 12 ≤ 128` when terrain-adapted) — the two uses must stay numerically consistent if either is ever made configurable.
- **The `references` counter on `StructureStart` caps at `getMaxReferences()=1`** for every vanilla structure (base-class default, never overridden) — a structure can only be "referenced" (contribute to reference-based lookups like `/locate`'s Eye-of-Ender path) once per lifetime. This is easy to accidentally generalize away when reimplementing generically.
