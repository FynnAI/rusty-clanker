# Physics, Movement & Collision

## 1. Purpose

This subsystem governs how every entity in vanilla occupies and moves through space: the exact-rational-feeling but floating-point-exact shape geometry blocks expose for collision/interaction/rendering (`VoxelShape`), the per-tick integration of an entity's position against that geometry (`Entity.move`, `LivingEntity.travel`), and every specialised physical interaction layered on top — gravity, drag, friction, fluids, climbing, elytra flight, vehicles, projectile ballistics and hit-scanning, explosions, falling blocks, fall damage, suffocation, and raycasting. It is the single most parity-sensitive subsystem in the server: nearly all of it is pure floating-point arithmetic executed in a fixed operation order, and any reordering, precision change, or missed edge case is externally observable as "the physics feels wrong" even when every other subsystem is bit-perfect.

## 3. How it works

### 3.1 VoxelShape representation

A `VoxelShape` (`net.minecraft.world.phys.shapes.VoxelShape`) is **not** a mesh — it is a set of axis-aligned sub-boxes defined by the Cartesian product of three sorted per-axis coordinate lists (`DoubleList` X/Y/Z, each in local block-relative `[0,1]` space, though `Shapes.box` allows arbitrary extents for entity-relative shapes such as the world border). Two parallel representations exist:

- **`DiscreteVoxelShape`** — the *boolean occupancy grid*: for a shape subdivided into `xSize × ySize × zSize` cells, `isFull(x,y,z)` says whether cell `(x,y,z)` is occupied. `BitSetDiscreteVoxelShape` backs this with a single `java.util.BitSet` (row-major index `(x*ySize+y)*zSize+z`) plus cached `xMin/yMin/zMin/xMax/yMax/zMax` bounds that are updated incrementally on `fill()`, so `firstFull(axis)`/`lastFull(axis)` are O(1). `isEmpty()` on `DiscreteVoxelShape` is defined generically as "any axis has `firstFull >= lastFull`"; `BitSetDiscreteVoxelShape` overrides it to just check the `BitSet`.
- **`VoxelShape`** (continuous) wraps a `DiscreteVoxelShape` plus the three `DoubleList`s that convert cell indices to world coordinates. Two concrete flavours exist purely as an optimisation: **`CubeVoxelShape`** stores no coordinate lists at all — its cells are always evenly spaced at `1/size` intervals, so `getCoords(axis)` returns a lazily-computed `CubePointRange` (an implicit arithmetic sequence, not a materialised array). **`ArrayVoxelShape`** stores explicit `DoubleArrayList`s for shapes with irregular subdivisions (produced by unions/rotations/offsets of non-cube-aligned shapes). `SliceShape` is a thin 2D wrapper used internally by face/occlusion queries; `OffsetDoubleList` lazily adds a constant to every element of another list without copying (used by `VoxelShape.move`).

**Bit budgeting.** `Shapes.create(minX,minY,minZ,maxX,maxY,maxZ)` (used to build a single box, e.g. a block's collision box) calls `findBits(min,max)` per axis: it tries `bits = 0..3` (i.e. subdivisions of `1, 2, 4, 8` per axis) and picks the smallest that lands both `min` and `max` on a grid line within `1e-7` tolerance. If no power-of-two subdivision up to `1/8` fits (irregular fractional coordinates), it falls back to a two-point `ArrayVoxelShape` instead of a `BitSetDiscreteVoxelShape`. If bits are `0` on all three axes (i.e. the box *is* the full unit cube), the shared singleton `Shapes.block()` is returned instead of allocating.

**Boolean algebra.** `Shapes.join(a, b, op)` (`op` from `BooleanOp`, e.g. `OR`, `AND`, `ONLY_FIRST`, `NOT_SAME` — implemented as tiny functional lambdas over two booleans) merges two shapes:
1. Fast paths: identical shape references, empty operands, or non-overlapping bounding boxes on any axis (checked before doing real work) resolve immediately based on which operand(s) matter per `op.apply(true,false)` / `op.apply(false,true)`.
2. Otherwise, for each axis independently, `Shapes.createIndexMerger` builds an `IndexMerger` that interleaves the two shapes' coordinate lists into one merged list, remembering which of the two original cell indices each merged cell maps back to. Three merger strategies exist depending on the input shapes' regularity: **`DiscreteCubeMerger`** (both operands are regular cube subdivisions — the merged grid is their `lcm`, gated by a cost heuristic `cost * lcm ≤ 256` to avoid blow-up), **`IdenticalMerger`** (identical coordinate lists — degenerate 1:1 mapping), **`NonOverlappingMerger`** (bounding boxes don't touch on this axis — trivial), and **`IndirectMerger`** (general case — a linear merge-sort of the two coordinate lists with a `1e-7` epsilon to coalesce near-duplicate values, optionally skipping runs that only one operand's boolean-op branch cares about).
3. The three per-axis mergers are then combined into a new `BitSetDiscreteVoxelShape` by iterating the Cartesian product of merged cells and evaluating `op.apply(first.isFullWide(...), second.isFullWide(...))` per merged cell (`BitSetDiscreteVoxelShape.join`). If all three axis mergers turned out to be `DiscreteCubeMerger`, the result is wrapped as a fast `CubeVoxelShape`; otherwise it's an `ArrayVoxelShape` carrying the merged coordinate lists.
4. `Shapes.join` (used by most call sites) additionally calls `.optimize()` on the result, which re-derives a minimal set of disjoint boxes via `forAllBoxes` + repeated `OR`-joining — this collapses many small cells that happen to tile into larger boxes, keeping later collision sweeps cheap. `Shapes.joinUnoptimized` skips this for callers that only need the raw grid (e.g. intermediate steps).
5. `Shapes.joinIsNotEmpty(a, b, op)` is a separate, allocation-free short-circuiting variant used for pure yes/no tests (occlusion checks, `Entity.isInWall`, world-border/entity overlap checks) — it never builds a result shape.

**Shape kinds per block state** (all on `BlockBehaviour`/`BlockState`, dispatched through the `Block` subclass):

| Shape | Method | Used for |
|---|---|---|
| Outline | `getShape` | Selection/outline box the client draws; hit-scan default for `ClipContext.Block.OUTLINE` |
| Collision | `getCollisionShape` | Entity movement collision (`Entity.move`), most raycasts |
| Interaction | `getInteractionShape` | Overrides collision-clip direction for interactive parts (e.g. a hinge) without changing physical collision |
| Visual | `getVisualShape` | What eye-line/vision checks (mob AI sight, `ClipContext.Block.VISUAL`) treat as solid — defaults to collision shape |
| Block-support | `getBlockSupportShape` | What standing/support checks use — defaults to the *entity-empty-context* collision shape, decoupled so a block can be walkable but not otherwise collidable (or vice versa) |
| Occlusion | `getOcclusionShape` | Face-culling for adjacent-block rendering; also feeds `blockOccludes`/`faceShapeOccludes`/`mergedFaceOccludes` used for light/render occlusion, not physics |
| Entity-inside | `getEntityInsideCollisionShape` | Per-entity-type overridable "am I inside this block's hitbox" check, defaulting to the plain collision shape |

**Caching.** For any `BlockState` whose block is *not* marked `dynamicShape` (i.e. its shape is a pure function of its own property values, not of world context beyond its own state — true for the overwhelming majority of blocks including stairs/fences/walls, since their connections are encoded as state properties), `BlockBehaviour.BlockStateBase.initCache()` eagerly computes a `Cache` object once at state-registration time containing the collision shape, whether it's a "large" (extends outside the unit cube) collision shape, per-direction/per-`SupportType` face-sturdiness booleans, and whether it's a full-block shape. Every subsequent `getCollisionShape` call for that exact state (from any position, since block coordinates are always position-relative before world placement) is a cache hit. Blocks whose shape genuinely depends on world position (position-seeded random offset blocks) opt into `dynamicShape()` and pay the recomputation cost every call.

**Ray clipping against a shape.** `VoxelShape.clip(from, to, pos)`: nudge a test point 0.1% along the segment from `from`, check if that point already lands inside a full discrete cell (degenerate "already touching" case, returns a hit at the nudge point with direction from the segment's dominant axis), otherwise fall back to `AABB.clip` over `toAabbs()` (the shape decomposed into disjoint boxes via `forAllBoxes`) and take the closest hit.

**Collision sweep along one axis.** `VoxelShape.collideX` (invoked through `VoxelShape.collide(axis, movingAABB, distance)`, itself driven per-axis by `Shapes.collide`) is the core "how far can this AABB move before this shape stops it" primitive: it transforms the query into a canonical X-major frame via `AxisCycle`, computes the index range of the shape's B/C-axis cells the moving box's B/C extents overlap, then walks the *shape's* A-axis cells outward from the box's current A-extent in the direction of travel and returns the first cell boundary that would be crossed (clamped so the returned distance never overshoots the requested `distance`, and clamped to `0` if the box is already touching within `1e-7`). This is invoked once per candidate block/entity shape and the result distance for the next shape's query uses the *already-reduced* distance from the previous one, so `Shapes.collide(axis, moving, allShapes, distance)` iteratively tightens the bound across a whole `Iterable<VoxelShape>` and can early-exit once the remaining distance is `~0`.

### 3.2 Entity movement pipeline (`Entity.move`)

`Entity.move(MoverType, Vec3 delta)` is the single, universal entry point for displacing any entity (players call it via `Player`/`LivingEntity.travel`; non-physics entities skip it via `noPhysics`). Per invocation:

1. **No-physics fast path.** If `this.noPhysics`, position is set directly with the raw delta and all collision flags are cleared — no shape queries at all (used for spectators, and briefly for item entities stuck inside solid blocks).
2. **Piston clamp.** If `moverType == PISTON`, the delta is passed through `limitPistonMovement`, which tracks a per-axis cumulative displacement (`pistonDeltas[]`, reset every game tick via `pistonDeltasGameTime`) and clamps it to `±0.51` blocks total for the tick — this bounds how far a piston push can carry an entity in one game tick regardless of how many individual push calls happen. A clamped-to-zero result short-circuits the whole `move()` call.
3. **Stuck-multiplier consumption.** If a "stuck speed multiplier" is pending (set by cobwebs/berry bushes/powder snow etc.), it's applied once to the delta (unless this is a piston move) and then cleared, and delta-movement is zeroed.
4. **Sneak edge-keep.** `maybeBackOffFromEdge(delta, moverType)` — no-op on the base `Entity`, overridden on `Player` (see §3.2.1).
5. **Collision resolution.** `collide(delta)` (§3.2.2) reduces the raw delta to the actual free movement, handling step-up internally.
6. **Fall-distance reset probe.** If the entity had accumulated fall distance and the resolved movement is at least 1 block long, a `ClipContext` ray (`FALLDAMAGE_RESETTING` block filter, `WATER` fluid filter) is cast up to 8 blocks along the movement direction; any hit resets fall distance early (this is what makes falling *through* a nether portal or descending waterfall not accumulate fall damage even before actually landing).
7. **Position commit.** The entity's position is advanced by the resolved movement vector (recorded into a per-tick movement-segment ring buffer capped at 100 entries, used later for "which blocks did I pass through this tick" effect application — §3.2.3).
8. **Collision-flag bookkeeping.** `horizontalCollision` is set if the resolved X or Z component differs from the requested one; `verticalCollision`/`verticalCollisionBelow` similarly for Y (only recomputed when Y actually moved, or for the locally-authoritative instance), which in turn feeds `onGround()`. `minorHorizontalCollision` flags a "small" collision (subclass-defined, e.g. boats use it to distinguish nudges from real stops).
9. **Fall damage check.** For the locally-authoritative instance, `checkFallDamage` runs immediately here (see §3.6).
10. **Bounce/restitution.** If the entity both moved and collided, `restituteMovementAfterCollisions` (§3.2.4) runs.
11. **Sound/vibration emission**, then **block speed factor** is reapplied to delta-movement (soul sand/honey block horizontal dampening, applied every move call, not just once per tick).

#### 3.2.1 Sneak edge-keep (`Player.maybeBackOffFromEdge`)

Only applies when: not flying, not moving upward, mover type is `SELF`/`PLAYER`, the player `isStayingOnGroundSurface()` (sneaking and not swimming), and the player is currently "above ground" (on ground, or within `maxUpStep` of it without an unavoidable fall). The algorithm walks the requested X and Z delta components toward zero in `0.05`-block increments (independently, then jointly) as long as `canFallAtLeast(dx, dz, maxUpStep)` — a `noCollision` probe of the player's bounding box translated by `(dx, 0, dz)` and dropped by `maxUpStep` — reports that the destination would leave solid ground. This is why a sneaking player's feet visually "catch" on a block edge instead of sliding off: the horizontal delta is truncated in 0.05 steps *before* the general collision resolver ever runs, so the resolver never even attempts to move the player past the edge.

#### 3.2.2 Step-up mechanics (`Entity.collide`)

1. Run the normal shape-based collision sweep (`collideBoundingBox`) against the union of nearby entity collision shapes and block collision shapes (obtained via `Level.getBlockCollisions`), producing `movementStep`.
2. If `maxUpStep() > 0` and the entity is on the ground (either already, or as a result of this very sweep landing it on the ground — `onGroundAfterCollision = yCollision && movement.y < 0`) and the sweep hit something horizontally:
   - Build a "grounded" AABB (shifted down onto the ground if it just landed) and expand it upward by `maxUpStep()` plus the requested horizontal delta, to gather every collider shape that could matter for a step.
   - Collect the Y-axis coordinate of every candidate collider's top/bottom face relative to the grounded box's bottom, filter to `[0, maxUpStep]`, sort ascending — these are the *candidate step heights* (not just `maxUpStep` itself; a half-slab at 0.5 or a stair tread produces its own candidate so the entity steps onto the exact surface height rather than the maximum).
   - For each candidate height (ascending), re-run the collision sweep from the grounded position with Y forced to that candidate height; if the resulting horizontal distance moved is *strictly greater* than what the plain sweep achieved, that step height is accepted, and the final result is that stepped movement, adjusted back down by however far the grounded box had already dropped.
   - If no candidate improves horizontal distance, the plain `movementStep` from step 1 stands (no step happened).
3. `maxUpStep()` itself: `0` on `Entity`, and on `LivingEntity` it is `Attributes.STEP_HEIGHT` (default `0.6`), boosted to at least `1.0` whenever the controlling passenger is a `Player` (mounted vehicles can step a full block when player-ridden — this is the "boats/horses climb 1-block steps" rule).

#### 3.2.3 Applying block effects along a movement path

Because a single `move()` call can traverse multiple blocks in one tick (e.g. a fast-falling entity), `Entity` doesn't just check the destination block for "inside block" effects (fire, powder snow, honey, cactus, sweet berry bush, etc.) — `checkInsideBlocks` walks every recorded per-tick movement segment, and for movement with an "axis-dependent" character (i.e. produced by the collision resolver's per-axis order) it further decomposes each segment axis-by-axis in `Direction.axisStepOrder` order and probes intermediate positions, capped at 16 iterations per tick to bound worst-case cost; if the cap is hit, a final catch-up probe at the very last position covers whatever was skipped.

#### 3.2.4 Bounce / restitution (`restituteMovementAfterCollisions`)

After a collision, delta-movement (not position — this affects *next* tick, since position already used the pre-bounce delta this tick) is corrected:
- Horizontal: for each axis that collided, the post-collision velocity component is set to `-oldVelocity * restitution` (i.e. it reflects, scaled by restitution — `0` restitution just zeroes it, matching ordinary wall-stop behaviour).
- Vertical, only on a downward (`verticalCollisionBelow`) landing: restitution is boosted to `max(restitution, blockBounciness)` unless the entity is sneaking, the fall speed didn't exceed effective gravity, or the landed-on block is tagged `SUPPRESSES_BOUNCE`. Block bounciness comes from `Block.getBounceRestitution()` (slime block = `1.0`; further multiplied by `0.8` for any non-`LivingEntity`, i.e. thrown items/projectiles bounce less than mobs on slime). If restitution ends up `> 0`, the new vertical velocity is computed by re-deriving how much of the requested fall was actually "spent" (`movement.y / currentMovement.y`) and using it to interpolate an "effective drag" between `1.0` and the entity's normal air drag, then applying `(gravityCompensation - currentVelocity) * effectiveDrag * restitution` — this is what makes bouncing on slime feel springy rather than instantly snapping to a fixed bounce velocity.
- `getEntityBounciness()` (per-entity, e.g. throwables have positive bounciness independent of the block) is combined via `max` with block bounciness, but only when not `isSuppressingBounce()` (sneaking).

### 3.3 Gravity, drag, and per-category tick formulas

Gravity and drag are **not** unified into one code path — item entities, falling blocks, arrows, and living entities each implement their own tick order, and the *order of add vs. multiply operations differs between them*, which is exactly where naive reimplementations diverge from vanilla:

| Category | Gravity/tick | Order within one tick | Air drag |
|---|---|---|---|
| **Item entity** (`ItemEntity`) | `0.04` (constant, `getDefaultGravity` override) | `applyGravity()` (velocity.y -= gravity) **before** `move()`; **after** `move()`, multiply all three axes by drag (`airDrag` on Y, `airDrag * blockFriction` on X/Z if on ground); if on ground and Y velocity is still negative, additionally halve-and-invert it (`y *= -0.5`) | `0.98` (base `Entity.getAirDrag()`, not overridden) |
| **Falling block** (`FallingBlockEntity`) | `0.04` | `applyGravity()` **before** `move()`; drag (`* getAirDrag()`, i.e. `0.98`) applied **after** `move()` to all three axes uniformly | `0.98` |
| **Arrow-family projectile** (`AbstractArrow`) | `0.05` (`getDefaultGravity` override) | Position is advanced first using the *previous* tick's stored velocity (via a ray-clip, not the shape-collision sweep — arrows fly through open air and only stop on a genuine block/entity hit); **then** drag is applied (`applyInertia`, a plain multiply — water uses `0.6`, air uses `getAirDrag() = 0.99`); gravity is applied **last**, *after* drag, and only if the arrow didn't just embed itself in a block this tick | `0.99` |
| **Living entity, in air** (`LivingEntity.travelInAir`) | `Attributes.GRAVITY` (default `0.08`), via `LivingEntity.DEFAULT_BASE_GRAVITY` | Horizontal input is converted to a delta-movement contribution first (`moveRelative` + friction-influenced speed), **then** `move()` is called with the *current* delta-movement (i.e. this tick's move uses last tick's post-drag velocity); gravity is subtracted from the Y component of the *next* tick's velocity (computed here but not yet applied to position) **before** the whole vector (X/Z always, Y conditionally) is multiplied by drag for storage as next tick's velocity | `computeModifiedFriction(0.98, AIR_DRAG_MODIFIER)`, separately for horizontal (`blockFriction * airDrag`) and vertical (`computeModifiedFriction(0.98, modifier)`, or the horizontal air-drag value itself for "omnidirectional" flyers like bats/parrots) |

Key parity-critical details:
- **Item/falling-block order is "subtract-then-move-then-multiply"**; **arrow order is "move-then-multiply-then-subtract"**; **living-entity order is "compute-horizontal-then-move-with-stale-velocity-then-subtract-and-multiply-for-next-tick"**. These are three genuinely different tick shapes, not one formula parameterised three ways — a reimplementation that tries to unify them into a single `applyPhysics(entity)` function will diverge unless it preserves each category's exact operation order.
- `Entity.getGravity()` always routes through `isNoGravity()` first (entity-data flag `NoGravity`, settable via commands/NBT) — `0` gravity whenever set, regardless of category.
- `LivingEntity.getEffectiveGravity()` additionally clamps to `min(gravity, 0.01)` while falling (`deltaMovement.y <= 0`) under Slow Falling — this is a *ceiling* on the magnitude of downward acceleration, not a flat override, so a custom `Attributes.GRAVITY` value below `0.01` is preserved.
- Elytra flight (`LivingEntity.travelFallFlying` → `updateFallFlyingMovement`) is its own formula, not a variant of `travelInAir`: `liftForce = cos²(pitchRadians)`; vertical velocity gets `+gravity * (liftForce * 0.75 - 1)` added; if still descending and the entity is looking somewhat horizontally, a pitch-down "glide" term redirects some of the vertical speed into the horizontal look direction (`convert = velocity.y * -0.1 * liftForce`); if pitching downward while moving forward, a "dive acceleration" term adds `moveHorLength * -sin(pitch) * 0.04` scaled and redirected similarly (with `3.2×` extra applied to the resulting vertical component — the "diving accelerates you much faster than climbing" asymmetry); a horizontal-velocity-toward-look-direction correction blends `10%` of the gap between current horizontal velocity and look-aligned velocity every tick; finally the whole vector is scaled by `(0.99, 0.98, 0.99)`. Flying into a wall while gliding (`horizontalCollision` after an elytra move) deals `(oldHorizontalSpeed - newHorizontalSpeed) * 10 - 3` damage if positive (`flyIntoWall` damage source).

### 3.4 Knockback

`LivingEntity.knockback(power, xd, zd, source, damage, comesFromEffect)`: `power` is first scaled by `1 - Attributes.KNOCKBACK_RESISTANCE`; if a degenerate (near-zero) direction was supplied, a tiny random direction is substituted so knockback never silently no-ops. The horizontal push is computed as `normalize(xd, zd) * power` and **halves the entity's existing horizontal velocity before subtracting** the push (`velocity/2 - push`, not `velocity - push`) — this is why chained hits don't linearly stack knockback distance. Vertical: if the entity is on the ground, velocity.y becomes `min(0.4, velocity.y/2 + power)` (also halved-then-added, capped at `0.4`); if airborne, vertical velocity is untouched (you can't be knocked further upward while already in the air from a ground-only vertical kick).

Melee attack knockback (`Player.stabAttack`) applies knockback in **two separate calls**: a flat `0.4` "sprint attack" bump (independent of enchantments, applied whenever `dealsKnockback` and unconditionally of sprint state — the parameter name is legacy) directed along the attacker's facing (`sin(yRot)`, `-cos(yRot)`), then a second call using `getKnockback(target, damageSource)` (attribute `ATTACK_KNOCKBACK`, default `0`, plus the Knockback enchantment) marked `comesFromEffect = true`. Both go through `causeExtraKnockback`, which also always scales the *attacker's own* horizontal velocity by `(0.6, 1.0, 0.6)` and cancels sprinting on a successful knockback-dealing hit — the attacker's own recoil-braking is unconditional, not knockback-magnitude-dependent.

Explosion knockback (§3.8) uses an entirely separate, distance/exposure-weighted formula, not `LivingEntity.knockback`.

### 3.5 Friction, block speed/jump factors

`Block`/`BlockBehaviour` carry three physically-relevant per-block float fields set at registration: `friction` (default `0.6`), `speedFactor` (default `1.0`), `jumpFactor` (default `1.0`).

- **Friction** feeds `LivingEntity.getFrictionInfluencedSpeed`: while on ground, if the supporting block's friction exceeds `0.6`, the horizontal input speed is scaled by `getSpeed() * (0.216 / friction³)` instead of the raw speed — `0.216 = 0.6³`, so this exactly cancels the extra multiplicative decay that a higher-friction (slippery) surface would otherwise apply during `travelInAir`'s post-move drag multiply, keeping steady-state top walking speed identical on any surface while still letting the *deceleration* on release of input feel slippery. Ice family (`ICE`, `PACKED_ICE`, `FROSTED_ICE` = `0.98`; `BLUE_ICE` = `0.989`) exploits exactly this mechanic.
- **Speed factor** (soul sand `0.4`, honey block `0.4`) directly scales delta-movement's horizontal components at the *end* of every `Entity.move()` call (`getBlockSpeedFactor`, applied unconditionally, not just to living entities) — checked at the entity's current block first, falling back to the block below only if the current block isn't water/bubble-column and its own factor is the neutral `1.0`.
- **Jump factor** (honey block `0.5`) multiplies into `getJumpPower` alongside `Attributes.JUMP_STRENGTH` and any Jump Boost bonus (`+0.1` per amplifier level).

### 3.6 Fall damage

`checkFallDamage(velocityY, onGround, ...)` runs every `move()` call for the locally-authoritative instance: whenever not in water and `velocityY < 0`, `fallDistance -= velocityY` (subtracting a negative, so this *accumulates* distance fallen); on landing (`onGround`), if accumulated `fallDistance > 0`, the landed-on block's `fallOn` hook fires (this is the generic entry point — most blocks just call the damage formula, but e.g. beds/slime/hay bales/powder snow override it to soften or nullify damage) and fall distance resets to `0` regardless of whether damage was actually dealt.

`LivingEntity.calculateFallDamage`: `basePower = fallDistance + 1e-6 - Attributes.SAFE_FALL_DISTANCE` (default safe distance `3.0`), then `damage = floor(basePower * damageModifier * Attributes.FALL_DAMAGE_MULTIPLIER)` (both attributes default to values that reduce to the classic "1 damage per block beyond 3"). Entities tagged `FALL_DAMAGE_IMMUNE` always take `0`. A separate "ignore fall damage from current impulse" mechanism (`isIgnoringFallDamageFromCurrentImpulse`, set by e.g. wind-charge/breeze knock-up effects with a 40-tick grace window) clips the effective fall distance to only the portion fallen *below* the impulse's original impact height, so being launched upward by an effect doesn't itself count as "fall distance" once you come back down past that point.

### 3.7 Suffocation / in-wall checks

`Entity.isInWall()`: builds a flat (near-zero-height) AABB centred on the entity's eye position, sized to `80%` of the entity's width, and checks every block position it overlaps for `!isAir() && state.isSuffocating(...)` with an actual non-empty intersection between that block's (world-space) collision shape and the probe box (`Shapes.joinIsNotEmpty(..., AND)` — a pure yes/no shape query, no result shape built). `LivingEntity.isInWall()` additionally excludes sleeping entities. If true, `LivingEntity.baseTick` deals `1.0` suffocation damage (`inWall` damage source) every tick — there is no cooldown or ramp-up, it is a flat per-tick amount, so being stuck for `n` ticks deals `n` damage until the entity dies or is freed.

### 3.8 Fluid physics

**Height/flow query.** `EntityFluidInteraction` (one instance per entity, tracking one `Tracker` per relevant fluid tag) rescans the entity's fluid-interaction AABB every tick: for every fluid-containing block cell that overlaps the box, it accumulates the highest submersion height (`fluidTop - entityBoundingBoxMinY`) and, unless movement should ignore current (i.e. the entity isn't pushed by fluids), accumulates that cell's flow vector (scaled down proportionally if the tracked height is under `0.4`, softening current near the surface). Whether the entity's eye position specifically sits inside a fluid cell is tracked separately (`eyesInside`) for breath/underwater-fog purposes.

**Flow-vector computation** (`FlowingFluid.getFlow`, per source/flowing cell): for each of the four horizontal neighbours, compare fluid height; a neighbour that's empty of this fluid but has a *further-below* neighbour of this fluid contributes a synthetic height difference of `thisHeight - (belowNeighbourHeight - 0.8889)` (`8/9`, i.e. treats a below-and-empty-above neighbour as if it were almost a full block lower, biasing flow toward drop-offs). The accumulated `(Σ dx·Δheight, 0, Σ dz·Δheight)` vector is then, if the cell is itself a "falling" (downward-flowing) cell adjacent to any solid vertical face, redirected to add a strong `(0, -6, 0)` pull before final normalization — this is what makes water/lava visually and physically "pour down" a waterfall face instead of just draining sideways.

**Pushing entities.** Applied only if `isPushedByFluid()` (false for e.g. boats): water uses scale `0.014`; lava uses `0.007` if the dimension's "fast lava" environment attribute is set (Nether-like dimensions), else `0.00233`. The accumulated flow is normalized (or, for players, averaged rather than normalized — `accumulatedCurrent / sampleCount` — so a player standing at the boundary of many weak-current cells isn't shoved as hard as a non-player entity would be) and scaled; if the entity's existing horizontal velocity is already near-zero and the computed impulse is weaker than `0.0045`, the impulse is renormalized up to exactly `0.0045` magnitude — a floor that guarantees a stationary entity in current always gets *some* perceptible push rather than being lost in float noise.

**Swimming (`LivingEntity.travelInWater`).** Slowdown factor: `0.9` if sprinting, else `getWaterSlowDown()` (`0.8` base). `Attributes.WATER_MOVEMENT_EFFICIENCY` (Depth Strider) blends the slowdown toward `0.546` and blends effective move speed toward `getSpeed()`, halved in effectiveness while airborne (not touching a floor while swimming). Dolphin's Grace overrides slowdown outright to `0.96`. After moving, delta-movement is scaled `(slowDown, 0.8, slowDown)`; if there was horizontal collision while on a climbable, vertical velocity is forced to `0.2` (climbing out of water onto a ladder). `getFluidFallingAdjustedMovement` (shared with lava) applies a small terminal-velocity smoothing near `-gravity/16` so entities don't visibly "step" between fall-rates frame to frame; lava additionally applies a flat `-gravity/4` per tick on top when not shallow, and multiplies velocity by `0.5` uniformly when not in shallow lava (viscous resistance) or `(0.5, 0.8, 0.5)` when shallow. `jumpOutOfFluid`: if there was horizontal collision and the space `0.6` blocks above the pre-move Y is free, vertical velocity is set to a flat `0.3` (the "bob out of the water when hitting a wall while swimming" nudge).

**Bubble columns** (`BubbleColumnBlock` + `Entity.onAboveBubbleColumn`/`onInsideBubbleColumn`): a column of fluid cells flagged `DRAG_DOWN` or not, propagated upward from a source block tagged `ENABLES_BUBBLE_COLUMN_PUSH_UP`/`_DRAG_DOWN` (magma block / soul sand respectively) each tick. An entity *inside* the column (something solid above it, i.e. submerged) gets `velocity.y = max(-0.9, v.y - 0.03)` (drag) or `min(1.8, v.y + 0.1)` (push); an entity at the *top* of the column (open air above) gets a gentler `v.y - 0.03` drag or `v.y + 0.1` push directly (no clamp) via `handleOnAboveBubbleColumn`/`handleOnInsideBubbleColumn` — note the differing clamps and magnitudes between "inside" and "above the top of" the column. `Projectile` overrides both with its own smaller constants (`±0.03`/`0.1` above, `±0.03`/`0.06` inside).

### 3.9 Ladders and climbing

`LivingEntity.onClimbable()`: true if the block at the entity's feet is tagged `CLIMBABLE` (ladders, vines, scaffolding, twisting/weeping vines), or is an *open* trapdoor whose facing matches a ladder block directly beneath it (the vanilla "trapdoor as ladder" trick) — always false while spectating, and false while gliding through a `CAN_GLIDE_THROUGH`-tagged climbable (so elytra flight isn't interrupted by brushing a vine). `handleOnClimbable` clamps horizontal delta to `±0.15` and vertical delta to a minimum of `-0.15` (i.e. climbing down is capped in speed, climbing/holding up is not additionally capped here); if descending and the block is not scaffolding and the entity is a sneaking player, vertical delta is forced to `0` (holding shift while on a ladder halts descent — the vanilla "grip" behaviour), and fall distance is reset every tick spent on a climbable regardless of direction.

### 3.10 Riding & vehicles

Passenger placement is push-based, not pull-based: every tick a vehicle with passengers calls `positionRider(passenger)` (also called immediately whenever a new passenger mounts), which computes `vehicle.getPassengerRidingPosition(passenger)` (vehicle's own position plus a per-passenger-index attachment point looked up from `EntityDimensions.attachments()`, an `EntityAttachments` table baked per entity type/pose) minus the passenger's own `getVehicleAttachmentPoint(vehicle)` offset, and directly sets the passenger's position (or snaps it, depending on caller) — the passenger's own physics tick (`rideTick`) zeroes its delta-movement and lets the vehicle's placement fully own its position instead.

`startRiding`/`stopRiding`: mounting fails if the target can't accept passengers, if serialisation isn't possible client-side-safely, or if it would create a cycle in the vehicle chain; `canRide` (rider-side gate, default: not sneaking and no boarding cooldown) and `canAddPassenger` (vehicle-side gate) must both pass unless `force` is set. Dismounting (`stopRiding`→`removeVehicle`) always fires an `ENTITY_DISMOUNT` game event unless the entity's removal reason says otherwise.

**Safe dismount search** (`DismountHelper.findSafeDismountLocation` + `offsetsForDirection`): tries the eight ground cells around the vehicle in a fixed order — right, left, back-right, back-left, forward-right, forward-left, back, forward (relative to the vehicle's facing) — for each, requires the floor height there to be finite and `< 1.0` (i.e. not a full extra block up), that the resulting bounding box has zero block-collision overlap, and that it stays within the world border; a `checkDangerous` mode additionally rejects lava/fire/etc. at the candidate or (if the floor is flush) at the block below it.

### 3.11 Projectile motion & hit detection

**Free-flight (non-arrow) projectiles** (`Projectile` base) don't run through `Entity.move`'s shape-sweep collision at all for their core flight — `shoot`/`shootFromRotation` set an initial velocity (direction-normalised, jittered by `random.triangle(0, 0.0172275 * uncertainty)` per axis — the classic "bow inaccuracy" triangular-distribution spread — then scaled by power), and per-tick motion is a straight-line `ClipContext` raycast from the current position to `position + deltaMovement` against `ClipContext.Block.COLLIDER`/no fluid, refined against nearby entity AABBs (`ProjectileUtil.getHitResultOnMoveVector`/`getEntityHitResult`), landing exactly at the first hit point rather than at the naive destination.

**Arrow-family** (`AbstractArrow`, §3.3) additionally supports an *embedded* state: each tick first checks whether the arrow's exact position already lies inside the current block's collision shape (if so, it snaps to rest — velocity zeroed, `inGround = true`) before doing any raycast movement; while embedded it periodically re-checks whether the block state changed and whether the space around it is now open (`shouldFall`), in which case it resumes falling with a fresh, heavily-randomised residual velocity (`velocity * (0..0.2, 0..0.2, 0..0.2)` per axis) rather than continuing at its pre-impact speed.

**Entity hit margin.** `ProjectileUtil.computeMargin(source)` grows a projectile's effective entity-hitbox inflation from `0` up to `0.3` blocks linearly over its first `~22` ticks of life (`(tickCount - 2) / 20`, clamped `[0, 0.3]`) — this is the mechanism that prevents a projectile from immediately re-hitting the entity that just fired it at point-blank range while still allowing normal hits shortly after.

**`ClipContext`** bundles `(from, to, Block filter, Fluid filter, CollisionContext)`. `Block` filter is an enum of shape-getter strategies: `COLLIDER` (normal physical raycast), `OUTLINE` (selection-box raycast, used for block-breaking reach), `VISUAL` (vision/vanish checks), `FALLDAMAGE_RESETTING` (only "counts" tagged blocks, or end-portal/gateway/nether-portal specifically for players, as hits — used purely for the fall-distance-reset probe in §3.2). `Fluid` filter: `NONE`, `SOURCE_ONLY`, `ANY`, `WATER`.

### 3.12 World clip / raytrace (DDA traversal)

`BlockGetter.traverseBlocks(from, to, ...)` implements an "Amanatides–Woo"-style 3D DDA voxel walk in its own words:
1. Both endpoints are nudged by a `1e-7` epsilon *toward each other* first (`Mth.lerp(-1e-7, to, from)` for the effective "to" and the mirrored expression for "from") — this avoids the walk landing exactly on a cell boundary and picking the wrong neighbour due to floating-point rounding at axis-aligned ray directions.
2. The starting cell is `floor()` of the (epsilon-adjusted) `from` point; the caller's hit-test callback is tried against it immediately (a ray that starts inside a solid block hits at t=0).
3. For each axis, `tDelta = sign / axisDelta` (the parametric-`t` distance to cross one full cell along that axis; `Double.MAX_VALUE` if that axis doesn't move — makes the axis effectively never selected as "next"), and the initial `t` to the *first* cell boundary is `tDelta * (fractional distance already into the current cell, direction-dependent)`.
4. The loop repeatedly advances whichever axis has the smallest accumulated `t` (ties broken in fixed axis order: check X-vs-Y first, then between the loser and Z), steps that axis's cell coordinate by its sign, accumulates that axis's `tDelta`, and re-invokes the callback on the new cell — until all three `t` values exceed `1.0` (past the destination) or the callback returns a non-null hit.

The entity-AABB-sweep variant (`forEachBlockIntersectedBetween`, used for entity-vs-block traversal along a full box rather than a single point) is a related but separate algorithm: it walks blocks touched by the *leading corner* of the moving AABB via the same DDA stepping, then for each step also sweeps the *opposite* corner backward from the leading-corner's exact block-boundary hit point to catch every block the box's full cross-section grazes, deduplicating via a `LongSet` of already-visited block positions — this is what lets a large or fast-moving entity correctly register collisions/effects with every block its box passes through in one tick, not just the blocks its center-point's straight-line path would hit.

### 3.13 Explosion mechanics

`ServerExplosion.explode()`:
1. **Ray-sampled block destruction** (`calculateExplodedPositions`): fires `16×16×16 - interior` = 1352 rays, one per cell on the surface shell of a `16³` cube centred at the origin (i.e. every point where at least one coordinate is `0` or `15` out of `16`), normalized to a unit direction. Each ray starts with `power = radius * (0.7 + random*0.6)` (randomised per-ray, so identical explosions with the same radius still destroy a randomised-looking blob) and steps `0.3` blocks at a time; at each step, the traversed block's `(explosionResistance + 0.3) * 0.3` is subtracted from remaining power (resistance from `max(block resistance, fluid resistance)`, further adjustable by a source-entity hook — see below), a flat `0.225` is *also* subtracted from power every step regardless of resistance (this is the base "ray runs out of steam over distance" decay, independent of what it's passing through), and the block is added to the destroy-set if remaining power is still positive after resistance is paid. The ray stops at the world's vertical bounds.
2. **Entity damage & knockback** (`hurtEntities`): every entity within `2*radius + 1` blocks (bounding-box query, not sphere) is considered if `dist = distanceToCenter / (2*radius) ≤ 1`. `exposure` (line-of-sight fraction, `getSeenPercent`) is computed by sampling a grid of points across the entity's bounding box sized so roughly one sample falls on each half-block-ish cell (`1/((size)*2+1)` per axis) and raycasting each to the explosion centre, counting the fraction that reach it unobstructed — **skipped (defaults to `0`) if the entity wouldn't be damaged and has zero knockback multiplier**, an optimisation. Damage: `getEntityDamageAmount` = `floor(((pow² + pow)/2 * 7 * 2radius) + 1)` where `pow = (1-dist)*exposure`. Knockback: `direction * (1-dist) * exposure * knockbackMultiplier * (1 - Attributes.EXPLOSION_KNOCKBACK_RESISTANCE)`, applied via the generic `Entity.push` (an additive velocity impulse, not `LivingEntity.knockback`'s halving formula) — separately tracked per hit `Player` for use by the "explosion knockback" client-reconciliation packet.
3. **Block interaction & fire**: for `BlockInteraction != KEEP`, every exploded block's `onExplosionHit` runs (drops item stacks, merged up to 16-per-stack via a simple linear-scan collector) in shuffled order (avoids any positional bias in which stack absorbs merges); if `fire` is set, each exploded position has a `1/3` chance to become fire if it's air with a solid-render floor beneath it.

**The per-entity explosion-behaviour hook**: `Entity.getBlockExplosionResistance(explosion, level, pos, block, fluid, resistance)` and `Entity.shouldBlockExplode(explosion, level, pos, state, power)` are virtual methods on `Entity` itself (default: pass through unchanged / always `true`), consulted through `EntityBasedExplosionDamageCalculator` whenever an explosion has a source entity — this is how creeper-vs-charged-creeper resistance multipliers or wind-charge selective block immunity are implemented, without a separate strategy-object hierarchy per explosion type. `ExplosionDamageCalculator` (no source entity — TNT, bed/respawn-anchor explosions) uses the block/fluid's raw registered resistance unmodified. `Explosion.BlockInteraction` is a 4-way enum: `KEEP` (damage entities only), `DESTROY`, `DESTROY_WITH_DECAY` (loot table decay applied to drops), `TRIGGER_BLOCK` (fires block-specific explosion reactions, e.g. respawn anchor charge, without destroying terrain).

### 3.14 Falling blocks

`FallingBlockEntity` gravity is `0.04` (same as items), applied *before* `move()`, with `getAirDrag() = 0.98` applied at the very end of `tick()` unconditionally. Landing logic (only evaluated once not on-ground-with-collision or specifically stuck, and only server-side): on contact, delta-movement is force-set to `(0.7, -0.5, 0.7)` (bounce-damped horizontal carry, velocity inversion+halving vertically) *before* deciding whether to actually place the block — if the destination can be replaced and the origin block would survive there without immediately wanting to fall again, the real block is placed (re-attaching any carried block-entity NBT); otherwise, depending on `dropItem`/`cancelDrop`, an item drop or a `Fallable.onBrokenAfterFall` hook fires instead. Concrete powder gets a special "solidify on contact with any water it clips through mid-fall" check (`ClipContext` with `SOURCE_ONLY` fluid filter) in addition to normal landing. Falling-block entity-damage (anvils, by default) is capped at `40` and computed as `min(floor((ceil(fallDistance-1)) * perDistance), max)`, and specifically for anvils has an independent `5% + 5%×fallBlocks` chance per landing to degrade the anvil one damage stage.

### 3.15 Movement anti-desync (server reconciliation)

The server treats the client's reported position as a hint, not ground truth. `ServerGamePacketListenerImpl.handleMovePlayer` (packet `minecraft:move_player_pos`/`_pos_rot`/`_rot`/`_status_only`):

1. Reject the packet outright (disconnect) if any coordinate/rotation is NaN or non-finite.
2. Clamp reported position to `±3×10⁷` horizontally, `±2×10⁷` vertically (`clampHorizontal`/`clampVertical`) — bounds far beyond the playable world but well within double precision, preventing overflow-adjacent exploits.
3. **Speed check** (only when `PLAYER_MOVEMENT_CHECK` gamerule is on, skipped entirely for the singleplayer-integrated-server owner, and skipped for dimension-changing players): tracks `receivedMovePacketCount` vs. `knownMovePacketCount` since the last server tick to detect packet flooding (clamped to counting as `1` "tick's worth" if more than 5 arrived), then compares `movedDistSquared - expectedDistSquared` (expected = the server's own last-known velocity squared) against `100` (or `300` while elytra-flying, gated by a separate `ELYTRA_MOVEMENT_CHECK` gamerule) times the packet-count multiplier; exceeding it snaps the player back to their last good position/rotation and returns without applying any of the reported movement.
4. **Authoritative replay.** The server does **not** trust the reported destination directly — it computes the delta from its own last-good position, calls `player.move(MoverType.PLAYER, delta)` (running the *exact same* collision pipeline described in §3.2 server-side), and only then compares the *server's own resulting position* against what the client reported. If the residual mismatch exceeds `0.0625` (`0.25²`) blocks squared and the player isn't sleeping/creative/spectator/dimension-changing/in a post-impulse grace period, the move is flagged as failed.
5. A failed move is only actually rejected if the server's own `move()` call detected a real collision at the old position (`level.noCollision(player, oldAABB)` fails) **or** the new position would newly collide with something the old position didn't already overlap (`isEntityCollidingWithAnythingNew` — computed by diffing block collision shapes at the new AABB against the *old* AABB expressed as a `VoxelShape`, so a player already clipped into a block by some other means isn't punished for staying clipped) — otherwise the client's claimed exact fractional position is accepted (`absSnapTo`) even though it doesn't precisely equal the server's own recomputation, i.e. minor client-server floating-point drift within the collision envelope is tolerated and the client is treated as authoritative for the exact sub-block position as long as it's collision-consistent.
6. On acceptance: `onGround`/`horizontalCollision` flags are taken from what the *client* reported in the packet (not recomputed server-side), fall damage is checked using the *server-computed* delta, and a "floating" flag (`clientIsFloating`, used by the anti-fly-hack check elsewhere) is set based on whether the vertical delta was non-negative, ground wasn't already being stood on, and various fly/levitation/spin-attack exemptions don't apply.
7. On rejection: the player is server-side teleported back to the pre-move position (generating a position-correction packet to the client) and the just-recorded movement segment is un-recorded (`removeLatestMovementRecording`) so it doesn't pollute the inside-block effect tracking from §3.2.3.

`handleMoveVehicle` mirrors the same shape (clamp → speed-sanity-check → authoritative replay) for the boat/minecart the player is the controlling passenger of, gated on the vehicle actually still being the last vehicle the server has on record for that connection (prevents packets from targeting a vehicle the player already dismounted).

## 6. Cross-subsystem interfaces

**Consumes from:**
- **World/chunks (doc 03)** — block/fluid state lookups at every shape query, chunk-load gating for fluid-interaction scanning (`hasFluidAndLoaded`), light/height data not directly but via block state queries.
- **Game mechanics (doc 05)** — status effects (Slow Falling, Jump Boost, Dolphin's Grace, Levitation), attribute modifiers from enchantments/potions feeding every `Attributes.*` lookup above, damage sources (`damageSources().fall/inWall/explosion/flyIntoWall/...`).
- **Modding API (doc 06)** — must expose hooks equivalent to the per-entity `getBlockExplosionResistance`/`shouldBlockExplode` virtuals and custom `VoxelShape` construction for mod blocks/entities.
- **Protocol/networking (doc 02, jointly with doc 11)** — inbound movement/vehicle packets consumed by the anti-desync reconciliation in §3.15; movement/velocity is echoed back out via `set_entity_motion`/`move_entity_*`/`player_position` packets.

**Provides to:**
- **Game mechanics (doc 05)** — the physical substrate every gameplay feature that involves position, velocity, or block/entity contact builds on (redstone-triggered pistons, combat knockback, potion of levitation, riptide/loyalty tridents, etc.).
- **World/chunks** — `Entity.move` results drive chunk-section entity tracking updates (`ChunkSource.move`).
- **Cluster architecture (doc 13)** — since redstone/scheduled block ticking is strictly single-worker per region (a project-wide invariant) but entity physics is not similarly restricted, entity movement across a region/partition boundary is exactly the kind of cross-partition interaction the message substrate must carry without blocking a tick; piston/shulker pushing and explosion knockback in particular can reach across chunk (and therefore potential partition) boundaries in one call.
- **Testing/quality (doc 09)** — this is the highest-value target for differential/determinism testing given its reliance on exact floating-point operation order.

## 8. Notes for Rusty Clanker

- **Do not unify the four gravity/drag tick shapes into one function.** Item/falling-block ("subtract gravity, move, then multiply drag, with a post-hoc ground-bounce special case"), arrow ("move with stale velocity, multiply drag, then add gravity"), and living-entity ("compute horizontal input, move with stale velocity, then add gravity and multiply drag together for next tick, with per-axis drag values that differ") are three distinct, independently-evolved formulas (§3.3). A shared `apply_gravity_and_drag(entity)` ECS system that tries to parameterise all three with flags will silently diverge from vanilla the first time someone adds a fourth category (e.g. fireworks) that doesn't fit the existing three shapes. Model this as three (or more) distinct systems/components from day one, keyed by entity category, not by a generic "gravity value" field.
- **The step-up algorithm is not "step onto the highest reachable surface within maxUpStep" — it's "try every candidate surface height in ascending order and take the first one that actually improves horizontal travel distance."** This matters for parity on staircases and multi-height terrain where naively snapping to `maxUpStep` (or to the topmost collider) produces visibly different behaviour (entities floating above a step they should have partially climbed, or refusing a step a real player could take). Implement the full candidate-height enumeration from §3.2.2, not a shortcut.
- **VoxelShape boolean-op caching is state-keyed, not position-keyed.** Because vanilla block coordinates in shape space are always block-local `[0,1]³` before world placement, a `BlockState`'s collision/support/occlusion shapes are cacheable once at state-registration time for the overwhelming majority of blocks (everything not marked "dynamic"). An ECS ports of this should precompute and intern shapes per `BlockState` id at startup/data-load rather than recomputing per-query — this is a straightforward, safe, and very valuable optimisation to carry over, but it requires correctly identifying which few blocks have genuinely world-position-dependent shapes (the `dynamicShape` flag) and excluding only those from the cache.
- **The `IndexMerger` family exists purely for performance, not for correctness** — a reimplementation is free to always use the general `IndirectMerger`-equivalent (linear merge of two sorted coordinate lists) for correctness first, and only add the `DiscreteCubeMerger` fast path (both operands are regular power-of-two subdivisions, merged via `lcm`) later once profiling shows it matters. Get the semantics right before chasing the `256`-cost-heuristic optimisation.
- **Friction and speed-factor are applied at very different points in the pipeline** — friction only affects `LivingEntity`'s input-to-velocity conversion (`getFrictionInfluencedSpeed`, living entities only), while block speed-factor is applied unconditionally to *every* entity at the tail of `Entity.move()` regardless of category. A generic "block modifies movement" ECS component needs two separate hooks, not one, or non-living entities (arrows, boats, minecarts) will incorrectly pick up friction-based speed compensation that vanilla never applies to them.
- **The DDA raytrace (§3.12) epsilon-nudges both endpoints toward each other before flooring them.** Skipping this (a very easy thing to drop when reimplementing "just a standard DDA") causes off-by-one cell selection specifically for rays that travel exactly along an axis or start/end precisely on a block boundary — an easy-to-miss determinism hazard that will only manifest in specific, hard-to-reproduce edge cases (arrows fired perfectly horizontally at integer Y, etc.).
- **Server movement reconciliation trusts the client's exact fractional position whenever it's collision-consistent** (§3.15) — the server does not silently overwrite the client's claimed position with its own recomputed one on every packet, only on genuine failure. A reimplementation that always snaps to the server-authoritative position (simpler to write, and arguably "more correct") will produce visibly different rubber-banding/micro-jitter behaviour than vanilla under lag or fast-terrain movement, which is exactly the kind of "vanilla parity is bit-identical by default" deviation the project's binding principles forbid without an explicit, documented exception.
- **Explosion ray sampling is intentionally randomised per-ray** (`radius * (0.7 + random*0.6)`), meaning identical explosion parameters at different times produce different destroyed-block sets — this randomness must be seeded from the same RNG stream vanilla uses (world random, consumed in the fixed nested-loop ray order) for any deterministic replay/testing infrastructure (doc 09) to be able to assert exact block-destruction equality against a reference vanilla server capture.
- **Minecart physics has two live implementations gated by a (vanilla-default-enabled) feature flag** (`FeatureFlags.MINECART_IMPROVEMENTS`, `AbstractMinecart.useExperimentalMovement`) — `OldMinecartBehavior` vs. `NewMinecartBehavior`, with a dedicated `MinecartCollisionContext` that suppresses collision against the rail block itself and, on slopes, the block the cart is ascending/descending into. Since the pinned target version (26.2) ships this flag vanilla-enabled by default, only the "new" behavior needs implementing for parity — but the collision-context special-casing (ignoring the rail's own collision box while riding it) is a real, easy-to-miss requirement, not an artifact of legacy code that can be skipped.
- **Suffocation damage has no cooldown** — it is a flat `1.0` per tick with no invulnerability-frame-style throttling beyond the entity's normal hurt-immunity ticks (which do reduce effective frequency, but that's a game-mechanics-layer behaviour, not a physics-layer one). Any ECS "damage over time while condition holds" abstraction built for this must not assume a fixed tick-interval trigger pattern shared with, say, fire damage, which uses a different cadence.
