# Blocks & Block States — Vanilla Server Domain Map

## 1. Purpose

This domain covers everything that turns a coordinate in the voxel grid into meaningful, behaving matter: the `Block`/`BlockBehaviour` class hierarchy that defines *what a block does*, the `StateDefinition`/`Property` machinery that builds the finite set of *variants* a block can be in (a `BlockState`), the global sequential ID space vanilla uses to serialize those states on disk and over the wire, and the `BlockEntity` system that gives selected block instances mutable per-position data and per-tick behavior. It is the single largest override surface in the vanilla codebase (326 files directly in `net.minecraft.world.level.block`, plus 72 more for block entities) and almost every other server subsystem — world storage, redstone, worldgen, mobs, items — calls into it.

## 3. How it works

### 3.1 The `BlockBehaviour` virtual-method contract

`Block extends BlockBehaviour implements ItemLike`. `BlockBehaviour` (1312 lines) is the abstract base that defines the entire override surface a concrete block subclass can hook into. All hook methods are `protected` (or `public` for the handful that must be reachable from outside the package) and every one has a no-op or trivially-correct default, so a subclass overrides only what it needs. The methods fall into clear functional groups:

| Group | Methods (selected) | Purpose |
|---|---|---|
| Lifecycle / placement | `getStateForPlacement`, `canSurvive`, `setPlacedBy`, `canBeReplaced` (×2 overloads), `onPlace`, `affectNeighborsAfterRemoval`, `destroy` | Decide what state a block places as, whether it can exist at a position, and side effects when it appears/disappears |
| Update propagation | `updateShape`, `updateIndirectNeighbourShapes`, `neighborChanged`, `skipRendering` | React to a neighboring block/fluid changing; recompute this block's own state (e.g. fence connections) |
| Ticking | `tick`, `randomTick`, `animateTick`, `isRandomlyTicking` | Scheduled deterministic ticks, random per-chunk ticks, client-only particle/sound ticks |
| Interaction | `useWithoutItem`, `useItemOn`, `attack`, `triggerEvent`, `onProjectileHit`, `stepOn`, `fallOn`, `entityInside` | Right-click, left-click, block-events (e.g. note block trigger byte pair), entity contact |
| Shape / physics | `getShape`, `getCollisionShape`, `getVisualShape`, `getInteractionShape`, `getBlockSupportShape`, `getOcclusionShape`, `isCollisionShapeFullBlock`, `getEntityInsideCollisionShape` | All physical geometry queries, each returning a `VoxelShape` in the 0..1 unit cube |
| Rendering-adjacent (server still computes these for logic, not pixels) | `getRenderShape`, `useShapeForLightOcclusion`, `getLightDampening`, `propagatesSkylightDown`, `getShadeBrightness`, `emissiveRendering` | Feed the light engine and client model selection |
| Signals | `isSignalSource`, `getSignal`, `ownSignal`, `getDirectSignal`, `hasAnalogOutputSignal`, `getAnalogOutputSignal` | Redstone power surface — implementations live in redstone-family blocks, contract lives here |
| Drops / destruction | `getDrops`, `spawnAfterBreak`, `getDestroyProgress`, `getExplosionResistance` (on `Block`), `onExplosionHit`, `dropFromExplosion`, `wasExploded` | Loot-table wiring and explosion interaction |
| Misc data | `getSoundType`, `getMenuProvider`, `getFluidState`, `getCloneItemStack`, `rotate`, `mirror`, `getOffset` (random model jitter), `isPathfindable`, `getSeed` | Everything else queried per-state |

Every method that logically needs the concrete `BlockState` and world context receives both explicitly (`BlockState state, Level level, BlockPos pos, ...`); there is no implicit `this.state` — `BlockBehaviour` instances are the *shared, stateless* behavior object, one per distinct Java class-with-constructor-args, while `BlockState` instances (see 3.3) are the *per-permutation* immutable value objects. `BlockBehaviour.BlockStateBase` (an inner abstract class, extends `StateHolder<Block, BlockState>`) is the actual runtime object every `BlockState` is; it forwards essentially every public getter to `this.getBlock().<protectedMethod>(this.asState(), ...)`, so callers never call `BlockBehaviour` methods directly — they call the equivalent public method on `BlockState`, which dispatches to the block. Some derived values are computed once and memoized in a private `BlockStateBase.Cache` object built by `initCache()`: collision shape, `largeCollisionShape` flag, per-direction/per-`SupportType` sturdiness bitset, and "is full block" — this cache exists only for blocks *without* `dynamicShape()`, and is what lets `isFaceSturdy`/`isCollisionShapeFullBlock` be O(1) array lookups instead of shape recomputation on every call.

### 3.2 `BlockBehaviour.Properties` — construction-time configuration

`Properties` is a private-constructor builder (`Properties.of()`) that every `Blocks.java` entry configures fluently before the concrete `Block` subclass constructor consumes it (constructors store the *resolved* scalar fields onto `final` fields of `BlockBehaviour`, so properties are frozen at registration time). Notable fields: `hasCollision`, `explosionResistance`, `destroyTime` (`strength(time, resistance)` / `instabreak()` = `strength(0)` / `INDESTRUCTIBLE = -1.0F`), `soundType`, `lightEmission` (a `ToIntFunction<BlockState>`, so light can depend on state e.g. `LIT`/`age`), `friction` (default `0.6F`), `speedFactor`/`jumpFactor` (both default `1.0F`, honey/soul-sand-style speed blocks override), `bounceRestitution`, `pushReaction` (piston behavior enum), `isRandomlyTicking`, `dynamicShape()` (opt out of the state cache because shape depends on world context, e.g. fences), `offsetType` (`NONE`/`XZ`/`XYZ` — the random per-position model jitter used by grass, flowers, saplings), `isValidSpawn`/`isRedstoneConductor`/`isSuffocating`/`isViewBlocking` (all `StatePredicate` lambdas with sensible shape-derived defaults, overridable per block), `noOcclusion()`, `replaceable()`, `requiresCorrectToolForDrops()`, and `requiredFeatures(...)` (feature-flag gating, e.g. experimental content). `Properties.ofLegacyCopy(block)` and `ofFullCopy(block)` are how derived-shape blocks (stairs/slabs/walls built from a base block) inherit most tuning without re-specifying it — `ofFullCopy` additionally copies loot table, description id, spawn/redstone/suffocation predicates, `jumpFactor`.

### 3.3 State permutation building — `StateDefinition`, `Property<T>`, `StateHolder`

Every `Block` constructor builds a `StateDefinition.Builder<Block, BlockState>`, calls the block's overridable `createBlockStateDefinition(builder)` (default no-op; concrete blocks call `builder.add(PROP_A, PROP_B, ...)`), then `builder.create(Block::defaultBlockState, BlockState::new)`. Properties are stored in an `ImmutableSortedMap<String, Property<?>>` — **keyed and iterated by natural (alphabetical) name ordering**, not declaration order. `StateDefinition` then eagerly materializes **every legal permutation** as a concrete `BlockState` object:

- 0 properties → a single singleton state.
- 1 property → one state per possible value of that property.
- ≥2 properties → `Lists.cartesianProduct` over the property value lists, **in the alphabetical property-name order** described above (first property varies slowest/outermost, last property varies fastest/innermost) — this exact nesting order is externally observable (see 3.4/§7) and must be reproduced bit-for-bit by a reimplementation that wants matching state IDs.

Each generated `BlockState` additionally gets a **neighbor table**: for every property it holds, an array of the sibling states obtained by varying only that one property, indexed by the property's `getInternalIndex(value)`. `setValue(property, value)` is therefore not "clone and mutate" — it is `this.neighbors[propertyIndex][valueIndex]`, an O(1) array lookup into the pre-built table (`StateHolder.setValueInternal`). `cycle(property)` walks to the next value in `getPossibleValues()`, wrapping around. This is why `BlockState` objects are safely reference-comparable/interned: the full permutation set is built once at classload and never mutated afterward.

`Property<T extends Comparable<T>>` is abstract with three concrete leaf types:
- `BooleanProperty` — always exactly `[true, false]` (in that index order — note **true is index 0**, not the natural ordinal).
- `IntegerProperty.create(name, min, max)` — a contiguous inclusive `[min, max]` range, `min` must be ≥ 0, values serialize as their decimal string.
- `EnumProperty.create(name, class[, filter|explicit list])` — wraps a `StringRepresentable` enum, optionally restricted to a subset (e.g. `RAIL_SHAPE_STRAIGHT` excludes the four diagonal `RailShape` values) or reordered; string names come from `getSerializedName()`, not `name()`.

`BlockStateProperties` is the shared catalog every block pulls from instead of declaring ad hoc properties, so that e.g. `WATERLOGGED`, `FACING`, `AGE_7`, `POWER` (0–15) are single canonical `Property` instances reused by hundreds of blocks — property *equality* is by `(name, valueClass)`, so two independently-created properties with the same name/type are `.equals()` but **not** the same object, and `StateHolder.hasProperty` uses reference identity (`==`) internally for the fast path — always fetch properties from `BlockStateProperties` (or the owning block's static field) rather than recreating them. Property names must match `^[a-z0-9_]+$` and a block may not register the same property twice or a property with ≤1 possible values (validated in `StateDefinition.Builder.add`, throws otherwise).

### 3.4 Block-state IDs and the `blocks.json` mapping

Vanilla assigns every `BlockState` in existence a single flat, global, sequential integer ID shared across all blocks (not per-block-type-relative). Mechanism, exactly:

1. `Blocks.java` runs its ~1200 `public static final Block X = register(...)` field initializers top-to-bottom; `register` calls `Registry.register(BuiltInRegistries.BLOCK, id, block)`, which assigns each *block* a registry-order integer (this is a separate, smaller ID space used for e.g. protocol block-type ids, not the block-state id space).
2. After every field is initialized, `Blocks.java` runs one `static { }` block that iterates `BuiltInRegistries.BLOCK` **in block-registration order**, and for each block iterates `block.getStateDefinition().getPossibleStates()` **in the StateDefinition permutation order described in 3.3**, calling `Block.BLOCK_STATE_REGISTRY.add(state)` (an `IdMapper<BlockState>`) for each. `IdMapper.add` assigns `nextId++` — a plain monotonic counter starting at 0 — then `state.initCache()` runs (builds the shape/sturdiness cache described in 3.1).
3. The result: block-state ID = "how many states, across all blocks in registration order, come strictly before this one." `Block.getId(state)` / `Block.stateById(id)` are the two static accessors; `stateById` falls back to `Blocks.AIR.defaultBlockState()` for an unmapped/invalid id. This is the ID space used to serialize block states into the wire protocol (chunk data packets) and effectively defines the palette space chunk sections index into.

`datagen/generated/reports/blocks.json` is the generator-produced ground truth for this exact mapping (see §7): per block it lists `definition` (the `BlockTypes` codec name plus any construction parameters, e.g. `oak_door` → `{"type":"minecraft:door","block_set_type":"oak"}`), `properties` (property name → **alphabetically-ordered** value list), and `states[]` — each with its global `id` and its `properties` map, with exactly one entry flagged `"default": true`. For the current pin (26.2) there are **1196 distinct registered blocks** and **32366 total block states** (highest observed id `32365`); `oak_door` alone occupies ids `5655..5718` (5 properties × 2/2/2/2/2 boolean-ish + a 4-valued facing = 4×2×2×2×2 = 64 states), with `facing` (alphabetically first) as the outermost/slowest-varying axis and `powered` (alphabetically last) as the innermost/fastest-varying axis inside `states[]` — direct, load-bearing confirmation of the ordering rule in 3.3.

### 3.5 Block registration flow

`Blocks.java` (5875 lines) is a flat list of `public static final Block NAME = register(id, [factory,] properties)` calls; there is no dynamic/data-driven block registration in vanilla proper (a `BlockTypes` codec registry exists for serialization dispatch, see below, but the *set* of blocks is fixed Java code). Four `register` overloads (private, at the bottom of the file):

- `register(BlockItemId id, Function<Properties,Block> factory, Properties properties)` — the general form; resolves `id` to a `ResourceKey<Block>` then delegates.
- `register(ResourceKey<Block> id, Function<Properties,Block> factory, Properties properties)` — the actual worker: `properties.setId(id)` (properties need their owning id for default loot-table/description-id derivation), `factory.apply(properties)` constructs the block, `Registry.register(BuiltInRegistries.BLOCK, id, block)` inserts it.
- `register(BlockItemId id, Properties properties)` — convenience for plain `Block::new`.
- `registerStair/registerSlab/registerWall(id, baseBlock)` — the derived-shape helpers that copy the base block's `Properties` (`ofFullCopy`/`ofLegacyCopy`) and construct `StairBlock`/`SlabBlock`/`WallBlock` around it; `registerWall` additionally forces `forceSolidOn()` since a wall's *shape* isn't a full cube but it must still count as `isSolid()` for e.g. mob spawning/redstone.

`BlockTypes.java` is a parallel, separate registry (`BuiltInRegistries.BLOCK_TYPE`, a `MapCodec<? extends Block>` per named "type" string like `"door"`, `"amethyst_cluster"`, `"multiface"`) used purely for (de)serialization dispatch (`BlockTypes.CODEC = BLOCK_TYPE.byNameCodec().dispatchMap(Block::codec, identity())`) — this is what lets `blocks.json`'s `definition.type` field exist and is the mechanism the `minecraft:block_type` datapack registry (see §7) exposes. It is not itself a source of new blocks; every concrete `Block` subclass exposes a `MapCodec<? extends X>` via its abstract `codec()` override, almost always built with the `BlockBehaviour.simpleCodec(ctor)` helper for parameterless constructors or a hand-written `RecordCodecBuilder` for blocks that take extra construction data (e.g. `DoorBlock` takes a `BlockSetType`, `LiquidBlock` takes a `FlowingFluid`, `SulfurSpikeBlock` takes the block it grows on).

### 3.6 Placement and update propagation (setBlock → onPlace → neighborChanged/updateShape)

`Level.setBlock(pos, state, updateFlags[, updateLimit])` is the single entry point for changing a block anywhere in the world (also used by `removeBlock`/`destroyBlock`/`setBlockAndUpdate`). `updateFlags` is a bitmask (`Block.UPDATE_*` constants, see §5) rather than a boolean soup, letting callers suppress client sync, neighbor updates, block-entity side effects, or the recursive shape-update fan-out independently. Sequence:

1. `LevelChunk.setBlockState` writes the new state into the `LevelChunkSection`'s palette storage, updates all four heightmaps incrementally, flips chunk light-source/empty-section bookkeeping if light-relevant properties changed, and — if the block *type* changed and the old state carried a block entity that the new state doesn't want to keep (`shouldChangedStateKeepBlockEntity`) — removes the old block entity (`preRemoveSideEffects` runs first, which for `Container` block entities spills inventory contents).
2. If the block type changed (or it's a rail — special-cased for legacy connectivity reasons) and `UPDATE_NEIGHBORS` is set, `oldState.affectNeighborsAfterRemoval(serverLevel, pos, movedByPiston)` fires (default no-op; used by e.g. sculk catalyst spawn-experience-on-break-adjacent-logic and copper golem's analog-signal recompute).
3. Unless `UPDATE_SKIP_ON_PLACE` is set, `state.onPlace(level, pos, oldState, movedByPiston)` fires.
4. If the new state wants a block entity (`state.hasBlockEntity()`, i.e. `Block instanceof EntityBlock`) and none valid already exists at the position, `((EntityBlock)newBlock).newBlockEntity(pos, state)` constructs one and it's registered into the chunk; if a compatible one already exists, its cached `BlockState` reference is refreshed and its ticker is re-resolved (state changes can change which `BlockEntityTicker` applies, e.g. a furnace's lit/unlit state does not, but a potent-sulfur block's `PotentSulfurState` does — see 3.15).
5. Back in `Level.setBlock`: if `UPDATE_NEIGHBORS` was requested, `updateNeighborsAt` fires (`Block.neighborChanged` on the 6 orthogonal neighbors — the redstone/general "something adjacent changed" notification), and if `updateLimit > 0` and `UPDATE_KNOWN_SHAPE` wasn't set, both the **old** and **new** state get `updateIndirectNeighbourShapes` + `updateNeighbourShapes` calls, which walk the neighbors in the fixed order `WEST, EAST, NORTH, SOUTH, DOWN, UP` (`BlockBehaviour.UPDATE_SHAPE_ORDER`, deterministic — order matters for e.g. fence/wall connection results) and invoke each neighbor's `updateShape(level, ticks, neighborPos, directionBackToUs, ourPos, ourNewState, random)`. `updateShape`'s contract: return the state this neighbor block *should become* given what just happened next to it (or `Blocks.AIR.defaultBlockState()` to self-destruct, e.g. a torch losing its supporting wall, a door half losing its other half) — `Block.updateOrDestroy` is what actually applies that returned state (destroying via `level.destroyBlock` if air, otherwise `level.setBlock`), and `updateLimit` decrements on each recursive hop to bound runaway propagation chains (default budget 512, `Block.UPDATE_LIMIT`).
6. `Block.pushEntitiesUp` and the whole `updateOrDestroy`/`updateFromNeighbourShapes` static-helper family exist because some callers (world generation post-processing, structure placement) want to run the *same* shape-reconciliation pass without going through the full `setBlock` event pipeline.

This is the mechanism that gives fences, walls, glass panes, iron bars, redstone wire, and every other "look at my neighbors and pick a shape" block their connectivity — and it is the same mechanism doors, piston heads, and multi-part blocks use to keep their two halves in sync or self-destruct when support is removed.

### 3.7 Tick pipeline: scheduled ticks vs. random ticks

Two independent, unrelated tick mechanisms exist per block state, both server-only:

- **Scheduled ticks** (`BlockState.tick` → `Block.tick`) are explicitly queued via `ScheduledTickAccess.scheduleTick(pos, block, delay)` (e.g. redstone dust, repeaters, falling sand, liquids scheduling their own next flow step, a waterlogged block re-checking on `updateShape`) and fire exactly `delay` ticks later at fixed order per position — this is the deterministic, "I asked to be ticked" path. Ownership/queueing details belong to the world/chunk persistence document (`03-world-chunks-persistence.md`, `ScheduledTickAccess`/`LevelChunkTicks`).
- **Random ticks** (`BlockState.randomTick` → `Block.randomTick`) are the "ambient, statistically-driven" path: `ServerLevel.tickChunk(chunk, tickSpeed)` runs once per loaded, block-ticking-eligible chunk per server tick. `tickSpeed` is the live value of the `random_tick_speed` game rule (`GameRules.RANDOM_TICK_SPEED`, **default `3`**, min `0`). For **each loaded `LevelChunkSection`** in the chunk, the loop only enters if `section.isRandomlyTicking()` — a cheap O(1) check backed by a `short tickingBlockCount`/`short tickingFluidCount` pair that the section increments/decrements incrementally on every single `setBlockState` call (comparing the leaving and entering state/fluid's `isRandomlyTicking()`), never by scanning the section. If eligible, the section runs `tickSpeed` iterations, each picking one uniformly-random `(x,y,z)` inside the 16×16×16 section via `Level.getBlockRandomPos` and only *then* checking `blockState.isRandomlyTicking()`/`fluidState.isRandomlyTicking()` before invoking the tick — so a section with e.g. one grass block among 4095 stone blocks still spends its `tickSpeed` random draws mostly missing, exactly reproducing vanilla's statistical growth/spread rates is inseparable from reproducing this "uniform random position in a *possibly-mostly-irrelevant* section, `tickSpeed` times, memoryless" draw pattern. `isRandomlyTicking()` on a `BlockState` itself can be state-dependent (`Properties.randomTicks()` sets a fixed default, but e.g. `CropBlock.isRandomlyTicking` overrides it to return `false` once `isMaxAge`, so fully-grown crops stop costing random-tick draws).
- Block **entity** ticking is a third, separate mechanism (3.8) driven by a flat per-`Level` ticker list, unrelated to random ticks and unconditional on `random_tick_speed`.

All three are strictly single-threaded per world/region in vanilla — there is no per-chunk or per-block parallelism anywhere in this pipeline.

### 3.8 Block entities: hierarchy, type registry, per-chunk ticker wiring

`BlockEntity` (abstract) is *not* subordinate to `Block`/`BlockState` inheritance-wise — it's a separate object graph, one instance per world position, that a `Block` opts into by implementing the `EntityBlock` interface (`newBlockEntity(pos, state)` factory + optional `getTicker(level, state, type)`). `BaseEntityBlock extends Block implements EntityBlock` is the common base almost every block-entity-bearing block uses; it also provides the `createTickerHelper(actual, expected, ticker)` idiom every `getTicker` override uses to type-safely return `null` unless `actual == expected` (guards against a shared `BlockEntityType` — e.g. `CHEST` covers both `Blocks.CHEST` and `Blocks.COPPER_CHEST` — accidentally reusing a ticker meant for a different concrete block-entity subtype).

`BlockEntityType<T>` wraps a `BlockEntitySupplier<T>` factory plus a `Set<Block>` of every block that may legally host this type (`isValid(state)` = `validBlocks.contains(state.getBlock())`); `BlockEntity.isValidBlockState` is checked in the constructor and throws if violated. `BlockEntityTypes.java` is the flat registration list (49 registered types for 26.2, confirmed against `registries.json`), each a `register(id, factory, Block... validBlocks)` call — note several types accept multiple otherwise-unrelated blocks (`SIGN` covers all ~26 wood-type standing+wall sign variants; `CHEST` covers vanilla chest and the new `COPPER_CHEST`), sharing one behavior implementation across a whole family.

Ticker wiring is entirely per-chunk, driven from `LevelChunk`:
1. On block-entity creation/reload/state-change, `LevelChunk.updateBlockEntityTicker(blockEntity)` calls `state.getTicker(level, blockEntityType)`. If `null`, any existing ticker registration for that position is torn down; otherwise a `RebindableTickingBlockEntityWrapper` is created (or an existing one is `rebind()`-ed in place, so a chunk-load reference already handed to `Level` stays valid across a rebind) and — only if the chunk is actually "in level" — `Level.addBlockEntityTicker(wrapper)` appends it to a flat `List<TickingBlockEntity>` on the `Level` (`blockEntityTickers`, with a `pendingBlockEntityTickers` staging list to avoid concurrent-modification while a tick is in progress).
2. `Level.tickBlockEntities()` iterates that flat list once per server tick, calling `.tick()` on each; each wrapper re-checks `blockEntity.isRemoved()`, `hasLevel()`, `chunk.isTicking(pos)` (chunk full-status gate), and that the live `BlockState` at the position still matches the entity's registered type before delegating to the actual `BlockEntityTicker<T>.tick(level, pos, state, entity)` lambda the block supplied.
3. This is a single flat list across the whole level/dimension — not partitioned per chunk or per region for iteration — so block-entity ticking, like random ticking, is inherently sequential per world in vanilla.

Block entities persist their own NBT via `saveAdditional`/`loadAdditional` (subclass-overridable) plus a generic `DataComponentMap` "components" bag (`components`/`applyComponents`/`collectImplicitComponents` — the same data-component system items use, letting a block entity's data be partially represented as item components when the block is mined with `preserveState`-style tools, e.g. a shulker box's contents surviving a pickaxe break).

### 3.9 Doors

`DoorBlock` (not abstract — parametrized by a `BlockSetType`, see 3.19) is the canonical two-tall, multi-part, redstone-openable block. 5 properties: `FACING` (4-way horizontal), `HALF` (`UPPER`/`LOWER`), `HINGE` (`LEFT`/`RIGHT`), `OPEN`, `POWERED`. Placement (`getStateForPlacement`) requires the block above the click position to be replaceable; the lower half is placed with `HINGE` resolved by `getHinge(context)`, a solid-block-adjacency heuristic (counts solid blocks diagonally-left vs diagonally-right of the placement point, tie-broken by exact click-position sub-pixel) that reproduces vanilla's "door swings away from the wall it's set into" convention — then `setPlacedBy` places the paired upper half directly (`level.setBlockAndUpdate(pos.above(), state.setValue(HALF, UPPER))`), *not* through the normal item-placement path. `updateShape` enforces the two-half pairing: if the *other* half of the same door still exists in the expected relative position, propagate `HALF`; otherwise the whole door (both halves, via cascading `updateShape` calls) turns to air. Redstone: `neighborChanged` recomputes `hasNeighborSignal` at both the door's own position and its vertical pair position (either half can be powered and both must react identically) and keeps `OPEN == POWERED` when a signal is present, while direct hand-interaction (`useWithoutItem`, gated by `type.canOpenByHand()`) simply cycles `OPEN` and does not touch `POWERED` (so hand-opening a door a redstone circuit considers "closed" is possible and is exactly vanilla's known door-desync-with-redstone behavior). Wind-charge explosions can toggle unpowered doors (`onExplosionHit`, gated by `type.canOpenByWindCharge()`).

### 3.10 Pistons

`PistonBaseBlock` (regular/sticky share one class, `isSticky` constructor flag) has 2 properties (`FACING`, `EXTENDED`) and constant `PLATFORM_THICKNESS = 4` (the extended piston-arm collision-shape thickness, in 1/16ths). *When and whether* a piston fires is entirely a redstone-power question — owned by doc 08 — but the **movement mechanics** themselves are a pure block-state concern and live here: `PistonStructureResolver` walks outward from the piston in the push direction, building a `toPush` list capped at **12 blocks** (`blockCount + toPush.size() > 12` aborts the push entirely for that whole structure — vanilla's hard-coded max-push-length) and a `toDestroy` list for anything unpushable-but-non-solid in the way (fully solid, non-block-entity-bearing, `PushReaction != BLOCK` positions are destroyed rather than blocking the push); sticky pistons additionally trace attached blocks perpendicular to the push axis via `PushReaction.NORMAL` block adjacency to build the "pulled along" set on retraction. During an active extension/retraction, affected block positions are temporarily replaced with `MovingPistonBlock` (a thin `Block` wrapper whose *actual* rendering/collision come from a `PistonMovingBlockEntity` that interpolates a `progress` field every client/server tick and, on completion, swaps itself back to the real stored `BlockState` and removes the temporary block entity) — this "temporary block entity carries the animation, then commits the final `BlockState` in one atomic `setBlock`" pattern is unique to pistons among vanilla blocks and is the mechanism that lets entities be smoothly pushed without ever seeing a jump-discontinuous collision shape mid-tick.

### 3.11 Crops & growth (`VegetationBlock`/`CropBlock`/`BonemealableBlock`)

`CropBlock extends VegetationBlock implements BonemealableBlock`, single `AGE` property (`AGE_7`, i.e. `0..7`, `MAX_AGE = 7`), one `VoxelShape` per age precomputed via `Block.boxes(7, age -> Block.column(16, 0, 2 + age*2))` (linearly taller per age). `mayPlaceOn` requires `BlockTags.SUPPORTS_CROPS` (farmland) below; `canSurvive` additionally requires `hasSufficientLight` (**raw sky+block brightness ≥ 8**, checked at light-level index 0). `isRandomlyTicking` is overridden to return `false` once `isMaxAge`, so mature crops stop costing random-tick draws entirely (see 3.7). The growth algorithm (`randomTick`, fires only if raw brightness ≥ 9, one level higher than the survive-threshold): with probability `1 / (floor(25/growthSpeed) + 1)` advance `AGE` by exactly 1 via `level.setBlock(pos, ..., 2)` (update flag 2 = client-sync only, no neighbor-update fan-out — crop growth does not trigger `neighborChanged` on adjacent blocks). `growthSpeed` (`getGrowthSpeed`, static, shared by all `CropBlock`s and used for stem/gourd growth too) starts at `1.0F` and, for each of the 8 horizontal neighbors of the block *below* the crop (3×3 minus center), adds `1.0F` if that neighbor is tagged `BlockTags.GROWS_CROPS` (`3.0F` instead if it's farmland with `MOISTURE > 0`), halved (`/4`) for the 4 diagonal neighbors — then applies a **crowding penalty**: if crops of the *same block type* exist both horizontally (west/east) and vertically (north/south) adjacent to this one, or diagonally on both relevant sides, the accumulated speed is halved again. Bonemeal (`performBonemeal`) jumps age by a uniform-random `2..5` (`getBonemealAgeIncrease`), clamped to `MAX_AGE`. `entityInside` special-cases `Ravager` (with `mob_griefing` on) trampling the crop to nothing via `destroyBlock`. `GrowingPlantHeadBlock`/`GrowingPlantBodyBlock` (kelp, cactus-adjacent vine-style growth, bamboo) and `StemBlock`/`AttachedStemBlock` (melon/pumpkin) are structurally parallel but separate class families, not `CropBlock` subclasses.

### 3.12 Bells

`BellBlock extends BaseEntityBlock`, 3 properties: `FACING`, `ATTACHMENT` (`FLOOR`/`CEILING`/`SINGLE_WALL`/`DOUBLE_WALL`), `POWERED`. Placement tries, in order: ceiling/floor (vertical click face), single-wall (horizontal click face, checked against `canSurvive`), then falls back to floor or ceiling depending on what's structurally available — `DOUBLE_WALL` is auto-upgraded from `SINGLE_WALL` post-placement (`updateShape`) if a second horizontal support becomes sturdy on the opposite side, and downgraded back if it's removed. Ringing (`attemptToRing`) requires a "proper hit" — `isProperHit` checks the click direction's axis against `FACING`'s axis (must match for floor mounts, must differ for wall mounts, any axis works for ceiling) plus a `clickY > 0.8124` cutoff near the top face that always fails — and delegates the actual chime animation/redstone-power-detection window entirely to `BellBlockEntity` (event byte `EVENT_BELL_RING = 1`, dispatched via the generic `triggerEvent`/block-event mechanism, same channel note blocks and chests use for client-visible pulses). `neighborChanged` auto-rings on a redstone signal rising edge. Bells are **not** pathfindable (`isPathfindable` hard-`false`) despite having no collision box on most faces.

### 3.13 Sculk family

A shared `SculkBehaviour` interface (default `DEFAULT` instance) parametrizes how the *sculk vein* spreading mechanism interacts with a candidate destination block — implementers are `SculkBlock` itself and every sculk sensor/catalyst/shrieker variant, each tuning `getSculkSpreadDelay()`, `depositCharge`, `attemptUseCharge`, `updateDecayDelay`, `canChangeBlockStateOnSpread`. The generic spreading engine is `SculkSpreader` + its inner `ChargeCursor`: each catalyst/spread event creates cursors (capped at `MAX_CURSORS = 32` concurrently) that carry a decrementing `charge` (max `MAX_CHARGE = 1000`), a `decayDelay`, and a `MAX_GROWTH_RATE_RADIUS = 24`/`MAX_CURSOR_DISTANCE = 1024` search envelope; cursors randomly hop through `NON_CORNER_NEIGHBOURS` positions, converting eligible neighbor blocks toward `Blocks.SCULK` (via `SculkBehaviour.attemptSpreadVein`, which special-cases growing a `SculkVeinBlock` "skin" over non-air/non-water-incompatible neighbors versus converting the block itself) and losing charge as they go, until exhausted. `SculkCatalystBlock` (single `PULSE`/`BLOOM` boolean property) is the entity-death trigger: on a nearby mob death event it "blooms" (`PULSE = true`, briefly), spawns `SculkCatalystBlockEntity`-managed cursors seeded with charge proportional to the XP the death would have dropped, and awards the killer `xpRange = ConstantInt.of(5)` XP directly for the catalyst activation itself. `SculkSensorBlock`/`CalibratedSculkSensorBlock` and `SculkShriekerBlock` consume the vibration/game-event system (owned elsewhere) to trigger, but their **block-state** surface (`SculkSensorPhase` — `INACTIVE`/`ACTIVE`/`COOLDOWN`, `POWER` 0–15, `WATERLOGGED`) is defined here. `SculkVeinBlock` and `GlowLichenBlock` are the two vanilla `MultifaceSpreadeableBlock` implementations — see 3.16 for the shared multi-face mechanism both build on; `SculkVeinBlock` additionally implements `SculkBehaviour` itself so it can regrow after being locally destroyed by sculk-vein-hostile effects.

### 3.14 Copper family, including oxidation

Copper's weathering ("oxidation") is a generic, reusable mechanism, not copper-specific code: `ChangeOverTimeBlock<T extends Enum<T>>` is the interface (`getAge()`, `getNext(state)`, `getChanceModifier()`), and `changeOverTime(state, level, pos, random)` — called from each implementer's `randomTick` — rolls a flat **`5.688889%`** per-tick chance (`eachBlockOncePerDayChance`, a constant tuned so a block ticks roughly once per vanilla in-game day at default random-tick-speed) to attempt `getNextState`. `getNextState` scans every position within **Manhattan distance 4** (`ChangeOverTimeBlock.SCAN_DISTANCE = 4`) for other blocks sharing the *same* `ChangeOverTimeBlock` enum type, counting how many are strictly younger (`olderCount` from this block's perspective is actually "found an *older* neighbor" — read the field name literally, it counts weathering-neighbors that are further along) vs. same-age; if **any** neighbor is *less* weathered, the attempt aborts outright (a block cannot advance past its least-weathered neighbor in one step... more precisely: any strictly-younger neighbor blocks advancement entirely for this tick), otherwise `chance = (older+1)/(older+same+1)`, squared, times `getChanceModifier()` (copper: `0.75` from `UNAFFECTED`, `1.0` otherwise — makes the very first oxidation step from freshly-placed copper slightly rarer than subsequent steps) gates the actual transition to `getNext(state)`. `WeatheringCopper` is the copper-specific glue: a `WeatherState` enum (`UNAFFECTED → EXPOSED → WEATHERED → OXIDIZED`) and a lazily-built `BiMap<Block,Block>` (`NEXT_BY_BLOCK`/`PREVIOUS_BY_BLOCK`) covering **every** shaped copper variant in one place — `COPPER_BLOCK`, `CUT_COPPER` (+slab/stairs), `CHISELED_COPPER`, `COPPER_DOOR`, `COPPER_TRAPDOOR`, `COPPER_BARS`, `COPPER_GRATE`, `COPPER_BULB`, `COPPER_LANTERN`, `COPPER_CHEST`, `COPPER_GOLEM_STATUE`, `LIGHTNING_ROD`, `COPPER_CHAIN` — so a `withPropertiesOf`-preserving `getNext`/`getPrevious` step (used by both natural weathering *and* the axe-scrape/honeycomb-wax interactions, owned by the item-interaction side) works uniformly across every shaped variant without per-shape special-casing. Each shape has its own `WeatheringXxxBlock` wrapper class (`WeatheringCopperFullBlock`, `WeatheringCopperStairBlock`, `WeatheringCopperDoorBlock`, `WeatheringCopperBulbBlock`, `WeatheringCopperChestBlock`, `WeatheringCopperGolemStatueBlock`, etc.) that mixes the shape-specific `Block` subclass with `implements WeatheringCopper`.

### 3.15 26.2-era additions found in this domain

- **Potent Sulfur / geyser family** (new): `PotentSulfurBlock extends BaseEntityBlock`, single `EnumProperty<PotentSulfurState>` (`DRY`/`WET`/`DORMANT`/`ERUPTING`/`CONTINUOUS`). State is entirely derived from world context, not player choice: `validBlockState` checks for a water source directly above (else `DRY`); if wet, checks the block *below* for `BlockTags.CAUSES_CONTINUOUS_GEYSER_ERUPTIONS` / `CAUSES_PERIODIC_GEYSER_ERUPTIONS` tags (volcanic-terrain blocks) to decide `CONTINUOUS`/`DORMANT`→`ERUPTING` cycling, otherwise plain `WET`. `PotentSulfurBlockEntity` drives the actual eruption: constants `EFFECT_APPLICATION_FREQUENCY_TICKS = 10`, `EFFECT_DURATION_IN_TICKS = 80` (4.0s), `EFFECT_RANGE = 3.0F` (a nausea-style status effect applied to nearby entities while erupting/wet, `EFFECT_PREDICATE` excludes spectators/dead entities), `PARTICLE_FREQUENCY_TICKS = 20`, `SOUND_FREQUENCY_TICKS = 40`, `GEYSER_BASE_LAUNCH_SPEED = 0.3F`/`GEYSER_LAUNCH_FORCE = 0.2F` (entity-launching physics while `ERUPTING`/`CONTINUOUS`). `getTicker` dispatches to a *different* `BlockEntityTicker` per `PotentSulfurState` value *and* per client/server side — a five-state × two-side ticker-selection matrix entirely driven by the state enum, the most granular example of state-conditional ticker dispatch in the codebase. `SulfurSpikeBlock extends SpeleothemBlock` (`MAX_GROWING_LENGTH = 2`) — `SpeleothemBlock` is a new **shared abstract base** generalizing the growing-stalactite/stalagmite mechanic that `PointedDripstoneBlock` also now extends, so dripstone-style growth logic is no longer dripstone-specific.
- **Copper Golem Statue** (new): `CopperGolemStatueBlock extends BaseEntityBlock implements SimpleWaterloggedBlock` and also `implements WeatheringCopper`-family via its `WeatheringXxx` wrapper — one Java class parametrized by `WeatheringCopper.WeatherState` at construction (like stairs/slabs, one `Block` instance per oxidation stage rather than an in-state property) plus `FACING` (horizontal) and a `POSE` enum (`STANDING → SITTING → RUNNING → STAR`, cycled by right-click with an axe-exempt `useItemOn`) and `WATERLOGGED`. Exposes an analog redstone signal equal to `POSE.ordinal() + 1` — a block-as-4-position-dial pattern.
- **Sulfur Cube — not a block.** The datagen tree contains a `data/minecraft/sulfur_cube_archetype/` folder (`bouncy`, `explosive`, `fast_flat`, `fast_sliding`, `high_resistance`, `hot`, `light`, `regular`, `slow_bouncy`, `slow_flat`, `slow_sliding`, `sticky` — 12 archetypes) defining **entity** attribute-modifier sets (knockback resistance, bounciness, friction/air-drag modifiers, hit/push sounds) for what is a Slime-like mob variant system, unrelated to `net.minecraft.world.level.block`. It shares the volcanic/sulfur theme with 3.15's Potent Sulfur block family but belongs to the entity/mob domain, not this one.
- **Shelf** (new, simple): `ShelfBlock`/`ShelfBlockEntity` — a small item-display block entity family, structurally unremarkable relative to the rest of this document (container-adjacent, not covered further here).

### 3.16 Multiface blocks (glow lichen, sculk vein, and the shared bitfield pattern)

`MultifaceBlock` (base) / `MultifaceSpreadeableBlock` (adds autonomous spreading via `MultifaceSpreader`) is the generic "this block can independently occupy any subset of the 6 faces of its position" mechanism, reused by `GlowLichenBlock` and `SculkVeinBlock`. Rather than one enum property, it reuses `PipeBlock.PROPERTY_BY_DIRECTION` — six independent `BooleanProperty` instances, one named per `Direction` (`up`/`down`/`north`/`east`/`south`/`west`) — plus `WATERLOGGED`, giving `2^6 × 2 = 128` theoretical permutations per multiface block (fewer in practice, a state with zero faces set is invalid/unreachable). `hasFace(state, direction)` reads the relevant boolean; shapes are precomputed per-direction as thin `1/16`-thick slabs against each face and unioned per state (falling back to a full cube if somehow no face is set, defensive). `canRotate`/`canMirrorX`/`canMirrorZ` are derived once at construction by checking whether the block's *supported* face set (not every block using this base supports every direction — e.g. wall-only variants) is itself rotation/mirror-symmetric. `MultifaceSpreader` (generic engine, `MultifaceSpreadeableBlock.getSpreader()`/`SculkBehaviour`'s vein-specific override) implements the actual random-walk "try to grow onto more faces of me or my neighbors" logic that both glow lichen's natural bonemeal-assisted spread and sculk vein's catalyst-driven spread share.

### 3.17 Fluid interaction points

Blocks touch the fluid system (owned by the world/materials domain, `03-world-chunks-persistence.md`) through a small set of interfaces defined in this package:

- **`LiquidBlockContainer`** — `canPlaceLiquid`/`placeLiquid`: implemented by any block that can *host* a fluid inside itself without being replaced (waterlogged shapes, cauldrons via their own subclass logic).
- **`BucketPickup`** — `pickupBlock`/`getPickupSound`: implemented by anything a bucket can scoop (source fluid blocks themselves via `LiquidBlock implements BucketPickup`, and any waterlogged block).
- **`SimpleWaterloggedBlock extends BucketPickup, LiquidBlockContainer`** — the default-method convenience almost every waterloggable non-fluid block (stairs, slabs, fences, doors, bells, multiface blocks, copper golem statue, etc.) implements as-is: `canPlaceLiquid` accepts only `Fluids.WATER`; `placeLiquid` sets `WATERLOGGED = true` and self-schedules a fluid tick; `pickupBlock` clears `WATERLOGGED`, destroys the block outright if it can no longer `canSurvive` without the water, and returns a `WATER_BUCKET` item stack.
- **`LiquidBlock`** (water/lava source-and-flow block itself) holds a `FlowingFluid` reference and a `BlockStateProperties.LEVEL` property; `POSSIBLE_FLOW_DIRECTIONS` fixes flow-neighbor check order (`DOWN, SOUTH, NORTH, EAST, WEST` — down is always checked first, matching vanilla's "fluids prefer falling" rule) and `BUBBLE_COLUMN_CHECK_DELAY = 20` gates how often a `LiquidBlock` re-evaluates whether it should spawn/maintain a bubble column beneath a soul-sand-or-magma source.

Detailed flow-spread algorithms, source/flowing distinction, and `FluidState` itself belong to the fluids/materials write-up, not this document — only the block-facing contract points above live here.

### 3.18 `SupportType` and placement/survival rules

`SupportType` is a 3-value enum (`FULL`, `CENTER`, `RIGID`), each an independent face-sturdiness predicate over a neighboring block's *support shape* (`getBlockSupportShape`, defaults to the collision shape) intersected against a reference shape: `FULL` requires the whole face to be solid (`Block.isFaceFull`); `CENTER` requires only a small 2×2 (in 16ths) center column to be covered (used for e.g. bell/lantern-style "hangs from a point" attachments and — with the `UNSTABLE_BOTTOM_CENTER` tag short-circuit in `Block.canSupportCenter` — things like fences refusing to hang from certain thin blocks below); `RIGID` requires a 12×12 (in 16ths) inset column, the middle ground used by e.g. redstone-adjacent placement checks. These three predicates, plus the block-entity-cached `Cache.faceSturdy` bitset (3.1), are the whole vocabulary vanilla uses to answer "can X be placed against/on top of/hanging from Y" — individual blocks then compose them in `canSurvive`/`getStateForPlacement` (bell in 3.12 uses `CENTER` for ceiling and the generic `FaceAttachedHorizontalDirectionalBlock.canAttach` helper for walls; doors/crops use plain `FULL`).

### 3.19 Block tags in behavior, and cross-cutting config records

249 distinct `TagKey<Block>` constants exist in `BlockTags` and are used pervasively as the *extension point* for "which blocks count as X for this behavior" without hard-coding block lists into individual `Block` subclasses — examples seen throughout this document: `SUPPORTS_CROPS`/`GROWS_CROPS` (farmland detection for crop placement/growth), `UNSTABLE_BOTTOM_CENTER` (center-support exclusion), `GUARDED_BY_PIGLINS`/`SHULKER_BOXES` (`Block.isExceptionForConnection`), `CAUSES_CONTINUOUS_GEYSER_ERUPTIONS`/`CAUSES_PERIODIC_GEYSER_ERUPTIONS` (potent sulfur), `COPPER_GOLEM_STATUES` (block-entity-preservation check on state change). Separately, two **shared configuration record types** parametrize whole block *families* by construction argument rather than by subclassing per-material: `BlockSetType` (name, `canOpenByHand`, `canOpenByWindCharge`, `canButtonBeActivatedByArrows`, pressure-plate sensitivity, `SoundType`, and 8 distinct `SoundEvent`s covering doors/trapdoors/pressure-plates/buttons) drives every door/trapdoor/button/pressure-plate/fence-gate variant (wood, iron, copper), and `WoodType` plays the analogous role for sign/hanging-sign/fence-gate wood-specific data. A reimplementation should mirror this "behavior class × config record → many block instances" shape rather than generating one Rust type per wood/metal variant.

## 6. Cross-subsystem interfaces

**Consumes from:**
- **World/chunks (doc 03):** `LevelChunk`/`LevelChunkSection` host the actual palette storage `setBlockState` writes into, own heightmap/light-source bookkeeping, and own `ScheduledTickAccess` for scheduled ticks; `BlockEntity` NBT (de)serialization rides the chunk's `ValueInput`/`ValueOutput` (`TagValueInput`/`TagValueOutput`) machinery.
- **Worldgen (doc 04):** `TreeGrower` and sapling/stem growth link block behavior to `ConfiguredFeature`/`TreeConfiguration` placement; initial chunk generation writes `BlockState`s directly without going through the full `Level.setBlock` event pipeline.
- **Redstone/mechanics (doc 08 → `05-game-mechanics.md`):** all `neighborChanged`/signal (`getSignal`/`ownSignal`/analog output) contract points defined here are *implemented* by redstone-family blocks living in the same Java package but owned by that document; piston *triggering* (when to extend/retract) is redstone-owned even though piston *movement mechanics* (3.10) are owned here.
- **Items (doc 06 modding-API-adjacent item behavior, or wherever item interaction lives):** `BlockItem` is the item-side counterpart that calls into `getStateForPlacement`/`canBeReplaced`/`setPlacedBy`; tool/enchantment interaction feeds `getDestroyProgress`/`requiresCorrectToolForDrops`.
- **Fluids/materials:** `FluidState`, `Fluid`, `FlowingFluid` are consumed via `getFluidState`, `LiquidBlockContainer`, `BucketPickup` (3.17) but owned elsewhere.
- **Loot tables/storage:** `getDrops` resolves through `ServerLevel.getServer().reloadableRegistries().getLootTable(key)`; default loot-table key is derived from the block's registry id (`blocks/<id>` path) unless overridden.

**Provides to:**
- **Networking/protocol (doc 02):** the global block-state ID space (3.4) is exactly what chunk-data and block-update packets serialize; `Block.getId`/`Block.stateById` are the wire<->state boundary.
- **World storage:** `BlockState` NBT (de)serialization (`StateHolder.codec`, dispatch-by-name-then-properties) is what Anvil region files persist.
- **Mobs/AI:** `isPathfindable`/`isFaceSturdy`/collision shapes feed pathfinding and physics for every entity.
- **Client rendering (Phase 2 relevance):** `getRenderShape`, occlusion/light-dampening, `getOffset` (model jitter) are consumed by chunk mesh building — server-computed but rendering-relevant.

## 8. Notes for Rusty Clanker

- **Behavior class ≠ block instance, ratio ~1:3.7.** 326 Java files in `.block` back 1196 registered blocks — most concrete classes are instantiated many times with different `Properties`/constructor args (stairs/slabs/walls/weathering-stage wrappers are the extreme case). An ECS/data-oriented reimplementation should mirror this: one Rust behavior-trait-impl or component-tag per *family*, parametrized data (properties, config records like `BlockSetType`/`WoodType`) driving per-instance variation — not one generated type per registered block id.
- **State permutation order is a hard compatibility surface, not an implementation detail.** The block-state ID space is a flat global counter over `(block registration order) × (cartesian product of that block's properties in alphabetical-name order, first property slowest)`. Any persistence format, network encoding, or palette compression scheme that wants to interoperate with vanilla saves/clients — or even just match `blocks.json` for testing — must reproduce this exact enumeration order bit-for-bit, including the counterintuitive **`BooleanProperty` index order `[true, false]`** (not `[false, true]`) and alphabetical-not-declaration property ordering. Get this wrong and every persisted numeric block-state id silently means a different block.
- **`setValue` is a table lookup, not a constructor call — and this is a legitimate design to copy.** Because the entire permutation space is finite and enumerated once at startup, vanilla never allocates a new `BlockState` at runtime; `cycle`/`setValue`/`trySetValue` all resolve through a pre-built neighbor-index array. A Rust reimplementation gets an easy, safe win reproducing this: intern all `(Block, property-values)` combinations once (e.g. behind an arena/interner keyed by a packed property-value tuple) and make state transitions pure index arithmetic — this also makes `BlockState` trivially `Copy`/small-integer-sized if the global state id itself is used as the in-memory representation.
- **The `updateShape` fan-out order (`WEST, EAST, NORTH, SOUTH, DOWN, UP`) is observable and load-bearing**, not an arbitrary iteration detail — fence/wall/pane connectivity, door-half destruction cascades, and any chain of blocks that each `updateShape` off the next can produce different final states depending on visitation order when several neighbors change "simultaneously" in one `setBlock` call. Preserve this exact order.
- **Random ticking is a two-stage rejection sampler, and reproducing vanilla's statistical growth rates requires reproducing *both* stages** — not just "pick a random ticking block and tick it." Vanilla picks a **uniformly random position within a whole 16×16×16 section** (gated only by whether the section has *any* randomly-ticking content) `tickSpeed` times, and only then checks whether that specific position happens to hold a randomly-ticking state. A reimplementation that instead maintains a list of "randomly-ticking block positions per chunk" and samples directly from that list will tick every eligible block strictly more often than vanilla and desyncs growth rates, sapling/mushroom spread, copper weathering, etc. The `tickingBlockCount`/`tickingFluidCount` incremental short-counter-per-section is worth copying as-is for the cheap eligibility gate, but the *sampling* must still go through the full-section uniform draw.
- **Two structurally different "temporary state" carriers exist and must not be conflated:** the piston's `MovingPistonBlock`/`PistonMovingBlockEntity` pair (interpolated animation, commits a real `BlockState` atomically on completion — a genuine block-entity-as-animation-carrier pattern) versus ordinary `updateShape` cascades (pure, synchronous, same-tick state recomputation with no intermediate visible state). Only pistons use the former; do not reach for a "temporary block entity" abstraction for door/fence/wall state recomputation.
- **`BlockEntityType` sharing across unrelated-looking blocks is intentional and must survive re-architecture** — e.g. `CHEST` backs both `Blocks.CHEST` and `Blocks.COPPER_CHEST`, `SIGN` backs ~26 wood-species sign variants. `createTickerHelper`'s `actual == expected` guard exists specifically because of this sharing; a reimplementation keying block-entity behavior off the *block* rather than off the *registered `BlockEntityType`* would silently break this reuse and duplicate behavior code per wood species/material.
- **Block-entity ticking and random ticking are both strictly single-threaded, flat, per-`Level` iterations in vanilla** (a `List<TickingBlockEntity>` and a per-loaded-chunk loop respectively) — there is no per-chunk or per-region parallelism to preserve *within* one owned partition; this aligns with the project's ARCH-D1-family decision to keep one owned region's ECS single-threaded-shared-memory, but it means block-entity tick order (append order = block-entity creation order, not spatial order) is itself an observable, if usually inconsequential, vanilla behavior — worth a conscious decision (reproduce exactly vs. deliberately relax) rather than an accidental divergence.
- **`ChangeOverTimeBlock`'s neighbor-scan-then-chance formula is generic infrastructure, not copper-specific — implement it once.** Anything using the same "ages up over time, influenced by nearby same-family ages" shape (copper oxidation today; historically also sculk-adjacent and stone-decay-style mechanics elsewhere in vanilla) should share one engine keyed by an enum-like age axis, matching vanilla's `ChangeOverTimeBlock<T>` generic interface rather than being reimplemented per material.
- **The `blocks.json`/`registries.json` datagen reports are the authoritative, legally-clean source for the state ID table and property schema** — a Rust build script can regenerate the equivalent mapping from a locally-fetched copy of these generator outputs (never checked into the repo per the clean-room/no-Mojang-content rule) rather than hand-transcribing 32366 state definitions.
