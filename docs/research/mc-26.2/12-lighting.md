# Lighting Engine — Vanilla 26.2 Cartography

## 1. Purpose

This subsystem computes and maintains the two independent per-block light channels — sky light (sunlight, column-sourced from above) and block light (point sources: torches, lava, glowstone, …) — as 4-bit values per block, stored one nibble array per 16×16×16 chunk section. It runs an incremental breadth-first "dynamic fixed point" relaxation: instead of recomputing a chunk's lighting from scratch on every change, it enqueues only the blocks whose light *could* have changed and propagates the delta outward until the field is consistent again. It also owns the asynchronous scheduling that keeps this relaxation off the main server thread, the copy-on-write publishing that lets other threads read a stable light snapshot concurrently, and the wire encoding used to keep connected clients' light in sync.

## 3. How it works

### 3.1 Two engines, one façade

`LevelLightEngine` owns at most two `LightEngine` instances — a `BlockLightEngine` (always present) and a `SkyLightEngine` (present only for dimensions with `hasSkyLight()`, i.e. not the Nether/End) — and fans every `LightEventListener` call out to both. Each engine is fully independent: separate BFS queues, separate section storage (`BlockLightSectionStorage` / `SkyLightSectionStorage`), separate `DataLayer` per section. `getLayerListener(LightLayer)` hands out the per-layer view (`LayerLightEventListener`); when a layer is absent, callers get `LayerLightEventListener.DummyLightLayerEventListener.INSTANCE`, a no-op singleton, so dimension-agnostic code never null-checks.

`LevelLightEngine.LIGHT_SECTION_PADDING = 1`: the tracked section range extends one section **below** the world's lowest section and one **above** the highest (`getMinLightSection() = minSectionY - 1`, `getLightSectionCount() = levelHeightAccessor.getSectionsCount() + 2`, `getMaxLightSection() = getMinLightSection() + getLightSectionCount()`). These two padding sections give sky light a source plane to seed from above the build limit and give block light a defined (empty) boundary below bedrock, without special-casing the world edges in the propagation code.

### 3.2 The packed `long` queue-entry encoding (`LightEngine.QueueEntry`)

Both the increase and decrease work queues are flat `LongArrayFIFOQueue`s storing **pairs** of `long`s: a block-position key (`BlockPos.asLong()`) immediately followed by one packed metadata `long`. The metadata packs into the low 12 bits:

| Bits | Width | Meaning |
|---|---|---|
| 0–3 | 4 | `FROM_LEVEL` — the light level (0–15) this entry propagates *from* |
| 4–9 | 6 | one flag bit per `Direction` ordinal (`DOWN,UP,NORTH,SOUTH,WEST,EAST`) — "should this entry propagate toward this neighbor" |
| 10 | 1 | `FROM_EMPTY_SHAPE` — treat the source block as `Blocks.AIR` (empty occlusion shape) rather than re-fetching its real `BlockState`, an optimization for emission-seeded entries |
| 11 | 1 | `INCREASE_FROM_EMISSION` — only meaningful on increase entries: re-check the source's own stored level against the emission level before propagating (a block's emission can itself have just increased) |

Constructor helpers on `QueueEntry` build these values without exposing the bit layout to callers: `decreaseAllDirections(level)`, `decreaseSkipOneDirection(level, skip)` (all 6 minus one — the direction just walked in from, to avoid immediately re-deriving the same value backward), `increaseLightFromEmission(level, emptyShape)`, `increaseSkipOneDirection(...)`, `increaseOnlyOneDirection(level, emptyShape, direction)` (exactly one bit set — used to "probe" a single neighbor rather than fan out), and `increaseSkySourceInDirections(down, north, south, west, east)` (sky-source seeding never propagates `UP`, since a full-sun column has nothing brighter above it). A precomputed sentinel `PULL_LIGHT_IN_ENTRY = decreaseAllDirections(1)` is enqueued whenever a block's own value didn't actually drop below its emission — its `fromLevel = 1` makes `propagateDecrease`'s "did neighbor come from me" test (`toLevel <= oldFromLevel - 1`, i.e. `toLevel <= 0`) always false for any already-lit neighbor, so the decrease phase does no damage but its `else` branch still re-queues an increase check in every direction, effectively asking "can any neighbor push a brighter value back into me" without a genuine decrease ever happening. `SOURCE = Long.MAX_VALUE` (on the unrelated `DynamicGraphMinFixedPoint`, see §3.10) plays an analogous "this node has no parent" role in that separate structure.

### 3.3 `checkNode` — the block-change entry point

`LightEngine.checkBlock(pos)` just adds the position to a `LongOpenHashSet blockNodesToCheck` (min-sized 512, trimmed back to that floor every drain) — cheap, dedupes repeated touches to the same block within one batch, and defers real work to the next `runLightUpdates()` call. `runLightUpdates()` first iterates and clears that set via each subclass's `checkNode`, *then* drains the two BFS queues (§3.6).

- **`BlockLightEngine.checkNode`**: skip entirely if the containing section isn't tracked (`storingLightForSection`, §3.9). Otherwise read the current `BlockState`'s emission (`getEmission`, which forces 0 if `lightOnInSection` is false — see §3.10 on `setLightEnabled`). If emission dropped below the block's currently stored level, zero the stored value and enqueue a full decrease from the *old* level; otherwise enqueue `PULL_LIGHT_IN_ENTRY` (the block's own contribution didn't shrink, but its opacity/shape may have changed, so ask neighbors to re-offer light). If emission is now `>0`, additionally enqueue an increase seeded at that emission level.
- **`SkyLightEngine.checkNode`**: first asks `ChunkSkyLightSources` for the column's current lowest full-sun Y (`getLowestSourceY`); if that changed since the block last checked, `updateSourcesInColumn` walks the column up/down converting blocks between "is a 15-source" and "is propagated" (§3.8) before doing the normal per-block decrease/increase enqueue identical in shape to the block-light case (with `isSource` computed as `y >= lowestSourceY` instead of a stored emission).

### 3.4 Increase propagation (`propagateIncrease`)

`propagateIncreases()` drains the increase queue to empty. For each dequeued `(fromNode, increaseData)` pair it re-reads the *current* stored level at `fromNode`; if `INCREASE_FROM_EMISSION` is set and the stored level is still below the entry's target, the stored value is bumped up to the target first (lazily "materializing" an emission increase only once it's actually about to propagate). The entry is only acted on if the from-node's stored level still equals the entry's `FROM_LEVEL` — a cheap staleness check that discards entries superseded by a later, larger increase to the same node.

`propagateIncrease(fromNode, increaseData, fromLevel)` then walks the 6 `Direction`s, skipping any not flagged in the entry. For each flagged neighbor: skip if its section isn't tracked; compute `maxPossibleNewToLevel = fromLevel - 1` and bail early if that's not already better than the neighbor's stored level (avoids fetching the neighbor's `BlockState` at all in the common "already brighter" case). Otherwise fetch the neighbor's state, compute `newToLevel = fromLevel - getOpacity(toState)` (`getOpacity = max(1, state.getLightDampening())` — every block costs *at least* 1 level, see §3.7), and if that beats the stored value, run the shape-occlusion test between the source and destination faces (`shapeOccludes`, §3.7; the source state is lazily resolved to `Blocks.AIR` if `FROM_EMPTY_SHAPE` was set, saving a chunk lookup for the common emission-seeded case). If the pair of faces doesn't fully occlude, store `newToLevel` and, if it's still `>1` (a value of exactly 1 has nothing left to propagate further), enqueue a further increase from the neighbor with the reverse direction bit cleared (never immediately bounce back where it came from).

`SkyLightEngine.propagateIncrease` additionally calls `propagateFromEmptySections` after each successful neighbor update — see §3.8.

### 3.5 Decrease propagation (`propagateDecrease`)

`propagateDecreases()` drains the decrease queue to empty, unconditionally invoking `propagateDecrease` for every entry (no staleness re-check — a decrease is idempotent against having already happened, since it only acts on neighbors still `<= oldFromLevel - 1`). For each flagged direction: if the neighbor's stored level is `0`, nothing to do. If it's `<= oldFromLevel - 1` (i.e. the neighbor's light *could only* have come, at that magnitude, from the node being decreased), zero it, and: if the neighbor's own light source (block emission, or "am I above the sky-source line") is weaker than the value it just lost, cascade the decrease further (skipping the direction just walked back); if the neighbor emits its own light `>0`, additionally enqueue a fresh increase seeded from that emission (so the neighbor immediately reclaims its own baseline glow rather than waiting for a separate `checkNode` pass). If instead the neighbor's stored level is *higher* than `oldFromLevel - 1`, it has an independent, still-valid source — enqueue a single-direction increase probe (`increaseOnlyOneDirection`) back toward the node that just decreased, letting that unaffected neighbor re-illuminate it in the following increase phase. This "decrease, then let survivors refill" pattern is what makes the relaxation exact without a full recompute: every affected node is definitely zeroed once, and every node that still has a legitimate source is guaranteed a chance to re-propagate into the hole.

`SkyLightEngine.propagateDecrease` calls `propagateFromEmptySections` symmetrically (§3.8) and, unlike the increase path, does **not** re-check emission (sky light has no per-block "emission", only the source-column flag handled in `checkNode`/`updateSourcesInColumn`).

### 3.6 Drain order and `runLightUpdates`

`LightEngine.runLightUpdates()` always runs in this fixed order: (1) drain `blockNodesToCheck` via `checkNode`, populating the two queues; (2) `propagateDecreases()` to completion; (3) `propagateIncreases()` to completion; (4) clear the 2-entry chunk lookup cache (§3.9); (5) `storage.markNewInconsistencies(this)` — reconcile section add/remove bookkeeping accumulated this pass (§3.9); (6) `storage.swapSectionMap()` — publish the copy-on-write visible snapshot and fire `onLightUpdate` for every section touched this pass (§3.12). Running decreases to full completion *before* any increase is processed is load-bearing: decreases can enqueue increases (to refill from surviving sources) but increases never enqueue decreases, so this ordering is the only one that guarantees termination without re-interleaving passes. `LevelLightEngine.runLightUpdates()` simply runs the block engine's pass, then the sky engine's, and sums their returned work counts; `hasLightWork()` is true if either engine still has queued work or unconsumed `blockNodesToCheck` entries.

### 3.7 Opacity, dampening and shape occlusion

Two independent light-blocking models exist and are mixed depending on the block:

- **Scalar opacity (`getLightDampening`)** — the fast path used for nearly all blocks. Default logic: a fully solid-rendering block (`isSolidRender()`, its full-cube occlusion shape covers a whole block) dampens by **15** (blocks everything outright); otherwise a block that `propagatesSkylightDown()` (its own collision/render shape isn't a full cube *and* it has no fluid) dampens by **0**; every other non-full block dampens by **1**. `getOpacity(state) = max(1, dampening)` is what the BFS actually subtracts per hop — meaning even a declared 0-dampening block still costs one level of light per block traveled *unless* it also passes the shape-occlusion test in the direction of travel (see below), and even a declared-0 propagating block can never be a perfect pass-through for BFS math alone.
- **Shape-accurate occlusion (`useShapeForLightOcclusion` = true, default false)** — opted into by a handful of blocks with non-cube geometry that still needs directional light blocking to look right (e.g. stairs, slabs, fences/walls, snow layers, chunks of partial-height blocks). When either side of a propagation step has this flag set, the engine additionally calls `shapeOccludes(fromState, toState, direction)`, which resolves each state's `getFaceOcclusionShape(direction)` (a cached per-state, per-`Direction` `VoxelShape`, precomputed once in `BlockStateBase.initCache`) and tests `Shapes.faceShapeOccludes(fromShape, toShape)` — true only if the union of the two adjoining faces fully covers the 1×1 shared face. This is a strict veto: even if the scalar-opacity subtraction would have produced a positive new level, a fully-occluding face pair blocks propagation entirely in that direction. `getOcclusionShape(state, direction)` (static helper) and `isEmptyShape(state) = !canOcclude() || !useShapeForLightOcclusion()` are the two guard predicates gating whether this heavier path is even entered.
- **`getLightDampeningInto(fromState, toState, direction, simpleOpacity)`** is a third, standalone static helper — *not* called by the BFS itself — used by gameplay code (`SpreadingSnowyBlock`/`NyliumBlock` "can this block survive/spread here") to combine both models in one call: if both shapes are empty it just returns the scalar opacity; otherwise it returns **16** (an intentionally-unreachable "more than max light" sentinel) if `Shapes.mergedFaceOccludes` finds the two faces jointly occlude, else the scalar value. `SpreadingSnowyBlock.canStayAlive` treats "dampening `< 15`" as "sky-lit enough to survive," a concrete gameplay-facing threshold.
- **`getShadeBrightness(state, level, pos)`** is unrelated to the light *level* computation — it is a client-rendering-only multiplier (`0.2F` if the block's collision shape is a full cube, else `1.0F`) applied to face brightness for pseudo-ambient-occlusion, not consumed by `LightEngine` at all.

### 3.8 Sky light column source tracking and the empty-section shaft optimization

`ChunkSkyLightSources` (one instance per chunk, held on `ChunkAccess`) is a 16×16 `BitStorage` heightmap — **not** the block heightmaps used by worldgen — recording, per `(x,z)` column, the lowest Y at which sky light transitions from "guaranteed full sun (15)" to "must be propagated/attenuated." `fillFrom(chunk)` computes it once by scanning each column top-down through `LevelChunkSection`s (skipping all-air sections in bulk via `section.hasOnlyAir()`) for the first pair of vertically-adjacent block states whose shared horizontal face fully occludes (`isEdgeOccluded`, the same `Shapes.faceShapeOccludes` test as §3.7, gated first by a cheap `getLightDampening() != 0` check). `update(level, x, y, z)` incrementally patches one column after a block change by re-testing only the edge immediately above and below the changed position, walking further down only if the edge that used to be the boundary is no longer occluding. This heightmap is what `SkyLightEngine.checkNode`/`propagateLightSources` use to decide, per block, whether it *is* a level-15 source rather than something that must receive light from above — decoupling "is this the top of the world" from any actual light computation.

Two related optimizations exist purely to avoid touching all-air sections:
- **`countEmptySectionsBelowIfAtBorder`** — when a propagation step lands on a block at the bottom edge of its section (`localY == 0`) *and* at a horizontal chunk-section edge, it counts how many consecutive sections below are currently untracked (`!storingLightForSection`) but still within the world's tracked range (`hasLightDataAtOrBelow`).
- **`propagateFromEmptySections`** — if that count is nonzero and the direction just walked crossed a chunk-section horizontal boundary (`crossedSectionEdge`, one specific local-coordinate value per direction: `NORTH`→`z==15`, `SOUTH`→`z==0`, `WEST`→`x==15`, `EAST`→`x==0`), the engine directly fills or clears the entire vertical run of untracked sections below in one pass (writing every block in every 16-row plane, no further BFS enqueue needed for interior blocks — only the boundary rows get an outgoing propagate entry with `FROM_EMPTY_SHAPE=true`, since a section with no stored `DataLayer` is definitionally all-air).

This means a wide-open shaft of air many sections tall never gets 4096-per-section BFS treatment for its interior — only its walls do — while still producing bit-identical results to running the general algorithm through every block, because untracked sections are guaranteed uniform (§3.9).

### 3.9 Section storage lifecycle: trivial, light-only and light-and-data sections

`LayerLightSectionStorage<M>` tracks, per section node, a packed `byte` state (`SectionState`: bit 5 = "has data" i.e. the section itself is non-air; bits 0–4 = a 0–26 count of the section's 26 3D neighbors that currently have data). `getDebugSectionType`/`SectionType` exposes three states: **`EMPTY`** (packed state `0` — no `DataLayer` allocated at all, not tracked by the BFS, "trivial" in the classic sense), **`LIGHT_ONLY`** (state nonzero but the "has data" bit clear — allocated only because an adjacent section has data, i.e. this section is a buffer zone that needs graduated values near its border), **`LIGHT_AND_DATA`** (the section itself is non-air and directly participates as an opacity/emission source).

`updateSectionStatus(sectionNode, sectionEmpty)` — invoked whenever a `LevelChunkSection`'s air/non-air status flips (`LevelChunk.setBlockState`/`ProtoChunk.setBlockState`, guarded there by `wasEmpty != isEmpty`) — updates the "has data" bit for that node, then walks the full 3×3×3 neighborhood (26 cells) incrementing or decrementing each neighbor's stored count. `putSectionState` is the single choke point that reacts to a `0 ↔ nonzero` transition: `initializeSection` (transition into nonzero) allocates a fresh `DataLayer` via `createDataLayer` (which, for `SkyLightSectionStorage`, either copies queued disk data or — if this section sits directly below an already-initialized column — **repeats the section immediately above it** via `repeatFirstLayer`, a byte-array tile-copy, so a newly-exposed all-air section under full sun starts pre-filled at 15 instead of needing a BFS seed pass) and marks all 26 neighbors' "affected" set (forces them to be considered for the client-sync diff even though their own value didn't change); `removeSection` (transition to zero) doesn't free memory immediately — it stages the node in a `toRemove` set consumed by `markNewInconsistencies` at the top of the next `runLightUpdates` (§3.6), which actually drops the `DataLayer` (or hands it off to `queuedSections` if the column is marked "retain," §3.13) and calls the subclass hook `onNodeRemoved` (in `SkyLightSectionStorage`, re-derives the column's cached "top tracked section" index by scanning downward).

`DataLayerStorageMap<M>` (`updatingSectionData`) is the mutable side of a copy-on-write pair; `visibleSectionData` is a `disableCache()`d snapshot swapped in wholesale by `swapSectionMap()` whenever `changedSections` is non-empty, and is the only side other threads (packet construction, debug rendering) may read without racing the BFS. Both directions carry a tiny **2-entry** direct-mapped LRU (`lastSectionKeys`/`lastSections` on the map; a parallel `lastChunkPos`/`lastChunk` pair on `LightEngine` itself for chunk lookups) — sized for the common case of many consecutive BFS steps touching the same section/chunk.

### 3.10 Chunk-status integration and the `ThreadedLevelLightEngine` batching model

`ChunkStatus.INITIALIZE_LIGHT` (task `ChunkStatusTasks.initializeLight`) and `ChunkStatus.LIGHT` (task `ChunkStatusTasks.light`) are two separate steps in the generation/loading pyramid; `LIGHT` declares `addRequirement(INITIALIZE_LIGHT, 1)` — a Chebyshev radius-1 (3×3) neighbor dependency. `initializeLight`: calls `chunk.initializeLightSources()` (populates `ChunkSkyLightSources` from the fully-generated terrain, §3.8), attaches the light engine reference to the `ProtoChunk` (so its own `setBlockState` starts doing light bookkeeping from this point on — see §3.11, and note bulk terrain/feature/carver placement *before* this step never touches the light engine at all), then calls every `updateSectionStatus` for the chunk's own non-air sections up front. `light`: calls `lightChunk`, which — only if the chunk wasn't already correctly lit (`isLighted = persistedStatus.isOrAfter(LIGHT) && isLightCorrect()`) — runs `propagateLightSources` (§3.8's `SkyLightEngine.propagateLightSources` seeds every source column in the chunk plus reads its 4 orthogonal neighbors' `ChunkSkyLightSources` to correctly seed cross-boundary source runs; `BlockLightEngine.propagateLightSources` walks every non-air `LevelChunkSection` via a palette-level `maybeHas(predicate)` pre-filter and enqueues an emission-seeded increase for every emitting block found) and marks `chunk.setLightCorrect(true)` once the resulting future completes.

`ThreadedLevelLightEngine extends LevelLightEngine` and overrides every `LightEventListener` method to **never touch the engine synchronously** — each override wraps the real (`super.`) call in a `Runnable` tagged `PRE_UPDATE` or `POST_UPDATE` and hands it to `ChunkTaskDispatcher.submit`, keyed by chunk position and the chunk's current ticket-derived queue level (`ChunkMap.getChunkQueueLevel`) so nearby/urgent chunks get their light work prioritized over distant ones. `runLightUpdates()` itself is overridden to unconditionally throw (`UnsupportedOperationException`, "ran automatically on a different thread") — nothing may call it directly. Instead, `tryScheduleUpdate()` — invoked opportunistically after every task submission and once per queue drain — schedules `runUpdate()` onto the single `ConsecutiveExecutor` named `"light"` (constructed in `ChunkMap`, backed by the shared background executor pool but serialized: a `ConsecutiveExecutor` guarantees at most one of its own queued tasks executes at a time, so `LightEngine`'s mutable state needs no internal locking as long as every mutation flows through this one dispatcher). `runUpdate()` drains up to **`taskPerBatch = 1000`** queued `(TaskType, Runnable)` pairs per invocation: first every `PRE_UPDATE` task up to that cap runs (queueing BFS work), then `super.runLightUpdates()` actually drains the BFS queues once, then every `POST_UPDATE` task up to the same cap runs (these are typically `CompletableFuture` completions like "chunk is now lit," deliberately sequenced *after* the BFS so waiters observe the post-BFS state) and is removed from the pending list; any tasks beyond the 1000-cap remain queued for the next `runUpdate()` invocation, which `tryScheduleUpdate` re-triggers as long as `lightTasks` is non-empty or `hasLightWork()` is true. `waitForPendingTasks(x,z)` gives callers a `CompletableFuture` that resolves only after every task queued for that chunk so far has been popped in a `POST_UPDATE` slot — the mechanism `ChunkMap`/generation pipeline code uses to sequence "wait until this chunk's light is settled" without polling.

### 3.11 Block-change end-to-end flow

`LevelChunk.setBlockState`/`ProtoChunk.setBlockState` both follow the identical shape after writing the new state into the section: (1) if the section's air/non-air status flipped, call `getLightEngine().updateSectionStatus(pos, isEmpty)` (§3.9); (2) if `LightEngine.hasDifferentLightProperties(oldState, newState)` — true whenever dampening or emission differ, or *either* state opts into shape-based occlusion (a conservative "might matter" test, not "definitely matters") — update the column's `ChunkSkyLightSources` edge (§3.8) and call `getLightEngine().checkBlock(pos)` (§3.3), which is the sole entry point back into the BFS machinery for ordinary gameplay block edits. On a `LevelChunk` (post-generation, live world) this call chain runs through `ThreadedLevelLightEngine` and is therefore asynchronous relative to the block write itself — the write is visible immediately, the light correction lands on a subsequent light-executor batch, and clients see the corrected light only once `swapSectionMap`/`onLightUpdate`/`ChunkHolder.broadcastChanges` (§3.12) has run.

### 3.12 Client synchronization

`LayerLightSectionStorage.swapSectionMap()` — called at the end of every `runLightUpdates` pass (§3.6) — iterates `sectionsAffectedByLightUpdates` (populated by `setStoredLevel`, which marks the touched block's own section plus all 26 3D neighbors — `markSectionAndNeighborsAsAffected` — since a value written near a section boundary can change what a neighboring section's client-visible edge looks like) and calls `chunkSource.onLightUpdate(layer, sectionPos)` for each. `ServerChunkCache.onLightUpdate` hops back onto the **main** thread (`mainThreadProcessor.execute`) and calls `ChunkHolder.sectionLightChanged(layer, chunkY)`, which sets one bit in a per-`ChunkHolder` `BitSet` (`skyChangedLightSectionFilter` / `blockChangedLightSectionFilter`, indexed `chunkY - lightEngine.getMinLightSection()`) and enqueues the holder for the next broadcast pass if this is the first change since the last flush. `ChunkHolder.broadcastChanges` — driven from the normal per-tick chunk-holder broadcast sweep alongside ordinary block-update packets — builds one `ClientboundLightUpdatePacket` per dirty chunk from the accumulated bitsets and sends it, then clears both bitsets, **only to "border" players**: `playerProvider.getPlayers(pos, borderOnly=true)`, which further reduces to players for whom this chunk sits on the edge of their currently-tracked chunk square (at least one of its 8 neighbors is not yet tracked by that player) rather than every player who has the chunk loaded at all. Interior light diffs are not separately pushed to clients whose entire local neighborhood is already tracked; a legitimate vanilla client runs the same deterministic BFS locally off the block-update packets it already receives, so its own recomputation reproduces the server's result bit-for-bit inside fully-tracked territory — the border-only broadcast exists specifically to correct clients at the edge of their view, where they lack visibility into the far side of the boundary and cannot rederive the correct value themselves. `ClientboundLightUpdatePacketData`'s constructor iterates every tracked light section (`lightEngine.getLightSectionCount()`) for the requested layer(s), reads each section's `DataLayer` (via `getDataLayerData`, which prefers a not-yet-adopted `queuedSections` entry over the live section, §3.13) and buckets it into one of three outcomes per section: absent (untracked/trivial, contributes to neither mask), present-but-uniform (`data.isEmpty()`, set in the *empty*-mask bitset, no bytes sent), or present-with-content (set in the main mask bitset, the full 2048-byte nibble array copied into the update list). The **initial** full-chunk send (`PlayerChunkSender`, `ClientboundLevelChunkWithLightPacket`) passes `null` for both filters, which the same constructor logic treats as "every section," i.e. a brand-new chunk always ships its complete sky+block light state regardless of dirty tracking.

### 3.13 Persistence and retain-data reload

On chunk load, `SerializableChunkData.read` walks the on-disk per-section light nibble arrays and, for the first section that has saved block or sky light, calls `lightEngine.retainData(pos, true)` **before** feeding every saved layer in through `lightEngine.queueSectionData(layer, sectionPos, data)`. `queueSectionData` stashes the array in `LayerLightSectionStorage.queuedSections` and sets `hasInconsistencies = true`; because this typically happens before the chunk has reached `INITIALIZE_LIGHT` (no `DataLayer` is allocated for its sections yet), the queued data has nowhere to attach immediately. `retainData(pos, true)` marks the chunk's column in `columnsToRetainQueuedDataFor` so that, in `markNewInconsistencies`, a queued entry surviving a `toRemove` reconciliation is deliberately **re-inserted** into `queuedSections` rather than dropped — the queued disk data is kept alive across any number of intervening add/remove churn until a real section actually gets initialized. Once `initializeSection` does run for that section, `createDataLayer` finds the pending entry in `queuedSections` and adopts it directly as the section's live array — the persisted nibble data becomes the section's `DataLayer` with **no BFS recomputation**, provided the chunk's persisted status was already `≥ LIGHT` and its `isLightCorrect` flag was true (§3.10's `isLighted` check), in which case `lightChunk`/`initializeLight` skip calling `propagateLightSources` entirely and trust the loaded data outright. `ThreadedLevelLightEngine.initializeLight`'s async continuation calls `super.retainData(pos, false)` immediately after setting `lightEnabled`, so the retain window is intentionally narrow — just long enough to survive the section-initialization race, not held indefinitely.

### 3.14 Chunk unload teardown

`ChunkMap.scheduleUnload` calls `lightEngine.updateChunkStatus(pos)` after the chunk has been saved and detached from the level. That method (`ThreadedLevelLightEngine`-only, `protected`) disables light-source contribution for the column (`setLightEnabled(pos, false)`), turns off data retention (`retainData(pos, false)` — an unloaded chunk's light must be rebuilt from disk data, not kept "pending" indefinitely), queues a `null` `DataLayer` for every tracked section of both layers (which `queueSectionData` treats as "remove queued entry" — see §3.9's `putSectionState`/`toRemove` path), and finally calls `updateSectionStatus(pos, sectionEmpty=true)` for every section in the level's actual height range, which drives every section back through the `0 ↔ nonzero` transition machinery to fully deallocate its `DataLayer`s. In-memory light state for an unloaded chunk is therefore not preserved across unload/reload; the next load rebuilds it via the retain-data path (§3.13) or, absent saved light data (`isLightCorrect` false / not yet reached `LIGHT`), via a fresh `propagateLightSources` BFS pass.

### 3.15 Ungenerated-neighbor edge case

`LightEngine.getChunk(chunkX, chunkZ)` delegates to `chunkSource.getChunkForLighting(x, z)`, which on `ServerChunkCache` returns `null` unless the target chunk's `ChunkHolder` has already reached `ChunkStatus.INITIALIZE_LIGHT.getParent()` (i.e. `FEATURES` — full terrain but not yet light-initialized). `LightEngine.getState(pos)` treats a `null` chunk as **`Blocks.BEDROCK.defaultBlockState()`** — fully opaque, zero emission — rather than air or "unknown." Consequently, any BFS step that would cross into a not-yet-generated or not-yet-feature-complete neighbor chunk is silently blocked at that boundary exactly as if solid bedrock stood there; no light leaks across an ungenerated edge, and — critically — the BFS never blocks waiting for that neighbor to materialize (it just gets a wrong-but-safe answer this pass). When the neighbor later does reach `FEATURES`/`INITIALIZE_LIGHT`, nothing automatically re-triggers propagation across that boundary from the *already-lit* side; correctness there instead falls out of `LIGHT`'s own radius-1 dependency (§3.10) forcing every chunk's own `propagateLightSources` pass to run only once its four immediate neighbors are past `INITIALIZE_LIGHT`, and ordinary gameplay `checkBlock` calls on either side of the boundary after both chunks are loaded will correct any residual discrepancy the next time either side changes.

## 6. Cross-subsystem interfaces

**Consumes from:**
- **Chunk/world storage** (`03-world-chunks-persistence` domain): `LevelChunkSection` block/fluid state, `hasOnlyAir()`, palette-level `maybeHas(predicate)` filtering; `ChunkStatus`/`ChunkPyramid` step sequencing and neighbor-radius dependency graph; `SerializableChunkData` for saved per-section nibble arrays and `isLightCorrect`/persisted status flags.
- **Block/blockstate registry** (`07-blocks-blockstates` domain): per-`BlockState` emission, dampening, `useShapeForLightOcclusion`, cached per-direction occlusion shapes — none of this is queried through data-driven config; it is Java-side `BlockBehaviour.Properties` set at block registration.
- **Threading substrate** (`01-server-architecture`/bootstrap domain): `ConsecutiveExecutor`/`ChunkTaskDispatcher`/`PriorityConsecutiveExecutor`, the shared background executor pool.
- **Networking** (`02-protocol-networking` domain): player tracking/view-distance state (`ChunkMap.getPlayers`, border-vs-tracked distinction) to decide packet fan-out.

**Provides to:**
- **Rendering/client** (Phase 2 client domain): per-section `DataLayer` snapshots via the wire packets; the client is expected to run an equivalent local BFS off ordinary block-update packets rather than receive every interior light diff.
- **Gameplay/mechanics** (`05-game-mechanics` domain): `getRawBrightness`/`getBrightness`/`getMaxLocalRawBrightness` as the sole light-value read API for mob spawning, crop/sapling growth, mushroom placement, glow squid despawn conditions, and similar; `LightEngine.getLightDampeningInto` as a standalone geometric helper for grass/mycelium/nylium survival checks, independent of the stored light field.
- **Redstone/tick domain**: none directly — the two subsystems are architecturally parallel (both live partly in packages that also host an unrelated `DynamicGraphMinFixedPoint`-style graph algorithm) but do not call into each other.
- **World generation**: `ChunkStatusTasks.initializeLight`/`light` as two pipeline steps; `WorldGenContext.lightEngine()` threads the `ThreadedLevelLightEngine` reference through the generation context.

## 7. Data-generator cross-reference

None of the files under `datagen/generated/` encode lighting data. `reports/blocks.json` enumerates block-state definitions, properties and numeric state IDs only — it does **not** carry light emission, opacity/dampening, or occlusion-shape values for any block (verified: the `minecraft:torch`/`minecraft:glowstone` entries contain only `type`, block-specific definition fields like `particle_options`, and the state ID list). Those physical light properties exist solely as Java-side `BlockBehaviour.Properties.lightLevel(...)` / default-shape-derived `getLightDampening()` calls made once per block at `Blocks` class registration, and must be extracted from that registration code (numeric per-block constants, which the clean-room policy in `CLAUDE.md` treats as facts, not copyrightable expression) rather than from any generator report. `reports/registries.json` lists the block/blockstate registry names only, with no physical metadata. No `data/minecraft/` datapack folder (loot tables, tags, worldgen, etc.) touches light propagation; the one adjacent data-driven surface is the `minecraft:light` block item's placeable `LEVEL` block-state property (0–15, `BlockStateProperties.LEVEL`), which is ordinary gameplay content, not an input to the engine's algorithm.

## 8. Notes for Rusty Clanker

- **The two work queues are the entire mutable "hot" state, and they're not thread-safe by design.** `LightEngine`'s queues, caches and the `LayerLightSectionStorage.updatingSectionData` side are only ever touched from within the single `"light"` `ConsecutiveExecutor`'s serialized task stream. A Rust reimplementation on a work-stealing ECS pool must either replicate that single-writer discipline exactly (one exclusive light-owning task/actor per world, matching ARCH's message-substrate model) or prove a different concurrency scheme still produces the identical relaxation order — the algorithm's correctness argument (§3.6: decreases-then-increases, staleness checks by re-reading current stored level) implicitly assumes no concurrent mutation mid-drain.
- **Bit-identical parity requires the exact decrease→increase two-phase drain, not just "a" correct BFS.** Multiple mathematically-valid orderings converge to the same final light field but not necessarily to the same *packet sequence* or *intermediate frame*, and since interior clients are expected to re-derive light locally from block-update packets, any client-visible divergence in when/how a value stabilizes is directly observable as visual flicker or a light "pop" that doesn't match vanilla. The `PULL_LIGHT_IN_ENTRY` sentinel (§3.2) and the single-direction "probe" increase entries (§3.5) are two known subtle patterns that are easy to drop when re-deriving the algorithm from first principles instead of porting it directly.
- **"Trivial section" allocation must be replicated, not just treated as an optimization.** Because `SkyLightSectionStorage.createDataLayer` special-cases a newly-initialized section directly below an already-lit column (tile-copying the section above instead of running BFS), and because `propagateFromEmptySections` bulk-fills/-clears untracked shafts without individually enqueuing their interior blocks, an implementation that always allocates real per-block storage and always BFS-propagates will still reach the same final values but at a different (much higher) cost — and, more importantly, at different intermediate states if any intermediate state is observable (e.g. a client connecting mid-BFS-batch).
- **Ungenerated-neighbor handling (§3.15) is a correctness trap, not just a performance shortcut.** Treating a missing neighbor chunk as bedrock, rather than as air or as "block until available," is what keeps generation embarrassingly parallel and prevents any cross-partition blocking (a hard project-wide rule, `ARCH`) — but it also means a chunk's light is *provisionally wrong* at its edges until all four orthogonal neighbors clear `INITIALIZE_LIGHT`, and nothing pushes a correction proactively across that boundary once it does; correctness is restored lazily via `LIGHT`'s radius-1 dependency plus incidental future `checkBlock` calls. A reimplementation must reproduce this exact "safe-wrong-until-corrected" behavior (including *which* pass corrects it) rather than "fixing" it by making neighbor chunks block-load, which would violate the no-cross-partition-blocking rule and also silently diverge from vanilla's actual observable light values during generation.
- **Retain-data (§3.13) is a load-time-only fast path with a narrow validity window**, gated on the *combination* of `isLightCorrect` and persisted status `≥ LIGHT` — reusing saved light data when either condition is false (e.g. a `.mcregion`/Anvil chunk saved mid-generation, or with corrupted/foreign light data) is exactly the vanilla "recompute if untrusted" bug class to avoid; the flag pairing, not just the presence of saved arrays, is what vanilla treats as "trustworthy."
- **Two independent light-blocking models coexist (§3.7) and most of the per-block "opacity" data currently has no first-class data-generator source.** Building the full ~1,000-block emission/dampening/occlusion table will require a one-time extraction pass over `Blocks.java`'s `Properties.lightLevel(...)`/shape registrations (own-words/numeric-constant extraction, not verbatim reproduction) or systematic packet-capture cross-validation against a legally-owned vanilla server — this table does not currently exist anywhere in `docs/planning/` and is a hard prerequisite for parity-testing this subsystem (see `09-testing-quality.md`'s domain).
- **Client-side re-lighting is load-bearing for the border-only broadcast optimization (§3.12).** If Phase 2's client does not implement a bit-identical local `LightEngine`, the server's border-only broadcast strategy will produce visibly wrong light for any client relying on server-authoritative sync inside its own tracked interior — this couples the client architecture domain (`07-client-architecture.md`) to this document more tightly than a typical "client renders what the server sends" subsystem would suggest, and should be called out explicitly wherever that document defines the client's own lighting responsibilities.
- **`DynamicGraphMinFixedPoint` living in the `lighting` package is a historical/organizational artifact, not a lighting dependency in 26.2** — its only live subclasses (`ChunkTracker`, `SectionTracker`) belong to the chunk-ticket-distance subsystem. A clean-room reimplementation should feel free to place the equivalent generic leveled-graph-relaxation utility (if reused at all) wherever it's actually consumed, without preserving this package placement as if it implied a real coupling.

## 9. Open questions

- Whether `SectionTracker`'s use of `DynamicGraphMinFixedPoint` (chunk-ticket distance propagation) is close enough in shape to the block/sky-light BFS that a single shared Rust "leveled graph relaxation" abstraction is worth building, versus keeping the light BFS's simpler two-`VecDeque` scheme fully separate as this document describes it.
- Exact behavior of `ChunkHolder.sectionLightChanged`'s inclusive `chunkY <= maxLightSection` bound (§3.10/§4) against the exclusive-looking definition of `getMaxLightSection()` — worth a differential test against vanilla before committing to a section-index range in the Rust port, since an off-by-one here would silently drop or duplicate the top padding section's client sync.
