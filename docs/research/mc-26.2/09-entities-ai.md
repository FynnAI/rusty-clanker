# Entities & AI — Vanilla Server Research (MC 26.2 / protocol 776)

## 1. Purpose

This domain covers everything that makes a non-block, non-item-stack "thing in the world" exist, move, and decide what to do next: the `Entity`/`LivingEntity`/`Mob` class hierarchy and its ~150 concrete leaf types; the attribute and data-synchronization substrates every entity is built on; the two independent AI frameworks vanilla runs side by side (the legacy priority `Goal`/`GoalSelector` system and the newer `Brain`/`Behavior`/`Sensor` system); pathfinding and navigation; and the natural-spawning, breeding, and taming systems that create and manage mob populations. It is the largest single subsystem in the codebase by file count.

## 3. How it works

### 3.1 Entity base class & lifecycle

`Entity` (`net.minecraft.world.entity.Entity`) is the root of everything spatial. Every instance owns: an `EntityType<?>` back-reference, an integer network id (`level.getNextEntityId()`), a `UUID`, position/rotation state (`position: Vec3`, cached `blockPosition`/`chunkPosition`, `xRot`/`yRot` plus `*O` "previous tick" mirrors used for client-side interpolation), an `AABB bb` bounding box, motion (`deltaMovement`), collision flags (`horizontalCollision`, `verticalCollision`, `verticalCollisionBelow`, `minorHorizontalCollision`), a `RandomSource random` seeded insecurely per-instance (`Mth.createInsecureUUID`), and passenger/vehicle links (`ImmutableList<Entity> passengers`, `@Nullable Entity vehicle`).

Every `Entity` also carries an `EntityDimensions dimensions` (copied from its `EntityType` at construction, but can change per-instance — see Pose-driven resizing below) and a `SynchedEntityData entityData` instance built in the constructor via a `SynchedEntityData.Builder`. The base class pre-registers 8 synced fields before calling the overridable `defineSynchedData(Builder)` hook: `DATA_SHARED_FLAGS_ID` (byte bit-flags: on-fire=0, shift-key=1, sprinting=3, swimming=4, invisible=5, glowing=6, fall-flying=7), `DATA_AIR_SUPPLY_ID`, `DATA_CUSTOM_NAME`, `DATA_CUSTOM_NAME_VISIBLE`, `DATA_SILENT`, `DATA_NO_GRAVITY`, `DATA_POSE`, `DATA_TICKS_FROZEN`.

Removal uses a typed `Entity.RemovalReason` enum rather than a boolean: `KILLED`/`DISCARDED` (destroy=true, save=false — never written to disk), `UNLOADED_TO_CHUNK` (destroy=false, save=true — chunk unload, entity persists), `UNLOADED_WITH_PLAYER` and `CHANGED_DIMENSION` (neither destroyed nor saved standalone — carried across by the caller).

Movement bookkeeping caps at `MAX_MOVEMENTS_HANDELED_PER_TICK = 100`: an `ArrayDeque<Entity.Movement>` records sub-tick movement segments (used for block-collision event detection such as trampling and pressure plates) and is capped to avoid pathological block-crossing counts (`MAX_BLOCK_ITERATIONS_ALONG_TRAVEL_PER_TICK = 16` per movement step).

### 3.2 EntityType, dimensions & hitboxes

`EntityType<T extends Entity>` is an immutable registry entry built through `EntityType.Builder<T>`. Key builder knobs: `sized(width, height)` → `EntityDimensions.scalable`, `eyeHeight(float)` (overrides the default `height * 0.85`), `clientTrackingRange(int)` (defaults to 5 *chunks*), `updateInterval(int)` (defaults to 3 ticks — how often a full position/rotation resync packet is forced even without movement), `fireImmune()`, `immuneTo(TagKey<Block>)` (defaults to `BlockTags.DEFAULT_IMMUNE_TO`), `canSpawnFarFromPlayer()` (auto-true for `CREATURE`/`MISC` categories), `noSummon()`/`noSave()`, `notInPeaceful()`, `requiredFeatures(...)` (feature-flag gating), attachment points (`passengerAttachments`, `vehicleAttachment`/`ridingOffset`, `nameTagOffset`).

`EntityDimensions` is a record: `(width, height, eyeHeight, EntityAttachments attachments, boolean fixed)`. `fixed` dimensions (used by e.g. block-display entities sized 0×0) never rescale; non-fixed ones support `.scale(factor)` for pose/age/potion-effect driven resizing (baby mobs, dragon-fireball-shrunk creepers, `SCALE` attribute, etc.) — scaling multiplies width/height/eyeHeight and rescales attachment points but is a no-op if the scale factor is 1.0. `makeBoundingBox(pos)` centers the AABB on `(x,y,z)` horizontally and extrudes upward by `height`.

`EntityType.spawn(...)`/`.create(...)` is the canonical construction path used by commands, spawn eggs, and structure loaders: it constructs via the registered `EntityFactory`, positions the entity (optionally probing downward for the first non-colliding Y via `getYOffset`, using `Shapes.collide`), randomizes yaw, and — if the result is a `Mob` — calls `finalizeSpawn` (see §3.9) before adding it to the level.

### 3.3 SynchedEntityData (data watcher protocol)

`SynchedEntityData` (package `net.minecraft.network.syncher`) is the entity data-watcher: a fixed-size array of `DataItem<T>` slots indexed by a small integer id, one instance per entity. IDs are **not** globally unique — they are assigned per-class via a `ClassTreeIdRegistry` (`defineId(Class<? extends SyncedDataHolder>, EntityDataSerializer<T>)`), so a subclass's own `defineId` calls continue numbering from where its superclass left off; the hard cap is **254** (`MAX_ID_VALUE`, and the builder throws past that). Every subclass must define a value for every id up to the class's slot count or `Builder.build()` throws `IllegalStateException`.

Each `DataItem<T>` holds `value`, an immutable `initialValue` (used for `isSetToDefault()`, i.e. whether the field needs shipping at all in the spawn packet), and a `dirty` flag. `set(accessor, value)` is a no-op unless the new value differs (`ObjectUtils.notEqual`) or `forceDirty=true`; on an actual change it calls `entity.onSyncedDataUpdated(accessor)` synchronously (this is how e.g. pose-dependent bounding-box recompute is triggered) and marks both the item and the whole `SynchedEntityData` dirty.

Two extraction paths exist: `packDirty()` — drains and clears the dirty set, used every tick by `ServerEntity` to build an incremental `ClientboundSetEntityDataPacket`; and `getNonDefaultValues()` — a full non-default snapshot used once, when the entity first enters a player's view, to build the initial spawn packet. `DataValue<T>` (the wire record) carries `(id, serializer, value)`; `write`/`read` use a VarInt-coded serializer-type id looked up in the global `EntityDataSerializers` table, so unknown/removed serializer ids fail closed with a `DecoderException`.

### 3.4 Attributes system

`Attributes` (`ai.attributes`) registers a flat, entity-type-agnostic set of ~38 named attributes, each a `RangedAttribute(descriptionId, defaultValue, min, max)` with optional `.setSyncable(true)` (sent to the client) and `.setSentiment(POSITIVE|NEUTRAL|NEGATIVE)` (only affects tooltip coloring). See §5 for the full value table.

`AttributeInstance` holds one live attribute on one entity: a `baseValue` plus modifiers bucketed by `AttributeModifier.Operation` in three ordered groups. `getValue()` is lazily cached (`dirty` flag, invalidated on any modifier/base-value mutation) and computed as:
1. `base = baseValue`; add every `ADD_VALUE` modifier's `amount` to it.
2. `result = base`; for every `ADD_MULTIPLIED_BASE` modifier, add `base * amount` to `result` (multiple such modifiers are **additive against each other**, not compounding).
3. For every `ADD_MULTIPLIED_TOTAL` modifier, multiply `result` by `(1 + amount)` — these **do** compound with each other since they're applied sequentially to the running total.
4. Clamp via `Attribute.sanitizeValue` (the range enforced by `RangedAttribute`'s min/max).

Modifiers are keyed by `Identifier` and can be `transient` (`addTransientModifier`, not saved, used by potion-effect-style short-lived buffs) or `permanent` (`addPermanentModifier`/`addOrReplacePermanentModifier`, saved and re-applied on load — used by equipment, enchantments, and one particular vanilla case: every freshly-spawned mob gets a permanent, per-instance `ADD_MULTIPLIED_BASE` modifier on `FOLLOW_RANGE` sampled from `random.triangle(0.0, 0.11485)` in `Mob.finalizeSpawn` — a small, deterministic-looking-but-RNG-order-dependent "chase range" individuality bonus).

`AttributeSupplier` is the per-`EntityType` template: an immutable map of `Attribute → default AttributeInstance` values, built once via `AttributeSupplier.Builder` (`.add(attribute)` uses the attribute's own default; `.add(attribute, value)` overrides it) and instantiated per-entity into a mutable `AttributeMap`. `DefaultAttributes` is the master `EntityType → AttributeSupplier` table (see §5 for the composition chain: `LivingEntity.createLivingAttributes()` → `Mob.createMobAttributes()` (+`FOLLOW_RANGE`) → `Monster.createMonsterAttributes()` → concrete-mob `createAttributes()`). `DefaultAttributes.validate()` asserts every non-`MISC`-category `EntityType` has a supplier registered (logged, not thrown, in dev builds).

### 3.5 Goal system (`GoalSelector`)

The legacy AI system is a priority-ordered, flag-locking scheduler. Every `Goal` declares a `boolean canUse()` (can it start), `canContinueToUse()` (defaults to re-checking `canUse()`), `isInterruptable()` (defaults `true`), and an `EnumSet<Goal.Flag>` of exactly four control flags it exclusively needs while running: `MOVE`, `LOOK`, `JUMP`, `TARGET`.

Every `Mob` owns two independent `GoalSelector` instances: `goalSelector` (behavior goals) and `targetSelector` (goals that only set the attack/interaction target, e.g. `HurtByTargetGoal`, `NearestAttackableTargetGoal`). Each `GoalSelector.tick()` does, per call:
1. **Cleanup pass** — stop every currently-running goal whose flags now overlap a globally disabled flag (`disableControlFlag`, used e.g. while a mob is being ridden) or whose `canContinueToUse()` now returns false.
2. Drop any `lockedFlags` entry whose owning goal is no longer running.
3. **Start pass** — for every non-running goal, in **insertion order** (an `ObjectLinkedOpenHashSet`, so goals of equal priority tie-break by registration order), if none of its flags are globally disabled, and for every flag it needs the currently-locking goal `canBeReplacedBy` it (`WrappedGoal.canBeReplacedBy`: the incumbent must be interruptable **and** the challenger's numeric priority must be strictly lower — **lower number = higher priority**, priority 0 preempts everything), and `canUse()` returns true → start it, claiming all its flags (evicting/stopping whatever previously held them).
4. Tick every currently-running goal via `tickRunningGoals(true)` (force-tick).

`Mob.serverAiStep()` (declared `final`, so brain-based mobs cannot override it — they hook `customServerAiStep` instead) drives this every tick but **throttles the full re-selection pass to every other tick** based on entity-id parity: `if ((tickCount + entityId) % 2 != 0 && tickCount > 1)` only `tickRunningGoals(false)` runs (which only ticks goals whose `requiresUpdateEveryTick()` is true), skipping the expensive `canUse()`/`canContinueToUse()` sweep entirely on the "off" tick. This is a deliberate load-spreading trick: across a population of mobs, roughly half re-evaluate their AI on any given tick, staggered by entity id so they don't all recompute in lockstep.

Representative goals surveyed (non-exhaustive, by category): movement — `RandomStrollGoal`/`WaterAvoidingRandomStrollGoal`/`RandomSwimmingGoal`, `FollowParentGoal`, `FollowOwnerGoal`, `MoveTowardsRestrictionGoal`, `PanicGoal`, `FloatGoal` (swim-up-when-in-water, priority 0 on almost every mob); combat — `MeleeAttackGoal`, `RangedAttackGoal`/`RangedBowAttackGoal`/`RangedCrossbowAttackGoal`, `ZombieAttackGoal` (extends `MeleeAttackGoal`), `AvoidEntityGoal`, `LeapAtTargetGoal`, `SwellGoal` (Creeper fuse-approach); breeding/taming — `BreedGoal`, `TemptGoal`, `SitWhenOrderedToGoal`; village-interaction — `MoveThroughVillageGoal`, `GolemRandomStrollInVillageGoal`; doors — `OpenDoorGoal`/`BreakDoorGoal`/`DoorInteractGoal`; look — `LookAtPlayerGoal`, `RandomLookAroundGoal`. Targeting: `HurtByTargetGoal` (retaliate against whatever last damaged this mob), `NearestAttackableTargetGoal<T>` (generic nearest-of-type finder taking an optional `TargetingConditions`-style selector predicate), `DefendVillageTargetGoal` (golems), `OwnerHurtByTargetGoal`/`OwnerHurtTargetGoal` (tamed-animal owner defense).

### 3.6 Brain / behavior system

The newer system layers on top of the same `Mob`/`LivingEntity` chassis rather than replacing it: brain-driven mobs still own an (often empty or near-empty) `GoalSelector`, but their real decision-making runs through `LivingEntity.brain : Brain<?>`, ticked from inside their `customServerAiStep` override (Villager, all Piglin variants, Hoglin/Zoglin, Warden, Allay, Frog/Tadpole, Goat, Camel, Armadillo, Sniffer, Breeze, Creaking, HappyGhast, CopperGolem, Nautilus/ZombieNautilus — confirmed by grep for `Brain<...>` field declarations under `world.entity`).

**Memory** (`ai.memory`): `MemoryModuleType<U>` is a typed registry key (~90 entries — walk/look/attack/breed/interaction targets, hurt-by, nearest-X sensors' outputs, per-mob cooldown/state flags). A `MemorySlot<T>` wraps an `ExpirableValue<T>` (value + optional countdown-to-live in ticks); `Brain.forgetOutdatedMemories()` runs every brain tick before anything else and decrements/clears expired slots. `MemoryStatus` is a 3-state check used everywhere as a behavior precondition: `REGISTERED` (slot exists, value irrelevant), `VALUE_PRESENT`, `VALUE_ABSENT`.

**Sensors** (`ai.sensing`): a `Sensor<E>` populates memories from the surrounding world every `tick()` call (each sensor self-declares which `MemoryModuleType`s it `requires()`, auto-registering their slots on the owning brain). `Brain.tick()` runs sensors before behaviors, unconditionally, every tick — sensors are **not** throttled the way goals are. ~23 `SensorType`s exist, notably: `NEAREST_LIVING_ENTITIES`, `NEAREST_PLAYERS`, `NEAREST_ITEMS`, `NEAREST_BED`, `HURT_BY`, species-specific pairs (`PIGLIN_SPECIFIC_SENSOR`/`PIGLIN_BRUTE_SPECIFIC_SENSOR`/`HOGLIN_SPECIFIC_SENSOR`, `VILLAGER_HOSTILES`/`VILLAGER_BABIES`/`SECONDARY_POIS`/`GOLEM_DETECTED`, `AXOLOTL_ATTACKABLES`/`FROG_ATTACKABLES`, `WARDEN_ENTITY_SENSOR`, `BREEZE_ATTACK_ENTITY_SENSOR`), and generic `FOOD_TEMPTATIONS`/`FROG_TEMPTATIONS`/`NAUTILUS_TEMPTATIONS` (each parameterized with a per-mob temptation-item predicate supplied by that mob's `*Ai` helper class, e.g. `FrogAi.getTemptations()`). Separately, `Sensing` (singular, one per `Mob`, **not** the same class as `Sensor`) is a tiny per-tick line-of-sight cache keyed by target entity id (two `IntSet`s, `seen`/`unseen`, cleared every tick) so repeated `hasLineOfSight(target)` checks within one tick don't re-raycast.

**Behaviors** (`ai.behavior`): `Behavior<E>` is a `BehaviorControl<E>` with an explicit two-state lifecycle (`Status.STOPPED`/`RUNNING`) and a **randomized duration**: on `tryStart`, if `hasRequiredMemories` and `checkExtraStartConditions` both pass, it picks a random tick duration uniformly between constructor-supplied `minDuration` and `maxDuration` (default both 60) and commits to an `endTimestamp`; `tickOrStop` calls the subclass's `tick()` while `!timedOut && canStillUse()`, otherwise force-stops it. This randomized-duration mechanic is why brain-driven mobs don't hard-lock onto one behavior indefinitely even when its condition stays true.

Behaviors are organized into `Activity`-scoped priority buckets: `Brain.addActivity(Activity, priorityPairs, entryMemoryConditions, memoriesToEraseOnStop)` stores each `(priority, Behavior)` pair in a `TreeMap<Integer, Map<Activity, Set<BehaviorControl>>>` (so lower-numbered priority buckets are considered first, mirroring goal priority). Every brain tick, `startEachNonRunningBehavior` walks that map in priority order and, for each behavior belonging to a **currently active** `Activity`, calls `tryStart` if it's stopped; `tickEachRunningBehavior` then ticks every behavior that's actually running, across all priorities/activities, in one flat pass.

**Activities** (`entity.schedule.Activity`, ~26 registered: `CORE`, `IDLE`, `WORK`, `PLAY`, `REST`, `MEET`, `PANIC`, `RAID`, `PRE_RAID`, `HIDE`, `FIGHT`, `CELEBRATE`, `ADMIRE_ITEM`, `AVOID`, `RIDE`, `PLAY_DEAD`, `LONG_JUMP`, `RAM`, `TONGUE`, `SWIM`, `LAY_SPAWN`, `SNIFF`, `INVESTIGATE`, `ROAR`, `EMERGE`, `DIG`) — a brain has a fixed `coreActivities` set (always active, default `{CORE}`) plus at most one non-core "current" activity at a time. `setActiveActivity` clears and rebuilds `activeActivities = coreActivities ∪ {activity}`, and erases any memory the *previous* activity registered as `memoriesToEraseWhenStopped` — this is the mechanism that, e.g., forgets a villager's walk target the instant it switches from WORK to PANIC. `setActiveActivityToFirstValid(List<Activity>)` scans a priority-ordered candidate list and commits to the first whose `activityRequirements` (a set of `(MemoryModuleType, MemoryStatus)` pairs, e.g. "WORK requires JOB_SITE present") are satisfied, falling back to `useDefaultActivity()` (usually `IDLE`) otherwise.

Composition helpers used heavily in behavior lists rather than writing new `Behavior` subclasses: `RunOne` (weighted random pick of one sub-behavior per activation, re-rolled once it stops), `GateBehavior` (runs a fixed sub-set of behaviors only while certain memory conditions hold, then optionally clears them — used for e.g. "only trade while `INTERACTION_TARGET` is present"), `TriggerGate` (variant used for shuffled one-shot triggering), and the `BehaviorBuilder` declarative DSL (`sequence(...)`, `triggerIf(predicate)`) for short conditional chains without a full class.

### 3.7 Villager schedule in detail

The villager is the fullest showcase of the brain system. `Villager.brainProvider()` registers 9 sensors (`NEAREST_LIVING_ENTITIES`, `NEAREST_PLAYERS`, `NEAREST_ITEMS`, `NEAREST_BED`, `HURT_BY`, `VILLAGER_HOSTILES`, `VILLAGER_BABIES`, `SECONDARY_POIS`, `GOLEM_DETECTED`) and 7 `Activity` packages built by the standalone `VillagerGoalPackages` class (not inline in `Villager.java`):

| Activity | Requires (to enter) | Representative behaviors |
|---|---|---|
| `CORE` (always active) | — | swim, door interaction, look-at-target sink, panic trigger, wake-up, bell reaction, raid-status set, POI-slot validation/acquisition (job site → home → meeting point), profession (re)assignment |
| `WORK` | `JOB_SITE` memory present | `WorkAtPoi` (or `WorkAtComposter` for farmers), stroll around/to job site, harvest farmland / apply bonemeal (farmer), show trades, `UpdateActivityFromSchedule` re-check at priority 99 |
| `PLAY` (baby only) | — | tag with other kids, interact with villagers/cats, village-bound stroll, jump on bed |
| `REST` | — | walk to home bed, validate home POI, sleep in bed, fallback wandering if homeless |
| `MEET` | `MEETING_POINT` present | stroll around meeting point, socialize at bell, trade, gift-to-hero |
| `IDLE` | — | interact/breed with nearby villagers and cats, village-bound stroll, gift-to-hero, trade |
| `PANIC` | — | calm-down check, flee from nearest hostile/hurt-by-entity, village-bound stroll at 1.5× speed |
| `PRE_RAID` / `RAID` / `HIDE` | raid state | ring bell, move to meeting point / sky-seeing spot, locate + move to hiding place |

Every non-panic, non-raid activity package ends with an `UpdateActivityFromSchedule.create()` behavior at priority **99** (lowest priority = last considered, but still runs every tick since it's always eligible) that re-samples the schedule and can pre-empt the current activity mid-tick. `Brain.updateActivityFromSchedule(EnvironmentAttributeSystem, gameTime, pos)` throttles the actual re-sample to once per **20 ticks** (`SCHEDULE_UPDATE_DELAY`); it asks the villager's own registered `EnvironmentAttribute<Activity>` (`EnvironmentAttributes.VILLAGER_ACTIVITY` for adults, `BABY_VILLAGER_ACTIVITY` for babies — position/time-sampled, **not** the old hardcoded `Schedule`/`Timeline` day-cycle table) for the currently-scheduled `Activity`, and if the brain isn't already in it, calls `setActiveActivityIfPossible` (which itself falls back to `IDLE` if that activity's memory requirements aren't met — e.g. scheduled `WORK` but no `JOB_SITE` yet).

Trading is data-driven, not hardcoded per profession in Java: `VillagerProfession` (15 professions: `NONE`, `ARMORER`, `BUTCHER`, `CARTOGRAPHER`, `CLERIC`, `FARMER`, `FISHERMAN`, `FLETCHER`, `LEATHERWORKER`, `LIBRARIAN`, `MASON`, `NITWIT`, `SHEPHERD`, `TOOLSMITH`, `WEAPONSMITH`, plus `WanderingTrader`) registers, per trading level 1–5, a `TradeSets` holder resolved from the `trade_set`/`villager_trade` datapack registries (§7) rather than the historical hardcoded `VillagerTrades.ItemListing[]` tables.

### 3.8 Navigation & pathfinding

`PathNavigation` (abstract) owns one `NodeEvaluator` + one `PathFinder`, constructed with `maxVisitedNodes = floor(FOLLOW_RANGE attribute × 16)`. Five concrete navigations pick the evaluator: `GroundPathNavigation`→`WalkNodeEvaluator`, `FlyingPathNavigation`→`FlyNodeEvaluator` (extends walk), `WaterBoundPathNavigation`→`SwimNodeEvaluator`, `AmphibiousPathNavigation`→`AmphibiousNodeEvaluator` (extends walk), `WallClimberNavigation` extends `GroundPathNavigation` (spiders).

Path (re)computation: `recomputePath()` is rate-limited to once per **20 game-ticks** (`MAX_TIME_RECOMPUTE`) — a call within that window just sets `hasDelayedRecomputation = true` and defers. `createPath` builds a `PathNavigationRegion` (a snapshotted chunk-cache window) sized to `maxPathLength + radiusOffset` blocks around the mob (radius offset 8 for a block-position target, 16 for an entity target, since entities move) and hands it to `PathFinder.findPath`.

**`PathFinder` A\*** (`level.pathfinder.PathFinder`): classic A* over `Node`s keyed by integer block coordinates. `g` = accumulated cost, `h` = heuristic (`Node.distanceTo`, straight-line, scaled ×1.5 — the `FUDGING` constant — to bias the search toward greedily approaching the goal and bound runtime), `f = g + h`, stored in a custom `BinaryHeap` open-set. Each expansion step adds `distance(current, neighbor) + neighbor.costMalus` to `g` — so a neighbor's `PathType`-derived malus is a **flat additive cost**, not a probability or a hard block (only `costMalus < 0` behaves as impassable, via `isNeighborValid`'s `neighbor.costMalus >= 0 || current.costMalus < 0` check, which specially allows a path to *leave* an already-malus'd node like water). Search terminates early the moment any target is within Manhattan `reachRange` of the current best node, or after `maxVisitedNodes × maxVisitedNodesMultiplier` node expansions, whichever comes first; if no target was ever reached the closest-approach node (tracked continuously via `Target.updateBest`) is used to build a "best effort" unreached path instead of failing outright.

**`WalkNodeEvaluator.getNeighbors`**: examines the 4 cardinal directions first, then the 4 diagonals — but a diagonal is only considered if **both** adjacent cardinal neighbors are themselves valid (`isDiagonalValid`), preventing the path from cutting through a solid corner. Vertical step-up size is `floor(max(1, mob.maxUpStep()))` (i.e. driven by the `STEP_HEIGHT` attribute, default 0.6 → still yields a 1-block step), and is disabled entirely (`jumpSize = 0`) if the block directly above the mob has a negative pathfinding malus or the mob is standing in sticky honey.

`PathType` (level.pathfinder) has a fixed default malus per terrain classification (see §5); `Mob.getPathfindingMalus(PathType)`/`setPathfindingMalus(PathType, float)` let a concrete mob override any of these per-instance (e.g. spiders zero out `FENCE`'s malus (climbing), most land mobs set `WATER`'s malus very high to avoid swimming, blaze/ghast reduce `LAVA`/`DAMAGING`).

Stuck detection (`PathNavigation.doStuckDetection`, checked every 100 ticks) compares distance actually traveled against `effectiveSpeed² × 100 × 0.25`; if the mob hasn't moved far enough it's flagged `isStuck` and the path is aborted. A separate per-waypoint timeout (`timeoutLimit = distanceToNextNode / speed × 20`, tripped at `3×` that limit) catches a mob wedged trying to reach one specific node.

Random-destination sampling for wander/panic/flee goals lives in `ai.util`: `LandRandomPos`, `AirRandomPos`, `AirAndWaterRandomPos`, `HoverRandomPos`, `DefaultRandomPos` — all build on `RandomPos`'s generic "sample N candidate offsets, score by a caller-supplied `ToDoubleFunction<BlockPos>` (usually `Mob.getWalkTargetValue`), keep the best" pattern; `Monster.getWalkTargetValue` specifically returns the **negated** light-level pathfinding cost, i.e. monsters bias their random wandering toward darker ground.

### 3.9 Natural spawning

`NaturalSpawner` (`world.level`) runs once per server tick per level, gated by `emptyTime < 300` (i.e. spawning pauses entirely once no chunk has had a ticket for 300 ticks / 15s). The mob-cap formula, evaluated per `MobCategory` (excluding `MISC`, which is never naturally spawned): a category may spawn more only while `currentCount < category.maxInstancesPerChunk × spawnableChunkCount / 289` — `289 = 17²` (`MAGIC_NUMBER`) is the reference chunk-count baseline the per-chunk caps (`MobCategory.getMaxInstancesPerChunk()`, see §5) were tuned against, so the effective world-wide cap scales linearly with the number of currently-loaded "spawnable" chunks (chunks with an active spawning ticket, tracked separately per-chunk via `LocalMobCapCalculator` for a secondary **local** per-chunk-neighborhood cap).

Per eligible chunk, `spawnCategoryForChunk` picks one random column position (`getRandomPosWithin`, X/Z uniform in the 16×16 column, Y uniform between world min and one above the motion-blocking heightmap) and attempts **3 spawn-group tries**, each placing up to `ceil(random.nextFloat()×4)` mobs in a random walk (±5 block X/Z jitter per step) around that anchor, subject to: player-distance gate (`nearestPlayerDistanceSqr > 576` i.e. > 24 blocks, `MIN_SPAWN_DISTANCE`), world-spawn-point exclusion (must be >24 blocks from the map spawn), the biome's `MobSpawnSettings` weighted mob list (or the hardcoded Nether-fortress override table when standing on nether bricks inside fortress structure bounds), `EntityType.canSummon()`, `SpawnPlacements` placement-type + height-map check, `SpawnPlacements.checkSpawnRules` (per-mob predicate, e.g. light level), and finally a `noCollision` AABB test. A successful spawn extends the group up to `SpawnerData.minCount..maxCount`, capped overall at `Mob.getMaxSpawnClusterSize()` (default **4**) unless `isMaxGroupSizeReached` (default false, i.e. unbounded within that cap) says otherwise.

**Placement types** (`SpawnPlacementType` implementations in `SpawnPlacementTypes`): `ON_GROUND` (block below must be a valid spawn surface for the type, the target block and the block above must both be non-solid/non-signal/fluid-free/non-dangerous — `NaturalSpawner.isValidEmptySpawnBlock`), `IN_WATER` (target block must be a water fluid and the block above not a full redstone-conductor), `IN_LAVA` (target block must be lava), `NO_RESTRICTIONS` (always ok — used by phantoms, shulkers, evokers/illusioners/vindicators/vex, panda, fox, wandering trader, warden).

**Monster darkness gate** (`Monster.isDarkEnoughToSpawn`, feeding `checkMonsterSpawnRules`): sky-light brightness must not exceed `random.nextInt(32)` (so it's probabilistic, not a hard threshold — brighter skylight makes spawning progressively less likely rather than flipping off at one value), block-light must not exceed the dimension's `monsterSpawnBlockLightLimit` (usually well below 15), and overall local raw brightness (using a widened 10-block sample radius while thundering) must not exceed the dimension's `monsterSpawnLightTest` sampled curve. `checkSurfaceMonstersSpawnRules` additionally requires open sky (`level.canSeeSky`) unless the spawn reason is a spawner block.

Persistence/despawn (`Mob.checkDespawn`, called every tick from the entity-tick loop before the actual AI/physics tick): peaceful-only mobs are discarded outright on `Difficulty.PEACEFUL`. Otherwise, unless `isPersistenceRequired()` (named, leashed, tamed, carrying data, etc. — mob-specific override) or `requiresCustomPersistence()` (currently a passenger or leashed), it finds the nearest player and: if farther than the category's `despawnDistance` (squared) **and** `removeWhenFarAway(distSqr)` (default `true` for all mobs, overridable), discards immediately; separately, if `noActionTime > 600` ticks (30s with no AI-relevant activity) there's a `1/800` chance per tick to instant-despawn once beyond the category's `noDespawnDistance` (always **32** blocks, `MobCategory.getNoDespawnDistance()`); `noActionTime` itself resets to 0 whenever the mob is within the no-despawn radius.

### 3.10 Breeding & taming

`AgeableMob` tracks age as a single signed tick counter: negative = baby counting up toward adulthood, `BABY_START_AGE = -24000` (20 real minutes at 20 tps), zero or positive = adult (a positive value is "forced adult lock" bookkeeping, e.g. breeding cooldown). Age advances/regresses by 1 per tick in `ageUp`/`ageDown` and crosses the `0` boundary exactly once to fire `ageBoundaryReached()`. Age-locking (`AGE_LOCKED` synced boolean) is a distinct, separate 26.x mechanic — golden-dandelion item use — with its own 40-tick cooldown, unrelated to breeding.

`Animal` (extends `AgeableMob`) adds breeding: `inLove` is a plain tick counter, set to **600** (30s) when a valid breeding item is fed (`setInLove`), decremented every tick, and every 10th tick while active spawns heart particles. `BreedGoal` (a plain `Goal`, priority-driven — breeding uses the legacy system even on some brain-based animals, via a wrapper `AnimalMakeLove`/`VillagerMakeLove` behavior for the brain path) scans within an 8-block `TargetingConditions.forNonCombat()` radius for the nearest same-species partner that's also `isInLove()` and not panicking; once within 3 blocks (`distanceToSqr < 9.0`) for 60 ticks (`loveTime`, throttled like other goals via `adjustedTickDelay`) it calls `spawnChildFromBreeding`, which sets **both** parents' age to `PARENT_AGE_AFTER_BREEDING = 6000` (5 minutes) as a shared breeding cooldown, resets `inLove`, and spawns the offspring via the mob's `getBreedOffspring` hook.

`TamableAnimal` adds an owner reference (`DATA_OWNERUUID_ID`, a synced `Optional<EntityReference<LivingEntity>>`) and sit-state (`DATA_FLAGS_ID` bit 0 = "ordered to sit", bit 2 = "interested"/begging animation). Owner-following teleport kicks in once the pet is farther than `TELEPORT_WHEN_DISTANCE_IS_SQ = 144` (12 blocks) from its owner, and lands it 2–3 blocks away horizontally / within 1 block vertically of the owner.

### 3.11 Entity ticking order & the entity manager

Per-level entity storage lives in `world.level.entity`: `PersistentEntitySectionManager` indexes every loaded entity twice — spatially into `EntitySectionStorage<T>` (a sparse `Long2ObjectOpenHashMap<EntitySection<T>>` keyed by packed 16³-block `SectionPos`, each `EntitySection` internally a `ClassInstanceMultiMap` for fast type-filtered AABB queries; an AABB query pads the query box by 2 blocks horizontally, 4 blocks below, 0 above before resolving overlapped sections) and by id/UUID via `EntityLookup`/`UUIDLookup`. Each section also carries a `Visibility` tri-state (`HIDDEN` < `TRACKED` < `TICKING`, derived from the owning chunk's `FullChunkStatus`) — only `TICKING`-visible entities are eligible for the per-tick AI/physics pass.

`EntityTickList` is the flat per-level "who ticks this tick" set: an `Int2ObjectLinkedOpenHashMap` (insertion-ordered) that supports safe mutation-during-iteration by swapping to a shadow copy (`ensureActiveIsNotIterated`) the instant an add/remove happens while a `forEach` is in progress, rather than throwing `ConcurrentModificationException`.

`ServerLevel.tick()` order, top to bottom: world border → weather → sleep-skip check → sky brightness → game time advance → pending block ticks then fluid ticks (each capped at 65536 scheduled events per call) → raids → chunk source tick → block events → **entities** (only if `emptyTime < 300`): ender-dragon-fight tick first if present, then `entityTickList.forEach`: for each non-removed, non-frozen (tick-rate-manager-respecting) entity — `checkDespawn()` always runs; the actual `tickNonPassenger` only runs if the entity is a `ServerPlayer` **or** its chunk is within the chunk-map's entity-ticking distance (mounted passengers are skipped here and ticked recursively instead — see below) — then block entities tick.

`tickNonPassenger(entity)`: `setOldPosAndRot()`, increment `tickCount`, call `entity.tick()` (which for `LivingEntity` chains into `aiStep()` → `serverAiStep()`/brain-tick as described above, then physics/collision), then recursively `tickPassenger(entity, passenger)` for every rider — **the vehicle always ticks fully before any of its passengers**, and a passenger only rides (`rideTick()`, not a full `tick()`) rather than independently pathing/AI-ing while mounted; passenger chains recurse arbitrarily deep (a rider's own riders tick after it).

## 6. Cross-subsystem interfaces

**Consumes from:**
- **World/chunks** (`03-world-chunks-persistence.md`): block/fluid states for collision, pathfinding cost lookup, heightmaps for spawn-Y and natural-spawn candidate columns; chunk `FullChunkStatus` drives `Visibility`/ticking eligibility.
- **Worldgen** (`04-worldgen-parity.md`): per-biome `MobSpawnSettings` (weighted spawner lists + spawn "cost"/energy budget consumed by `NaturalSpawner.SpawnState`'s potential-field throttling), structure bounds (Nether fortress override table, structure-gated variant spawn conditions).
- **Game mechanics** (`05-game-mechanics.md`): damage sources/combat resolution consumed by `HURT_BY` memory/sensor and `HurtByTargetGoal`; potion effects and equipment feed attribute modifiers; loot tables referenced by `EntityType.getDefaultLootTable()`.
- **Protocol/networking** (`02-protocol-networking.md`): `SynchedEntityData` and attribute sync are the payloads of `ClientboundSetEntityDataPacket`/`ClientboundUpdateAttributesPacket`; `EntityType.clientTrackingRange`/`updateInterval`/`trackDeltas()` drive `ServerEntity`'s per-viewer tracking decisions.
- **`world.attribute` environment-attribute system**: villager (and baby-villager) work/idle/sleep scheduling is sampled from `EnvironmentAttributes.VILLAGER_ACTIVITY`/`BABY_VILLAGER_ACTIVITY` rather than a hardcoded day-cycle table — this is a different subsystem this document treats as an external dependency, not part of Entities & AI itself.
- **Item/trading** (`world.item.trading`): villager trade offers are resolved from data (`trade_set`/`villager_trade` registries) through `VillagerProfession`'s registered `TradeSets`, not hardcoded Java listings.

**Provides to:**
- **Protocol/networking**: entity spawn/move/animation packets are built from `Entity`/`LivingEntity` state every tick.
- **World/chunks**: entities are saved/loaded per-chunk via `EntityPersistentStorage`, keyed into the same section grid as blocks.
- **Modding API** (`06-modding-api.md`): `Goal`, `Behavior`, `MemoryModuleType`, `SensorType`, `Attribute`, and `EntityType` are all registry-based extension points a mod can add entries to.
- **Cluster architecture** (`13-cluster-architecture.md`): entity ownership/handoff must preserve `Brain` memory state, `GoalSelector` running-goal state, and `PathNavigation` in-flight paths across a sector boundary crossing — none of vanilla's in-process AI state has a native serialize/deserialize path (it's rebuilt from `Brain.Packed`/memory codecs on load, not hot-migrated), which is a design point Rusty Clanker's cluster mode must solve explicitly (see §8).

## 7. Data-generator cross-reference

Under `datagen/generated/reports/`: `blocks.json` (block properties consumed by `PathType`/`NodeEvaluator` classification and `SpawnPlacements` surface checks), `registries.json` (confirms the full `entity_type`, `attribute`, `memory_module_type`, `activity`, `villager_profession`, `sensor_type` registry contents), `datapack.json` (worldgen/entity-related datapack registry list).

Under `datagen/generated/data/minecraft/`:
- **`worldgen/biome`** (via `blocks.json`/`registries.json` cross-reference, not a standalone folder in this domain) supplies each biome's `MobSpawnSettings` mob-spawner tables consumed by `NaturalSpawner`.
- **`cat_variant/`**, **`cat_sound_variant/`**: per-cat-texture spawn-condition records — `asset_id`/`baby_asset_id` + a priority-ordered `spawn_conditions` list (`structure`-tag and `moon_brightness`-range condition types observed).
- **`wolf_variant/`**, **`wolf_sound_variant/`**: richer variant record with separate `assets`/`baby_assets` maps each keyed `angry`/`tame`/`wild`, plus `biome`-type spawn conditions.
- **`chicken_variant/`**, **`chicken_sound_variant/`**, **`cow_variant/`**, **`cow_sound_variant/`**, **`pig_variant/`**, **`pig_sound_variant/`**: same variant/spawn-condition pattern for the remaining "visual variant" farm animals.
- **`frog_variant/`**: frog skin variants (biome-linked, matching the frog's swamp/warm/cold classification).
- **`zombie_nautilus_variant/`**: single-entry variant registry for the new Zombie Nautilus (26.x mob), `spawn_conditions` currently trivial (priority-0, unconditional) — i.e. only one visual variant exists so far.
- **`painting_variant/`**: painting artwork registry (size + asset id per painting), consumed by `Painting`/`entity.decoration.painting`, not AI-relevant but co-located with the other variant registries.
- **`villager_trade/<profession>/<level 1-5>/*.json`**: individual trade records — `wants` (1 or 2 `ItemStack`-shaped cost entries), `gives` (result), `max_uses`, `reputation_discount` (how much per-player reputation reduces effective price).
- **`trade_set/<profession>/level_<n>.json`**: groups a tag-referenced pool of trade records (`trades: "#minecraft:<profession>/level_<n>"`) with a `random_sequence` (deterministic-shuffle seed key) and `amount` (how many of the pool are offered simultaneously) — this is what `VillagerProfession`'s per-level `TradeSets` entries resolve to at runtime.

## 8. Notes for Rusty Clanker

- **Two full AI engines coexist, not one replacing the other.** A correct reimplementation needs the priority `GoalSelector` machinery *and* the `Brain`/`Behavior`/`Sensor` machinery simultaneously — brain-driven mobs still carry (often-empty) goal selectors, and some cross-cutting behaviors (breeding, being ridden, sitting) are implemented once in the legacy system and reused by brain-based mobs via thin wrapper goals/behaviors. Treat these as two ECS-side scheduling systems that must be able to run per-entity, not "the new one" and "the deprecated one."
- **The goal-selector half-tick throttle (`(tickCount + entityId) % 2`) is a determinism hazard disguised as an optimization.** It makes goal re-evaluation timing depend on the entity's numeric id, which in vanilla is assignment-order and therefore **not** stable across a save/reload or across a cluster hand-off unless ids are preserved exactly. Any parity-based load-spreading trick in the Rust port needs an explicitly defined, save-stable key (not "whatever id the allocator happened to hand out this session") if bit-identical behavior across restarts is required.
- **Modifier-order matters and is easy to get subtly wrong.** `ADD_VALUE` sums onto base, `ADD_MULTIPLIED_BASE` modifiers are mutually additive against the *original* base (not against each other), and only `ADD_MULTIPLIED_TOTAL` modifiers compound against the running total. A naive "apply all modifiers in registration order with one running total" implementation gives different numbers than vanilla the moment more than one modifier of the same operation is present.
- **`SynchedEntityData` ids are per-class-hierarchy-position, not globally stable.** They're assigned by call order of `defineId` up the class chain at class-load time. A Rust ECS component-based reimplementation doesn't need to reproduce this exact numbering scheme (it only has to match the *wire* semantics per entity type for protocol compatibility), but the numbering **is** part of the wire protocol per `EntityType`, so it must be derived once, pinned, and never silently reordered by refactoring — reordering `defineSynchedData` calls changes packet contents.
- **Natural spawning's mob cap is chunk-count-relative, not player-count-relative directly** (`spawnableChunkCount / 289`), and combines a *global* per-category cap with a *separate local per-chunk-neighborhood* cap (`LocalMobCapCalculator`). Both must be reproduced together — implementing only the global formula under-spawns relative to vanilla in sparse-player, large-loaded-area scenarios (exactly the shape of monolithic-mode dedicated servers this project targets) and cluster mode additionally needs this cap computed per **spatial partition**, not per node, to stay observationally equivalent to monolithic per the project's dual-mode requirement.
- **Villager scheduling is no longer a static hardcoded day-cycle table in this version.** It flows through the generic `world.attribute.EnvironmentAttribute<Activity>` sampler (position + game-time sampled, invalidated once per tick via `invalidateTickCache()`). This is architecturally significant: it means "what should this villager be doing right now" is answered by the *same* general-purpose spatial-attribute system that (per `world.attribute`'s other registrations) also drives weather-linked ambience — a Rust port should probably model this as one generic "sampled environment field" abstraction reusable well beyond villagers, rather than a villager-specific clock.
- **Redstone/scheduled-block-tick sequencing (ARCH policy: always single-worker per region) interacts with entity ticking order**, since `ServerLevel.tick()` runs block/fluid ticks *before* the entity pass in the same region tick — path-affecting block changes (doors opening, water flow) from this tick's block ticks are visible to this same tick's pathfinding and `NodeEvaluator` block-state reads. Splitting entity AI onto worker threads separate from the single redstone/block-tick worker (as ARCH's ECS/executor design implies) must preserve this within-tick ordering per region, or mob pathing decisions will read stale terrain relative to vanilla.
- **Cross-partition/cluster hand-off has no native serialize path for AI state in vanilla** — `Brain` memories serialize via `Brain.Packed`/per-`MemoryModuleType` codecs (only the subset with `canSerialize()==true`, i.e. a registered `Codec`), but **running** `Behavior`/`Goal` state (what's mid-execution, `WrappedGoal.isRunning`, in-flight `Path`, `MoveControl`/`JumpControl` operation state) is transient and just gets rebuilt from scratch (`makeBrain`, fresh `GoalSelector`) whenever an entity is reloaded — vanilla only ever does this at chunk load, never at 60fps mid-tick. Zero-disconnect cluster sector handoff (`CLUSTER-` policy) crossing an owning-node boundary needs an explicit answer for what happens to a mob's in-flight `Path`/running `Behavior`/goal-selector lock state, since vanilla's own answer ("stop everything and rebuild from persisted memories") would visibly glitch a live handoff.
- **Per-spawn RNG-order dependent individuality** (the `FOLLOW_RANGE` triangle-distributed bonus, `Mob.finalizeSpawn`'s 5% left-handed roll) consumes the level's shared `RandomSource` at spawn time in a fixed method-call order. For bit-identical parity, spawn-time attribute randomization must consume the RNG in exactly this order relative to every other RNG draw in the same spawn call (placement jitter, group size, etc.), which constrains how spawning logic can be parallelized across a work-stealing executor — this is exactly the kind of "vanilla parity is bit-identical by default" case (per this project's binding principles) that needs the RNG draws serialized in a defined order even if the surrounding spawn-candidate search runs concurrently.
