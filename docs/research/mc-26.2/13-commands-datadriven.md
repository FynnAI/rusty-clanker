# Commands, Registries & Data-Driven Core — Vanilla 26.2 Research

## 1. Purpose

This subsystem is the spine that every other server feature is wired into. It comprises three tightly coupled layers: (1) **Brigadier**, the command-tree parser/dispatcher and its ~57 vanilla argument types; (2) the **command execution model** — permission gating, the `CommandSourceStack`, the queue-based executor that runs `/execute` chains, forks and `.mcfunction` files with bounded cost; and (3) the **registry system** — `Registry`/`Holder`/`HolderSet`, the four-layer `RegistryAccess` stack, the codec-driven loader that turns datapack JSON into frozen, tag-bound, network-synchronized registries, and the `ResourceManager`/`PackRepository` machinery that discovers and stacks the packs those JSON files come from. Nearly every vanilla feature (blocks, items, worldgen, loot, recipes, advancements, dialogs, permissions themselves) is expressed as either a **built-in** (code-registered, Java-defined) or **data-driven** (datapack JSON, codec-decoded) `Registry<T>`, and commands are the primary way a player or `.mcfunction` script reaches into that data.

## 3. How it works

### 3.1 Brigadier integration and the dispatcher

Brigadier itself (`com.mojang.brigadier.*`) is a separate MIT-licensed library and is **not present in this decompile** (only `net.minecraft` and `com.mojang.math` are decompiled sources); its API surface below is reconstructed from how `net.minecraft.commands` calls into it.

`Commands` owns one `CommandDispatcher<CommandSourceStack>` (`com.mojang.brigadier.CommandDispatcher`) built once per `Commands` instance (one instance per world/registry reload — see §3.9). Registration uses the builder DSL: `Commands.literal(name)` → `LiteralArgumentBuilder<CommandSourceStack>`, `Commands.argument(name, ArgumentType<T>)` → `RequiredArgumentBuilder<CommandSourceStack, T>`, chained with `.then(...)`, `.executes(ctx -> int)`, `.requires(Predicate<CommandSourceStack>)`, and `.redirect(CommandNode)`/`.fork(CommandNode, RedirectModifier)` (used heavily by `ExecuteCommand` for `execute … run`, and command aliasing).

Parsing/execution flow (`Commands.performPrefixedCommand` → `performCommand`):
1. `dispatcher.parse(command, source)` → `ParseResults<CommandSourceStack>` (pure parse, no side effects, can partially fail per node — errors accumulate per exception-per-node in `parse.getExceptions()`).
2. `Commands.validateParseResults` picks the single relevant `CommandSyntaxException` (or synthesizes `dispatcherUnknownCommand`/`dispatcherUnknownArgument` if the reader didn't fully consume the input or context range is empty).
3. `ContextChain.tryFlatten(parse.getContext().build(input))` collapses the parsed `CommandContextBuilder` tree (which may contain **redirect chains**, e.g. `/execute … run kill`) into a linear `ContextChain` of stages (`Stage.MODIFY*` → `Stage.EXECUTE`), or returns empty if the tree doesn't resolve to a runnable command.
4. The flattened chain is *not* run inline — it is handed to `Commands.executeCommandInContext`, which lazily creates one `ExecutionContext` per top-level invocation (see §3.4) and queues the chain as the initial work item.

Ambiguity/registration-time validation (`Commands.validate()`, run at startup with `Commands.CommandSelection.ALL` against `VanillaRegistries.createLookup()`): calls `dispatcher.findAmbiguities` (Brigadier warns on sibling nodes whose grammars overlap) and cross-checks every `ArgumentType` reachable from the root against `ArgumentTypeInfos.isClassRecognized` — an unregistered argument type is a **hard startup failure** (`IllegalStateException`), because it could never be serialized into `ClientboundCommandsPacket`.

### 3.2 Argument types

Every vanilla argument type is registered once in `ArgumentTypeInfos.bootstrap` into the built-in registry `Registries.COMMAND_ARGUMENT_TYPE` (`BuiltInRegistries.COMMAND_ARGUMENT_TYPE`), keyed by a string id (`"brigadier:integer"`, `"minecraft:entity"`, …). This id is exactly the `parser` field in the `commands.json` datagen report. **57 types are registered** (matches `registries.json`'s `minecraft:command_argument_type` entry count).

Each registration supplies an `ArgumentTypeInfo<A, Template>` — the object responsible for turning a live `ArgumentType<?>` instance into (a) a network-serializable `Template` (`ClientboundCommandsPacket` payload, so the client's own Brigadier-alike parser/tab-completion can reconstruct the same grammar) and (b) a JSON `properties` object for the `commands.json` report. Two shapes cover almost every case:
- **`SingletonArgumentInfo`** — for argument types with no construction parameters (`contextFree`, e.g. `BlockPosArgument::blockPos`) or that need a `CommandBuildContext` only to look up a `HolderLookup` at construction time (`contextAware`, e.g. `BlockStateArgument::block`, `ItemArgument::item`, `ParticleArgument::particle`). Its `Template` carries no fields; network/JSON serialization is a no-op beyond the type id.
- **Custom `Info` classes** — for parameterized types. `EntityArgument.Info` packs two booleans (`single`, `playersOnly`) into one network byte and into JSON `"amount"`/`"type"` strings. `ResourceKeyArgument.Info<T>`/`ResourceArgument.Info<T>`/`ResourceOrTagArgument.Info<T>`/etc. carry a `ResourceKey<? extends Registry<T>>` and serialize it as a `registry` identifier (network: `FriendlyByteBuf.writeResourceKey`; JSON: `"registry": "minecraft:..."`) — this is how the client learns, e.g., that a given argument slot must resolve against `minecraft:enchantment`. `RangeArgument`, `TimeArgument.Info` (minimum-value flag) follow the same pattern.

Full type roster (id → Java class → shape): `brigadier:bool/float/double/integer/long/string` (plain Brigadier), `entity`, `game_profile`, `block_pos`, `column_pos`, `vec3`, `vec2`, `block_state`, `block_predicate`, `item_stack`, `item_predicate`, `team_color`, `hex_color`, `component`, `style`, `message`, `nbt_compound_tag`, `nbt_tag`, `nbt_path`, `objective`, `objective_criteria`, `operation`, `particle`, `angle`, `rotation`, `scoreboard_slot`, `score_holder`, `swizzle`, `team`, `item_slot`, `item_slots`, `resource_location`, `function`, `entity_anchor`, `int_range`, `float_range`, `dimension`, `gamemode`, `time`, `resource_or_tag`, `resource_or_tag_key`, `resource`, `resource_key`, `resource_selector`, `template_mirror`, `template_rotation`, `heightmap`, `loot_table`, `loot_predicate`, `loot_modifier`, `dialog`, `uuid`.

**Suggestions.** Brigadier argument types optionally supply `listSuggestions(CommandContext, SuggestionsBuilder)`; most vanilla types resolve suggestions locally from an in-memory `HolderLookup` (e.g. `SharedSuggestionProvider.listSuggestions` walks a registry's keys). The one case that must round-trip to the server is the free-text `ASK_SERVER` provider (`SuggestionProviders`, id `minecraft:ask_server`) attached to `ArgumentCommandNode.customSuggestions` — this is how `@e[type=` gets live entity-type suggestions from a client that doesn't have the authoritative registry state. `SuggestionProviders` is itself a small flat name→provider map (`AVAILABLE_SOUNDS`, `SUMMONABLE_ENTITIES`, `ASK_SERVER`), not a full `Registry`. A node's `suggestionId` in `ClientboundCommandsPacket` is `null` unless it carries a *registered* provider — an ad-hoc lambda provider serializes as if it used `ASK_SERVER`.

**Permission gating is per-node, not per-argument-type.** Every `ArgumentBuilder.requires(Predicate<CommandSourceStack>)` call is evaluated against the *acting* `CommandSourceStack`; `ClientboundCommandsPacket.NodeInspector.isRestricted` (used only for building the player-visible command tree, see §3.3) evaluates the same predicate against a synthetic zero-permission `CommandSourceStack` (`Commands.createCompilationContext(PermissionSet.NO_PERMISSIONS)`) to decide whether to prune a node from what is sent to a given client.

### 3.3 Commands, `CommandSourceStack`, and the permission model

**26.2 replaced the classic 0–4 integer op-level gate with a full `Permission`/`PermissionCheck`/`PermissionSet` object model**, itself codec-driven and registry-backed (`Registries.PERMISSION_TYPE`, `Registries.PERMISSION_CHECK_TYPE` — 2 entries each in `registries.json`).

- `Permission` (sealed via two record variants, `Codec` dispatch on `BuiltInRegistries.PERMISSION_TYPE`): `Permission.Atom(Identifier id)` — an opaque named capability (`commands/entity_selectors`, `chat/send_messages`, `chat/send_commands`, `chat/receive_player_messages`, `chat/receive_system_messages`); `Permission.HasCommandLevel(PermissionLevel level)` — the legacy op-level check re-expressed as a permission.
- `PermissionLevel` — the 5-rung op ladder, unchanged in spirit: `ALL(0) < MODERATORS(1) < GAMEMASTERS(2) < ADMINS(3) < OWNERS(4)`, compared via `isEqualOrHigherThan`.
- `PermissionSet` — `boolean hasPermission(Permission)`, with a `union` combinator (`PermissionSet.NO_PERMISSIONS`/`ALL_PERMISSIONS` singletons). `LevelBasedPermissionSet` is the concrete op-based implementation: a level satisfies `HasCommandLevel` by rung comparison, and additionally satisfies `COMMANDS_ENTITY_SELECTORS` only at `GAMEMASTERS` or above — i.e. **using a target selector (`@e`, `@a`, …) at all requires gamemaster**, independent of the command's own permission requirement.
- `PermissionCheck` (also codec-dispatched, `Registries.PERMISSION_CHECK_TYPE`): `AlwaysPass` and `Require(Permission)`. `Commands` exposes five canonical checks as `PermissionCheck` constants — `LEVEL_ALL` (`AlwaysPass`), `LEVEL_MODERATORS`, `LEVEL_GAMEMASTERS`, `LEVEL_ADMINS`, `LEVEL_OWNERS` (each `Require(Permissions.COMMANDS_*)`).
- `Commands.hasPermission(PermissionCheck)` returns a `PermissionProviderCheck<T extends PermissionSetSupplier>`, a `Predicate<T>` that calls `check.check(t.permissions())` — this is exactly the `Predicate<CommandSourceStack>` Brigadier's `.requires(...)` wants, since `CommandSourceStack implements ExecutionCommandSource<CommandSourceStack>` and `ExecutionCommandSource extends PermissionSetSupplier`.

`CommandSourceStack` is an **immutable value with copy-on-write mutators** (`withPosition`, `withRotation`, `withLevel`, `withEntity`, `withPermission`, `withMaximumPermission` (`union`), `withAnchor`, `withCallback`, `withSuppressedOutput`, `withSigningContext`) — every `execute … as/at/positioned/…` sub-command produces a new stack rather than mutating one, which is what makes `execute`'s per-branch forking (§3.4) safe to run many times from one parse. It carries: the underlying `CommandSource` (feedback sink — console/player/command block/RCON, each with different `acceptsSuccess`/`acceptsFailure`/`shouldInformAdmins`/`alwaysAccepts` policy), world position + rotation, the owning `ServerLevel`, a `PermissionSet`, display name/text name, the owning `MinecraftServer`, an optional source `Entity`, a `silent` flag, a `CommandResultCallback` (chained via `CommandResultCallback.chain`, feeding `execute store` and function return values), an `EntityAnchorArgument.Anchor` (feet/eyes, for `facing`), a `CommandSigningContext` (resolves chat-signed message arguments back to their `PlayerChatMessage`, for signed `/say`/`/tellraw` message content), and a `TaskChainer` for ordered async chat-message dispatch.

`sendSuccess`/`sendFailure`/`sendSystemMessage` route through `CommandSource` policy plus the `sendCommandFeedback`/`commandBlockOutput`/`logAdminCommands` game rules (`broadcastToAdmins` only fires for ops, gated by `GameRules.SEND_COMMAND_FEEDBACK`, and separately logs to the console if `GameRules.LOG_ADMIN_COMMANDS`).

`Commands.sendCommands(ServerPlayer)` builds a **per-player pruned command tree**: it walks the full dispatcher root and copies only nodes where `child.canUse(player.createCommandSourceStack())` (i.e. the node's `requires` predicate passes for *that* player), preserving `.redirect()` targets by remapping through a `Map<CommandNode, CommandNode>`, then ships it as `ClientboundCommandsPacket`. This is why a player who lacks permission for a command never even sees it in tab-completion — filtering happens server-side before the tree is sent, not client-side after.

**Command roster** (`Commands` constructor, `net.minecraft.server.commands.*`). Availability: **A** = always registered (both dedicated and integrated servers), **D** = dedicated-server-only, **I** = integrated (singleplayer)-only, **G** = only if `SharedConstants.DEBUG_DEV_COMMANDS || IS_RUNNING_IN_IDE` (debug/dev build), **J** = only if JFR profiling is available on the JVM. ### 3.4 Command execution: the queue, `/execute` forking, and macros/functions

Execution never recurses through Java call stacks — every command, redirect, fork, and function call is a **work item pushed onto an explicit deque**, run by a trampoline loop. This is what lets a single `/execute` chain or a deeply recursive `.mcfunction` tree run without blowing the JVM stack, and what makes the per-tick command budget enforceable.

**`ExecutionContext<T>`** (one instance per *top-level* invocation — nested calls reuse the current one via a `ThreadLocal<ExecutionContext<CommandSourceStack>>` set in `Commands.executeCommandInContext`) holds:
- `commandQuota` — starts at `Math.max(1, gameRules.get(GameRules.MAX_COMMAND_SEQUENCE_LENGTH))` (default game rule value **65536**) and is decremented by `incrementCost()` on every dispatched command/fork/function-call step; hitting zero aborts the remaining queue for that invocation and logs `"Command execution stopped due to limit"`.
- `forkLimit` — `gameRules.get(GameRules.MAX_COMMAND_FORKS)` (default **65536**); exceeding it while expanding a `RedirectModifier` (e.g. `execute as @e[...] run ...` fanning out to too many sources) throws `command.forkLimit` and aborts that branch.
- `commandQueue` (a `Deque<CommandQueueEntry<T>>`) plus a staging list `newTopCommands` — `queueNext` appends to staging, and each loop iteration first `pushNewCommands()` (staged entries pushed onto the **front** of the deque, in reverse order, so they run *before* whatever was already queued — i.e. work queued during a step's execution runs depth-first, immediately after that step) then pops one entry and executes it.
- A hard **`MAX_QUEUE_DEPTH = 10_000_000`** safety cap on total pending entries (`newTopCommands.size() + commandQueue.size()`); exceeding it is a distinct failure mode (`queueOverflow`) from the quota — it clears everything and logs `"Command execution stopped due to command queue overflow"`. This exists to bound pathological fan-out (e.g. a fork multiplying faster than the per-step cost check can catch) independent of the nominal per-tick cost budget.
- `currentFrameDepth`, `tracer` (an optional `TraceCallbacks` hook used by `/execute … run function` debugging/return-value tracing), and the `ProfilerFiller`.

**`Frame`** — a lightweight record `(depth, returnValueConsumer: CommandResultCallback, frameControl: FrameControl)`. `depth` increases by one per nested function call (or per `IsolatedCall`); `frameControl.discard()` clears every still-queued entry belonging to that frame or deeper (`ExecutionContext.discardAtDepthOrHigher`) — this is exactly the mechanism `return`/`return run`/`FallthroughTask` (see below) use to unwind the rest of the *current function's* remaining lines without touching the caller.

**`ChainModifiers`** — 2 packed bits: `FORKED` (this branch came from a `RedirectModifier` fan-out, e.g. `as @e[...]`) and `IS_RETURN` (the branch was reached through `execute … run` with `return run` semantics, so its numeric result should propagate to the frame's return callback instead of being discarded).

**`BuildContexts`** is the engine that turns one `ContextChain` (produced once at parse time) into queue work, three flavors: `TopLevel` (the very first command a player/console typed), `Continuation` (queued by a redirect/fork step), `Unbound` (a pre-compiled `.mcfunction` line, not yet bound to a specific source — see below). Its core loop walks `ContextChain.Stage` from the first modifier stage to `EXECUTE`: for each stage it reads the node's `RedirectModifier`; if the modifier implements `CustomModifierExecutor` (vanilla's `/execute` sub-commands like `as`, `at`, `positioned`, `if`/`unless`, `store` are implemented this way) control is handed off directly and `BuildContexts` returns; otherwise a generic Brigadier `RedirectModifier` is applied per current source (`ContextChain.runModifier`), each source's expansion contributing to `nextSources`, checked against `forkLimit` as it grows. Once the chain reaches `EXECUTE`, if `getCommand()` implements `CustomCommandExecutor` (again, `/execute`'s own terminal actions) it's invoked directly per source; otherwise an `ExecuteCommand` task is queued per current source via `ContinuationTask` (see below), each one calling Brigadier's `ContextChain.runExecutable` for that single source.

**`ContinuationTask<T,P>`** is the fan-out helper: given N arguments (e.g. N forked sources) it special-cases 0/1/2 arguments as direct immediate queuing, and for N≥3 queues itself repeatedly, consuming one argument per invocation — an explicit **linked continuation instead of a `for` loop that queues N items at once**, so a fork over an unbounded selector still yields to the deque/quota check between each fanned-out source rather than front-loading all N in a single step.

**Functions** (`.mcfunction`). `CommandFunction.fromLines` compiles a file: blank lines and `#`-comment lines are skipped, a trailing `\` continues a line onto the next (each concatenation step re-checks the 2,000,000-character line cap), a line starting with `/` is rejected (functions don't use the `/` prefix), a line starting with `$` is a **macro line** (`FunctionBuilder.addMacro`), everything else is parsed once against the dispatcher using a synthetic `Commands.createCompilationContext(functionCompilationPermissions)` source (so a function compiles successfully only if every line is syntactically valid *and* passes permission `.requires()` checks for the compile-time permission set — by default `LevelBasedPermissionSet.GAMEMASTER`, see `ServerFunctionManager.getGameLoopSender`) and stored as a pre-built `UnboundEntryAction`.

- **Plain functions** (`PlainTextFunction`) are compiled once at datapack load and cached forever; calling one just replays its pre-built `UnboundEntryAction` list.
- **Macro functions** (`MacroFunction`, triggered by any `$(var)` line): parameters are collected from the first macro line's variable names; `instantiate(CompoundTag arguments, dispatcher)` stringifies each NBT argument (numbers via a locale-independent `DecimalFormat` with up to 15 fraction digits, strings verbatim, everything else via `Tag::toString`) and re-parses only the macro-containing lines through `StringTemplate.substitute`, producing a fresh `InstantiatedFunction` — **cached per distinct argument tuple**, LRU-bounded to **8 entries** (`Object2ObjectLinkedOpenHashMap`, `MAX_CACHE_ENTRIES = 8`) so repeatedly calling a macro function with the same arguments (e.g. `function ns:foo with entity @s`) doesn't re-parse every time, but a hot loop cycling through many distinct argument sets will still re-parse most calls. `StringTemplate.fromString` requires at least one `$(...)` occurrence and validates variable names as `[A-Za-z0-9_]+`.

**Calling a function** (`CallFunction`, an `UnboundEntryAction`) increments the cost counter once *per call*, not per line, then schedules the function's entire `entries()` list via `ContinuationTask` under a **new** `Frame` one depth deeper (unless `returnParentFrame` is set, used by tail-call-style `function` invocations that should attribute their return value to the caller's frame instead of creating a nested one). Each individual command line inside the function is a further queue entry and pays its own `incrementCost()` when it runs, so the effective cost of calling a function is `1 (call) + sum of costs of every command/fork it triggers`, all drawn from the *same* top-level `commandQuota` — nested function calls do not get their own budget.

`ReturnCommand`/`FallthroughTask`: reaching the end of a function frame's queued entries — or explicit `return`/`return run`/`return fail` — resolves that frame's `returnValueConsumer` (`Frame.returnSuccess`/`returnFailure`) and discards anything else still queued at that frame's depth or deeper (`frame.discard()`), which is how `return` "exits early" from a function without special-casing every remaining line.

`ScheduleCommand` (`/schedule function id in|at <time> [append|replace]`) does **not** go through `ExecutionContext` at all at schedule time — it registers a deferred callback (see doc 01 for the tick-scheduler mechanism) that, when it fires, calls `ServerFunctionManager.execute`, which opens a *fresh* top-level `ExecutionContext` (fresh quota/fork budget) exactly like a player-typed command would.

`ServerFunctionManager` additionally auto-runs two well-known function **tags** every tick while the tick-rate manager reports `runsNormally()`: `#minecraft:load` (once, right after a resource reload completes — `postReload` flag) and `#minecraft:tick` (every tick, in tag-declaration order), both executed with a synthetic "game loop" `CommandSourceStack` (`getGameLoopSender`) at `GAMEMASTER` permission with output suppressed.

### 3.5 Registry architecture

`Registry<T>` (interface) `extends IdMap<T>, Keyable, HolderLookup.RegistryLookup<T>` — every registry is simultaneously a dense int-id ↔ value map (for network/NBT compactness — see doc 02), a name ↔ value map, and a self-lookup source for `Holder`/`HolderSet` resolution. `MappedRegistry<T>` is the sole production implementation: five parallel indices (`byId: ObjectList<Holder.Reference<T>>`, `toId: Reference2IntMap<T>`, `byLocation: Map<Identifier,…>`, `byKey: Map<ResourceKey<T>,…>`, `byValue: IdentityHashMap<T,…>`) plus `registrationInfos` (per-entry `Lifecycle` + optional owning `KnownPack`) and a `frozenTags` map.

**Freeze lifecycle.** A registry is mutable only until `freeze()` is called, which: (1) binds every `Holder.Reference`'s backing value (`bindValue`), (2) fails hard if any registered key has no bound value (`Unbound values in registry …`) or any tag created via `createRegistrationLookup` was never actually populated (`Unbound tags in registry …`) — both are startup-time correctness checks, not runtime-recoverable, (3) locks in `unregisteredIntrusiveHolders` must be empty for intrusive-holder registries, (4) builds the `DataComponentLookup` (per-entry default `DataComponentMap`, used by items/blocks-with-defaults; owned by doc 06/05), and (5) computes `allTags`/`refreshTagsInHolders` so every `Holder.Reference.tags()` is answerable in O(1) from then on. **After freeze, `register()` throws unconditionally** — this is the mechanism that makes "you can't register a new block after the game has started" a hard invariant rather than a convention.

**`Holder<T>`** is a sealed interface with exactly two implementations: `Holder.Direct` (an inline, unregistered value — e.g. a datapack JSON that embeds an object literal instead of a registry reference, or the empty `HolderSet.emptyNamed` bootstrap case; `is(ResourceKey)`/`is(TagKey)` always return `false` since it has no identity) and `Holder.Reference` (the normal case — a registry-backed slot that starts either **stand-alone** — created empty and bound later, the path every `MappedRegistry.register` and every `createRegistrationLookup().getOrThrow(key)` forward-reference goes through — or **intrusive** — created *from* an already-constructed value for a small set of legacy registries (`BLOCK`, `ITEM`, `FLUID`, `ENTITY_TYPE`) where the value object itself needs to hold a self-reference before it has a key, e.g. `Block` caching its own `Holder.Reference<Block>`). `canSerializeIn(HolderOwner<T>)` is the check `RegistryFileCodec` uses to refuse encoding a `Holder` that came from a *different* registry instance than the one currently being serialized against (guards against cross-registry-generation contamination when registries get rebuilt on reload).

**`HolderSet<T>`** — either `Direct` (a concrete, ordered, deduplicating list of holders — used for e.g. explicit block lists in generated code) or `Named` (a live view over a `TagKey`, populated by `MappedRegistry.bind`/`bindTags` — dereferencing an unbound `Named` set throws `IllegalStateException`, so tag resolution order relative to registry freezing matters, see §3.8).

**`HolderLookup<T>`/`HolderGetter<T>`** are the read-side abstraction every codec and command-argument constructor actually depends on (never `Registry<T>` directly, so that both a live `Registry` and a partially-loaded/forward-referencing view can satisfy the same contract). `HolderLookup.RegistryLookup<T>` adds `key()`/`registryLifecycle()` and a `Delegate` mix-in used pervasively to build filtered/patched views without re-implementing the interface (`filterFeatures`, `filterElements`, the pending-tag patch view in `prepareTagReload`, `CommandBuildContext.createValidationContext`'s tag-defaulting wrapper). `HolderLookup.Provider` is the multi-registry aggregate (`RegistryAccess` implements it) — `listRegistryKeys`/`lookup`/`lookupOrThrow`/`createSerializationContext(DynamicOps)` (wraps a plain `DynamicOps` into a `RegistryOps`).

### 3.6 Registry layering, built-in vs. data-driven, and the load pipeline

Registries fall into two populations with different lifecycles:

**Built-in (`BuiltInRegistries`, `RegistryLayer.STATIC`).** ~40 registries are populated entirely from Java code at class-init time (`registerSimple`/`registerDefaulted`/`registerDefaultedWithIntrusiveHolders`, each taking a `Bootstrap` lambda that calls `Registry.register` per entry) into a private **registry-of-registries** (`WRITABLE_REGISTRY: WritableRegistry<WritableRegistry<?>>`, itself keyed by `Registries.ROOT_REGISTRY_NAME`). `RegistryLayer.STATIC_ACCESS = RegistryAccess.fromRegistryOfRegistries(BuiltInRegistries.REGISTRY)` turns that into the bottom, always-present layer of every `LayeredRegistryAccess<RegistryLayer>`. `DefaultedRegistry`/`DefaultedMappedRegistry` variants (`BLOCK`→`air`, `ITEM`→`air`, `FLUID`→`empty`, `ENTITY_TYPE`→`pig`, `CHUNK_STATUS`→`empty`, `VILLAGER_TYPE`→`plains`, `SENSOR_TYPE`→`dummy`, `GAME_EVENT`→`step`, …) fall back to a fixed default value instead of erroring on an unknown id — chiefly so that malformed/forward-incompatible NBT/network data degrades to a visible placeholder rather than crashing. These registries **cannot** be extended by a datapack (there is no JSON directory for them — confirmed by `datapack.json`, `"elements": false` — though most still accept **tags**, `"tags": true`).

**Data-driven (`RegistryDataLoader`, `RegistryLayer.WORLDGEN`/`DIMENSIONS`/`RELOADABLE`).** `RegistryDataLoader` hard-codes three lists of `RegistryData<T>(key, elementCodec, validator)`:
- `WORLDGEN_REGISTRIES` — 44 registries loaded once per world load from `data/<ns>/<registry-path>/*.json`, each paired with its `DIRECT_CODEC`: `dimension_type`, `worldgen/biome`, `chat_type`, `worldgen/configured_carver`, `worldgen/configured_feature`, `worldgen/placed_feature`, `worldgen/structure`, `worldgen/structure_set`, `worldgen/processor_list`, `worldgen/template_pool`, `worldgen/noise_settings`, `worldgen/noise`, `worldgen/density_function`, `worldgen/world_preset`, `worldgen/flat_level_generator_preset`, `trim_pattern`, `trim_material`, `trial_spawner` (`TrialSpawnerConfig`), `wolf_variant`/`wolf_sound_variant`, `pig_variant`/`pig_sound_variant`, `frog_variant`, `cat_variant`/`cat_sound_variant`, `cow_variant`/`cow_sound_variant`, `sulfur_cube_archetype`, `chicken_variant`/`chicken_sound_variant`, `zombie_nautilus_variant`, `painting_variant`, `damage_type`, `worldgen/multi_noise_biome_source_parameter_list`, `banner_pattern`, `enchantment`, `enchantment_provider`, `jukebox_song`, `instrument`, `test_environment`, `test_instance`, `dialog`, `world_clock`, `timeline` (with a custom validator, `Timeline::validateRegistry`), `villager_trade`, `trade_set`. Nine of the animal-variant registries carry `RegistryValidator.nonEmpty()` — a datapack that removes every wolf/pig/frog/cat/cow/chicken/zombie-nautilus/painting variant fails registry loading outright rather than silently producing a broken game.
- `DIMENSION_REGISTRIES` — just `worldgen/dimension` (`Registries.LEVEL_STEM`, note its resource-key *path* is `"dimension"`, shared with — but distinct `ResourceKey` type from — `Registries.DIMENSION`), loaded in a second pass because a `LevelStem`'s `ChunkGenerator`/`NoiseGeneratorSettings` reference entries from `WORLDGEN_REGISTRIES`.
- `SYNCHRONIZED_REGISTRIES` — 29 registries, each with a (usually leaner) `NETWORK_CODEC` distinct from its `DIRECT_CODEC`, defining exactly what gets sent to clients (§3.7); notably narrower than `WORLDGEN_REGISTRIES` — worldgen internals (`configured_feature`, `placed_feature`, `structure`, `density_function`, `noise`, …) are **server-only** and never reach the client, only their *effects* (chunk data) do.

A **fourth**, separately-loaded population lives at `RegistryLayer.RELOADABLE`: `Registries.LOOT_TABLE`, `Registries.PREDICATE` (loot conditions — not the block/entity/item predicate DSL of §3.11, a different, smaller "loot condition type" concept reused as a nameable, referenceable registry), and `Registries.ITEM_MODIFIER`, enumerated by `LootDataType.values()` and loaded by `ReloadableServerRegistries` using a bespoke path (`SimpleJsonResourceReloadListener.scanDirectory` per type + `TagLoader.loadTagsForRegistry`) rather than `RegistryDataLoader` — because these three, plus recipes and advancements, must reload on `/reload`/`/datapack` changes *without* tearing down world-identity data (dimensions, biomes, worldgen), whereas `WORLDGEN_REGISTRIES`/`DIMENSION_REGISTRIES` are fixed for the lifetime of a loaded world.

**`RegistryLayer`** (`STATIC → WORLDGEN → DIMENSIONS → RELOADABLE`) composes via `LayeredRegistryAccess<RegistryLayer>`: each layer is an independent frozen `RegistryAccess`, and `getAccessForLoading(layer)` exposes every layer *before* it as read context for loading that layer (so `WORLDGEN` codecs can resolve `Holder<Block>` etc. against `STATIC`, and `RELOADABLE` codecs can resolve against `STATIC + WORLDGEN + DIMENSIONS`). `getAccessFrom(layer)` is the complementary "this layer and everything above" view used for client synchronization (only `WORLDGEN`-and-above is ever networked — `RegistrySynchronization.networkedRegistries`). `replaceFrom(layer, newAccess…)` produces a new `LayeredRegistryAccess` with everything below `layer` untouched — this is exactly how `/reload` swaps in a fresh `RELOADABLE` layer without rebuilding `STATIC`/`WORLDGEN`/`DIMENSIONS` (`ReloadableServerRegistries.createUpdatedRegistries`).

**Load algorithm** (`RegistryDataLoader.load`, `WorldLoader.load`): for a batch of `RegistryData`, each gets its own fresh `MappedRegistry` and its own `RegistryLoadTask` (`ResourceManagerRegistryLoadTask` for datapack JSON, `NetworkRegistryLoadTask` for a client receiving `ClientboundRegistryDataPacket`-style payloads). A shared `RegistryOps.RegistryInfoLookup` is built up-front spanning *both* the read-only context registries (layers already loaded) *and* every registry in this batch (via `ConcurrentHolderGetter`, thread-safe forward-reference creation into a not-yet-frozen registry) — so registries within one batch **can reference each other** (e.g. a `placed_feature` referencing a `configured_feature` loaded in the same pass) even though nothing is frozen yet. All tasks run their element-decode step concurrently on the background executor; only after every task's `CompletableFuture` completes does the loader call `freezeRegistry` on each (collecting per-registry freeze exceptions) and, only if that succeeded for all, `validateRegistry` (running each `RegistryValidator`, e.g. the non-empty checks above) — a failure at either stage aborts the whole batch and produces a `CrashReport` (`ReportedException`) listing every failing element grouped by registry, sorted for determinism.

### 3.7 Registry synchronization to the client

`RegistrySynchronization` restricts itself to `RegistryDataLoader.SYNCHRONIZED_REGISTRIES` (`NETWORKABLE_REGISTRIES`, a precomputed key set). `packRegistries` walks each such registry and, per element, checks whether the *connecting client* already has this exact entry cached (`RegistrationInfo.knownPackInfo()` — the `KnownPack` the entry came from — present in the client's `clientKnownPacks` set, sent during configuration). If so, the entry is packed with **empty contents** (`PackedRegistryEntry(id, Optional.empty())`) — the client is expected to already hold it from its own vanilla data or a previously-synced identical datapack; otherwise the element is fully encoded via `elementCodec.encodeStart(TagOps-over-NBT, value)` and sent inline. This "known pack" short-circuit is why enabling/disabling a vanilla-identical datapack doesn't necessarily re-transmit megabytes of biome/dimension-type data on every join. `networkSafeRegistries`/`networkedRegistries` additionally always include the entire `STATIC` layer's registry *set* (not their full contents — those are implicitly known) so the client can validate registry *existence* even for non-networked built-ins.

### 3.8 Tags

`TagKey<T>(ResourceKey<? extends Registry<T>> registry, Identifier location)` — a weakly-interned value type (`Interners.newWeakInterner`), so identical `TagKey`s are reference-equal, letting `Holder.Reference.is(TagKey)` do a plain `Set.contains`. Codec forms: plain (`#`-less JSON string), `hashedCodec` (expects a leading `#`, used where a field can hold either an element id or a tag reference and the `#` disambiguates — see `ResourceOrTagArgument`/loot-table entry codecs), and `streamCodec` for network.

**On-disk format** (`data/<ns>/tags/<registry-tag-dir>/<path>.json`, `TagFile.CODEC`): `{"values": [...], "replace": false}`. Each `values` entry (`TagEntry.CODEC`) is either a bare string (a required element or, prefixed with `#`, a required nested tag) or an object `{"id": "...", "required": false}` (optional — silently dropped if missing rather than erroring). `replace: true` discards every entry contributed by lower-priority packs for that tag id before appending this pack's own entries — i.e. **tag merging is last-pack-wins for `replace`, additive-union otherwise**, and multiple packs can each append to the same tag id.

**Loading algorithm** (`TagLoader.load` + `TagLoader.build`): `load` collects, per tag id, the ordered list of `(TagEntry, sourcePackId)` pairs across **every** pack that defines that path (`FileToIdConverter.listMatchingResourceStacks` — lowest to highest priority), honoring `replace` per file as it's encountered. `build` then resolves tag→tag nesting via `DependencySorter` — a topological sort keyed by each tag's `visitRequiredDependencies` (only *required* `#tag` references count as hard edges; optional nested-tag references are excluded from the dependency graph, consistent with "missing optional tag ⇒ empty, not an error") — and resolves each tag bottom-up through a `TagEntry.Lookup` that can answer both "give me element X" (delegating to the registry, honoring the entry's own `required` flag for missing elements) and "give me the already-built contents of tag Y" (from the tags resolved so far in this pass). A tag with an unresolvable **required** dependency (missing element or missing tag) is dropped for this reload and logged; it does not abort the whole load.

Tags for a **frozen** registry attach via `Registry.prepareTagReload(TagLoader.LoadResult)` → `Registry.PendingTags` — a two-phase commit: `lookup()` exposes a patched `HolderLookup.RegistryLookup` (new/updated tag contents visible immediately, for cross-referencing during a subsequent load stage) while `apply()` (called only once every dependent layer/registry in the same reload batch has finished loading — see `WorldLoader`/`ReloadableServerResources` call sites) actually rebinds the registry's live `HolderSet.Named` instances and refreshes every `Holder.Reference`'s cached tag set. This two-step exists precisely because tag *content* for `STATIC`/`WORLDGEN` registries must be visible to codecs decoding `RELOADABLE`-layer data (loot tables referencing `#minecraft:swords`, etc.) before those tags are irrevocably bound into the long-lived registry objects.

### 3.9 Resource loading: packs, `ResourceManager`, and reload-listener ordering

**Discovery.** `PackRepository` holds a set of `RepositorySource`s (`FolderRepositorySource` for the world's `datapacks/` folder, `ServerPacksSource` for the always-present "vanilla" pack plus any `--resource-pack`); `reload()` re-runs every source and rebuilds the `available: Map<String,Pack>` (each `Pack` reads its `pack.mcmeta` once via `Pack.readMetaAndCreate` — `PackFormat` compatibility, `FeatureFlagsMetadataSection` required flags, `OverlayMetadataSection` version-conditional overlay folders). `Pack.Position` (`TOP`/`BOTTOM`) plus `PackSelectionConfig.fixedPosition`/`required` govern where auto-inserted packs land relative to explicitly-ordered ones (`rebuildSelected`).

**Enabling** (`MinecraftServer.configurePackRepository`): starts from the world's persisted `DataPackConfig` (explicit enabled/disabled lists), then for every *available* pack not explicitly disabled: if it isn't already selected and its `PackSource.shouldAddAutomatically()` (true for the world-save `datapacks/` folder, false for e.g. a fixed built-in pack) it's auto-enabled **only if** its required feature flags are a subset of the currently-allowed set — this is the mechanism by which a datapack requiring an experimental feature flag silently fails to load rather than half-loading. `safeMode` forces the selection down to just `"vanilla"`.

**`ResourceManager` stack.** `MultiPackResourceManager` composes one `FallbackResourceManager` per namespace; each `FallbackResourceManager.push(pack[, filter])` appends the pack to that namespace's `fallbacks` list in **selection order (lowest priority first)**, and `getResource`/`listMatchingResourceStacks` iterate that list **in reverse** — i.e. **the last-pushed (highest-priority, "closer to the top of the list" in the `/datapack` UI) pack wins** for single-resource lookups, while stack-returning lookups (used by tags, which must *merge* rather than override) return every pack's copy in priority order. A pack can also register a name-only "filter" entry (`ResourceFilterSection`) that makes the manager report a resource as deliberately absent (and log a warning) rather than falling through to a lower-priority pack — the datapack author's way of *removing* a vanilla file rather than overriding it.

**Reload-listener ordering** is the crux of "what depends on what being loaded first," and it happens in two structurally different stages:

1. **Registry-layer bootstrap** (`WorldLoader.load`, run once per world load, *not* re-run by `/reload`): STATIC tags load → `WORLDGEN_REGISTRIES` load (against STATIC+its own tags) → `DIMENSION_REGISTRIES` load (against STATIC+WORLDGEN) → the embedding server supplies its dimension/level-data cookie → `ReloadableServerResources.loadResources` begins, which itself first fully completes `ReloadableServerRegistries.reload` (loot tables/predicates/item-modifiers, against STATIC+WORLDGEN+DIMENSIONS+their tags) *before* constructing `RecipeManager`/`Commands`/`ServerAdvancementManager`/`ServerFunctionLibrary` — so **recipes, commands (hence every `ResourceKeyArgument`/`ResourceArgument` suggestion source), advancements, and functions can all assume loot tables/predicates/item modifiers already exist**, but not vice versa.
2. **`PreparableReloadListener` list** (`ReloadableServerResources.listeners() = [recipes, functionLibrary, advancements]`, run by `SimpleReloadInstance`, and this *is* what `/reload` re-runs from scratch): every listener's async `prepare` phase (data decode, no shared mutation) runs **concurrently** on the background executor; but each listener's `PreparationBarrier.wait(...)` future only completes once **every** listener in the batch has finished preparing **and** the *previous* listener in list order has finished its own apply step — so decode work is fully parallel, but the observable **apply/commit order is exactly list order**: `RecipeManager` commits first, then `ServerFunctionLibrary` (which compiles every `.mcfunction` against the dispatcher built from the *already-committed* recipe state — irrelevant for functions specifically, but the ordering guarantee is general), then `ServerAdvancementManager`. This barrier pattern (all-prepare-before-any-apply, then apply-in-order) is also exactly how the client-side asset reload pipeline is structured, though that is out of scope here.

`/reload` (`ReloadCommand`) and `/datapack enable|disable` both funnel through the same `configurePackRepository` → `ReloadableServerRegistries.reload` → `ReloadableServerResources.loadResources` path used at world load, just re-executed against the *current* STATIC/WORLDGEN/DIMENSIONS layers instead of loading them fresh — which is precisely why a datapack cannot add a new dimension type or biome at runtime via `/reload` (those live in the WORLDGEN/DIMENSIONS layers, fixed for the world's lifetime) but can add a new loot table, recipe, advancement, or function immediately.

### 3.10 Codec / `DynamicOps` usage patterns

`com.mojang.serialization` (Codec/DataFixerUpper) is likewise an external MIT-family library and absent from this decompile; the patterns below are reconstructed from its call sites across `net.minecraft`.

- **Everything is a `Codec<T>` or `MapCodec<T>`.** Records overwhelmingly self-describe via `RecordCodecBuilder.create`/`.mapCodec` (`i -> i.group(fieldCodec.fieldOf("name").forGetter(Record::accessor), …).apply(i, Record::new)`), giving JSON-object codecs for free from constructor shape. `Codec.either(A, B)`, `.xmap`, `.comapFlatMap` (fallible transforms via `DataResult`), and `.optionalFieldOf` are the everyday combinators; `Codec.STRING.comapFlatMap(...)` is the idiom for "parse-and-validate a string into a richer type."
- **Every registerable "type-with-config" family is a dispatch codec over a `Registry<MapCodec<? extends X>>`.** The pattern (`X.CODEC = registry.byNameCodec().dispatch(X::codec, c -> c)`) is used identically for `Permission`, `PermissionCheck`, and *dozens* of worldgen/loot/enchantment sub-types (density functions, loot conditions/functions, structure processors, placement modifiers, …): a `"type": "minecraft:..."` field selects which registered `MapCodec` decodes the rest of the object. This is the single most repeated shape in the entire data-driven surface, and it is exactly why `registries.json` lists so many `*_type` registries (`block_predicate_type`, `enchantment_*_type`, `loot_*_type`, `worldgen/*_type`, …) — each is the dispatch table for one such family.
- **Registry-aware decoding is opt-in via `RegistryOps<T> extends DelegatingOps<T>`**, which wraps a plain `DynamicOps` (`JsonOps.INSTANCE` for datapacks, an NBT `DynamicOps` for network) with a `RegistryOps.RegistryInfoLookup` (per-registry `HolderOwner` + `HolderGetter` + `Lifecycle`). Codecs that need registry access don't take a registry parameter directly; they pattern-match `ops instanceof RegistryOps<?>` at decode/encode time (`RegistryFileCodec`, `RegistryOps.retrieveGetter`/`retrieveElement` — the latter two are "context injection" combinators for `RecordCodecBuilder` fields that don't consume any JSON, just pull a `HolderGetter`/`Holder` out of the ambient `RegistryOps`) — so the exact same `Codec<T>` object works for JSON-file decode, network decode, and (with a plain `DynamicOps`) registry-free contexts, degrading gracefully (`RegistryFileCodec` falls back to inline-only decode when `ops` isn't a `RegistryOps`).
- **The "inline object or registry reference" pattern** (`RegistryFileCodec<E>`): decodes either a bare `Identifier` string (resolved via the ambient `HolderGetter<E>`, producing a `Holder.Reference`) or, if `allowInline` and the input isn't a valid identifier string, a full inline `E` object (wrapped `Holder.Direct`). `RegistryFixedCodec` is the reference-only variant (no inline form — used where every value *must* be a named, freeze-time-resolvable registry entry). `RegistryCodecs.homogeneousList` layers `HolderSetCodec` on top to additionally accept a `#tag` string or a JSON array of the above, producing a `Codec<HolderSet<E>>` — this triple (`RegistryFileCodec`/`RegistryFixedCodec`/`HolderSetCodec`) is what every `"blocks": [...]`/`"items": "#minecraft:..."` field in loot tables, advancement predicates, and worldgen JSON ultimately bottoms out in.
- **`Lifecycle`** (`stable()`/`experimental()`, with `Lifecycle::add` as a monotonic "worst of both" combine) tracks whether a decoded value (or an entire registry) touched anything experimental/feature-flagged; it's threaded through nearly every registry API (`registrationInfo().lifecycle()`, `RegistryLookup.registryLifecycle()`, `Provider.allRegistriesLifecycle()`) purely as **diagnostic/warning metadata** — it does not itself gate functionality (that's `FeatureFlagSet`, a separate mechanism — see `HolderLookup.RegistryLookup.filterFeatures`, applied by `CommandBuildContext.simple` so disabled-feature registry entries are invisible to command argument suggestion/validation without being removed from the registry itself).

### 3.11 Predicates

Three unrelated `BlockPredicate` families exist (see the package table note in §2); the datapack-facing predicate DSL proper lives in `net.minecraft.advancements.predicates`:

- **`BlockPredicate`** (record: `Optional<HolderSet<Block>> blocks`, `Optional<StatePropertiesPredicate> properties`, `Optional<NbtPredicate> nbt`, `DataComponentMatchers components`) — used by loot conditions (`location_check`, `block_state_property`), advancement criteria, and structure-processor block matching. Every field is optional and absence means "don't filter on this axis"; `matches` short-circuits on block-set membership before touching properties/NBT/components, and only touches the `BlockEntity` at all if NBT or component matchers are actually present (an optimization that matters because fetching+serializing a block entity's full NBT, `saveWithFullMetadata`, is comparatively expensive).
- **`ItemPredicate`**/`SingleComponentItemPredicate` — item/tag/count/component matching, sharing `DataComponentMatchers` with `BlockPredicate` (component predicates are keyed by `Registries.DATA_COMPONENT_PREDICATE_TYPE`, itself a dispatch-codec registry — 15 entries in `registries.json`: `data_components`, `count`, `enchantments`, `stored_enchantments`, `custom_data` (NBT), `damage`, `unbreakable`, `potions`, `custom_potion_effects`, `container`, `bundle_contents`, `firework_explosion`, `fireworks`, `writable_book_content`, `written_book_content`).
- **`EntityPredicate`**/`EntitySubPredicate` (`advancements.predicates.entity`, 29 files) — the general entity-matching predicate reused by loot conditions (`entity_properties`), advancement criteria (killed-by/damage-source predicates), and selector `predicate=` grammar. `EntitySubPredicate`/`EntitySubPredicates` is another dispatch-codec registry (`Registries.ENTITY_SUB_PREDICATE_TYPE`, 25 entries) supplying per-entity-type extra fields (`SheepPredicate`: wool color; `FishingHookPredicate`: in-open-water flag; `PlayerPredicate`: gamemode/stats/recipes/advancements; `RaiderPredicate`: has-raid flag; `LightningBoltPredicate`: blocks-set-on-fire count; …) selected by the matched entity's own type.
- Command-facing predicate parsing is a **separate, hand-rolled shorthand grammar**, not the JSON DSL: `BlockStateParser` (shared by `BlockStateArgument`/`BlockPredicateArgument`, syntax `id[prop=val,...]{nbt}` or `#tag[vague_prop=val]{nbt}`) and `ItemParser` (`ItemArgument`/`ItemPredicateArgument`) produce their own lightweight result types (`BlockPredicateArgument.Result`, an interface with two implementations `BlockPredicate`/`TagPredicate` — note the name collision with, but no relation to, `advancements.predicates.BlockPredicate`) rather than constructing a `net.minecraft.advancements.predicates.BlockPredicate`. A datapack loot table and a typed `/execute if block ~ ~ ~ stone[...]` condition are matched by **independently implemented** code paths that happen to accept overlapping surface syntax.
- The **worldgen** `BlockPredicate` family (`world.level.levelgen.blockpredicates`, `Registries.BLOCK_PREDICATE_TYPE`) is a third, dispatch-codec-registry-backed implementation used exclusively as a placement/feature-generation gate (`BlockPredicateFilter` in the placement-modifier pipeline — owned by doc 04), combining primitives (`matching_blocks`, `matching_block_tag`, `matching_fluids`, `has_sturdy_face`, `solid`, `replaceable`, `would_survive`, `unobstructed`, `inside_world_bounds`, `matching_biomes`) via `all_of`/`any_of`/`not`.

## 6. Cross-subsystem interfaces

**Consumes from:**
- **World/tick core (doc 01)** — `GameRules` (command quota/fork limits, feedback flags), `ServerLevel`/`MinecraftServer` (the concrete objects a `CommandSourceStack` is bound to), the tick-rate manager (`ServerFunctionManager.tick` gates `#tick`/`#load` on `runsNormally()`), the scheduled-callback mechanism `/schedule` registers against, and `Profiler`/`ProfilerFiller` (every command/function/execute step is profiled).
- **Protocol/networking (doc 02)** — `ClientboundCommandsPacket` (the serialized command tree, built from `ArgumentTypeInfos` + per-node permission pruning), `ClientboundRegistryDataPacket`-style transfer consumed by `NetworkRegistryLoadTask`, chat-signing types (`PlayerChatMessage`, `MessageSignature`) consumed by `CommandSigningContext`/`ArgumentSignatures`, `FriendlyByteBuf`/`RegistryFriendlyByteBuf` for all network (de)serialization, `Identifier` used everywhere as the wire-safe id type.
- **World/chunks/persistence (doc 03)** — NBT (`CompoundTag`, `Tag`) as one of the two `DynamicOps` targets; block/entity save-with-metadata (`BlockEntity.saveWithFullMetadata`) consumed by `BlockPredicate`/`NbtPredicate`/`/data`.
- **Worldgen parity (doc 04)** — nearly all of `WORLDGEN_REGISTRIES`' *content* (structures, features, density functions, noise, carvers, world presets) is owned there; this doc owns only the loading mechanism.
- **Game mechanics (doc 05)** — loot tables/conditions/functions, recipes, advancements, triggers, game rules, block/entity/item predicate *content* is owned there; this doc owns the registry/reload-listener plumbing they're loaded through, and the block/entity/item predicate DSL types themselves (§3.11).
- **Modding API (doc 06)** — must integrate with `Registry.register`/`RegistrySetBuilder`/`BootstrapContext` for mod-contributed built-in registrations, and with `PreparableReloadListener` for mod data reload participation.

**Provides to:**
- Every other subsystem's data-driven configuration surface: worldgen (doc 04), game mechanics/loot/recipes/advancements (doc 05), and the modding API (doc 06) are all *consumers* of the `Registry`/`Holder`/`HolderSet`/codec/tag machinery defined here.
- The protocol layer (doc 02) consumes `ClientboundCommandsPacket` construction and `RegistrySynchronization`'s packed-registry-entry stream for the configuration-phase registry sync.
- `PackRepository`/`ResourceManager` (this doc) is the sole datapack/resource-pack discovery-and-stacking authority the whole server depends on for any file-backed configuration.

## 8. Notes for Rusty Clanker

- **The permission model is not the classic 4-level op system anymore.** 26.2's `Permission`/`PermissionCheck`/`PermissionSet` is itself data-driven and registry-backed (two 2-entry registries). A from-scratch reimplementation should model permission gating as *pluggable predicates over an opaque permission set*, not hard-code a 0–4 integer everywhere — vanilla still defaults every command to a `HasCommandLevel` check, but the door to atom-style capability permissions (`commands/entity_selectors`, `chat/*`) is already open in the wire format and should be respected by a compatible server (op level alone cannot express `COMMANDS_ENTITY_SELECTORS`'s current "target selectors need level ≥2" rule if a future datapack/plugin wants a different capability split).
- **Target-selector usage (`@e`/`@a`/`@p`/`@r`/`@s`/`@n`) is itself permission-gated**, independent of the containing command's own requirement — this is checked inside `EntitySelectorParser`/`EntityArgument`/`MessageArgument`/`GameProfileArgument`/`ScoreHolderArgument` at *parse* time, not at command-permission-check time. A reimplementation that only gates the outer command node will let a low-permission player use selectors inside e.g. `/say` messages or command blocks that vanilla would reject during parsing.
- **The command execution model is an explicit trampoline/queue, not recursion** — this is load-bearing for determinism and for the two independent safety limits (`commandQuota`/`forkLimit` from game rules, and the separate hard `10,000,000`-entry queue-overflow cap). A naive recursive interpreter will either stack-overflow on deep function/redirect chains that vanilla handles fine, or fail to reproduce vanilla's specific "ran out of budget mid-chain" truncation behavior (remaining queued commands are simply dropped, not rolled back — partial execution is a documented vanilla behavior, not a bug to fix).
- **Function macro caching is observable and cache-size-sensitive.** The 8-entry LRU on `MacroFunction` means calling a macro function with more than 8 distinct argument tuples in quick succession causes real re-parsing (and re-validation-time permission checks) on every miss — a reimplementation that caches unboundedly (or not at all) will have different performance characteristics but should still produce identical *results*; don't skip the compile-time permission check thinking the cache makes it unnecessary.
- **`ResourceLocation` has been renamed to `Identifier`** in this pinned version — every external reference (community docs, older mod source, the minecraft.wiki as of older revisions) will use the old name. Keep this naming consistent internally and flag it prominently for anyone cross-checking against older material.
- **Registry freeze order and cross-registry forward references are a genuine hazard.** Within one `RegistryDataLoader.load` batch, registries can forward-reference each other (via `ConcurrentHolderGetter`) *before* any of them are frozen, but **across** layers/batches only *already-frozen* layers are visible. A reimplementation must replicate the exact 4-layer sequencing (`STATIC → WORLDGEN → DIMENSIONS → RELOADABLE`, each fully frozen before the next begins loading) or subtle datapacks that rely on e.g. a loot table referencing a custom enchantment will fail to resolve. Get the *within-batch* concurrency model right too: it's why sibling worldgen registries (placed_feature ↔ configured_feature) can reference each other regardless of declaration order inside one datapack.
- **Tag resolution is two-phase for a reason** (`Registry.PendingTags`, `lookup()` vs `apply()`): reloadable-layer content must be decodable against *not-yet-committed* tag changes from the same reload before those tags are irrevocably bound. Collapsing this to a single "load tags, then load everything else" step will break datapacks that both modify a tag and reference that tag from a loot table/recipe/predicate in the same reload.
- **`FallbackResourceManager`'s reverse-iteration priority (last-pushed wins) plus per-file `replace` semantics on tags together define "override" behavior for the whole datapack system.** Get the push order and the reverse-scan direction backwards and every "datapack overrides vanilla" and "datapack extends a vanilla tag instead of replacing it" scenario silently inverts — this is a very easy off-by-one/off-by-direction bug to introduce and very hard to notice without a targeted test, since single-pack setups (the common dev-loop case) behave identically either way.
- **The reload-listener barrier (`SimpleReloadInstance`) is "all prepare, then apply-in-list-order," not "each listener fully finishes before the next starts.**" A reimplementation using a simple sequential `await` per listener will still be *correct* (apply order is preserved) but will lose the parallel-decode performance vanilla gets, and — more importantly — will not reproduce vanilla's "a slow-to-prepare listener stalls every apply step, even for listeners that finished preparing instantly" behavior, which matters for reload-time diagnostics/telemetry parity.
- **Three unrelated `BlockPredicate` classes and two unrelated command-permission-adjacent "predicate" concepts (`Registries.PREDICATE` = loot conditions; the advancement/loot `BlockPredicate`/`ItemPredicate`/`EntityPredicate` DSL; the command-line `BlockStateParser`/`ItemParser` shorthand) share names but not code paths in vanilla.** A reimplementation should resist the urge to unify them into one type — vanilla's own tooling (data generators, in-game validation) treats them as genuinely independent, and subtle behavior differences (e.g. the command-line block-predicate shorthand's "vague properties" partial-match mode for tag predicates has no equivalent in the JSON `BlockPredicate`) will be lost by a premature merge.
- **`/execute`'s custom-executor escape hatch (`CustomCommandExecutor`/`CustomModifierExecutor`) is how the single most complex vanilla command integrates with the generic queue/redirect machinery without the generic machinery needing any `/execute`-specific knowledge.** This is a clean extension point worth preserving in a Rust port (a trait object hook on the redirect/command-node types) rather than special-casing `/execute` inside the interpreter loop.
- **Command validation at startup (`Commands.validate()`) is a real correctness gate in vanilla**, not just a dev convenience — an unregistered argument type is a hard crash. A Rust reimplementation with a static, compile-time-checked argument-type registry can arguably upgrade this to a compile error instead of a runtime check, which would be strictly better than vanilla while remaining behaviorally equivalent for any datapack/mod that only uses registered types.
