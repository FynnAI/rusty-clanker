# World Generation (Terrain) — Vanilla 26.2 Research

## 1. Purpose

This subsystem turns a 64-bit world seed plus a set of data-driven parameters into deterministic terrain: 3-D density-function noise shapes the raw landmass, surface rules paint the top few blocks per biome, carvers cut caves/canyons/tunnels out of the noise shape, and a two-stage feature/placement pipeline scatters ores, vegetation, and other decoration on top. Every step is a pure function of world seed + block/chunk coordinates + registry data (no persisted RNG state, no order-of-chunk-generation dependence for the noise stage), which is what makes vanilla worldgen reproducible chunk-by-chunk regardless of generation order or thread count. This document covers noise-based overworld/nether/end/caves/floating_islands generation, surface rules, biome climate sampling, carvers, the feature/placement system, and the RNG/seed-derivation machinery that must be bit-identical for parity. Structures (villages, strongholds, jigsaw pools, etc.) are a separate domain and are out of scope here except where they interact with terrain shaping (`Beardifier`).

## 3. How it works

### 3.1 Random number generation & seed derivation

Two independent `RandomSource` implementations exist; picking the wrong one for the wrong context silently breaks parity, so both must be reimplemented bit-exact:

**`LegacyRandomSource`** (`net.minecraft.world.level.levelgen`) is a faithful `java.util.Random` 48-bit LCG: `seed' = (seed * 0x5DEECE66D + 0xB) & 0xFFFFFFFFFFFF`, seeded via `(seed ^ 0x5DEECE66D) & mask`, `next(bits)` returns the top `bits` of the 48-bit state. `BitRandomSource` (the shared default-method interface both legacy and Xoroshiro-under-the-hood implementations use for `nextInt`/`nextLong`/`nextDouble`/`nextFloat`) reproduces `java.util.Random`'s exact bit-consumption pattern, including the power-of-two fast path and the modulo-bias rejection loop for `nextInt(bound)`, `nextLong()` as two chained 32-bit `next()` calls, and `nextDouble()` as a 53-bit (26+27) combination — this must be copied precisely, not just "an RNG with the same distribution," because vanilla worldgen consumes an exact sequence of calls.

**`XoroshiroRandomSource`** (default since 1.18) wraps `Xoroshiro128PlusPlus`, a 128-bit state xoroshiro128++ generator. World seeds are only 64-bit, so a 64→128-bit seed upgrade happens via `RandomSupport.upgradeSeedTo128bit`: XOR the seed with the silver-ratio constant `SILVER_RATIO_64 = 0x6A09E667F3BCC909` to get the low 64 bits, add the golden-ratio constant `GOLDEN_RATIO_64 = 0x9E3779B97F4A7C15` to get the high 64 bits, then run both halves through `RandomSupport.mixStafford13` (a 64-bit avalanche mix: XOR-shift-multiply three times with the MurmurHash3 finalizer constants `0xBF58476D1CE4E5B9` and `0x94D049BB133111EB`, `z ^= z>>>30; z *= C1; z ^= z>>>27; z *= C2; z ^= z>>>31`).

Both sources implement `fork()` (derive an independent child from the next `nextLong()`) and `forkPositional()` (return a `PositionalRandomFactory`, a stateless factory keyed by position or by string hash rather than call sequence). `PositionalRandomFactory.at(x,y,z)` XORs a positional hash into the factory's stored seed and constructs a brand-new `RandomSource` — for both implementations the positional hash is `Mth.getSeed(x,y,z) = ((x*3129871) xor (z*116129781L) xor y)`, then `seed*seed*42317861L + seed*11L`, then arithmetic-shifted right 16. `fromHashOf(name)` derives a seed from an `Identifier`/string: legacy uses Java `String.hashCode()`; Xoroshiro uses an **MD5 hash of the UTF-8 string** split into two 64-bit halves (`RandomSupport.seedFromHashOf`), then XORed against the factory's stored seed pair (no Stafford mix applied to the hash itself). This name-hash path is how every named noise (`Noises.CONTINENTALNESS`, `"aquifer"`, `"ore"`, `"terrain"`, `"clay_bands"`, per-surface-rule `random_name` strings, per-`octave_N` Perlin sub-seeds, …) gets an independent, reproducible sub-RNG from one root `PositionalRandomFactory` — this is the master seed-fan-out mechanism for the entire worldgen stack and must be reproduced exactly including which algorithm (MD5 vs `hashCode`) applies to which `RandomSource` implementation.

`WorldgenRandom` (extends `LegacyRandomSource`, delegates its actual random draws to a wrapped `RandomSource` that may be Xoroshiro-backed) adds the classic decoration-seed derivation methods, all pure functions of the world seed and integer chunk/feature indices — **these are the parity-critical entry points for every carver and feature**:
- `setDecorationSeed(seed, chunkMinX, chunkMinZ)`: seed the generator with the world seed, draw two odd longs (`nextLong()|1`), fold `chunkX*xScale + chunkZ*zScale XOR seed`, and reseed with that — this is the per-chunk "decoration seed" root used once per chunk before the feature step loop.
- `setFeatureSeed(decorationSeed, index, step)`: `decorationSeed + index + 10000*step`, reseed — `index` is a **globally consistent** feature/structure index (see 3.13/`FeatureSorter`), `step` is the `GenerationStep.Decoration` ordinal.
- `setLargeFeatureSeed(seed, chunkX, chunkZ)`: seed with `seed`, draw two raw longs, fold `chunkX*xScale XOR chunkZ*zScale XOR seed` — used to seed carvers per source chunk (`NoiseBasedChunkGenerator.applyCarvers`, index = position in that chunk's carver list).
- `setLargeFeatureWithSalt(seed, x, z, salt)`: `x*341873128712L + z*132897987541L + seed + salt` — used by structure placement (out of scope here) but shares the mechanism.
- `seedSlimeChunk(x, z, seed, salt)`: `seed + x*x*4987142 + x*5947611 + z*z*4392871L + z*389711 XOR salt`, fed into a thread-local `RandomSource`.

### 3.2 `RandomState` — the per-dimension worldgen root object

`RandomState` (constructed once per `ServerLevel` in `ChunkMap`, from `NoiseGeneratorSettings` + the `NOISE` registry + the level's seed) is the single object that owns every derived RNG stream and every wired-up `DensityFunction` graph for one dimension:
1. `random = settings.getRandomSource().newInstance(seed).forkPositional()` — root positional factory, algorithm chosen by `NoiseGeneratorSettings.useLegacyRandomSource()` (`false` for overworld/large_biomes/amplified; `true` for nether/end/caves/floating_islands — i.e. **only the overworld family uses Xoroshiro**, everything else is legacy for historical-parity reasons).
2. `aquiferRandom = random.fromHashOf("aquifer").forkPositional()`, `oreRandom = random.fromHashOf("ore").forkPositional()` — two more positional factories hung off the root by name.
3. The dimension's `NoiseRouter` (a template built once at datapack-load time, sharing `DensityFunction` instances across dimensions) is *rewired* via a `DensityFunction.Visitor`: every `NoiseHolder` gets its `NormalNoise` instantiated on demand (`getOrCreateNoise`, cached per `ResourceKey`, using `random.fromHashOf(<noise resource key>)`); every `BlendedNoise` gets a freshly seeded `PerlinNoise` triple (via `"terrain"`-named hash for Xoroshiro or a legacy offset-seed scheme for legacy mode); every `EndIslandDensityFunction` gets reseeded with the raw world seed.
4. A second flattening `Visitor` strips `HolderHolder`/`Marker` wrapper nodes to build a `Climate.Sampler` directly from the wired `temperature`/`vegetation`/`continents`/`erosion`/`depth`/`ridges` density functions plus the preset's `spawnTarget` parameter list.
5. `SurfaceSystem` is constructed here too, sharing the same root positional factory.

`RandomState` is therefore the one place that must exist per (seed, dimension) pair; caching/synchronizing its construction is a correctness requirement, not an optimization, because `getOrCreateNoise` / `getOrCreateRandomFactory` memoize by resource key.

### 3.3 The `DensityFunction` system

`DensityFunction` is the core abstraction: `compute(FunctionContext) -> double`, `fillArray(double[], ContextProvider)` (batch form used inside `NoiseChunk`'s cell filling), `mapChildren`/`mapAll` (structural rewrite, used for the RandomState/NoiseChunk wiring passes above), plus static `minValue()`/`maxValue()` bounds carried on every node (used to prove `min`/`max` no-op comparisons and to short-circuit `TwoArgumentSimpleFunction`). Every concrete node type is a nested record/class inside `DensityFunctions` and is registered into the `minecraft:density_function_type` registry (the JSON `"type"` discriminator). Full enumeration:

| JSON `type` | Java type | Shape |
|---|---|---|
| `blend_alpha` | `BlendAlpha` (enum singleton) | constant `1.0` outside chunk blending; overridden per-position when `NoiseChunk` wires it against `Blender` |
| `blend_offset` | `BlendOffset` (enum singleton) | constant `0.0`, same override mechanism |
| `beardifier` | `BeardifierMarker` | marker resolved to the chunk's `Beardifier` instance at `NoiseChunk` construction |
| `old_blended_noise` | `BlendedNoise` | 3-octave-pair legacy 3-D Perlin terrain base (see 3.6 constants) |
| `interpolated` | `Marker.Type.Interpolated` | wraps a function for cell-corner sampling + trilinear interpolation (see 3.6) |
| `flat_cache` | `Marker.Type.FlatCache` | precomputes a 2-D (X,Z) grid at chunk-noise resolution, reused across all Y |
| `cache_2d` | `Marker.Type.Cache2D` | memoizes the last-computed value per (X,Z) column, lazily |
| `cache_once` | `Marker.Type.CacheOnce` | memoizes once per interpolation step (scalar or whole array) |
| `cache_all_in_cell` | `Marker.Type.CacheAllInCell` | precomputes every point inside the current noise cell (cell-width³) |
| `blend_density` | `Marker.Type.BlendDensity` | routes through `Blender.blendDensity` when old-chunk blending data exists nearby |

| `end_islands` | `EndIslandDensityFunction` | the classic 8×8-chunk-radius End island-placement Simplex field |
| `shifted_noise` | `ShiftedNoise` | samples a noise with per-axis shift-function offsets added before scaling |
| `range_choice` | `RangeChoice` | selects between two branches based on whether `input` falls in `[min,max)` |
| `interval_select` | `IntervalSelect` | selects among N+1 branches by comparing `input` against a sorted threshold list (used for the quantized-rarity spaghetti caves) |
| `shift_a` / `shift_b` | `ShiftA` / `ShiftB` | 2-D `NormalNoise` shift fields sampled at `(x*0.25,0,z*0.25)` / `(0,z*0.25,x*0.25)` — the biome/terrain warp offsets |

`DensityFunction.NoiseHolder` pairs a `Holder<NormalNoise.NoiseParameters>` registry reference with a (possibly still-unwired, `null`) instantiated `NormalNoise`; `DensityFunctions.HolderHolder` is the registry-indirection wrapper (`minecraft:density_function` entries reference other named entries by id) and is stripped during wiring. `MulOrAdd` is a decode/encode-transparent specialization: it still round-trips through the `add`/`mul` JSON codec, it just skips reconstructing a full `Ap2` node when one side is already known to be a compile-time constant.

### 3.4 `NoiseRouter` — the fixed 15-function interface between density functions and the rest of worldgen

`NoiseRouter` is a record of exactly 15 named `DensityFunction` slots that every dimension's noise setup must fill (unused ones are `DensityFunctions.zero()`): `barrierNoise`, `fluidLevelFloodednessNoise`, `fluidLevelSpreadNoise`, `lavaNoise` (all four feed `Aquifer`), `temperature`, `vegetation`, `continents`, `erosion`, `depth`, `ridges` (all six feed `Climate.Sampler`), `preliminarySurfaceLevel` (feeds `Aquifer`'s surface lookup and `SurfaceRules.Context`), `finalDensity` (the actual terrain shape sampled per block), `veinToggle`/`veinRidged`/`veinGap` (feed `OreVeinifier`).

`NoiseRouterData` builds the five router variants at datapack-bootstrap time (all sharing intermediate named `DensityFunction` registry entries, e.g. `overworld/continents`, `overworld/offset`, `overworld/caves/entrances`, so multiple presets can reuse the same field, and so the data-generator report can name/dump every intermediate node):

- **`overworld(largeBiomes, amplified)`**: builds `shift_x`/`shift_z` warp fields once; `continents`/`erosion`/`ridges` as 2-D `shifted_noise` samples at `xzScale=0.25`; `ridges_folded` = the "peaks and valleys" fold of `ridges` (`-3 * (|(|ridges|-2/3)| - 1/3)`, i.e. a triangle-wave remap into `[-1,1]` with knees at `|ridges|=1/3` and `2/3`); three parallel `offset`/`factor`/`jaggedness`/`depth`/`sloped_cheese` families (`OFFSET`, `OFFSET_LARGE`, `OFFSET_AMPLIFIED`, …) built from `TerrainProvider.overworldOffset/Factor/Jaggedness` cubic splines over `(continentalness, erosion, ridges/weirdness)` — `large_biomes` swaps in lower-frequency `continentalness_large`/`erosion_large` noise, `amplified` swaps in transform functions (`offset<0 ? offset : offset*2`, `1.25 - 6.25/(factor+5)`, `jaggedness*2`) applied around the same spline shapes; `sloped_cheese` = `noiseGradientDensity(factor, depth+jaggedness) + old_blended_noise` where `noiseGradientDensity(f,d) = 4 * (d*f).quarterNegative()`; cave shaping (`spaghetti_2d`, `spaghetti_roughness_function`, `entrances`, `noodle`, `pillars`, `underground`) combines multiple named `NormalNoise` fields via `min`/`max`/`range_choice`/`interval_select` into a single `caves` density that gets `min`'d against `sloped_cheese`; a `slide` helper linearly fades the final density toward fixed targets near the world's top and bottom (`yClampedGradient` + `lerp`) to guarantee flat bedrock-adjacent floors/ceilings; `preliminarySurfaceLevel` is computed via `find_top_surface` over a cheap approximation of the final density (no caves, no aquifer) — it exists purely so `Aquifer`, `SurfaceRules`, and ore-vein Y-bounding can cheaply ask "roughly how high is the ground here" without evaluating the full noise stack; ore veins (`vein_toggle`/`vein_ridged`/`vein_gap`) are three independent `NormalNoise` fields Y-limited to the union of `OreVeinifier.VeinType` Y ranges via `yLimitedInterpolatable` (wraps in `interpolated(range_choice(y, minY, maxY+1, whenInRange, constant(outOfRange)))` so the toggle itself benefits from the same cell interpolation as terrain density).
- **`nether(functions, noises)`**: only `temperature`/`vegetation`/`finalDensity` are non-zero; `finalDensity` = `postProcess(slideNetherLike(base_3d_noise_nether, minY=0, height=128))` — nether has no continentalness/erosion/ridges shaping at all, it is pure `BlendedNoise` sculpted by top/bottom `slide` fades.
- **`end(functions)`**: only `continents` (repurposed to carry the `end_islands` field, consumed directly by `TheEndBiomeSource`) and `finalDensity` (`postProcess(slideEndLike(sloped_cheese_end))`, where `sloped_cheese_end = end_islands + base_3d_noise_end`) are non-zero.
- **`caves(functions)`** and **`floatingIslands(functions, noises)`**: minimal single-function routers (`simpleRouter`) used only by the standalone `minecraft:caves` / `minecraft:floating_islands` noise-generator-settings presets (not used by any built-in dimension by default, but selectable via custom `world_preset`/`dimension` data).
- **`none()`**: the debug/dummy router, all-zero.

`peaksAndValleys(float)` (also exposed as a static helper, used by `MultiNoiseBiomeSource.addDebugInfo` and worldgen debug HUDs) is the scalar form of the same triangle-wave fold.

### 3.5 `NoiseSettings` / `NoiseGeneratorSettings` — per-dimension shape + material presets

`NoiseSettings` is four integers: `minY`, `height` (both must be multiples of 16, `minY+height <= DimensionType.MAX_Y+1`), `noiseSizeHorizontal`, `noiseSizeVertical` (both in `[1,4]`, expressed in "quarts" — 4-block units — and converted to block cell width/height via `QuartPos.toBlock`). Built-in values: overworld `(-64, 384, 1, 2)` → cell width 4, cell height 8; nether `(0, 128, 1, 2)`; end `(0, 128, 2, 1)` → cell width 8, cell height 4; caves `(-64, 192, 1, 2)`; floating_islands `(0, 256, 2, 1)`.

`NoiseGeneratorSettings` is the full per-preset bundle: `noiseSettings`, `defaultBlock`/`defaultFluid` (the material `NoiseChunk` falls back to before surface rules run — stone/water for overworld-shaped dimensions, netherrack/lava for nether, end_stone/air for end), `noiseRouter`, `surfaceRule`, `spawnTarget` (a `List<Climate.ParameterPoint>` used by `Climate.Sampler.findSpawnPosition`), `seaLevel`, `disableMobGeneration`, `aquifersEnabled`, `oreVeinsEnabled`, `useLegacyRandomSource`. Seven presets are registered: `overworld`, `large_biomes`, `amplified` (all three share `OVERWORLD_NOISE_SETTINGS` and differ only in `NoiseRouter`/biome-source wiring), `nether`, `end`, `caves`, `floating_islands`. `SharedConstants.DEBUG_DISABLE_AQUIFERS`/`DEBUG_DISABLE_ORE_VEINS` are AND'd into the enabled flags at read time (debug-build-only kill switches).

### 3.6 `NoiseChunk` — the cell/interpolation machinery

Per-chunk noise sampling never evaluates the full `DensityFunction` graph at every block — it exploits the fact that terrain-scale noise is smooth by evaluating expensive functions only at the corners of a coarse 3-D grid ("cells": `cellWidth × cellWidth × cellHeight` blocks, e.g. 4×4×8 for the overworld) and trilinearly interpolating everything in between. `NoiseChunk` is both a `DensityFunction.FunctionContext` (it *is* the "current position" while filling) and a `DensityFunction.ContextProvider` (it drives batch `fillArray` calls), which lets the `Marker`-wrapped nodes rewrite themselves into stateful caching wrappers the first time `NoiseChunk` sees them (`wrapNew`, memoized per source `DensityFunction` in a map so structurally-shared graph nodes only get one interpolator/cache instance):

- **`interpolated` → `NoiseInterpolator`**: allocates two "slices" (`double[cellCountXZ+1][cellCountY+1]`, one per adjacent X-column) of raw corner values. `initializeForFirstCellX()`/`advanceCellX()` fill slice 0 then slice 1 by calling the wrapped function at every (cellX, cellZ, cellY) corner (16 corners' worth of Y per XZ column, batched through `fillAllDirectly`). `selectCellYZ(cellY,cellZ)` reads the 8 corner values of the current cell out of the two slices into `noise000..noise111`. `updateForY`/`updateForX`/`updateForZ` progressively trilinearly interpolate (Y first, then X, then Z) as the fill loop walks in-cell block offsets, caching the four Y-interpolated XZ edge values and the two X-interpolated Z edge values so each axis is only re-lerped when that axis's in-cell offset actually changes. When filling every point of a cell directly (`fillingCell=true`, used for e.g. `cache_all_in_cell` children) it instead does a single `Mth.lerp3` per point.
- **`flat_cache` → `FlatCache`**: eagerly computes a `(noiseSizeXZ+1)²` 2-D grid at chunk-noise (quart) resolution when constructed, indexed by quart-X/quart-Z offset from the chunk origin; used for the biome-warp shift fields and the offset/factor/jaggedness/blend-alpha/blend-offset splines so they're computed once per chunk-column instead of once per block.
- **`cache_2d` → `Cache2D`**: lazy single-slot memo keyed by packed (blockX,blockZ).
- **`cache_once` → `CacheOnce`**: memoizes by a monotonically-incrementing `interpolationCounter`/`arrayInterpolationCounter` rather than by position — valid for exactly one "current sample" until the counter advances, used for values that are recomputed once per Z-column step or once per array fill.
- **`cache_all_in_cell` → `CacheAllInCell`**: eagerly fills a `cellWidth×cellWidth×cellHeight` array for the *current* cell only, recomputed every `selectCellYZ`; used for `finalDensity` itself (`fillFromNoise` wraps the whole `finalDensity + Beardifier` sum in `cacheAllInCell` before feeding it through the aquifer).
- **`beardifier`/`blend_density`/`blend_alpha`/`blend_offset`** resolve to chunk-specific objects (`Beardifier`, `Blender`) rather than generic caches.

`NoiseBasedChunkGenerator.doFill` (the `NOISE` `ChunkStatus` task body) drives the whole thing: for each of the 4×4 (16-wide / cellWidth) XZ cells in the chunk, `advanceCellX` fills the next interpolation slice; for each cell from **top to bottom** (`cellYIndex` descending — Y is walked top-down throughout worldgen, not bottom-up), `selectCellYZ` loads the cell corners and fills any `cache_all_in_cell` children; then for each in-cell Y (also top-down), X, Z block offset, `updateForY/X/Z` advance the interpolation and `getInterpolatedState()` (`MaterialRuleList.calculate`, i.e. try the aquifer's `computeSubstance` first, then `OreVeinifier` if enabled) produces the final `BlockState`, written into the chunk section and folded into the `OCEAN_FLOOR_WG`/`WORLD_SURFACE_WG` heightmaps as it goes; `swapSlices()` rotates slice buffers between X-cell iterations instead of reallocating.

`NoiseChunk.preliminarySurfaceLevel(x,z)` memoizes (`Long2IntOpenHashMap`, keyed by quantized quart position) evaluations of the router's `preliminarySurfaceLevel` function — every consumer (aquifer surface lookup, `SurfaceRules.Context.getMinSurfaceLevel`, `Aquifer`'s own surface-crossing test) shares this one cache per `NoiseChunk` instance.

### 3.7 Aquifers

`Aquifer.NoiseBasedAquifer` decides, for every below-`skipSamplingAboveY` block whose base density is `<= 0` (i.e. "would otherwise be air/fluid"), whether it should actually be air, water, or lava, by simulating localized underground water/lava pockets. It overlays a **jittered 3-D grid** on the world: cells are `16×12×16` blocks (`X_SPACING`/`Y_SPACING`/`Z_SPACING`), and each grid cell has one randomly-placed "aquifer location" (`positionalRandomFactory.at(gridX,gridY,gridZ)`, offset within the cell by `nextInt(10)`/`nextInt(9)`/`nextInt(10)` on X/Y/Z) with an associated `FluidStatus` (a fluid level + fluid block) computed lazily and cached per grid index. For a query position, the algorithm finds the **4 nearest** aquifer locations among the 2×3×2 = 12 neighboring grid cells (partial selection sort tracking `closestIndex1..4`/`distanceSqr1..4`), computes pairwise `similarity(d1,d2) = 1 - (d2-d1)/25` "closeness" scores for the 1st/2nd, 1st/3rd, and 2nd/3rd nearest pairs, and where similarity is positive (i.e. two locations are close enough to matter) computes a **pressure/barrier term** — a function of the two locations' fluid-level difference, the query Y's position relative to their average fluid level (asymmetric top/bottom bias constants `2.5`/`1.5` near the top, `10.0`/`3.0` near the bottom), and the `barrierNoise` density field — and rejects the fluid (returns `null`, i.e. "stays solid, evaluate normally") if `density + barrier > 0` for any of the three pairs. If none of the three barriers reject it, the closest location's `FluidStatus` wins. `shouldScheduleFluidUpdate()` reports whether the block sits near a barrier boundary (flowing water/lava tick needed) so `NoiseBasedChunkGenerator`/carvers can mark it for post-processing.

A `FluidStatus` itself (`computeFluid`) is derived, not stored: it samples `preliminarySurfaceLevel` at the query position and 12 nearby chunk-corner offsets (`SURFACE_SAMPLING_OFFSETS_IN_CHUNKS`) to find whether the aquifer cell is near/above the terrain surface (in which case it just inherits the global fluid picker's level — sea level water above, `y<min(-54,seaLevel)` lava below), otherwise computes a "floodedness" score from `fluidLevelFloodednessNoise` (clamped to a threshold that itself depends on distance below the lowest sampled surface, with `OverworldBiomeBuilder.isDeepDarkRegion` forcing near-zero floodedness under deep dark biomes) to decide fully-flooded (inherit global level) vs. partially-flooded (a **quantized randomized level**: `floorDiv(x,16)`/`floorDiv(y,40)`/`floorDiv(z,16)` cell, `fluidLevelSpreadNoise` sampled at the cell center scaled by 10 and quantized to steps of 3) vs. dry (`WAY_BELOW_MIN_Y`, meaning "no aquifer fluid here"). Fluid *type* (water vs. lava) for a non-global aquifer level below `y<=-10` is decided by a separate 64×40×64-cell-quantized `lavaNoise` sample thresholded at `|value|>0.3`.

The disabled-aquifer fallback (`Aquifer.createDisabled`) simply returns the global fluid picker's fluid for `density<=0`, i.e. plain sea-level water fill with no local variation — this is what every dimension except the overworld uses (`aquifersEnabled=false` for nether/end/caves/floating_islands presets).

### 3.8 Ore veins (`OreVeinifier`) vs. the classic `ore` feature

Two independent, unrelated ore-placement systems coexist. `OreVeinifier` is a **density-function-driven** system (introduced in 1.18) layered directly into `MaterialRuleList` right after the aquifer, evaluated for every solid block: it reads the router's `veinToggle` (sign picks copper vs. iron), `veinRidged` (ridged noise magnitude gates whether a vein exists here at all — must clear `0.4` after an edge-roundoff taper within 20 blocks of the vein type's Y bounds), and `veinGap` (thresholded at `>-0.3` to punch holes so veins aren't solid blobs) fields, plus a `oreVeinsPositionalRandomFactory.at(x,y,z)`-seeded per-block roll (`nextFloat()>0.7` bails entirely; a richness value interpolated between `0.1` and `0.3` as veininess climbs from `0.4` to `0.6` decides ore-vs-filler; a further `2%` chance upgrades ore to the raw-ore block). `VeinType.COPPER` spans Y `[0,50]` → copper ore / raw copper block / granite filler; `VeinType.IRON` spans Y `[-60,-8]` → deepslate iron ore / raw iron block / tuff filler. This system is what produces the large blobby copper/iron vein formations; it runs *before* the classic ore feature step and is purely a function of position (no per-chunk feature-seed involvement).

The **classic `ore` feature** (`OreFeature`, JSON type `minecraft:ore`, still used for coal/gold/redstone/diamond/lapis/copper-outside-veins/etc. via `PlacedFeature`s in the `underground_ores`/`underground_decoration` steps) is the traditional "blob along a random 3-D line segment" algorithm: pick a random horizontal direction, place two endpoints offset from the feature origin by `±sin/cos(direction) * size/8`, jitter each endpoint's Y independently by `±2`, then walk `config.size` points along the line, each with an ellipsoid radius derived from a `sin(π·t)` envelope times a per-point random scale; overlapping points whose radii dominate a neighboring point (radius difference exceeds their positional distance) suppress the smaller one, then every surviving point stamps blocks inside its ellipsoid (bounded scan, `BitSet` dedup) subject to `OreConfiguration.TargetBlockState` block-predicate matching and an optional `discardChanceOnAirExposure` roll when the candidate position is adjacent to air.

### 3.9 Surface rules system

`SurfaceRules.RuleSource` (JSON registry `minecraft:material_rule`) and `SurfaceRules.ConditionSource` (JSON registry `minecraft:material_condition`) are the two composable trees that `SurfaceRuleData` (datagen) assembles into one giant per-preset rule (see §7 for the JSON). `RuleSource.apply(Context)` compiles the JSON tree into a `SurfaceRule` closure (`tryApply(x,y,z) -> BlockState?`) once per chunk-column pass, not once per block — conditions and rules are pre-resolved against the shared mutable `Context` so that, e.g., a `noise_threshold` condition only samples its `NormalNoise` once per (X,Z) even if it appears many times in the tree.

**Rule types** (4): `sequence` (try each child rule in order, first non-null result wins — this is how the whole tree is built: an outer `sequence` of `condition`-wrapped sub-rules), `condition` (`TestRuleSource`: `if_true` / `then_run`, short-circuits to `null` if the condition fails), `block` (a fixed `BlockState` result), `bandlands` (delegates to `SurfaceSystem.getBand`, the striped-terracotta clay-band lookup used by badlands).

**Condition types** (11): `biome` (`biome_is`, a `HolderSet`, with a possible-biome fast path that resolves to a constant `true`/`false` when the whole chunk-region's possible biome set can't or must satisfy it), `noise_threshold` (samples a named `NormalNoise`, 2-D or 3-D, against `[min,max]`), `vertical_gradient` (`random_name`-keyed `PositionalRandomFactory`, deterministic below `true_at_and_below`, deterministic-false above `false_at_and_above`, linearly-probabilistic (`nextFloat() < linearMap(y)`) in between — this is how e.g. the bedrock floor's ragged edge is generated), `y_above` / `water` (both `YConditionSource`/`WaterConditionSource`-shaped: compare `blockY [+ stoneDepthAbove]` against an anchor/water-height plus `surfaceDepth * multiplier`), `temperature` (delegates to `Biome.coldEnoughToSnow`), `steep` (compares `WORLD_SURFACE_WG` heightmap samples of the 4 orthogonal neighbors, `>=4` height difference either axis), `hole` (`surfaceDepth <= 0`), `above_preliminary_surface` (`blockY >= preliminarySurfaceLevel + surfaceDepth - 8`, both cached per-XZ via a 4-corner bilinear lookup — `getMinSurfaceLevel`), `not` (negation), `stone_depth` (the workhorse: compares the running "how many solid blocks have we counted going down from the top/up from the ceiling" counter, `stoneDepthAbove`/`stoneDepthBelow`, against `offset [+ surfaceDepth] [+ secondaryDepthRange-scaled secondary noise]`, floor vs. ceiling selectable — this is what "N blocks below the surface" checks compile to; `SurfaceRules.ON_FLOOR`/`UNDER_FLOOR`/`DEEP_UNDER_FLOOR` (6) /`VERY_DEEP_UNDER_FLOOR` (30) /`ON_CEILING`/`UNDER_CEILING` are the canned depth thresholds used pervasively by biome-specific surface rules).

`Context` maintains per-XZ state (`surfaceDepth` = `getSurfaceDepth` below, `surfaceSecondary`, cached `minSurfaceLevel`) invalidated by an incrementing `lastUpdateXZ` counter, and per-Y state (`biome`, `waterHeight`, `stoneDepthAbove/Below`) invalidated by `lastUpdateY`; every `LazyCondition` subclass compares its own last-seen counter value against the context's to decide whether to recompute — this counter-based memoization (not position hashing) is why `SurfaceRules.Context` construction is inherently per-column-scan sequential.

### 3.10 `SurfaceSystem.buildSurface` — the per-column driver

For each of the 16×16 columns in a chunk: read the biome at the column's `WORLD_SURFACE_WG` height (special-cased to run eroded-badlands-pillar and frozen-ocean-iceberg pre/post extension passes for those two biomes specifically — both are self-contained noise-driven column edits unrelated to the general rule tree), then scan **downward from `WORLD_SURFACE_WG`+1 to the dimension floor**, tracking `stoneAboveDepth` (resets to 0 on air, increments on solid), `waterHeight` (top-of-fluid Y, reset on air), and a **lazily-computed** `nextCeilingStoneY` (a downward lookahead, computed only when the current position could plausibly be the top of a solid run, to derive `stoneDepthBelow`) — then for every position whose current block equals `defaultBlock` (i.e. "still raw stone/netherrack/end-stone, not yet touched by a carver or aquifer"), runs the compiled rule tree and overwrites the block if it returns non-null.

`getSurfaceDepth(x,z)` is the classic "surface noise" that gives biome surfaces their non-flat dirt-layer thickness: `SURFACE` `NormalNoise` value × `2.75` + `3.0` + a `noiseRandom.at(x,0,z).nextDouble()*0.25` jitter, truncated to `int`. Clay-band terracotta striping (`getBand`) offsets a fixed 192-entry palette (generated once at `SurfaceSystem` construction — random terracotta/orange/yellow/brown/red/white/light-gray band placement, see §5 for the exact random-band-count ranges) by `round(clayBandsOffsetNoise(x,z) * 4)` and indexes it by `(y + offset) mod 192`.

### 3.11 Biome sources and `Climate.Sampler`

`Climate.Sampler` is 6 `DensityFunction`s (`temperature`, `humidity`≡`vegetation`, `continentalness`, `erosion`, `depth`, `weirdness`≡`ridges`) plus a spawn-target parameter list; `sample(quartX,quartY,quartZ)` evaluates all 6 at the corresponding block position and quantizes each to a `long` via `Climate.quantizeCoord` (`float * 10000`, i.e. 4 fixed-point decimal digits) to form a `Climate.TargetPoint`.

`MultiNoiseBiomeSource` (used by the overworld and nether) resolves a `TargetPoint` to a biome via `Climate.ParameterList<Holder<Biome>>.findValue`, which is backed by a custom **7-dimensional R-tree** (`PARAMETER_COUNT=7`: temperature, humidity, continentalness, erosion, depth, weirdness, plus a fixed "offset" dimension used only by a few biomes like nether's warped/basalt-deltas to bias selection without a real climate axis) built once from the full flattened list of `(ParameterPoint, Biome)` pairs (the overworld's expanded list has **7594 entries** — see §7). Tree construction (`RTree.build`) recursively buckets children into groups of up to 6 (`CHILDREN_PER_NODE`), picking whichever of the 7 axes minimizes total bounding-box "cost" (sum of per-axis span) at each level; `findValue` does a branch-and-bound nearest-neighbor search using squared-distance-to-interval as the metric (`Parameter.distance`: 0 if the target falls inside `[min,max]`, else distance to the nearer bound) and a thread-local last-result cache as a warm-start candidate (biome queries are spatially coherent chunk-to-chunk, so the previous answer is usually still near-optimal). `OverworldBiomeBuilder` is the hand-authored logic that *constructs* the overworld's parameter-point list: fixed bands for 5 temperature ranges × 5 humidity ranges × several continentalness bands (mushroom fields / deep ocean / ocean / coast / near-inland / mid-inland / far-inland) × 7 erosion bands × weirdness (plateau vs. shattered vs. middle biome, ± variant tables), each combination looked up in one of several `ResourceKey<Biome>[][]` 5×5 tables (`MIDDLE_BIOMES`, `MIDDLE_BIOMES_VARIANT`, `PLATEAU_BIOMES`, `PLATEAU_BIOMES_VARIANT`, `SHATTERED_BIOMES`, `OCEANS`), plus special-cased rivers, frozen rivers, swamps, and badlands variants.

`TheEndBiomeSource` does **not** use the R-tree: it special-cases the central 8-chunk-radius island as `the_end`, then buckets everywhere else into `end_highlands`/`end_midlands`/`end_barrens`/`small_end_islands` purely from the sign/magnitude of the router's `erosion` slot (which for the end dimension is repurposed to carry the End's islands-density field, not real climate erosion) sampled at a fixed offset inside the 2×2-chunk region the query falls in — thresholds `0.25` (highlands), `-0.0625` (midlands), `-0.21875` (islands vs. barrens).

`FixedBiomeSource` and `CheckerboardColumnBiomeSource` are trivial (constant biome; deterministic checkerboard by chunk coordinate divided by a configurable scale) and used mainly for debug/testing presets.

### 3.12 Carvers

Three `WorldCarver`s are registered: `cave` (`CaveWorldCarver`), `nether_cave` (`NetherWorldCarver`, a thin subclass swapping default replaceable-block/debug-state sets and a wider Y range but reusing the same tunnel algorithm), `canyon` (`CanyonWorldCarver`). All three share `WorldCarver.carveEllipsoid`, the shared voxel-stamping primitive: given a center, per-axis radii, and a `CarveSkipChecker` (a per-block "would this normalized position fall outside my desired shape" predicate), it iterates the chunk-local XZ bounding box of the ellipsoid, and for each (x,z) column scans Y from top to bottom, calling `carveBlock` (replace-if-`canReplaceBlock`, defer to `Aquifer.computeSubstance` for the actual resulting fluid/air state, and specially re-run the surface-material rule one block above any carved position that used to be grass/mycelium so newly-exposed dirt gets re-topped) once per position not already set in the chunk's `CarvingMask` (a per-chunk bitset dedup so overlapping carve calls across the 17×17 chunk neighborhood — carvers run with `getRange()=4` chunks of horizontal reach — don't double-process a block). Carving always runs in the dedicated `CARVERS` `ChunkStatus` step (§3.14), strictly after `SURFACE`, with a fresh `LegacyRandomSource(RandomSupport.generateUniqueSeed())`-backed `WorldgenRandom` reseeded per-source-chunk via `setLargeFeatureSeed(seed+carverIndex, sourceChunkX, sourceChunkZ)` and iterated over a 17×17 chunk neighborhood (`-8..8` in both axes) so that a cave/canyon whose "home" chunk is a neighbor can still carve into the chunk being generated (`WorldCarver.canReach` prunes tunnel walks once they can no longer geometrically reach the center chunk).

`CaveWorldCarver.carve` rolls a randomized cave count (`nextInt(nextInt(nextInt(15)+1)+1)`, a strongly zero-biased nested distribution), and per cave optionally carves a starting "room" (an ellipsoid, `1/4` chance) before walking 1+ branching tunnels: each tunnel is a **worm walk** — `createTunnel` steps forward along a heading (`horizontalRotation`/`verticalRotation`) for `distance` steps, each step advancing position by `cos/sin` of the current heading, decaying the heading's own turn-rate (`verticalRotation *= 0.7` or `0.92` if "steep") while accumulating new random turn impulses (`xRota`/`yRota`, damped by `0.9`/`0.75` per step), carving an ellipsoid of `sin(π·t/distance)`-enveloped radius at each step (skipped ~1/4 of steps for organic gaps), and forking into two child tunnels at a random midpoint if `thickness>1`. `CanyonWorldCarver.doCarve` is the same heading-walk shape but with only one branch (no forking), an X/Y/Z-varying width-factor array precomputed once per canyon (`initWidthFactors`, a piecewise-constant random "spikiness" profile down the entire world height) instead of per-step thickness, and an ellipsoid `shouldSkip` test that scales the horizontal radius by that per-Y width factor and divides the vertical extent by 6 (much flatter, taller-than-wide shape — a ravine, not a tube).

### 3.13 Features & placement

**Composition.** A `Feature<FC>` (JSON registry `minecraft:worldgen/feature`, 63 concrete algorithms — full enumeration below) is pure algorithm; a `FeatureConfiguration` (JSON registry-adjacent, one of 40 config record types under `feature.configurations`) is pure data; together they form a `ConfiguredFeature<FC,Feature<FC>>` (registry `minecraft:worldgen/configured_feature`, `place(WorldGenLevel, ChunkGenerator, RandomSource, BlockPos origin)`). A `ConfiguredFeature` plus an ordered `List<PlacementModifier>` forms a `PlacedFeature` (registry `minecraft:worldgen/placed_feature`) — placement is a `Stream<BlockPos>` that starts as a single `origin` and gets `flatMap`'d through each modifier in order (a modifier can fan one input position out to zero, one, or many output positions, e.g. `count` repeats N times, `in_square` jitters to a random point in the 16×16 column, `heightmap` snaps to a heightmap-derived Y); the underlying `Feature.place` is invoked once per surviving position.

**Feature type enumeration** (JSON `type` under `minecraft:worldgen/configured_feature`, 63 entries): `no_op`, `tree`, `fallen_tree`, `block_pile`, `spring_feature`, `chorus_plant`, `replace_single_block`, `void_start_platform`, `desert_well`, `fossil`, `huge_red_mushroom`, `huge_brown_mushroom`, `spike`, `glowstone_blob`, `freeze_top_layer`, `vines`, `block_column`, `vegetation_patch`, `waterlogged_vegetation_patch`, `root_system`, `multiface_growth`, `underwater_magma`, `monster_room`, `blue_ice`, `iceberg`, `block_blob`, `disk`, `lake`, `ore`, `end_platform`, `end_spike`, `end_island`, `end_gateway`, `seagrass`, `kelp`, `coral_tree`, `coral_mushroom`, `coral_claw`, `sea_pickle`, `simple_block`, `bamboo`, `huge_fungus`, `nether_forest_vegetation`, `weeping_vines`, `twisting_vines`, `basalt_columns`, `delta_feature`, `netherrack_replace_blobs`, `fill_layer`, `bonus_chest`, `basalt_pillar`, `scattered_ore`, `random_selector` (deprecated), `weighted_random_selector`, `simple_random_selector`, `random_boolean_selector`, `sequence`, `template`, `geode`, `speleothem_cluster`, `large_dripstone`, `speleothem`, `sculk_patch`. Several of these are **combinators** over other `ConfiguredFeature`s rather than terminal placers (`sequence` places a fixed ordered list; `simple_random_selector` and the two weighted variants pick among a list at runtime), so a "feature" in the data sense is really a tree.

**Tree composition subsystem.** `TreeFeature` (and the specialized mega/fungus variants) doesn't hardcode tree shapes — a `TreeConfiguration` composes a `TrunkPlacer` (8 registered types: straight/forking/giant/mega-jungle/dark-oak/fancy/bending/cherry), a `FoliagePlacer` (10 types: blob/spruce/pine/acacia/bush/fancy/jungle/mega-pine/dark-oak/cherry), a `RootPlacer` (1: mangrove), a `FeatureSize` (2 types: two-layer/three-layer bounding envelopes used to decide which XZ radius is legal at a given height, purely for validity checks not shape), a `BlockStateProvider` (5 types: simple/weighted/noise/dual-noise/rotated-block, used for log/leaves state selection), and an ordered list of `TreeDecorator`s (10 types: trunk-vine, leave-vine, pale-moss, creaking-heart, cocoa, beehive, alter-ground, attached-to-leaves, place-on-ground, attached-to-logs) run after the trunk+foliage are stamped. This is the closest vanilla analogue to a general "procedural prefab" system in worldgen and is worth mirroring structurally in the modding API rather than flattening into a monolithic tree feature.

**Placement modifier enumeration** (JSON `type` under `minecraft:worldgen/placed_feature.placement[]`, 15 entries via `PlacementModifierType`): `block_predicate_filter`, `rarity_filter` (1-in-N chance), `surface_relative_threshold_filter`, `surface_water_depth_filter`, `biome` (re-checks the target biome actually wants this placed feature — required whenever a feature is shared across biomes with different feature lists, since placement happens at a fixed world position independent of which biome "owns" the call), `count` (fixed repeat count), `noise_based_count`, `noise_threshold_count`, `count_on_every_layer`, `environment_scan` (walks vertically from the input position looking for a target/matching-predicate transition, e.g. "find the first air block above solid ground"), `heightmap` (snap Y to a named heightmap type), `height_range` (sample Y from a `HeightProvider`), `in_square` (jitter to a uniformly random point in the containing 16×16 column), `random_offset`, `fixed_placement` (an explicit position list, used by a handful of hardcoded features like the bonus chest).

**Global deterministic ordering (`FeatureSorter`) — the parity-critical piece.** Every registered biome's per-step `List<HolderSet<PlacedFeature>>` (built via `BiomeGenerationSettings.Builder.addFeature(GenerationStep.Decoration, …)`, indexed by the 11-entry `Decoration` enum ordinal) is inspected once, across **all** biomes simultaneously, to assign every distinct `PlacedFeature` object a single global integer index (`FeatureSorter.buildFeaturesPerStep`), while also recording "feature A must run before feature B" edges wherever two features are adjacent in the *same* biome's *same* step list, then topologically sorting (DFS-based) to produce one canonical ordering per step that is consistent with every biome's locally-required relative order simultaneously (a cycle here — e.g. biome X wants A before B while biome Y wants B before A — is a hard bootstrap error, not resolved silently). `ChunkGenerator.applyBiomeDecoration` then, per `Decoration` step, per generation step index: places any structures registered for that step first (seeded via `setFeatureSeed(decorationSeed, structureIndexInStep, step)`), then computes the set of globally-indexed features that are actually reachable from the chunk's `possibleBiomes` set this step, sorts those indices numerically, and places each via `setFeatureSeed(decorationSeed, globalIndex, step) → PlacedFeature.placeWithBiomeCheck`. **The RNG draw for any given feature therefore depends only on the world seed, the chunk position (via `decorationSeed`), the feature's step, and its registry-load-order-derived global index — never on which biome triggered it or in what order biomes were visited.** A from-scratch reimplementation must replicate this exact global-index assignment (i.e. mirror vanilla's per-biome feature-list order and the DFS topological sort, not just "iterate features in registry order") or per-block RNG draws inside features will desync from vanilla even when every individual feature algorithm is bit-exact.

`applyBiomeDecoration` seeds its root `decorationSeed` once via `WorldgenRandom.setDecorationSeed(level.getSeed(), sectionOrigin.x, sectionOrigin.z)` at the start of the whole per-chunk decoration pass (using a throwaway `LegacyRandomSource(RandomSupport.generateUniqueSeed())`-backed `WorldgenRandom` as the *carrier* — only the derived seed value that comes out of `setDecorationSeed` is deterministic; the carrier's own initial state is thrown away immediately by the reseed).

### 3.14 Generation steps per `ChunkStatus` stage

`ChunkStatus` (`net.minecraft.world.level.chunk.status`) defines a strictly linear 12-stage ladder (`getIndex()` 0..11): `empty` → `structure_starts` → `structure_references` → `biomes` → `noise` → `surface` → `carvers` → `features` → `initialize_light` → `light` → `spawn` → `full`. `ChunkPyramid.GENERATION_PYRAMID` binds each non-trivial stage to a `ChunkStatusTasks` method and declares its cross-chunk data dependencies (`addRequirement(status, radius)` — how many neighboring chunks must already be at that earlier status before this chunk can advance, which is what drives the region-file/chunk-loading "border" radius):

| `ChunkStatus` | Task | Neighbor requirements | What runs |
|---|---|---|---|
| `structure_starts` | `generateStructureStarts` | — | (structures; out of scope) |
| `structure_references` | `generateStructureReferences` | `structure_starts`×8 | (structures; out of scope) |
| `biomes` | `generateBiomes` | `structure_starts`×8 | `ChunkGenerator.createBiomes` → `NoiseChunk` built (or reused), `fillBiomesFromNoise` samples `Climate.Sampler` per biome-grid cell (4×4×4 blocks) through the (possibly `Blender`-overridden) biome resolver |
| `noise` | `generateNoise` | `structure_starts`×8, `biomes`×1 | `ChunkGenerator.fillFromNoise` → §3.6's `doFill`; `BelowZeroRetrogen` legacy-bedrock-hole patching for chunks generated before the 1.18 depth expansion |
| `surface` | `generateSurface` | `structure_starts`×8, `biomes`×1 | `ChunkGenerator.buildSurface` → §3.10 |
| `carvers` | `generateCarvers` | `structure_starts`×8 | `Blender.addAroundOldChunksCarvingMaskFilter` (blend-boundary carve suppression) then `ChunkGenerator.applyCarvers` → §3.12 |
| `features` | `generateFeatures` | `structure_starts`×8, `carvers`×1 | prime the 4 "final" heightmaps, then `ChunkGenerator.applyBiomeDecoration` → §3.13, then `Blender.generateBorderTicks` (mark leaves/fluids at old/new chunk boundaries for a relight/fluid-tick pass) |
| `initialize_light` | `initializeLight` | — | seed the light engine's internal state for this chunk |
| `light` | `light` | `initialize_light`×1 | full block+sky light propagation |
| `spawn` | `generateSpawn` | `biomes`×1 | `ChunkGenerator.spawnOriginalMobs` — one-time initial mob population, seeded via `setDecorationSeed` + a fresh unique-seed RNG (not reproducible from the world seed alone; explicitly non-deterministic by design) |
| `full` | `full` | — | promote `ProtoChunk` → `LevelChunk` |

`ChunkPyramid.LOADING_PYRAMID` is the parallel table used when a chunk is read from disk instead of generated (only `structure_starts` load + light stages actually run tasks; everything else is a no-op because disk data already has it).

### 3.15 Blending old chunks with newly generated terrain (`Blender`)

When a chunk near the boundary of "already generated at an older world version" data exists, `Blender.of(region)` (constructed once per `WorldGenRegion`, `EMPTY` singleton short-circuit when no old chunk is within `HEIGHT_BLENDING_RANGE_CHUNKS` = `QuartPos.toSection(QuartPos.fromSection(7)-1+3)` chunks) collects `BlendingData` (persisted per old chunk: a captured height column + biome column + a coarse density-sample column, computed once when that chunk was first re-touched and cached in the chunk's NBT) for every old chunk within range, split into a wider `heightAndBiomeBlendingData` set and a narrower `densityBlendingData` set (`DENSITY_BLENDING_RANGE_CHUNKS` = `QuartPos.toSection(5)`, tighter because density blending is 3-D and expensive). `blendOffsetAndFactor(x,z)` and `blendDensity(context,noiseValue)` both do inverse-fourth-power-distance-weighted averaging (`weight = 1/distance⁴`) over every old-chunk sample within range, smoothstepped (`3α²-2α³`) by distance-to-nearest-sample for the alpha blend factor that `blend_alpha`/`blend_offset`/`blend_density` density-function nodes consume — this is literally what those three JSON node types exist to expose to the density-function graph (§3.3). `heightToOffset` is a closed-form remap (not a lookup) converting an old chunk's captured surface height into the same "density offset" units the new noise router works in, tuned around the constant `128`-block "old chunk height model" bucket size and a piecewise correction inside each 8-block band (`3·mod² - 3·(h-120)·mod` term) to compensate for the old flat/rounded terrain shape. Biome blending (`blendBiome`) additionally perturbs the search radius with a fixed `SHIFT_NOISE` (a `NormalNoise` seeded from the constant `42L`, shared process-wide, not derived from the world seed) so the old/new biome boundary isn't a perfectly straight blend front. `generateBorderTicks` and `addAroundOldChunksCarvingMaskFilter` are the companion passes that mark newly-exposed leaves/fluids for relight/fluid-update at the blend seam and suppress carving too close to an old chunk's already-carved volume (`distanceToCube` against each old chunk's bounding box, again jittered by the same shared `SHIFT_NOISE`).

## 6. Cross-subsystem interfaces

**Consumes from:**
- **World/dimension config** (`03-world-chunks-persistence.md`): `ChunkAccess`/`ProtoChunk`/`LevelChunk` section storage that `doFill`/carvers/features write into; `Heightmap` (`OCEAN_FLOOR_WG`/`WORLD_SURFACE_WG` maintained live during noise fill, the 4 "final" heightmaps primed before feature placement); `ChunkPos`/`SectionPos` coordinate math.
- **Structures domain**: `StructureManager`/`StructureStart` supply `Beardifier` its rigid-piece/junction list, and supply the `structure_starts`/`structure_references` `ChunkStatus` steps and the structure half of `applyBiomeDecoration`'s per-step seeding; `TerrainAdjustment` enum is defined in the structures package but consumed here.
- **Registry/datapack system**: every `DensityFunction`, `NoiseGeneratorSettings`, `NoiseSettings`, noise parameter, biome, surface rule, carver config, feature, placed feature, and world preset is a registry entry resolved through `HolderGetter`/`BootstrapContext` at datapack-load time — this whole subsystem is inert without the registry layer already up.
- **Block/state system**: every terminal output is a `BlockState`; `BlockPredicate`s and `BlockStateProvider`s consume the block-tag and blockstate-property machinery.

**Provides to:**
- **Chunk persistence**: fully generated `ChunkAccess` sections, heightmaps, carving masks, and (for blend-boundary chunks) `BlendingData` get serialized to region files.
- **Game mechanics** (`05-game-mechanics.md`): mob spawning consumes `NaturalSpawner.spawnMobsForChunkGeneration` (called from `spawnOriginalMobs`, `spawn` `ChunkStatus` step) and ongoing biome/heightmap queries; redstone/fluid ticking consumes carver/aquifer-marked post-processing positions.
- **Server networking** (`02-protocol-networking.md`): generated chunk data is what gets serialized into chunk-data packets sent to clients; the `NOISE`/`SURFACE`/etc. `ChunkStatus` gates are what "chunk not yet ready to send" checks against.
- **Cluster architecture** (`13-cluster-architecture.md`): because generation is a pure function of (seed, dimension, registry data, coordinates) with no cross-chunk mutable RNG state at the noise stage, chunk generation is trivially parallelizable/relocatable across worker threads or nodes — the one piece of *sequential* per-position state is the feature/decoration pass (`WorldgenRandom` draw sequence is order-dependent within one chunk's decoration pass, and `SurfaceRules.Context`'s counter-based memoization is inherently single-threaded per column) and the carve-mask/blend machinery that reads neighboring chunks.

## 8. Notes for Rusty Clanker

- **Two RNG algorithms, chosen per-dimension, must both be bit-exact, and the choice between them (`useLegacyRandomSource`) is per `NoiseGeneratorSettings`, not global.** Only the plain/large-biomes/amplified overworld presets use Xoroshiro128++; nether, end, caves, and floating_islands all use the legacy `java.util.Random`-compatible LCG. A reimplementation that assumes "modern MC = xoroshiro everywhere" will desync every non-overworld dimension.
- **The name-hash algorithm differs by RNG implementation, not just the RNG itself**: `fromHashOf(name)` is MD5-based for Xoroshiro but plain `String.hashCode()` for legacy. Every named sub-stream (every `NormalNoise`, `"aquifer"`, `"ore"`, `"terrain"`, `"clay_bands"`, every surface-rule `random_name`) depends on getting the right one of these two hash functions for the dimension's chosen algorithm.
- **`FeatureSorter`'s cross-biome global feature index is the single highest-risk determinism hazard in this whole domain.** It is not "iterate the registry in file order" — it's a DFS topological sort over an edge graph built from *every* biome's *own* per-step feature ordering simultaneously, and the result depends on `Object2IntOpenHashMap`'s insertion-order iteration semantics (a `PlacedFeature` gets its index the *first* time it's encountered while scanning biomes in registry order) as much as on the topological constraints themselves. Reimplementing "features look roughly right" without reproducing this exact index assignment will still desync per-block RNG draws inside every feature, because `setFeatureSeed` bakes the index directly into the seed.
- **`preliminarySurfaceLevel` is a distinct, cheaper approximation of the terrain surface, deliberately decoupled from the real final density** — it feeds the aquifer, surface rules, and vein Y-bounding, all of which need "roughly how high is the ground" without paying for cave/aquifer evaluation. Do not collapse this into "just sample the real height" — vanilla's aquifer/surface-rule visuals depend on this function's specific (cave-free, aquifer-free) shape, including its own `find_top_surface` scan-downward-in-cellHeight-steps algorithm.
- **The noise-cell interpolation machinery (§3.6) is not an optional performance shortcut — it is load-bearing for bit-exact parity.** Terrain shape is defined *by* trilinear interpolation between cell corners, not by evaluating the density function at every block; a reimplementation that evaluates every block directly (even with a mathematically-equivalent-looking density function) will produce visibly different terrain because vanilla's interpolation introduces its own systematic smoothing/blockiness at cell boundaries (visible as the classic 4×4×8 "staircase" in cliffs).
- **`MulOrAdd` is a decode-time optimization, not a distinct wire format** — a from-scratch density-function codec only needs to implement `add`/`mul`/`min`/`max` on the wire; the constant-folding specialization is purely a runtime performance detail safe to omit or implement differently.
- **Ore veins (`OreVeinifier`) and the classic `ore` feature are two unrelated systems that must both exist** — one is a density-function material rule evaluated per-block during noise fill (copper/iron only, Y-bounded, no `PlacedFeature`/`GenerationStep` involvement at all), the other is the traditional per-chunk feature-placement blob-along-a-line algorithm used for every other ore. Don't unify them; vanilla doesn't.
- **`WorldgenRandom` is a `LegacyRandomSource` subclass that never actually generates its own numbers** — it constructs with a dummy seed `0L` purely to satisfy the supertype and immediately overrides every RNG method to delegate to a wrapped `RandomSource` that can itself be either legacy or Xoroshiro-backed. A literal port must preserve this delegation shape (or the count-tracking `getCount()` behavior some carver/legacy code may depend on) rather than collapsing it into the wrapped source directly.
- **`Aquifer`'s "4 nearest neighbors, 3 pairwise barrier checks" shape is exact, not "roughly 4"** — the partial-selection-sort tie-breaking order (`>=` vs `>` comparisons, which of `closestIndex1..4` gets bumped on equal distances) affects which grid location wins on exact ties, which does occur (grid-aligned queries). Reproduce the comparison operators as written, not a generic "sort and take top 4."
- **Blender's `SHIFT_NOISE` is seeded from a hardcoded constant (`42L`), not the world seed** — it's process-global and identical across every world using the same version. This is a legitimate deliberate deviation from "everything derives from the world seed" and should be reproduced as a literal engine constant, not accidentally re-derived per-world.
- **Sequential, single-worker constraints already mandated by `ARCH-` decisions align naturally with two pieces of this domain**: `SurfaceRules.Context`'s counter-based memoization is inherently single-threaded per chunk column (safe — surface building is already a per-chunk operation), and carver/aquifer/blend logic reads a 17×17 (carvers) or wider (blending) chunk neighborhood, meaning **chunk generation is not embarrassingly parallel at chunk granularity** the way a naive "one thread per chunk" design might assume — a chunk's `carvers`/`features` stage genuinely depends on sibling chunks' `structure_starts` (and for blend chunks, arbitrary old-chunk data) having already completed, matching `ChunkPyramid`'s explicit `addRequirement` radii. Reimplementation must honor those exact radii (`structure_starts`×8, `biomes`×1, `carvers`×1, `initialize_light`×1) rather than inventing a different neighbor-completeness rule.
- **World seed is shared verbatim across all three built-in dimensions** — `RandomState.create` is called once per `ServerLevel` with that level's seed, and `WorldPresets` wires overworld/nether/end all from the *same* `WorldOptions.seed()` (no per-dimension seed offset). Differentiation between dimensions comes entirely from different `NoiseGeneratorSettings`/`NoiseRouter`/biome source, not a different seed.
- **Non-numeric seed strings hash via `String.hashCode()` at the `WorldOptions.parseSeed` boundary**, before any worldgen RNG algorithm is involved — this must be replicated exactly (Java's specific `s[0]*31^(n-1) + s[1]*31^(n-2) + … + s[n-1]` polynomial hash) for "type a word as your seed" parity, independent of which `RandomSource` implementation the resulting long seed later feeds.
