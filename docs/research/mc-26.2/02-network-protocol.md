# Networking & Protocol — Vanilla Server 26.2 (protocol 776)

## 1. Purpose

This subsystem carries every byte between a Java Edition client and the server: the Netty channel pipeline, varint-length framing, zlib compression, AES/CFB8 encryption, the five connection phases (handshake → status/login → configuration → play), and the ~256 packet types that ride on top. It also owns the side channels that never go through the game protocol at all — legacy (pre-Netty) server-list ping, the RCON remote-console protocol, and Mojang session-service HTTP calls made during login. Everything downstream (world sync, entity replication, chat, inventories) is expressed as a `Packet` serialized by a `StreamCodec` and dispatched through a `PacketListener`.

## 3. How it works

### 3.1 Netty pipeline construction (handler order)

`Connection` (extends `SimpleChannelInboundHandler<Packet<?>>`) is both the pipeline's terminal inbound handler and the public send API. Two bootstrap paths build (almost) the same pipeline:

- **Real TCP** (`ServerConnectionListener.startTcpServerListener`, and client-side `Connection.connect`): per accepted channel, `TCP_NODELAY` is set, then handlers are added in this exact order:
  1. `timeout` — Netty `ReadTimeoutHandler(30)` (30 s idle-read timeout; distinct from the application-level keep-alive below)
  2. `legacy_query` — `LegacyQueryHandler`, added only if the server replies to status; self-removes on any modern (0xFE-prefixed-but-not-legacy) traffic
  3. `splitter` — `Varint21FrameDecoder` (length-prefixed frame boundary)
  4. a `FlowControlHandler` (unnamed) — buffers extra decoded messages so at most one `Packet` is delivered per `channelRead`, needed because the bundle packer can emit zero or many logical packets per frame
  5. `decoder` — `PacketDecoder<ServerHandshakePacketListener>` bound to the handshake protocol (the only phase a fresh connection can be in)
  6. `prepender` — `Varint21LengthFieldPrepender` (writes the frame length)
  7. `encoder` — `PacketEncoder<ServerHandshakePacketListener>`
  8. `hackfix` — a no-op passthrough `ChannelOutboundHandlerAdapter` (present so `packet_handler` is never the pipeline's outbound head, working around a Netty ordering quirk)
  9. `packet_handler` — the `Connection` instance itself
- **In-process / singleplayer** (`Connection.connectToLocalServer`, `ServerConnectionListener.startMemoryChannel`, `Connection.fromChannel`): uses Netty's `LocalChannel`/`LocalServerChannel` transport. `splitter`/`prepender` become `LocalFrameDecoder`/`LocalFrameEncoder`, which pack/unpack a `HiddenByteBuf` wrapper instead of writing a length-prefixed byte stream — no varint framing, no TCP-level cost, because the buffer is handed across in-JVM. Compression and encryption are never installed on a memory connection (see 3.6).

After the handshake resolves to LOGIN, STATUS, or TRANSFER, `Connection.setupInboundProtocol`/`setupOutboundProtocol` **replace** the `decoder`/`encoder` handler in place (`ChannelPipeline.replace`) rather than adding new ones, rebinding them to the new phase's `ProtocolInfo`. Encryption is inserted later via `addBefore("splitter", "decrypt", …)` / `addBefore("prepender", "encrypt", …)`, and compression via `addAfter("splitter", "decompress", …)` / `addAfter("prepender", "compress", …)` — so the fixed pipeline order end-to-end (inbound) is:

```
[decrypt?] → splitter → [decompress?] → FlowControlHandler → decoder → packet_handler
```

and (outbound, reverse order of processing): `packet_handler → encoder → [compress?] → prepender → [encrypt?]`.

Handler name constants live in `HandlerNames` (`splitter`, `prepender`, `decoder`, `encoder`, `decompress`, `compress`, `decrypt`, `encrypt`, `bundler`, `unbundler`, `inbound_config`, `outbound_config`, `packet_handler`, `timeout`, `legacy_query`, `latency`).

### 3.2 Varint length framing

`VarInt`/`VarLong` implement LEB128-style variable-length integers: 7 data bits per byte, MSB = continuation bit. `VarInt.getByteSize` caps encode width at 5 bytes (32-bit); a value needing more throws. `Varint21FrameDecoder` reads at most 3 bytes for the frame-length prefix (`MAX_VARINT21_BYTES = 3`, i.e. length values up to 21 bits / 2 097 151) — it buffers a 3-byte scratch `helperBuf`, copies bytes until the continuation bit clears or 3 bytes are consumed (throwing `CorruptedFrameException` on a 4th continuation byte), then re-marks the reader index and waits if the full frame isn't buffered yet. A frame length of exactly 0 is rejected. `Varint21LengthFieldPrepender` (a `@Sharable` `MessageToByteEncoder<ByteBuf>`) writes the varint length ahead of the payload and throws `EncoderException` if the length's varint encoding would need more than 3 bytes.

### 3.3 Compression

Installed conditionally via `Connection.setupCompression(threshold, validateDecompressed)`, which idempotently adds/reconfigures `decompress`/`compress` handlers right after `splitter`/`prepender`. Wire format per frame (post length-prefix): `VarInt dataLength` followed by either the raw uncompressed bytes (if `dataLength == 0`, i.e. below threshold) or a zlib (`Inflater`/`Deflater`, default settings) stream of exactly `dataLength` uncompressed bytes. `CompressionEncoder` compares the *pre-compression* size against `threshold`: below it, it writes a `0` length marker and passes the payload through unmodified; at/above it, it deflates. `CompressionDecoder` validates (when `validateDecompressed`) that a nonzero declared uncompressed length is not below the threshold and not above `MAXIMUM_UNCOMPRESSED_LENGTH = 8 388 608` (8 MiB); `MAXIMUM_COMPRESSED_LENGTH = 2 097 152` is a hard cap Vanilla documents but does not itself enforce in this decoder (compressed size is bounded upstream by the 21-bit frame length). Compression threshold is negotiated once, immediately after login succeeds (see 3.7); a negative threshold means "compression disabled" and both handlers are removed from the pipeline.

### 3.4 Encryption

AES/CFB8 stream cipher, installed only for real TCP connections that authenticate online (never for memory/singleplayer connections — `handleHello` explicitly skips the key exchange when `connection.isMemoryConnection()`). `CipherBase` wraps a `javax.crypto.Cipher` and does heap-buffer `update()` calls (no padding, streaming mode); `CipherEncoder`/`CipherDecoder` are thin Netty adapters (`MessageToByteEncoder<ByteBuf>` / `MessageToMessageDecoder<ByteBuf>`) placed immediately around the frame splitter/prepender, i.e. **outside** compression — every byte on the wire after the handshake is ciphered, including the frame length varint itself, once encryption is active. Key derivation and the challenge/response protocol are covered in 3.8.

### 3.5 Packet encode/decode and the id-dispatch codec

`PacketEncoder<T>`/`PacketDecoder<T>` are thin `MessageToByteEncoder`/`ByteToMessageDecoder` wrappers around a `ProtocolInfo<T>`'s single `StreamCodec<ByteBuf, Packet<? super T>>`. That codec is built by `ProtocolCodecBuilder`, which is really an `IdDispatchCodec` keyed by `Packet::type`: **the packet ID on the wire is a VarInt equal to the packet's position in the `addPacket(...)` call sequence inside the phase's `*Protocols` class** — there is no explicit numeric ID anywhere in source. `IdDispatchCodec.decode` reads the id VarInt, indexes into a `List<Entry>` built in registration order, and delegates to that packet's own codec; `encode` looks the packet's declared type up in an `Object2IntOpenHashMap` (built the same way) and writes its index. `PacketDecoder` also asserts that a decoded packet consumes the *entire* frame (extra trailing bytes → `IOException`), and both directions call `ProtocolSwapHandler.handleInboundTerminalPacket`/`handleOutboundTerminalPacket` after processing a packet whose `isTerminal()` returns true (see 3.9).

Individual packet classes are Java records/classes each exposing a `static final StreamCodec<FriendlyByteBuf|RegistryFriendlyByteBuf|ByteBuf, X> STREAM_CODEC`, built either via `Packet.codec(writer, reader)` (a private constructor taking the buf, plus a private `write` method) or `StreamCodec.composite(...)` (up to 12 typed fields) for pure records. `StreamCodec` also offers `.map`, `.dispatch` (tagged-union, used for e.g. entity-data serializers and NBT-backed payloads), `.mapStream` (buffer-type adaptation, e.g. downcasting `RegistryFriendlyByteBuf`→`FriendlyByteBuf`), and `.recursive` (self-referential structures). `ByteBufCodecs` supplies the primitive vocabulary (`BOOL`, `BYTE`, `SHORT`, `UNSIGNED_SHORT`, `INT`, `VAR_INT`, `LONG`, `VAR_LONG`, `FLOAT`, `DOUBLE`, string/NBT/collection/optional/either helpers, `GAME_PROFILE`, etc.), all against raw `ByteBuf`; `FriendlyByteBuf` layers Minecraft-specific helpers (UUIDs, `BlockPos`, `ChunkPos`, `Identifier`, `ResourceKey`, NBT, bit sets, public keys, `Instant`) on top, and `RegistryFriendlyByteBuf` additionally carries a `RegistryAccess` reference so codecs can resolve/serialize registry entries (Holders) by id during play/config.

### 3.6 `ConnectionProtocol` phases and the state machine

`ConnectionProtocol` is a 5-value enum: `HANDSHAKING`, `STATUS`, `LOGIN`, `CONFIGURATION`, `PLAY` — with string ids `"handshake"/"status"/"login"/"configuration"/"play"`. Each phase has an independent `ProtocolInfo` per `PacketFlow` (`SERVERBOUND`/`CLIENTBOUND`), so inbound and outbound codecs can (and do) swap phases at different moments. Phase transitions are driven entirely by **terminal packets** — a packet whose `isTerminal()` override returns `true` — combined with an explicit `Connection.setupOutboundProtocol`/`setupInboundProtocol` call from the listener that handles it:

| Transition | Terminal packet (side that sends it) | Explicit protocol switch |
|---|---|---|
| fresh connection → HANDSHAKING | (initial state; connection is constructed already bound) | `Connection.setListenerForServerboundHandshake` |
| HANDSHAKING → STATUS or LOGIN/TRANSFER | `ClientIntentionPacket` (serverbound, `isTerminal()=true`) | `ServerHandshakePacketListenerImpl.handleIntention` calls `setupOutboundProtocol` immediately, then `setupInboundProtocol` once the intent is validated |
| LOGIN → CONFIGURATION | `ServerboundLoginAcknowledgedPacket` (terminal, empty unit packet) | `ServerLoginPacketListenerImpl.handleLoginAcknowledgement` sets outbound to `ConfigurationProtocols.CLIENTBOUND` and inbound to `ConfigurationProtocols.SERVERBOUND`, constructs `ServerConfigurationPacketListenerImpl` |
| CONFIGURATION → PLAY | `ServerboundFinishConfigurationPacket` (terminal, empty unit packet) | `ServerConfigurationPacketListenerImpl.handleConfigurationFinished` sets outbound to `GameProtocols.CLIENTBOUND_TEMPLATE.bind(...)`; inbound switch to play happens later inside player-spawn setup (`PrepareSpawnTask`/`JoinWorldTask`, outside this domain) |
| PLAY → CONFIGURATION (resource-pack reload, dimension-independent reconfigure) | `ClientboundStartConfigurationPacket` / `ServerboundConfigurationAcknowledgedPacket` (both terminal, empty unit packets) | round-trips back into the configuration listener without dropping the connection |

`ProtocolSwapHandler.handleInboundTerminalPacket`/`handleOutboundTerminalPacket` implement the generic half of this: on seeing a terminal packet they disable auto-read (inbound) and splice in an `UnconfiguredPipelineHandler.Inbound`/`Outbound` placeholder at the `decoder`/`encoder` slot, replacing the just-used codec. That placeholder throws if anything tries to decode/encode a real packet through it — it exists purely to buffer a subsequent `InboundConfigurationTask`/`OutboundConfigurationTask` message (an `UnconfiguredPipelineHandler.setupInboundProtocol`/`setupOutboundProtocol` closure) sent as a **pipeline message**, not a wire packet, which is what actually installs the next phase's `decoder`/`encoder`. `Connection.setupInboundProtocol`/`setupOutboundProtocol` write these configuration tasks through the channel and `syncUninterruptibly()` on the resulting future, so protocol swaps are synchronous from the caller's point of view (but still execute on the Netty event loop). A `PacketBundlePacker`/`PacketBundleUnpacker` handler is spliced in right after `decoder`/`encoder` whenever a phase's `ProtocolInfo.bundlerInfo()` is non-null (currently only PLAY, via `CLIENTBOUND_BUNDLE`).

### 3.7 Login state machine and compression negotiation

`ServerLoginPacketListenerImpl` (server side) is a `TickablePacketListener` with an internal `State` enum: `HELLO → KEY (if online-mode) → AUTHENTICATING → VERIFYING → [WAITING_FOR_DUPE_DISCONNECT] → PROTOCOL_SWITCHING → ACCEPTED`. Flow, in order:

1. `handleHello` validates the requested username (`StringUtil.isValidPlayerName`), then branches: singleplayer owner name → skip straight to verification with the local profile; else if the server authenticates and the connection isn't a memory connection → send `ClientboundHelloPacket(serverId="", serverPublicKey, challenge, shouldAuthenticate=true)` and move to `KEY`; else → build an offline-mode profile (`UUIDUtil.createOfflineProfile`) and go straight to `VERIFYING`.
2. `handleKey` validates the client's encrypted challenge response against the private key, derives the shared `SecretKey`, computes the Yggdrasil server-hash digest (`Crypt.digestData("", serverPublicKey, secretKey)` as a signed hex `BigInteger`), immediately calls `connection.setEncryptionKey(...)` (encryption is live from this point on), and spawns a **dedicated authenticator thread** (`"User Authenticator #N"`) that calls the Mojang session service's `hasJoinedServer(name, digest, address)`. On success it stores the real profile and moves state to `VERIFYING` (picked up on the next `tick()`); on `AuthenticationUnavailableException` or failure it falls back to an offline profile only if the server is in singleplayer, otherwise disconnects with `unverified_username`/`authservers_down`.
3. `tick()` (called every server tick while the listener is active) detects `VERIFYING` and calls `verifyLoginAndFinishConnectionSetup`, which re-checks ban/whitelist/slot limits (`PlayerList.canPlayerLogin`), checks the transfer-intent profile id if applicable, and — **only if the compression threshold ≥ 0 and this isn't a memory connection** — sends `ClientboundLoginCompressionPacket(threshold)` with a completion listener that calls `connection.setupCompression(threshold, true)` (compression is armed only after the packet carrying the threshold has actually flushed, so the client always receives that one packet uncompressed).
4. It then asks `PlayerList.disconnectAllPlayersWithProfile` to boot any stale session with the same UUID; if that requires waiting, state becomes `WAITING_FOR_DUPE_DISCONNECT` and `tick()` polls until the old session is truly gone, else it proceeds immediately to `finishLoginAndWaitForClient`, which sends `ClientboundLoginFinishedPacket(profile, connection-listener's sessionId)` and sets state to `PROTOCOL_SWITCHING`.
5. The client's `ServerboundLoginAcknowledgedPacket` (terminal) triggers the CONFIGURATION handoff described in 3.6.
6. A watchdog in `tick()` disconnects with `slow_login` if 600 ticks (30 s at 20 TPS) elapse without completing login (`MAX_TICKS_BEFORE_LOGIN = 600`).

Login-phase plugin messaging (`ClientboundCustomQueryPacket` / `ServerboundCustomQueryAnswerPacket`, keyed by an `Identifier` "channel", `CustomQueryPayload`/`CustomQueryAnswerPayload`) exists for mods that need to negotiate before the player profile is finalized; vanilla's default server implementation treats any answer to a query it didn't ask for as a protocol violation (`handleCustomQueryPacket` just disconnects with `unexpected_query_response`) — this hook is effectively a modding-API extension point outside this subsystem's own use.

### 3.8 Encryption handshake detail

The challenge is a random 4-byte value (`Ints.toByteArray(RandomSource.create().nextInt())`), generated once per `ServerLoginPacketListenerImpl` instance. `ClientboundHelloPacket` carries the server's RSA public key (DER-encoded bytes) and that challenge; the client encrypts a fresh AES secret key and echoes the encrypted challenge back inside `ServerboundKeyPacket`. The server decrypts both with its RSA private key, verifies the echoed challenge matches byte-for-byte, and only then derives two independent `Cipher` instances (`Crypt.getCipher(ENCRYPT_MODE/DECRYPT_MODE, secretKey)`) which are installed as the `encrypt`/`decrypt` pipeline handlers. The server keypair itself (`server.getKeyPair()`) is generated once at server startup, outside this domain.

### 3.9 Bundle packets

A `BundlePacket<T>` (abstract; `ClientboundBundlePacket` is the only current instantiation) wraps an `Iterable<Packet<? super T>>` of sub-packets that must be applied to client state atomically within one client tick (used for entity add + teleport + metadata batches, so partial application never renders a torn frame). `BundlerInfo.createForPacket` builds a matched encode/decode pair around a designated `BundleDelimiterPacket` marker (`ClientboundBundleDelimiterPacket`, itself a normal wire packet whose `handle()` throws — it is only ever consumed by the bundler machinery, never dispatched to a listener). On the wire a bundle is: `delimiter, sub-packet, sub-packet, ..., delimiter`. `PacketBundlePacker` (inbound, decoder side) accumulates sub-packets between two delimiters into a `List` capped at `BundlerInfo.BUNDLE_SIZE_LIMIT = 4096` entries (throws `IllegalStateException` past that) and only then emits one reassembled `BundlePacket` up the pipeline; a bundled sub-packet is rejected if it is itself terminal (`verifyNonTerminalPacket`). `PacketBundleUnpacker` (outbound, encoder side) does the reverse: one `BundlePacket` in becomes `delimiter, N sub-packets, delimiter` out. Both packer/unpacker self-remove from the pipeline the moment a *non-bundle* terminal packet passes through (protocol swap), matching `ProtocolSwapHandler`'s handling of the base `decoder`/`encoder`.

### 3.10 Keep-alive and timeouts

Two independent timeout layers exist:

- **Transport-level**: Netty's `ReadTimeoutHandler(30)` (30 s) on every real socket connection (both TCP listener and outbound client connect) — fires a `TimeoutException` through `Connection.exceptionCaught`, which translates it into a `disconnect.timeout` disconnect.
- **Application-level keep-alive**, implemented once in `ServerCommonPacketListenerImpl` and reused unchanged by both `ServerConfigurationPacketListenerImpl` and `ServerGamePacketListenerImpl` (both call `keepConnectionAlive()` from their own `tick()`): every tick it checks `now - keepAliveTime >= LATENCY_CHECK_INTERVAL (15000 ms)`; if a challenge is already pending and unanswered, disconnect immediately with `disconnect.timeout`; otherwise (and only if the connection isn't a further-delayed "closed" listener whose own 15 s grace period — `CLOSED_LISTENER_TIMEOUT = 15000` — has also elapsed) send a fresh `ClientboundKeepAlivePacket(challenge = now)` and mark pending. `handleKeepAlive` on the reply computes smoothed latency as `(latency*3 + roundTripMs) / 4` (a simple exponential moving average, weight ¼) and clears the pending flag; a mismatched or unsolicited response disconnects the connection unless it is the singleplayer owner (which is exempt from all keep-alive/timeout enforcement — `isSingleplayerOwner()`).

### 3.11 Chat signing and sessions

Vanilla chat integrity does **not** re-verify against the client's original Mojang-issued profile key on every message beyond initial validation; instead each client session establishes a **hash chain** of signed messages:

- `SignedMessageLink(index, sender UUID, sessionId UUID)` — `index` starts at 0 (`root`) and increments by one per signed message (`advance()`); `isDescendantOf` checks strict index/sender/session equality, giving the server a way to detect skipped or replayed links.
- `SignedMessageChain` (per-connection) holds the mutable `nextLink`. Its `Encoder` (client-side conceptually, but the class is shared code) produces a `MessageSignature` by RSA-signing (`Signer.sign`) the concatenation of the link (sender+session+index) and the message body; its `Decoder` (server-side) verifies an incoming signature against the sender's `ProfilePublicKey`, rejects out-of-order timestamps (message timestamp older than the last accepted one → chain broken), rejects expired profile keys, and on any failure permanently sets `nextLink = null` (`setChainBroken`), after which every subsequent message on that chain is rejected until the client establishes a new session.
- `MessageSignature` is a fixed 256-byte RSA signature (`BYTES = 256`); `MessageSignature.Packed` lets the wire encode either a full 256-byte signature or a small integer index into a shared `MessageSignatureCache` (a fixed-size ring, default capacity 128, per connection) — `Packed.id + 1` is written as a VarInt so `0` means "full signature follows". `MessageSignatureCache.push` folds a message's `lastSeen` acknowledgements plus its own signature into the cache using an LRU-ish eviction that preserves entries still referenced by the newly pushed set.
- `LastSeenMessages` (cap `LAST_SEEN_MESSAGES_MAX_LENGTH = 20`) is the sliding window of message signatures a client claims to have displayed; it is both attached to outgoing signed messages (as part of what gets signed, via `updateSignature`) and sent independently as `LastSeenMessages.Update(offset, BitSet acknowledged(20 bits), checksum)` inside `ServerboundChatPacket`/`ServerboundChatAckPacket`, letting the server efficiently advance its idea of the client's seen-window without resending full signatures. `computeChecksum` is a simple 31-multiplier rolling hash over signature hashcodes, truncated to a nonzero byte.
- `RemoteChatSession` binds a `sessionId` to a client's `ProfilePublicKey` (itself Mojang-issued, separate from the RSA login keypair) and exposes `createMessageDecoder`/`createMessageValidator`. A session is established via `ServerboundChatSessionUpdatePacket` (serverbound; server validates the embedded public key against the session-service's key-signature and, on success, replaces the connection's active `SignedMessageChain.Decoder`).
- Ordinary chat (`ServerboundChatPacket`: `message (≤256 chars), Instant timeStamp, long salt, MessageSignature? signature, LastSeenMessages.Update`) and commands with argument signing (`ServerboundChatCommandSignedPacket`, which additionally carries a signature per signable command argument via `SignableCommand`) both flow through this same chain. Plain unsigned chat is permitted only when the server does not `enforcesSecureChat` (see `ServerStatus.enforcesSecureChat` and `SignedMessageChain.Decoder.unsigned`).

### 3.12 Configuration-phase registry & tag sync

`ServerConfigurationPacketListenerImpl.startConfiguration()` runs, in order: send `ClientboundCustomPayloadPacket(BrandPayload)`, optionally `ClientboundServerLinksPacket`, `ClientboundUpdateEnabledFeaturesPacket` (serialized feature-flag names), then enqueue a `SynchronizeRegistriesTask`, then `addOptionalTasks()` (a `ServerCodeOfConductConfigurationTask` if any code-of-conduct text is configured, a `ServerResourcePackConfigurationTask` if a server resource pack is configured), then `returnToWorld()` appends `PrepareSpawnTask` and `JoinWorldTask`, and finally `startNextTask()` pops and starts the queue's head. Tasks run strictly sequentially — one `currentTask` at a time, advanced only when the matching serverbound "finished" packet arrives (`finishCurrentTask` asserts the finishing type matches what's active, else throws).

`SynchronizeRegistriesTask` itself is a two-step negotiation: `start()` sends `ClientboundSelectKnownPacks(requestedPacks)` (the list of datapacks the server has, each identified by `KnownPack{namespace, id, version}`) and waits; the client answers with `ServerboundSelectKnownPacks(knownPacks)` listing which of those it already has cached client-side. `handleResponse` then calls `sendRegistries`: if the client's answer exactly matches what was requested, registry entries the client already has (from a matching data-pack version) are **omitted** from the wire and only the delta is sent; otherwise nothing is assumed known and everything is sent. Registry contents are sent one `ClientboundRegistryDataPacket(registryKey, List<PackedRegistryEntry>)` per top-level registry (worldgen-layer registries only — biomes, dimension types, etc. — via `RegistrySynchronization.packRegistries` against the `WORLDGEN` `RegistryLayer`), followed by one `ClientboundUpdateTagsPacket` carrying every registry's tag-to-elements mapping (`TagNetworkSerialization.serializeTagsToNetwork`) for the whole layered registry access at once (not per-registry). This is also the only place vanilla NBT-serializes arbitrary registry content (via `NbtOps`) directly onto the wire, rather than through a fixed `StreamCodec`.

### 3.13 Legacy ping / query and server status

`LegacyQueryHandler` sits ahead of the modern framing pipeline and speaks the pre-Netty (≤1.6) "server list ping" protocol so old clients/tools don't corrupt the varint decoder: it peeks (`markReaderIndex`) for a leading `0xFE` byte; a bare `0xFE` (no payload) is the 1.3-and-earlier ping and gets a `§`-delimited 3-field legacy response (`motd§online§max`); `0xFE 0x01` (optionally followed by an `0xFA`-tagged `MC|PingHost` plugin message carrying protocol version + hostname + port for 1.6 clients) gets the 6-field `§1\0protocol\0version\0motd\0online\0max` response. Either way the reply is a single `0xFF`-tagged length-prefixed UTF-16BE string followed by `ChannelFutureListener.CLOSE`. Anything else resets the reader index, removes itself from the pipeline, and re-fires the read so the normal varint-framed handshake takes over — this handler runs at most once per connection.

Modern status/ping (post-handshake, `ClientIntent.STATUS`) is two independent request/response pairs on the `STATUS` protocol: `ServerboundStatusRequestPacket` (empty) → `ClientboundStatusResponsePacket(ServerStatus)` (JSON-shaped `description`/`players`/`version`/`favicon`(base64 PNG)/`enforcesSecureChat`, serialized as one JSON blob — `ServerStatus.CODEC` — inside the packet, not as individual fields), then `ServerboundPingRequestPacket(long time)` → `ClientboundPongResponsePacket(time echoed)`. The server-side listener (`ServerStatusPacketListenerImpl`) disconnects after answering exactly one status request (`hasRequestedStatus` guard) and always disconnects immediately after answering a ping — a status connection is single-shot by design.

### 3.14 RCON

A from-scratch (non-Netty) implementation of the Source-engine RCON protocol, entirely separate from the game `Connection`/`ProtocolInfo` machinery: `RconThread` is a blocking `ServerSocket.accept()` loop (500 ms `SoTimeout` so it can poll a `running` flag and reap dead `RconClient` threads between accepts); it only starts if `server.properties` sets a nonempty `rcon.password` and a port in `1..65535`. Each accepted socket becomes its own `RconClient` thread reading up to 1460 bytes at a time into a reused buffer. Frame layout (little-endian, unlike the rest of the protocol which is big-endian/varint): `int32 length | int32 requestId | int32 type | payload | 0x00 0x00`. Recognized `type` values: `3` = `SERVERDATA_AUTH` (password check — sets/clears an `authed` flag, replies with `type=2` on success or a `requestId=-1` "auth failure" frame), `2` = `SERVERDATA_EXECCOMMAND` (only honored once authenticated; runs the string through `ServerInterface.runCommand` and streams the textual response back, split into ≤4096-byte `SERVERDATA_RESPONSE_VALUE` (`type=0`) frames if needed). Command output is captured through `RconConsoleSource`, a `CommandSource` whose `sendSystemMessage` appends into a per-invocation `StringBuffer` rather than broadcasting; it always accepts both success and failure output and runs with owner-level permissions (`LevelBasedPermissionSet.OWNER`).

## 8. Notes for Rusty Clanker

- **Packet IDs are registration-order artifacts, not stable identifiers.** Any Rust reimplementation must reproduce the *exact* `addPacket()` sequence per phase (verified against `packets.json`'s `protocol_id` field) — reordering, inserting, or auto-sorting the packet table by name breaks wire compatibility silently. This argues for a build-time-generated (or otherwise change-detected) packet table in the Rust codebase, checked against the pinned `packets.json` for protocol 776 in CI, rather than a hand-maintained enum.
- **Protocol swap is asymmetric and stateful in a way that's easy to race.** Inbound and outbound codecs switch phases independently and at different times (e.g. HANDSHAKING→LOGIN sets outbound before inbound is even resolved). A Rust connection state machine should model inbound/outbound protocol as two separately-versioned slots, not one combined "connection phase" enum, or it will mishandle the brief window where a connection is (e.g.) outbound-LOGIN/inbound-not-yet-set.
- **Terminal-packet-driven transitions are a hidden contract.** `isTerminal()` is not visible from the packet's data — it's a behavioral flag on the class that must be replicated per packet type exactly (see the table in 3.6) or the pipeline will never re-arm for the next phase (client hangs) or will re-arm too early (desync/garbage decode).
- **Compression-then-arm ordering matters.** The compression-threshold packet must be flushed and acknowledged (via a completion listener, not "fire and immediately switch") before the pipeline starts compressing, because the packet announcing the threshold is itself sent uncompressed. Symmetric care is needed for encryption: the key-exchange response must be validated and ciphers installed synchronously in the same handler invocation that produced the shared secret, before any further packet processing.
- **Bundle packets require the codec layer to be stateful across multiple wire frames**, buffering an unbounded (well, 4096-capped) sequence between two delimiter frames before the listener ever sees a logical packet. A naive one-frame-in/one-packet-out codec design won't accommodate this without a dedicated intermediate buffering stage — plan for it in the ECS-facing ingestion path so a bundle applies within a single tick/frame boundary, matching vanilla's atomicity guarantee.
- **The RCON and legacy-ping protocols are not on the varint/`ProtocolInfo` codepath at all** and must never be threaded through the same abstraction — they are raw byte protocols with their own framing (little-endian fixed-length RCON frames; single-byte-tagged legacy strings). Treat them as two small, separate, self-contained transports layered ahead of / beside the main connection pipeline.
- **Chat signing chain-breaking is silent and sticky**: once `SignedMessageChain.Decoder.setChainBroken()` fires, *every* subsequent signed message on that connection is rejected until a brand-new `ChatSessionUpdate` is negotiated — there is no automatic recovery. A reimplementation must make this failure visible (log + clear user-facing message) rather than silently dropping chat, since vanilla itself is easy to misdiagnose here (its own comment flags client/server clock skew as a common cause of spurious chain breaks).
- **The singleplayer/memory-connection path intentionally skips compression, encryption, and the 15 s "closed listener" timeout** (`isSingleplayerOwner()` exemptions throughout `ServerCommonPacketListenerImpl`). Rusty Clanker's monolithic in-process mode (loopback/local play) should model this as a distinct `Connection` variant from day one — trying to force a real singleplayer-equivalent client through the encrypted/compressed TCP path would both waste cycles and diverge from vanilla's observable behavior (e.g. no encryption handshake at all on a local game).
- **Determinism hazard**: the login authentication thread and the tick-driven `VERIFYING`/`WAITING_FOR_DUPE_DISCONNECT` polling mean login completion time is inherently non-deterministic wall-clock-wise (bounded only by the 30 s watchdog) even though the *protocol sequence* is deterministic. Any deterministic-replay or cluster-handoff design must treat "player finished logging in" as an external event, not something to reproduce bit-for-bit from tick inputs.
- **`FriendlyByteBuf`/`RegistryFriendlyByteBuf` conflate two concerns** — raw wire primitives and registry-aware (Holder-resolving) primitives — via subclassing on a mutable buffer wrapper. A Rust port should keep these as two composable traits/contexts (a plain buffer codec context, and a registry-resolution context layered on top) rather than replicating the inheritance relationship, since PLAY and part of CONFIGURATION need the registry context while HANDSHAKING/STATUS/LOGIN and most of CONFIGURATION never do.
