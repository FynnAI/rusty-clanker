# Prior Art

## Purpose

Surveys the current (August 2026) state of every notable vanilla-compatible or vanilla-inspired Minecraft server/client reimplementation relevant to Rusty Clanker's goals, and records what this project adopts as validated architecture and what it deliberately avoids. This is a reference doc: it exists to justify and be cited by decisions made elsewhere (principally `02-protocol-networking.md`'s NET-D2/NET-D3 and the core architecture/ECS-threading document's domain-parallelism claims), not to narrate history.

## Scope

**In scope:** Pumpkin, Valence, Feather, Cuberite, Minestom, Paper + Folia, azalea, and notable Rust/native Minecraft *client* reimplementations (wgpu-mc, Minerust, Hematite).

**Out of scope:** exhaustive coverage of every Bukkit/Spigot/Sponge-ecosystem plugin platform (Paper/Folia is covered only as the region-threading exemplar); Bedrock-only projects; non-Rust/non-JVM curiosities with no architectural bearing on this project.

## Decisions

| ID | Decision |
|----|----------|
| PRIOR-D1 | **Pumpkin** (`github.com/Pumpkin-MC/Pumpkin`, GPL-3.0) is a from-scratch Rust reimplementation of the Minecraft server targeting current Java Edition protocol closely, with an experimental work-in-progress Bedrock listener; concurrency is a tokio async-I/O layer bridged via channels to a rayon thread pool for CPU-bound work (chunk generation, parallel world ticking) — a coarse I/O-vs-CPU split, not an ECS or a statically-declared per-domain data-access model. As of this writing it is the largest and most active Rust Minecraft server project (10.8k stars, 2,700+ commits, commits within days of this writing) but is explicitly pre-1.0 "heavy development," with a plugin system still on its roadmap rather than shipped. **Adopt:** the validation that a full from-scratch Rust vanilla-server rewrite is a tractable, community-scale goal, and the tokio-for-I/O / CPU-pool-for-work split as a reference point (see `02-protocol-networking.md` NET-D7). **Avoid:** its coarser concurrency ceiling — Rusty Clanker's ECS-driven, statically-declared-access domain parallelism deliberately allows multiple systems to touch one chunk simultaneously, which a tokio+rayon split without domain-declared access does not by itself provide; its GPL-3.0 license independently forecloses copying or porting any of its code, on top of the from-scratch mandate. |
| PRIOR-D2 | **Valence** (`github.com/valence-rs/valence`, MIT) is a Rust Minecraft-server framework built on Bevy ECS, explicitly scoped to track only the single most-recent stable Minecraft version with no multi-version support planned; `valence_protocol` ships as one tightly-coupled sub-crate among several. Actively maintained as of this writing (3.3k stars, 626+ commits, issues opened as recently as January 2026) but self-described as "early in development with many features unimplemented," and its only two standalone `valence_protocol` crates.io releases are `0.0.1` (October 2022) and `0.2.0-alpha.1+mc.1.20.1` (August 2023, itself targeting a Minecraft version three-plus years obsolete as of this writing) — real usage is via git dependency on a moving branch, i.e. no stable, independently-versioned protocol crate exists to depend on. **Adopt:** Bevy ECS as validated prior art for ECS-based Minecraft server architecture at real scale (informs the core architecture/ECS-threading document); the single-version-tracking policy (mirrored as `02-protocol-networking.md` NET-D2). **Avoid:** taking `valence_protocol` as a dependency (`02-protocol-networking.md` NET-D3) — it is not a separable, stably-versioned crate, and depending on it would couple this project's protocol data model and release cadence to an early-stage external project's own churn. |
| PRIOR-D3 | **Feather** (`github.com/feather-rs/feather`, historical/inactive) was an earlier Rust Minecraft server reimplementation that went through multiple incompatible ECS-architecture rewrites — including a WebAssembly plugin API, `quill` — before development stalled; it is now inactive, last supported client version 1.16.5, and its own README directs users to Valence instead. **Adopt:** a process lesson, not code — commit to one ECS/threading architecture and one mod-API design early and hold it (which this project's binding-decisions convention already enforces) rather than iterating through incompatible architectures mid-flight, the apparent pattern behind Feather's stall. **Avoid:** any dependency on or resumption of Feather's code — it predates several Minecraft protocol epochs and is unmaintained. |
| PRIOR-D4 | **Cuberite** (`github.com/cuberite/cuberite`, Apache-2.0) is a mature C++ Minecraft-compatible server with a Lua plugin API (`cPlugin`), one tick thread per loaded world plus auxiliary threads for chunk-generation/lighting queues; 5.4k stars, but its master branch's most recent commit as of this writing is from December 2025 — no commits have landed in 2026 — and its own README states current protocol support tops out at Java Edition 1.8–1.12.2, roughly nine major-version-eras behind NET-D1's pinned target. **Avoid, on both defining traits:** its per-world single-tick-thread model is exactly the coarse-grained concurrency ceiling the project vision rejects (one hot world still bottlenecks on a single thread, regardless of how many idle worlds exist), and its protocol stagnation is incompatible with `02-protocol-networking.md` NET-D1/NET-D2's "track the current stable release, deliberately" policy. Its Lua plugin API is not relevant prior art for the isomorphic Rust mod API goal (native Rust modding, not an embedded scripting language). Nothing is adopted from Cuberite beyond the negative example. |
| PRIOR-D5 | **Minestom** (`github.com/Minestom/Minestom`, Apache-2.0) is a Java framework, not a vanilla server — it ships almost no default game logic ("does not know what is a chest") — built on a chunk/instance model where a configurable thread pool ticks chunks independently of any per-world or per-region ownership; actively developed (6,400+ commits, README tracks Java Edition 26.2 directly as of this writing) and used in production by community projects. **Adopt:** the instance/thread-pool decoupling instinct — chunk work is not pinned to a single "world" or "region" owner — as partial precedent for the vision's dynamic worker pools. **Avoid:** its "bare framework, no vanilla behavior by default" philosophy entirely (vanilla parity is a hard requirement here, not opt-in), and note that its parallelism is still chunk-level, not domain-level — only one thread touches a given chunk at a time, which Rusty Clanker's ECS domain decomposition strictly improves on. |
| PRIOR-D6 | **Paper + Folia** (`github.com/PaperMC/Folia`) implement region-based threading on top of the Java vanilla-compatible Paper fork: the world is partitioned into geographic regions, each ticked by exactly one `TickThread` at 20 TPS via a `TickRegionScheduler`, giving 100%+ throughput gains on high-population servers; actively maintained (its `ver/26.2.x` branch received a commit as recently as August 19, 2026) but requiring plugin authors to rewrite Bukkit-API assumptions around thread-locality — a real adoption tax. **Adopt:** region-based spatial partitioning as validated proof that "batch quiet areas onto few threads, scale hot areas out" is a sound macro-strategy, directly underpinning the project vision's dynamic worker pools. **Avoid:** Folia's core ceiling — a region, once assigned, is still single-threaded internally, so redstone/entity-AI/lighting/network-encode can never run concurrently on the same chunk. Rusty Clanker's ECS-driven, statically-declared-access domain parallelism removes exactly that ceiling: multiple threads may work the same chunk simultaneously because access is split by domain, not by space alone. |
| PRIOR-D7 | **azalea** (`github.com/azalea-rs/azalea`, MIT) is a Rust library for headless Minecraft bots/clients on Bevy ECS that explicitly excludes rendering as a non-goal, and tracks the latest Minecraft version closely on its git `main` branch (unified workspace version `0.16.0+mc26.2` as of this writing, matching `02-protocol-networking.md` NET-D1's pinned target exactly) — but its last crates.io-*published* release, for both the `azalea` and `azalea-protocol` crates, is `0.16.0+mc26.1` (March 2026), a five-month-stale published artifact typical of its single-maintainer, hobby-project cadence: real consumers take a git dependency on a moving branch, not the published crate (1,862 commits, 763 stars). **Adopt:** validation that Bevy ECS scales to real Minecraft client-side packet/entity workloads (many concurrent bot sessions), informing confidence in an ECS-based approach for the Phase 2 client's shared logic crates. **Avoid:** depending on `azalea-protocol` (`02-protocol-networking.md` NET-D3 — same reasoning as `valence_protocol`: single-version tracking, project-specific data model, external single-maintainer release cadence) and azalea's headless/no-rendering scope — Phase 2 explicitly requires a full rendering pipeline, out of scope for azalea by design. |
| PRIOR-D8 | **Rust/native client reimplementations beyond azalea:** wgpu-mc (`github.com/wgpu-mc/wgpu-mc`) is a standalone `wgpu`-based renderer integrated into the real Java client via a Fabric mod (Electrum) using JNI/Project Panama bindings, replacing only Blaze3D rendering internals (not game logic or networking), and as of June 2026 is undergoing a large rewrite for Minecraft's newer rendering architecture. Minerust (`github.com/B4rtekk1/Minerust`) is a `wgpu`-based "Minecraft-inspired" voxel engine reaching 200+ FPS but is an original game, not a wire-compatible reimplementation, with no real-server networking. Hematite (`github.com/PistonDevelopers/hematite`, with companion `hematite_server`) is a historical Piston-engine Rust client dormant since ~2019 (last crates.io release `0.0.34`), effectively abandoned. **Avoid all three as dependencies:** wgpu-mc's integration model (a renderer bolted into the real Java client via JNI) is the architectural opposite of Phase 2's goal — a standalone native client sharing Rust logic crates with the server, not a Java-client plugin; Minerust is not protocol-compatible; Hematite is unmaintained. **Adopt:** the `wgpu` crate itself (not wgpu-mc's engine) remains the leading candidate rendering API surface for Phase 2, validated independently by both wgpu-mc's and Minerust's choice of it — the concrete decision is owned by the Phase 2 client planning doc, not this one. |
| PRIOR-D9 | **General dependency stance:** no direct library or code dependency on any project surveyed in this document for protocol, world-simulation, or ECS logic — each is studied for architecture lessons and validation signals only (per `02-protocol-networking.md` NET-D3). License terms are independently disqualifying for code reuse regardless of architectural merit: Pumpkin's GPL-3.0 forecloses copying or porting its source under any circumstance without relicensing the affected code as GPL-3.0, which this project does not do. |

## Interfaces

**Provides to other domains:**
- Direct justification for `02-protocol-networking.md` NET-D2 (single pinned protocol version) and NET-D3 (no `valence_protocol`/`azalea-protocol` dependency), via PRIOR-D1, PRIOR-D2, PRIOR-D7, PRIOR-D9.
- The region-vs-domain distinction (PRIOR-D5, PRIOR-D6) as the concrete competitive baseline the core architecture/ECS-threading document's domain-parallelism claims are measured against.
- A process lesson (PRIOR-D3) informing the project's binding "current-state-only, no architecture churn" documentation discipline.
- License-exclusion facts (PRIOR-D1, PRIOR-D9) as input to `08-assets-auth-legal.md`'s treatment of third-party Minecraft-reimplementation code.
- A rendering-API validation signal (PRIOR-D8) for whichever document scopes the Phase 2 client.

**Needs from other domains:**
- The pinned protocol version and its release date (`02-protocol-networking.md` NET-D1) to keep "current as of this writing" framing accurate on revision.

## Open Questions

- Re-survey wgpu-mc once its 2026 rewrite lands a stable, standalone (non-JNI) renderer — it may become directly relevant prior art for the Phase 2 client rather than only a validation signal for `wgpu`, at whichever point Phase 2 is formally scoped.
- Whether Pumpkin's or another project's eventual shipped plugin/mod-API design (none surveyed here has shipped one as of this writing) offers a negative or positive data point once Rusty Clanker's own isomorphic mod API is designed; revisit at that time.
- Whether a future ViaVersion-style multi-version translation layer (noted as prior art under Minestom's ecosystem but not separately surveyed here) becomes worth a dedicated entry if `02-protocol-networking.md` NET-D2's single-version policy is ever revisited.
